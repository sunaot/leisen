# 検索の知識と利用者の語を、経路の両端まで届ける

leisen の検索精度を上げる最短の道は、探索ループの回数を増やすことではなく、(1) 各コネクタが知っている検索の意味論(AND/OR、構文、語数上限、並び順)を「検索プロファイル」として探索 LLM に届け、(2) 利用者が打った語を LibreChat → `ask` → 最初の検索クエリまで一字も変えずに運ぶ経路をコードで保証し、(3) 先頭切りのスニペットと「0 件」だけの結果を、次の一手が分かる形に直すことである。外部の実践はこの 3 点でほぼ一致している。キーワード検索を持つ公式 MCP サーバー(esa、Slack、GitHub、Google Drive)はいずれもツール説明に構文と書き換え戦略を書き込み、しかもその戦略はソースごとに逆向きである(esa は「言い換えは OR で」、GitHub の issue 検索は「OR で繋ぐな」)。一方、現行の leisen は全ソース共通の一般則「多くのソースは AND、名詞 1〜2 語」しか持たず、この一般則は AND 部分一致の開発用コネクタでの失敗から作られたもので、実ソースでは検証されていない。オーナーの「3 ターン」という認識は上限ではなく実測の典型値であり、**現行の上限は 6 ツールターン・120 秒(加えて最終ターン 60 秒)、実測の LLM ターン平均は 3.5(4 問)〜4.2(20 問 × 2 回)**である。問題 (b) の多段劣化は、UI 側 LLM の言い換えに加えて、探索プロンプト自身が「質問文をそのまま入れるな、1〜2 語にせよ」と語を削る指示を持つことによる二重の脱落として説明できる。既存の評価は UI 側 LLM も実ソースの意味論も通っていないため、どちらの問題も現状では測れない。したがって最初の作業は計測(ホップ別の差し替え実験と、実ソースの意味論を模したフィクスチャ)であり、その上で ADR なしでできる文面・ハーネスの変更、次に ADR が要る IF 変更の順に進めるのがよい。

本レポートの根拠には強弱がある。Web ページの引用の多くは取得ツールの要約経由であり、2026 年の arXiv 論文の多くは査読前で、BrowseComp-Plus など主要ベンチマークは英語の Web 文書である。leisen 向けの設計案はこれらからの推論であって、実証された構成ではない。該当箇所は本文と末尾の表で明示する。

## 外部の実践は「短いキーワード・複数クエリ・ソース別の作法」で一致している

### クエリの様式はバックエンドで決まり、ツール説明に書くのが定石である

キーワード型の検索に対して何を渡すべきかについて、ベンダーと OSS の指示は驚くほど揃っている。Anthropic が Research 機能のプロンプトとして公開しているサブエージェント用プロンプトは、クエリを **「5 語未満」**に保ち、やや広めに始めて結果が多ければ絞ること、同じクエリを繰り返さないこと、検索スニペットで済ませず fetch で全文を読むことを明文で求めている([research_subagent.md](https://raw.githubusercontent.com/anthropics/claude-cookbooks/main/patterns/agents/prompts/research_subagent.md))。Jina の node-DeepResearch はクエリのスキーマ記述そのものに「2〜3 語が望ましい、全体で 30 文字未満」と書き、1 ステップに最大 5 本の「互いに直交する」クエリを出させる([schemas.ts](https://raw.githubusercontent.com/jina-ai/node-DeepResearch/main/src/utils/schemas.ts))。Perplexity の Search API も短いキーワード、1 クエリ 1 論点、1 リクエスト最大 5 クエリ、年や言語はクエリ語ではなくフィルタで、という指針を出している([Perplexity docs](https://docs.perplexity.ai/guides/search-best-practices))。逆に、ニューラル検索の Exa は「キーワードの集合ではなく欲しいページを記述せよ」と指示する([Exa docs](https://exa.ai/docs/reference/search-best-practices))。つまり **「キーワードか自然文か」に普遍解はなく、照合方式で決まる**。学術側でも、エージェントのキーワード型クエリを自然文の質問に書き直すと、学習型疎検索の SPLADE は改善するが BM25 は悪化する(精度 0.572 → 0.557)という結果があり([Revisiting Text Ranking in Deep Research](https://arxiv.org/abs/2602.21456))、質問文をそのまま BM25 に投げたときの Recall@1000 は 13.7% にとどまる([BrowseComp-Plus](https://arxiv.org/abs/2508.06600))。

公式 MCP サーバーはこの「ソースごとの作法」をツール説明で教えている。調査セッションに接続されていた実物のツール定義(公開ドキュメントではなく `tools/list` の観測であり、文言はサーバー側で変わりうる)では、Slack は検索を `keywords`(著者が書きそうな名詞、全部 AND)、`filters`(人・チャンネル・日付)、`natural_language_query`(利用者の言い回しを保つ、意味的な再順位付け用)の 3 フィールドに分解させ、「0 件ならフィルタを外すかキーワードを単純にせよ」「複雑な依頼は並列の検索に分解せよ」と戦略まで書く([Slack MCP server](https://docs.slack.dev/ai/slack-mcp-server/))。esa は `query` 引数の説明に「空白区切りは AND。広げたいときは OR を使え」「日本語と英語の技術用語を相互に変換せよ」と書き、さらに「GitHub や Gmail の `after:` `before:` を使うな」と警告する。これは LLM が他 SaaS の記法を持ち込む失敗が実際に起きることの一次的な証拠である([esaio/esa-mcp-server](https://github.com/esaio/esa-mcp-server))。GitHub の公式 MCP は `search_code` に構文チートシートと例を載せる一方、`search_issues` では「言い換えは OR で繋がず平文で並べよ」と esa と正反対の指示を出す([github-mcp-server README](https://github.com/github/github-mcp-server/blob/main/README.md))。Notion は使えなかった指定を黙って落とさず `notices` 配列で知らせる([Notion MCP](https://developers.notion.com/guides/mcp/tools-search-reference.md))。バックエンドがキーワード検索のベンダーほど説明文が長く具体的で、意味検索を持つベンダー(Atlassian Rovo、Glean)ほど短い。説明文の量は、弱い検索を LLM 側で補う必要量に比例している、と読める(これは観測からの推論である)。

### 5 つのバックエンドは空白の解釈からして違う

leisen が相手にするバックエンドの意味論を並べると、全ソース共通の一般則が成り立たないことが分かる。確認の水準は列ごとに異なるので、表の最後の列に記した。

| ソース | 空白区切りの解釈 | 照合・上限 | 並び順 | 確認の水準 |
|---|---|---|---|---|
| esa | AND。`OR` / `\|` で OR、`-` で否定、`"…"` で完全一致、`title:` `body:` `in:` `#tag` などの修飾子 | 通常の語は「表記の揺れを考慮した検索」(実体は非公開) | `best_match` はタイトル一致・Ship It 済み・ストック記事を優遇 | 公式ヘルプ([docs.esa.io/posts/104](https://docs.esa.io/posts/104)、要約経由)。リモート MCP 経由での実機挙動は未確認 |
| GitHub(REST) | AND が既定。`OR` `NOT` と引用符 | 演算子は 5 個まで、256 文字まで。コード検索は既定ブランチ・384KB 未満・毎分 10 回 | best match | 公式ドキュメント([GitHub REST: Search](https://docs.github.com/en/rest/search/search)、要約経由)。日本語の分かち書きは一次情報なし |
| Redmine | `all_words` で AND/OR を切り替え | 空白区切りのトークンを SQL LIKE で部分一致。**先頭 5 トークンだけを使い残りは黙って捨てる**。1 文字は漢字のみ可 | **関連度なし、日付の新しい順** | ソースコード([search.rb](https://github.com/redmine/redmine/blob/master/lib/redmine/search.rb)、[acts_as_searchable.rb](https://github.com/redmine/redmine/blob/master/lib/plugins/acts_as_searchable/lib/acts_as_searchable.rb))。全文検索プラグイン導入先では挙動が変わる |
| Google Drive | `fullText contains` はトークン単位、`name contains` は前方一致のみ | 日本語の分割規則は記載なし | コネクタは省略時に関連度順 | 公式ドキュメント([Drive API](https://developers.google.com/workspace/drive/api/guides/ref-search-terms)、要約経由) |
| Slack(RTS) | キーワード検索が既定(ステミングあり、同義語なし)。自然文の質問で意味検索が発動するのはプラン・設定次第 | 取得データの保存は禁止 | `score` が既定 | 公式ドキュメント([Slack RTS API](https://docs.slack.dev/apis/web-api/real-time-search-api/)、要約経由) |

Redmine に日本語の自然文を渡すと、空白がないため文全体が 1 トークンの `%…%` になり、ほぼ必ず 0 件になる。逆に名詞に分ければ部分一致なので複合語の一部にも当たる。この種の挙動は「多くのソースは AND」という一文では伝わらない。

### 回数は複雑さで決め、1 ターンに複数のクエリを並べる

予算については、固定の小さな回数ではなく、質問の複雑さに応じてモデル自身に見積もらせるのが共通の作法である。Anthropic のプロンプトは単純な質問で 5 回未満、中程度で 5 回、難しい質問で約 10 回、絶対上限 20 回のツール呼び出しを目安とし、収穫が逓減したら止めよと書く([research_subagent.md](https://raw.githubusercontent.com/anthropics/claude-cookbooks/main/patterns/agents/prompts/research_subagent.md))。公式ドキュメントも「単一事実の質問は通常 1〜3 回、比較や多エンティティの調査は 10 回以上」とする([Web search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool))。LangChain の open_deep_research は単純 2〜3 回、複雑 5 回までとしつつ、**「包括的に答えられる」「関連ソースが 3 件以上ある」「直近 2 回の検索が同じ情報を返した」**の 3 つを即時停止の条件として明記する([prompts.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/prompts.py))。Cognition の SWE-grep は最大 4 ターンと少ないが、1 ターンに最大 8 並列のツール呼び出しを行い、再現率より適合率を重く評価する([Cognition](https://cognition.com/blog/swe-grep)、要約経由)。ターン数が少なくても検索本数は多い、という構成である。

学術側の結果は「回数を増やせば良い」とは言っていない。強いモデルによる深い検索では 1 問あたり 10〜30 回の検索が行われ、検索量と精度は相関するが([BrowseComp-Plus](https://arxiv.org/abs/2508.06600))、最初の数ステップの後は累積再現率が飽和し、既に見た文書の再取得が増えるという分析があり、文書の新規性と質問の条件の充足度を信号にして続行・方向転換・停止を選ぶ制御器は、検索回数を平均 14 回減らしながら精度を平均 3 ポイント上げた([When Deep Research Agents Stagnate](https://arxiv.org/abs/2608.15191)、査読前)。質問を手掛かりに分解し、手掛かりごとの短い検索を合併・再順位付けして「最初の一手」として渡すだけで、以後のループを変えずに精度が 5〜11 ポイント上がったという報告もある([Question's Gambit](https://arxiv.org/abs/2609.14412)、査読前。通常のマルチホップでは +0.5〜1.0 ポイントと小さい)。これらは難しい多手掛かり質問のベンチマークでの値であり、答えが 1〜2 文書にある社内の事実照会に最適な回数を測った研究は見つかっていない。

### 0 件と失敗はツールの応答文で次の一手に変える

Anthropic は、切り詰めやエラーの応答文そのものでエージェントの行動を誘導できるとし、不透明なエラーコードではなく直し方を返すよう勧める([Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)、要約経由)。smolagents の検索ツールは 0 件のとき「より一般的なクエリを試すか、年フィルタを外せ」と返し([text_web_browser.py](https://raw.githubusercontent.com/huggingface/smolagents/main/examples/open_deep_research/scripts/text_web_browser.py))、Jina は失敗したクエリの一覧を次のプロンプトに差し戻し、重複検索を検出すると「別の角度から考えよ」という文を結果として返す([agent.ts](https://raw.githubusercontent.com/jina-ai/node-DeepResearch/main/src/agent.ts))。「同じクエリを繰り返すな」という指示だけでは弱いことは実測にも表れており、検索の委譲を調べた実験では重複回避の指示がほぼ無効だった([Lost in Delegation](https://arxiv.org/html/2611.16526)、査読前)。ハーネスが重複を検出して返す方が確実である。

### 委譲は情報を落とす。原文を残し、広げる言い換えは別のクエリにする

サブエージェントへの委譲について、Anthropic は目的・出力形式・使うツールと情報源・境界の 4 要素を渡せと言い([multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)、要約経由)、Cognition は「個別のメッセージではなく文脈とトレース全体を共有せよ」と言う([Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)、要約経由)。OpenAI の Agents SDK で agents-as-tools は既定で文字列 1 個を受け取り、親の会話は自動では渡らない([OpenAI Agents SDK](https://openai.github.io/openai-agents-python/tools/))。leisen の `ask({question})` はまさにこの形である。Perplexity の公式 MCP は入力を単一の query ではなく `messages` 配列にして会話を渡せるようにし、合成つきの `perplexity_ask` と合成なしの `perplexity_search` を並置して説明文で使い分けを誘導している([server.ts](https://raw.githubusercontent.com/perplexityai/modelcontextprotocol/main/src/server.ts))。

委譲の害を測った研究は、オーナーの観察 (b) と整合する。2026 年 11 月のプレプリントは、Web 検索を単一エージェントで行う場合と委譲する場合を比べ、32 条件中 21〜22 条件で委譲が悪化したと報告する。失敗の中身は、オーケストレーターの書き直しがタスクを変えてしまうこと、実行役の取得失敗が上流に伝わらないことだった([Lost in Delegation](https://arxiv.org/html/2611.16526))。ただしこの実験は同一モデルの組だけを使い、**利用者の原文を実行役に渡す緩和策は試していない**。また約 30B 級の Qwen3 だけは 8 条件中 6 条件で委譲が有利だった。プロンプトだけの LLM クエリ書き換えが、既によく合っているクエリの専門用語を置き換えて検索を悪化させるという報告もある(FiQA で nDCG@10 が平均 9.0% 低下。ただし密ベクトル検索・英語・査読前。[Not All Queries Need Rewriting](https://arxiv.org/html/2603.13301))。対話検索の研究は、代名詞と省略だけを解決して他の語を残す「最小限で忠実な書き換え」を軸にし、忠実なクエリを 2 倍の重みにして書き換え・生の発話の結果と順位融合する構成を採っている([Faithful Query Resolution](https://arxiv.org/abs/2610.15034)、査読前)。

LLM の知識だけで語を足す拡張は、LLM が知らない題材と曖昧なクエリで失敗する([Abe ら](https://arxiv.org/abs/2505.12694)、要旨のみ確認)。社内固有語はこの条件に当たる。BM25 に対する LLM 拡張は総じて効くが([再現研究](https://arxiv.org/abs/2604.27421))、これは語が OR 的に加点される検索器での結果であり、AND 既定の SaaS 検索に疑似文書を連結する手法は移せない。移せるのは「語彙の違う短いクエリを複数投げて合併する」形と、「1 回目の検索結果に出た語で 2 回目のクエリを作る」形である(これは外挿による推論で、AND 既定の SaaS 検索 API での統制実験は見つかっていない)。

### ライブのフェデレーテッド検索は主流の一角だが、品質は LLM 側で補っている

本人の資格情報でソースを都度叩く方式は、Microsoft 365 Copilot のフェデレーテッドコネクタ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365/copilot/connectors/federated-connectors-overview))や Claude の enterprise search([Claude Help](https://support.claude.com/en/articles/12489464-use-enterprise-search))が採る選択肢になっている。ただし Onyx は自社のフェデレーテッド Slack コネクタについて、インデックス方式の方が関連する結果をはるかによく見つけると自ら書いている([Onyx docs](https://docs.onyx.app/admins/connectors/official/slack/slack_federated.md))。ライブ方式を採る製品が弱いネイティブ検索を補う場所は、専用のシステムプロンプト、実行時のツール選択、ツール説明での構文の教育、利用者への助言(ソース名と期間を挙げる、1 ソースずつ検索する)であり、ほぼ LLM 側である。「ライブのみ」で品質を出し切った公開計測は見当たらないので、leisen の品質の根拠は自前の評価で作るしかない。

ハーネスの違いが検索器の違いと同程度に効くという報告は、今回の方針を支える。同じモデルでハーネスを替えると 93.1% と 76.7% の差が出た例([Is Grep All You Need?](https://arxiv.org/abs/2605.15184)、査読前、答えが文字どおり存在する課題に限る)、指示文だけの最適化で 71.6% → 75.6% になった例([Let Agents Design How They Search](https://arxiv.org/abs/2610.29250)、査読前)がある。BM25 と強いモデルの組で残る誤答のうち、正解文書が一度も表出しなかったのは 3.8% で、55.7% は「表出したのに抜粋を見ていない」だった([Question's Gambit](https://arxiv.org/abs/2609.14412))。課題は「見つけられるか」から「与えられた証拠を認識できるか」へ移っている。

## 現行の leisen は、経路の両端で語と知識を落としている

### 「3 ターン」は上限ではなく、1 文書の質問の典型的な軌跡である

オーナーの「3 ターン」は実装の上限ではない。既定の上限は `maxIterations` = 6(範囲 1〜20)で、これは「ツールを実行したターン数」で数える(`packages/orchestrator/src/config.ts:20-48`、`packages/orchestrator/src/orchestrator.ts:709-718`)。1 ターンあたり最大 8 件、1 run あたり最大 40 件のツール呼び出しができ、時間上限は `runTimeoutMs` = 120,000、上限到達後の最終ターンに 60,000 ms が別に与えられる。LibreChat 側の MCP タイムアウトは 300 秒である(`deploy/compose/librechat/librechat.yaml:66-67`)。実測は LLM ターンの平均で、v3 プロンプトの 4 問では 3.5(v2 の 5.25 から低下。`docs/eval/2026-10-08-explore-v3.md` §5)、20 問 × 2 回では 4.2、所要時間は中央値 52.2 秒・最大 178.1 秒、40 run 中 8 run が上限に達した(`docs/eval/2026-10-09-t022-generalization.md` §2)。1 文書で答えられる質問は search → fetch → submit の 3 LLM ターン(ツールターンとしては 2)で終わるので、「3 ターン」はこの典型と一致する。数え方が 2 種類ある点(LLM ターンとツールターン)にも注意が要る。なお、これらはすべて合成コーパス 7 文書・AND 部分一致の開発用コネクタ・LM Studio 上の Qwen 27B 系での値で、実ソース、Claude API、LibreChat 経由の計測は存在しない。

したがって外部の水準との比較は次のようになる。上限の 6 ツールターン × 8 並列は、Anthropic の「単純 5 回未満〜難 10 回」の範囲を呼び出し数としては十分に覆っている。足りないのは枠ではなく、枠の使い方(1 ターンに複数のクエリを並べる誘導、止める基準、足りないときに続ける基準)である。

### 劣化点は入口と出口に集中し、途中に補正する層がない

経路を順に追うと、情報が落ちる場所は次の表のとおりである。行番号は調査時点(2026-11-25 の作業ツリー)の静的な読解によるもので、実行による検証はしていない。

問題 (a) は、知識の置き場所(コネクタ)から LLM までの経路が `summary` の自由文 1,000 字しかなく、しかもどのコネクタもそこに構文を書いていないことで構造的に起きている。esa の既定 `summary` は英語 1 文の内容説明(`packages/connector-esa/src/connector.ts:138-140`)、Redmine は対象種別のみ(`packages/connector-redmine/src/redmine.ts:185`)、GitHub だけが「語彙一致検索」と container の形まで書いている(`packages/connector-github/src/connector.ts:749-764`)。esa コネクタ自身は `in:` `user:` `updated:` を組み立てており、LLM が `title:` や `OR` を書けばそのまま効く構造なのに、LLM はそれを知らされていない。

問題 (b) は二重の脱落である。UI 側 LLM が利用者の発話を「きれいな自然文」に直す段で固有語が落ちうるうえ、探索プロンプトが語を 1〜2 語に削るよう指示している。利用者が esa の検索窓に直接入れれば当たる語の組が、経路の途中で痩せる。この説明は実装の読解からの推論であり、UI 側 LLM が実際に `question` をどう書き換えているかの記録はリポジトリにない。

### 一般則が合わないソースがあり、評価環境は実ソースより LLM に有利である

プロンプトの一般則とコネクタ実装が食い違う具体例が Redmine である。コネクタは `all_words=0` を送っており、Redmine のソースではトークン間の結合が `all_words ? ' AND ' : ' OR '` なので、実装の意図は OR と読める。その場合「語を足すほど絞り込まれる」という指針は逆になり、しかも並び順は日付順なので、語を足すほど「最近更新された無関係な Issue」が上位に並ぶ。ただし **`all_words=0` が実機で OR になるのか AND になるのかは未確認**である。調査ノートは、Redmine 本体のコントローラがこのパラメータを「存在すれば真」と解釈する実装だった可能性(記憶に基づく指摘)を挙げており、バージョンや全文検索プラグインの有無でも変わりうる。どちらであっても、探索 LLM に Redmine の挙動が伝わっていないことは変わらない。加えて、プロンプトは区画内の検索に `filters.container` を勧めるが、Redmine はフィルタ指定でエラーになるため、1 ツールターンを失う罠がある。

esa については、公式ヘルプが空白区切りを AND、通常の語を「表記の揺れを考慮した検索」と説明しているが、**リモート MCP の `esa_search_posts` 経由で同じ意味論になるか、日本語の扱い、`best_match` の中身は実機で確認していない**。コネクタが修飾子を空白で後置する実装(`packages/connector-esa/src/connector.ts:206-233`)は、LLM のクエリに `OR` が含まれると結合の優先順位が意図と変わるおそれがある。esa のヘルプは「左から順に処理され、括弧で優先順位を調整できる」と述べているので、括弧で包む対処が考えられるが、これは未検証の推論である。

評価環境は実ソースより有利にできている。開発用コネクタは一致箇所中心のスニペットを返し、タイトル一致語数で順位付けする(`packages/gateway/src/dev/fixture-connector.ts:16`、`:389-399`)。v3 の「名詞 1〜2 語」は 7 文書のコーパスでは必ず上位に入るが、数千件以上の実ソースでは上位 10 件に目的の文書が入らない方向に働きうる。これはオーナーの「精度が低い」という観察と矛盾しない仮説だが、実測データはない。既存評価が示している残存の失敗は、複数文書の質問を事柄ごとの検索に分解できない(multi-doc 3/6)、見つけたヒットを fetch せずに打ち切る、文書にない質問で上限まで探し続ける(absent 6 run 中 4 run が上限到達)の 3 つである(`docs/eval/2026-10-09-t022-generalization.md` §3-4、§4)。

## 検索プロファイルと原文の保証を軸に、経路を作り直す

以下は外部の実践と現行実装のギャップからの設計案である。個々の要素には出典があるが、leisen の構成(日本語、SaaS のネイティブ検索、27B 級のローカルモデル)で組み合わせた効果は未検証であり、次節の評価で確かめる前提で読んでほしい。

### `ask` は原文を運ぶ器にし、言い換えを UI 側 LLM に任せない

`ask` の設計は 2 段階に分ける。第 1 段階は引数を変えず、description と `instructions` に入力側の指示を足す。内容は、利用者の直近の発言を言い換え・要約・翻訳せずに入れること、固有名詞・ID・エラー文・引用符で囲まれた語句を一字も変えないこと、直近の発言だけで意味が通らないときに限り指している対象を補うこと(最小限で忠実な書き換え)、利用者が言っていない用途・期間・範囲を足さないこと、`ask` は過去の会話を覚えていないこと、応答に時間がかかることである。Anthropic は、モデルが検索クエリに不要な「2025」を付け足す癖をツール説明の修正で直した実例を挙げており([Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)、要約経由)、説明文だけで引数の癖が変わる見込みはある。ただし gpt-oss-20b 級の UI 側モデルが従うかは未検証である。

第 2 段階は引数の追加で、ADR-018 決定 1(`ask({ question })`)の変更に当たるため ADR が要る。候補は、利用者の発話そのままを入れる `userMessage`(名前で役割を曖昧にしない)、会話から分かっている前提を入れる `context`、変えてはならない語の配列 `keepTerms`、対象ソース、期間、探索の深さである。原文と補足を別フィールドにする理由は、上流が足した条件を「利用者が言ったこと」と区別できるようにするためで、語彙検索では足された条件が AND を増やして取り逃しになる。フィールドを設けたときに UI 側モデルが実際に原文を入れるかの公開測定は見つかっていないので、採用の前に次節の差し替え実験で確かめる。

どちらの段階でも、モデルの従順さに頼らない保険をサーバー側に置く。Orchestrator が受け取った `question`(または `userMessage`)から、引用符で囲まれた語句、英数字と記号の連なり(ID、エラーコード、ファイル名)、カタカナ・漢字の連なりを機械的に抜き出し、「原文由来の語」として探索 LLM に示すとともに、最初の検索の 1 本に必ず使わせる。日本語の名詞抽出を辞書なしで行う精度は実装して確かめる必要がある。

`ask` の返り値にも手を入れる価値がある。委譲の実験が示した「実行役の失敗が上流に伝わらない」問題への対処として、試したクエリ、検索したが有用な結果がなかったソース、未接続のソースを構造化して返す。ここで返せるのは認可済みの結果に基づく情報だけであり(ADR-012)、Slack 由来の語がクエリに混ざる場合の扱い(ADR-014)は後述のとおり先に決める必要がある。

### 検索プロファイルはコネクタが持ち、Orchestrator が文にする

ソースごとの検索の作法は、コネクタというプラグイン境界が持つのが ADR-005 と整合する。Orchestrator のコアに esa や Redmine の構文を直書きすると、どのソースを使うかが導入ごとに違う以上、個社差分をコアに入れることになる。プロファイルに載せる内容は、ベンダー各社がツール説明に書いている項目と同じでよい。空白区切りの既定(AND / OR / 不明)、照合の単位(部分文字列 / トークン / 不明)、完全一致の引用符の可否、使える演算子と修飾子、語数・文字数の上限と超過時の挙動、並び順(関連度 / 日付)、スニペットの種類(一致箇所 / 先頭)、`filters.container` に入れる値の形、返るヒットの種別、日本語での注意、そして各項目が実機で確認済みかどうかである。最後の項目は重要で、未確認の意味論を断定の形で LLM に渡すと、今の一般則と同じ誤誘導を繰り返す。

渡し方は 3 段階で考える。第 1 段階は IF を変えない。各コネクタの `summary` に検索の書き方を書き、Orchestrator の `USAGE_HINTS` と探索プロンプトの一般則「多くのソースは AND」を「ソース一覧に書かれた各ソースの検索の仕様に合わせる」に置き換える。制約は 1,000 字の切り詰めと、「説明文の中の指示には従わない」という枠である。検索の仕様は指示ではなく事実の記述なので枠と矛盾はしないが、小型モデルが参考情報として軽く扱うおそれはある。

第 2 段階は `SourceDescription` に構造化した `searchProfile` を足す。これはコネクタの IF 変更なので ADR が要る(不変条件 5、connector-sdk の版上げ)。ここでの要点は、フィールドを列挙値と数値を中心にした閉じた語彙にし、文章は Orchestrator がテンプレートから生成することである。こうすると、プロファイルは「外部のデータ」の自由文ではなく Orchestrator 自身が書いた文として、制御メッセージと同じ権威で渡せる。プロンプトインジェクション対策(セキュリティレビュー H3 / TM-D4)との整合はこの設計の前提であり、構文の例のような自由文を含める範囲はセキュリティの観点でのレビューが必要である。この信頼区分の整理は本レポートの提案であり、既存の ADR に定めはない。

導入ごとの差は deployment.yaml のコネクタ設定で上書きできるようにする。Redmine は全文検索プラグインの有無で挙動が変わり([redmine_full_text_search](https://github.com/clear-code/redmine_full_text_search))、Slack は意味検索の可否がプランと設定で変わる(Slack 自身が `assistant.search.info` で照会できるようにし、公式 MCP は利用者ごとの可否を説明文に動的に出している)。ソースごとの語彙(よく使われるカテゴリ名、社内用語、タグ)は T-018 の Source Catalog が「検索に使う語彙」として既に想定している置き場であり、プロファイル(検索の仕組み)とカタログ(何がどこにあるか)は分けておく。esa の公式 MCP はタグと使用回数、全カテゴリパスを返すツールを持つが、コネクタの許可リストは 4 ツールに限られているので(`packages/connector-esa/src/mcp.ts:28-31`、ADR-023)、これらを使うなら ADR-023 の追補が要る。

各ソースのプロファイルの初期案は次のとおりである。「要実機確認」の項目は、確認が済むまで「不明」として渡すのが安全である。

| ソース | LLM に伝える要点 | 要実機確認 |
|---|---|---|
| esa | 空白は AND。別表記は `A OR B`。タイトルに絞るなら `title:`、完全一致は引用符。日付は `updated:>YYYY-MM-DD`(`after:` などは使えない)。順位はタイトル一致を優遇。スニペットは本文の先頭であり一致箇所ではない | MCP 経由での AND の厳密さ、「表記の揺れ」の範囲、OR と後置修飾子の優先順位 |
| GitHub | 空白は AND。演算子は 5 個まで・256 文字まで。1 回の検索は issue・PR・コードの混合。言い換えは別の検索に分ける。`filters.container` は `owner/repo` か組織名。author / 期間の指定があるとコードは検索しない | 日本語クエリの分かち書き、AND の厳密さ |
| Redmine | フィルタは使えない。語は部分一致。使われるのは先頭 5 語まで。順位は関連度ではなく新しい順。文ではなく空白で区切った名詞を渡す | `all_words=0` が OR か AND か、導入先のプラグインの有無 |
| 開発用 | 空白は AND の部分一致。タイトル一致を優先 | なし(コードで確定) |

Redmine については、プロファイルを書く前にコネクタの挙動自体を決める必要がある。関連度のない日付順の検索で OR を既定にすると適合率は構造的に低くなるので、AND を既定にし、0 件のときに OR へ緩める順序の方が筋がよい(これは Redmine の仕様からの推論で、実機での比較はしていない)。パラメータの切り替えを LLM に委ねるなら `filters` か引数の追加になり IF 変更である。コネクタ内部で「AND で 0 件なら OR で再検索する」と決めるなら IF は変わらないが、ADR-024 への追記として記録しておくのがよい。

### クエリは「原文の語で 1 本、言い換えは別に、根拠のない語は足さない」

クエリ生成の指針は、現行の「名詞 1〜2 語」を次の規則に置き換える。語数はソースのプロファイルに合わせ、関連度順のソースでは主題の名詞 2〜3 語を基本にする。1 語は 0 件を避けるための後退先であって初手ではない。最初のターンでは、原文由来の語をそのまま使ったクエリを必ず 1 本出し、表記の違う言い換え(カタカナの長音の有無、英語と日本語、略語と正式名、複合語をまとめた形と分けた形)は別のクエリとして同じターンに並べる。1 本のクエリに言い換えを並べてよいのは、プロファイルが OR の記法を明示しているソースだけである。質問に複数の事柄が含まれるときは事柄ごとに分ける(T-022 の不合格の原因であり、T-024 の改訂候補と一致する)。社内固有語を LLM の知識で言い換えない。知らない語は推測で広げず、1 回目の検索結果のタイトルやスニペットに現れた表記を拾って次のクエリに使う。期間や区画はクエリ語ではなく `filters` に入れる。Slack の公式 MCP が言う「著者が自然に書く語だけを入れる」という判定基準は、質問側の言い回し(「締め日」「連絡先」)を足すなという現行の指示をより一般的に言い直したもので、そのまま採用できる。

### 0 件・重複・切り捨ては、Orchestrator が制御メッセージで知らせる

0 件のときの誘導は、プロンプトの一般則ではなく、その場の状況に応じた制御メッセージにする。Orchestrator は自分が発行したクエリの形とソースのプロファイルを知っているので、コネクタの IF を変えずに次の判定ができる。語数がそのソースの上限を超えていた(Redmine の 5 語)、クエリが文のままで空白がない、フィルタを指定していた、同じソースに同じクエリを既に投げていた、今回のヒットがすべて既出の文書だった、の 5 つである。メッセージは既存の制御メッセージと同じく「[オーケストレーター]」で始まるテキストとして、ツール結果の外に置く。試したクエリの一覧(ソース、クエリ、新しく得た文書の数)も同じ場所に毎ターン示す。Jina の失敗クエリの差し戻しと、停滞の研究が最も効くとした「文書の新規性」信号を、安く実装する形である。

ここで守るべき線は ADR-012 である。メッセージに書けるのは、クエリの形と、認可を通って返ってきた結果から計算できることだけで、「権限がないため 0 件」と「本当に 0 件」を区別する情報は出せない。新規文書の数は返却済みのヒットから数えるので抵触しない。文面は「見つからなかったことは、文書が存在しない根拠にならない」という現行の原則を保つ。コネクタ自身が「語を捨てた」「指定を無視した」と知らせる `notices` 相当のフィールドは有用だが、`SearchResult` の変更なので ADR が要る。

### 予算はツール呼び出し数で語り、止める基準と続ける基準を書く

上限値は変えなくてよい。変えるのは見せ方と基準である。制御メッセージは「ツールを呼べるターンは最大 6 回」だけでなく、1 ターンに複数の検索を並べてよいこと、単純な質問は 2〜4 回の呼び出しで終えてよいこと、複数の事柄を含む質問は 10 回前後を使ってよいことを伝える。ローカルモデルでは所要時間の大半が LLM の推論なので、ターンを増やすより 1 ターンの並列度を上げる方が 120 秒の枠に合う。

停止条件は検査できる形で書く。質問の各事柄について本文を読んだ裏付けの文書がある、直近 2 回の検索が新しい文書を返さなかった、のどちらかで提出する。見つからない側の打ち切りは T-024 の候補どおり、原文の語での検索、語を減らした検索、表記を変えた検索がいずれも有用な結果を返さなければ、上限まで探さずに「探した範囲」を書いて unresolved で提出する。逆方向の基準も要る。ヒットを 1 件も fetch せずに提出しようとしたとき、質問の事柄のうち裏付けのないものが残っているときは、Orchestrator が 1 回だけ差し戻す。これは「早く止まりすぎるエージェントには制御器が検索を増やして再現率を上げた」という結果([When Deep Research Agents Stagnate](https://arxiv.org/abs/2608.15191))に対応する。

十分性の判定を独立した 1 回の LLM 呼び出しにする案もある。Google の研究では、文脈が不十分なのに答えてしまう傾向は強いモデルにもあり、小さいモデルは十分な文脈でも棄権や誤答が多い([Sufficient Context](https://arxiv.org/abs/2411.06037))。判定器を足せば 1 回分の時間が増えるので、ローカルモデルでの採否は評価で決める。

### 結果は「一致箇所が見える少量」にし、判断の前に本文を読ませる

スニペットが本文の先頭であることは、当たっていても当たりと分からないという、精度の問題の中心にある。esa の検索結果には本文の Markdown が含まれているので、コネクタの中でクエリの語の周辺を切り出すことができ、IF は変わらない。GitHub の issue・PR は REST の text-match で一致断片が得られる。この変更が ADR-016 のスニペット規約の範囲に収まるかは、同 ADR の本文を今回読んでいないので確認が必要である。あわせて、esa のヒットは `meta.category` をタイトルと並べて見せる(カテゴリは内容を推測する強い手掛かりで、esa 自身の順位付けもタイトルを重く見る)。スコアや一致語のフィールドを `SearchHit` に足すのは IF 変更である。

LLM に渡す形は、生の JSON よりも、順位番号・タイトル・区画・更新日・スニペット・documentId を並べた簡潔な形の方が小型モデルには読みやすいと考えられるが、これは推論であり、形式を変えて比べる価値のある評価項目である。古い検索結果を履歴から落として documentId とタイトルだけ残す軽い圧縮は、Anthropic が最も安全な圧縮として挙げる方法で([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)、要約経由)、文脈の小さいローカルモデルで効く。ただし出典の検証(EvidenceLedger)は履歴ではなく台帳で行われているので、圧縮しても検証は壊れない設計にできる。

fetch については、有望な上位 2〜3 件を同じターンで並行に読んでから採否を決めることをプロンプトに書く。弱いモデルは全文を読むツールをほとんど使わないという結果があるので(Qwen3-32B で 10.36% → 11.69%。[BrowseComp-Plus](https://arxiv.org/abs/2508.06600))、プロンプトだけでなく、前項の差し戻しで担保する。Redmine の fetch は 100,000 字単位、esa は 20,000 字単位で返るため、ローカルモデルの文脈を 1 回で埋めるおそれがある。文書内の該当箇所だけを返す手段(OpenAI の `find_in_page`、smolagents の `find_on_page` に当たるもの)は有効だが、`fetch` の IF 変更になる。

### 合併と再順位付けは Orchestrator の中で、順位だけを使って行う

1 ターンに複数のクエリを並べると、結果の合併が必要になる。重複は (sourceId, documentId) で除き、ソースごとにスコアの尺度が違う(そもそもスコアが返らない)ので、順位だけを使う融合にする。原文の語によるクエリの結果を 2 倍の重みにするのは、書き換えのずれへの保険として対話検索の研究から移せる([Faithful Query Resolution](https://arxiv.org/abs/2610.15034))。合併が効くのは結果集合が互いに異なるときだけで、重なりが大きいと逆効果になった例があるので([Better Together](https://arxiv.org/abs/2609.05637))、クエリの多様さは言い換えの数ではなく結果の違いで測る。

再順位付けは、深く取ってから選ぶ構成が文献上は最も確かな手段の一つである(BM25 の上位 50 件を再順位付けして精度 +20%、検索回数 −11%。[Revisiting Text Ranking in Deep Research](https://arxiv.org/abs/2602.21456))。Redmine のように日付順でしか返らないソースでは特に価値がある。選別役は、推論が要る質問で小さい cross-encoder が悪化した例があるので([BRIGHT](https://arxiv.org/abs/2407.12883))、探索 LLM 自身に題名とスニペットの一覧から選ばせるのが第一候補である。これらはすべて認可済みのヒットに対する Orchestrator 内の処理であり、コネクタの IF も ADR-012 の境界も変えない。注意点はレート制限(GitHub のコード検索は毎分約 10 回、Redmine は検索 1 回ごとに Issue を個別取得する)と、スニペットが先頭切りのままでは選別の材料が乏しいことである。スニペットの改善が先になる。

### 小型ローカルモデルには、手順をプロンプトではなくコードで固定する

27B 級のモデルを前提にするなら、足場はプロンプトの手順書を厚くする方向ではなく、決まった手順をコードに移す方向がよい。小型モデルの実力を測ったプレプリントでは、短い構造化されたツール利用は小型モデルで足りるが長い計画は足りず、計画・実行・提出に分解するプロンプトは試したすべてのモデルで悪化し、効いた介入はモデルごとに違った([AgentFloor](https://arxiv.org/html/2605.00334)、査読前、検索ではなくツール操作の合成ベンチ)。ここから「コードで固定する方が安全」と読むのは推論であり、同論文はコード側の固定を比較していない。

具体的には、最初の一手を決定的にする。原文由来の語の抽出、ソースごとのクエリへの整形(プロファイルに従う)、有効なソースへの並列検索、合併までをコードで行い、その結果を最初の観測として探索 LLM に渡す。LLM に任せるのは、言い換えの候補の生成(短い構造化出力)と、結果を見てからの続行・fetch・回答である。全ソースへの一斉検索は、同一のクエリを全ソースに撒く形にしないことが条件で、Claude の enterprise search や Glean の説明が示すとおり、ソースごとにクエリを作り直す工程が要る。ソースが増えたとき(product-design が言う 10 ソース超)は、LLM によるソース選択か Source Catalog に切り替える。

そのほか、指示は文脈の末尾に置く短いリマインダとして繰り返す(Onyx は古いモデルで引用の信頼性がリマインダの有無で約 70% から約 99% に変わったと書いている。[Onyx blog](https://onyx.app/blog/building-the-best-deep-research)、要約経由)、推論機能のないモデルには検索のたびに「分かったこと・足りないこと・次の一手」を短く書かせる、モデル系統ごとにプロンプトの派生を持つ(T-024 の限界の節が認めている)、OpenAI 互換のバックエンドでは strict なツール呼び出しが効かないので、引数の検証エラーを直し方つきで返す、といった手当てが考えられる。

### アーキテクチャは、現行の入れ子を保ち、初手だけ決定的にするのがよい

構成の選択肢は 4 つある。比較は次の表のとおりで、評価は引用した証拠からの推論である。

| 案 | 内容 | 利点 | 欠点・制約 |
|---|---|---|---|
| (a) 直接公開 | `search` / `fetch` を UI 側 LLM に見せ、Orchestrator を通さない | ホップが 1 つ減り、利用者の語とクエリの距離が最短 | UI 側の小型モデルが構文を誤る。検索結果がチャット履歴に残る。出典の検証と run 単位の記録をサーバー側で握れない。ADR-018 の変更 |
| (b) 薄いルーター + 決定的ファンアウト | LLM はキーワード抽出だけ、検索はコードが並列に実行 | 小型モデルの得意な範囲に収まる。回数が予測できる | 1 回で当たらない質問に弱い。複数文書の質問に対応しにくい |
| (c) 入れ子 + 厚い受け渡し | 現行の延長。原文・文脈・固有語を運び、失敗を上流に返す | 出典の検証、監査、文脈の節約を保てる。ADR の変更が最小 | 受け渡しの損失は残る。UI 側モデルの従順さに依存する部分がある |
| (d) 併置 | `ask` と生の `search` を並べ、説明文で使い分ける | 既知項目の検索を速く正確にできる(Perplexity、Exa、Glean が採る形) | ツールの重複は誤選択を招く。Orchestrator を通らない検索は run に紐づかない。ADR-018・ADR-019 に関わる |

推奨は (c) を土台に、(b) の決定的な初手を Orchestrator の中に入れる混成である。出典の検証と run の記録という leisen の中核を保ったまま、問題 (a) にはプロファイル、問題 (b) には原文の保証で対処できる。(d) は、差し替え実験で「人が書いたキーワードを直接入れる」条件が大きく勝ち続ける場合の次の手として残す。(a) は UI 側が小型モデルである限り勧めない。なお、委譲が単一エージェントに負けるという結果は同一モデルの組での Web 検索のものであり、leisen の構成(弱いフロントと弱い探索役、社内検索)に直接は当てはまらない。同じ実験で 30B 級だけは委譲が有利だったことも踏まえると、構成の優劣は自前の計測で決めるべきである。

## 劣化はホップごとに差し替えて測る

### 同じ質問で、最終ホップに入るクエリだけを替える

問題 (a) と (b) を分けて測るには、同じ質問と同じ正解文書に対して、バックエンドに入るクエリの作り手だけを差し替える。条件は 4 つである。第 1 は人が書いたキーワードをコネクタの `search` に直接入れる(オーナーの「直接打った方が良い」の基準値)。第 2 は利用者の原文をそのまま `search` に入れる。第 3 は利用者の原文を `leisen-ask` に直接渡す(UI 側 LLM を除く)。第 4 は UI 側 LLM が `ask` に渡した `question` を使う(現行の経路)。第 1 と第 3 の差が探索 LLM のクエリ生成の損失、第 3 と第 4 の差が UI 側 LLM のホップの損失である。指標は、正解文書が上位 k 件に入ったか(recall@k)、最初の正解文書の順位、正解文書を fetch したか、引用したかとする。この手順は公開の標準手法ではなく、「検索を IR 指標で先に切り分けよ」「多段のトレースでは最初の上流の失敗を見よ」という指針([Hamel Husain & Shreya Shankar の FAQ](https://hamel.dev/blog/posts/evals-faq/))から組み立てたものである。

第 4 の条件には UI 側 LLM の実際の出力が要る。LibreChat が UI 側モデルに渡すシステムプロンプト全体はリポジトリになく実装依存なので、まずは `ask` のツール定義と `instructions` を UI 側と同じモデルに与えて `question` を生成させる簡易な再現で始め、LibreChat の実走で採った `ask` の引数と突き合わせて再現の妥当性を確かめる。あわせて、`question` に利用者の固有語が残っている割合(固有語の保持率)を、ツール説明の改訂の前後で比べる。

### 実ソースの意味論を模したフィクスチャと、クエリが見えるトレースを先に作る

現行の評価環境は AND 部分一致の 1 種類で、プロンプトはそれに合わせて調整済みである。開発用コネクタに検索の方式を切り替える設定を足し、esa 型(AND、タイトル優遇、先頭切りスニペット)、Redmine 型(部分一致、5 語上限、日付順、AND と OR の両方)、GitHub 型(種別の混合)を模す。コーパスも 7 文書から、同じ語を含む無関係な文書が上位を争う規模(数百件)に増やさないと、適合率の問題は現れない。合成コーパスなので、クエリの原文・返ったヒット・fetch した文書を含むトレースを制約なく保存できる。監査がクエリをダイジェストでしか残さないために評価レポートが検索語を推定で書いている現状(`docs/eval/2026-10-09-t022-generalization.md` §4)は、dev-eval の側でトレースを出せば解消する。

実ソースの意味論そのものは、推測ではなく実測で埋める。同じ文書に対して、文、文節、名詞の AND、複合語、構成語、表記違い(長音、全角と半角、英語)、6 語以上のクエリを投げ、当たり方を記録する小さな探査スクリプトを、esa(実チームで接続確認済み)、GitHub(T-025 の開発用設定)、Redmine の実機に対して走らせる。Redmine の `all_words=0` と esa の MCP 経由の意味論はここで確定させ、結果をプロファイルの「確認済み」に反映する。

### 質問は 3 種に分け、失敗は遷移の行列で数える

質問セットは、既知項目(題名・ID・固有語で 1 文書に当たる)、複数文書(答えに必要な要点の一覧で採点)、答えられない質問(正しい棄権を二値で採点)の 3 種を分けて持つ。Anthropic は現実の失敗から採った 20〜50 件で始めること、起きるべき場合と起きるべきでない場合の両側を入れることを勧めている([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))。実運用での具体的な失敗事例の記録はリポジトリにないので、オーナーが把握している失敗(質問、期待した文書、直接打って当たった語)を最初の種にするのがよい。T-024 の規則どおり、質問は改訂の前に別コミットで固定する。

失敗の分類には、最後に成功した状態と最初に失敗した状態の行列を使う。状態は「UI 側 LLM が `ask` を呼んだ」「`question` に固有語が残った」「正しいソースを選んだ」「クエリが 1 件以上を返した」「正解文書が上位 k 件に入った」「正解文書を fetch した」「回答が正解文書に基づく」「引用が正しい」と置く。運用の指標として、0 件率(認可済みの結果が 0 件、と定義する)、同一クエリの再試行率、新規文書のないターンの割合、run あたりのツール呼び出し数と所要時間を追う。ローカルモデルはばらつきが大きいので、同じ質問を複数回走らせ、全試行で合格した割合を併記する。

## 進め方は計測、文面、コネクタ、IF の順にする

優先順位は、効果の見込みと、ADR の要否、検証できるかどうかで決める。

| 順 | 作業 | ADR | ねらい |
|---|---|---|---|
| 1 | dev-eval にクエリと結果のトレースを出す。実ソース型のフィクスチャとコーパスの拡大。4 条件の差し替え実験。実機の探査(Redmine `all_words`、esa の MCP 経由の意味論) | 不要 | 問題 (a)(b) を数値にする。以後の変更の判定基準を作る |
| 2 | `ask` の description と `instructions` に入力側の指示を足す。原文由来の語の抽出と、原文の語による初手の保証 | 不要(ADR-018 の IF は不変) | 問題 (b) |
| 3 | 各コネクタの `summary` に検索の仕様を書く。探索プロンプトと `USAGE_HINTS` の一般則をソース別の参照に替える(T-024 に統合)。Redmine の `filters.container` の罠を消す | 不要(評価レポートを添付) | 問題 (a) |
| 4 | 0 件・重複・語数超過の制御メッセージ、試したクエリの一覧、停止と差し戻しの基準 | 不要 | ターンの浪費、早すぎる打ち切り |
| 5 | コネクタの内部改善: 一致箇所のスニペット(esa、GitHub issue/PR)、全角空白などの正規化、Redmine の AND/OR の決定 | IF は不変。ADR-016 の規約との整合を確認。Redmine は ADR-024 に追記 | 当たりを当たりと認識させる |
| 6 | Orchestrator 内の合併・順位融合・LLM による選別、古い結果の圧縮 | 不要 | 適合率、文脈の節約 |
| 7 | `SourceDescription.searchProfile`、`SearchResult` の notices、認可済み件数の専用フィールド、`SearchHit` の一致情報 | 必要(不変条件 5、ADR-012、ADR-016) | 3 と 4 を構造化し、信頼区分を整理する |
| 8 | `ask` の引数追加(原文、文脈、固有語、対象ソース、深さ)と返り値の拡張(試したクエリ) | 必要(ADR-018。監査・生クエリ表は ADR-019) | 2 を IF として固定する |
| 9 | 生の `search` の併置、Source Catalog(T-018)、検索層への昇格判定 | 必要(ADR-018、ADR-019。ADR-008 の計画に従う) | 差し替え実験の結果しだい |

1〜4 は人手の前提なしで進められ、T-024 の範囲と重なる。7 と 8 は、1〜4 を文面とコードで試して効果を確かめた後に ADR を起こす方が、IF に入れる項目を絞れる。順 3 の `summary` の文面は、どのソースを使うかにかかわらずコネクタに属する知識なので、個社差分には当たらない。導入ごとの値(Redmine のプラグイン、社内の語彙)だけを deployment.yaml に出す。

## 不変条件と ADR は、変更の置き場所を決めている

提案の各要素と、リポジトリの不変条件・ADR の関係を整理する。ADR-016、ADR-007、ADR-011、ADR-013、ADR-015、ADR-017、ADR-019 の本文と脅威モデルの原文は今回読んでおらず、CLAUDE.md とコード内のコメント経由の把握である。

| 変更 | 関係する制約 | 扱い |
|---|---|---|
| 探索プロンプト、`USAGE_HINTS`、制御メッセージの改訂 | `prompt.ts:15-16` の運用規則 | ADR 不要。評価レポートを添付 |
| コネクタの `summary` に検索の仕様を書く | 不変条件 5、ADR-005 | IF は不変で ADR 不要。ソース固有の知識をコネクタに置くので ADR-005 と整合 |
| ソース別の構文を Orchestrator のコアに直書きする | ADR-005、不変条件 8 | 避ける |
| `SourceDescription` / `SearchResult` / `SearchHit` へのフィールド追加 | 不変条件 5 | ADR 必須、connector-sdk の版上げ |
| 件数を LLM に見せる | ADR-012、SDK のコメント(`packages/connector-sdk/src/index.ts:190-195`) | 「認可済みで返却可能な件数」だけを意味する専用フィールドを ADR で定義してから。それまでは `nextCursor` の有無と、返ったヒットから数えた値だけを使う |
| 0 件時のヒント、メトリクスの 0 件率 | ADR-012 | クエリの形と認可済みの結果だけから作る。権限外と不在を区別する情報は出さない |
| Orchestrator 内の合併・再順位付け・選別 | ADR-012、不変条件 2 | 対象は認可済みのヒットのみで、すべて Gateway 経由の呼び出しなので抵触しない。ADR 不要 |
| 検索結果やプロファイルのキャッシュ | 不変条件 4、ADR-014 | 利用者に依存する結果は userId をキーに含める。Slack 由来は不可。コネクタの静的なプロファイルは利用者のデータではない |
| `ask` の引数追加、生の `search` の併置 | ADR-018 決定 1、ADR-019 | ADR 必須。原文や文脈を受け取ると監査・生クエリ表に書く対象が増える |
| esa の MCP の追加ツール(構文ヘルプ、タグ、カテゴリパス)の利用 | ADR-023 の許可リスト | ADR-023 の追補 |
| クエリと結果を含む評価トレース | ADR-014、監査の保持方針 | 合成コーパスでは制約なし。実ソースでは保持期間に従い、Slack は対象外 |

Slack(ADR-014)については、提案の中に見落としやすい接点が 3 つある。第 1 に、「検索結果に出た語で次のクエリを作る」方式を Slack に適用すると、Slack 由来の語(チャンネル名、人名、本文の語)がクエリに入り、そのクエリが生クエリ表や「試したクエリ」の返り値、チャット UI の履歴に残りうる。これは Slack 由来データの永続化に当たるおそれがあり、既にある未決事項「Slack 有効時にクエリ原文を生クエリ表に書く挙動」と合わせて、T-006 の前に決める必要がある。第 2 に、Slack の Real-time Search は自然文の質問で意味検索が働きうる唯一のソースなので、Slack だけは原文をそのまま渡す検索が有効になりうる。ただしその可否は導入先のプランと設定で変わるため、プロファイルの上書きで表す。第 3 に、`leisen-ask serve` は Slack 系のソースが有効だと起動を拒否するので(ADR-018)、LibreChat 経由の経路に Slack は現状含まれない。

不変条件 9(2 社以上で再現した要件のみコア化)との関係では、検索プロファイルという仕組み自体はソースの種類に依存しない汎用の機構であり、コアに置ける。中身(特定の SaaS の構文)はコネクタに、導入先ごとの値は deployment.yaml に置く、という分担になる。

## 根拠の弱い点

本レポートの主張のうち、確度が低いものを種類別にまとめる。

| 種類 | 該当する主張 | 扱い |
|---|---|---|
| 要約経由の引用 | Anthropic のエンジニアリング記事、Cognition、Cursor、Onyx、OpenAI・Google・Slack・GitHub・Drive・esa の公式ドキュメント。取得ツールの小型モデルによる抽出を経ており、数値と逐語は原典での再確認が望ましい | 原文を直接確認したのは、Anthropic cookbook のプロンプト、LangChain・GPT Researcher・Jina・smolagents・Perplexity MCP のソース、Redmine のソースコード |
| 実物スキーマの観測 | esa、Slack、GitHub、Drive の MCP ツール説明。2026-11-25 の調査セッションでの `tools/list` の観測で、公開文書ではなく、文言は変わりうる。esa はリモート版と STDIO 版のどちらに由来するか未特定 | 設計の参考にとどめ、文面を引き写さない |
| 査読前のプレプリント | Lost in Delegation、Not All Queries Need Rewriting、AgentFloor、Question's Gambit、Pi-Serini、停滞の分析、SearchWeaver、Is Grep All You Need?、Faithful Query Resolution、SAFE-QE | 傾向として読む。数値を目標値にしない |
| 条件の違う実験からの外挿 | BM25(OR 的な加点)での拡張の効果を AND 既定の SaaS 検索に当てはめること。英語の Web 文書のベンチマークを日本語の社内検索に当てはめること。同一モデルの委譲実験を leisen の構成に当てはめること。密ベクトル検索での書き換えの害をキーワード検索に当てはめること | すべて推論。自前の評価で確かめる |
| 要旨のみ・原典未確認 | Weller ら、Abe ら、ReSLLM、RankGPT、HERB、HopRefusalBench、国内発表(IterKey ほか。PDF の抽出が不完全) | 本文では効果量を引用していないか、引用を避けた |
| 実機未確認の挙動 | Redmine の `all_words=0` が OR か AND か。esa の `esa_search_posts` の意味論(AND の厳密さ、表記の揺れの範囲、日本語の扱い、`best_match` の中身)。esa で OR と後置修飾子を混ぜたときの優先順位。GitHub・Slack・Drive の日本語の分かち書き | 探査スクリプトで実測するまで、プロファイルでは「不明」と書く |
| 静的な読解のみ | 現行実装の記述はすべてコードと文書の読解で、実行による検証はしていない。`capabilities.nativeSearch` を Orchestrator が参照していないという判断は網羅検索に基づかない。OpenAI 互換クライアントのサンプリング設定、`citations.ts` の細部は未読 | 行番号は 2026-11-25 時点 |
| データのない仮説 | 「名詞 1〜2 語」が実ソースで適合率を下げている。UI 側 LLM の言い換えで固有語が落ちている。結果を簡潔な形式にすると小型モデルが読みやすい | オーナーの観察と実装からの推論。差し替え実験の対象 |
| 本レポートの提案 | 検索プロファイルを列挙値にして Orchestrator が文を生成し、制御メッセージの権威で渡す設計。決定的な初手と入れ子の混成。差し替え実験の 4 条件 | 個々の要素に出典はあるが、組み合わせた構成の実証はない |

## Conclusion

調査から浮かぶのは、leisen の精度の問題が探索の量の不足ではなく、知識と語の輸送の問題だということである。上限は既に 6 ツールターン × 8 並列あり、外部の目安を覆っている。欠けているのは、コネクタが持つ検索の知識が LLM に届く経路と、利用者の語が最初のクエリまで残る保証であり、どちらも現行の IF を変えずに着手できる。そして、キーワード検索を持つベンダーが例外なくツール説明に作法を書き、その作法がソースごとに逆を向いているという事実は、leisen が統一 IF を保ちながら「ソースごとの検索プロファイル」という一段を持つべきことを示している。この一段は Phase 2 で内部実装を検索層に差し替えたときにも価値を失わない。差し替えた瞬間にそのソースのプロファイルが「自然文可、関連度順」に変わるだけで、探索側の作法は自動的に追随するからである。

もう一つの含意は順序に関するものである。プロンプトの v3 は開発用コネクタの AND 部分一致に合わせて最適化され、その環境で 37/40 に達した。同じことを v4 で繰り返すと、測れる環境での得点だけが上がり、オーナーが実ソースで見ている問題は動かない。実ソースの意味論を模したフィクスチャと、ホップごとの差し替え実験を先に用意することが、以後のすべての変更の判定基準になる。最初に確定させるべき事実は小さい。Redmine の `all_words=0` が実機で何を返すか、esa の MCP 経由の検索が空白をどう扱うか、UI 側 LLM が `question` に利用者の固有語を残しているか、の 3 つである。
