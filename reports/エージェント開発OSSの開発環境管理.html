公開リポジトリには AGENTS.md・スキル・ADR・設計書だけを残す

エージェントによる開発を積極的に行う OSS が、ハーネスと計画・決定の記録をどう管理しているかの調査と、leisen の今後の開発のあり方の提案

調査した約 50 の公開リポジトリに共通していたのは、いつ読んでも内容が正しい文書だけをリポジトリに置き、特定の時点では正しかった記録は Issues・PR・リリースに、個人の作業状態と実行時の情報は Git の外に置く、という使い分けである(図1)。タスクを 1 件 1 ファイルで管理するバックログをデフォルトブランチに常時置いている例は、1 つも見つからなかった。

leisen は backlog・ADR・設計書・.claude をすべてリポジトリに置いている。問題は文書の量ではない。進捗や決定の状態を管理する場所が決まっておらず、同じ情報が複数の文書に手作業で転記され、記述の不一致がすでに生じていることである。毎セッション読み込まれる CLAUDE.md の本文は、69% が日付付きの進捗記録になっている(5 章)。

提案は次の 3 点である。

  1. AGENTS.md を恒久的なルールだけにする。CLAUDE.md にある恒久的なルール(約 4,600 文字)を AGENTS.md に移し、CLAUDE.md は AGENTS.md をインポートする 1 行にする。
  2. タスクと未決事項は GitHub Issues で管理する。完了済みの backlog はコードから参照されているので、削除せず、変更しない履歴として残す。
  3. ADR は残し、追補を重ねる運用をやめる。決定後は書き換えない ADR と、現在の状態を記述する設計書に分ける。

非公開の内部リポジトリで開発し、公開リポジトリをそのミラーにする二重管理は、数人以下のチームではコストに見合わないので採用しない。OpenAI の社内プロダクトは設計書や実行計画までリポジトリに置いているが、同社が公開している OSS では実行計画を gitignore し、タスクを Issue Tracker で管理する方式を公開している。OpenAI の事例が支持しているのも、長期間有効な設計知識をリポジトリに置くことであり、タスクの進捗を置くことではない(2 章)。

内部リポジトリで開発する codex は、公開リポジトリからハーネスを削除した

社内プロダクトは、大きな AGENTS.md をやめ、約 100 行の目次と自動検査に切り替えた

当初は 1 つの大きな AGENTS.md にすべてを書いたが機能せず、約 100 行の AGENTS.md を目次として使い、詳細は docs/ の各文書から必要に応じて読み込む構成に変えた。文書の鮮度と相互リンクは lint と CI で検査し、古くなった文書はエージェントが定期的に修正の PR を出す。約 5 か月で約 100 万行のコードと約 1,500 件の PR を、当初 3 人のエンジニアで作成したと報告している(openai.com)。

提供された調査結果は、小規模な変更の計画は一時的なものとし、複雑な変更だけを実行計画(ExecPlan)としてリポジトリに残す、という区別も挙げている。この区別は、本調査で確認できた資料には見つからなかった。

公開 OSS の Agents SDK は、AGENTS.md とスキルをコミットし、実行計画はコミットしていない

AGENTS.md は、ブランチの切り替えとコミットに明示的な許可を求め、「Never push, open a PR, or otherwise mutate GitHub.」と定めている。PLANS.md は、複数の手順・複数のファイルにまたがる作業や約 1 時間を超える作業で ExecPlan を書くよう求め、Progress、Surprises & Discoveries、Decision Log、Outcomes & Retrospective の各節を定める。ただし plans/ は gitignore されており、計画ファイルもバックログもコミットされていない(PLANS.md、.gitignore)。2 つのリポジトリでマージされた PR は 3 か月間で 316 件から 457 件に増えたが、スキルの導入だけが原因であることを示す比較実験ではない(developers.openai.com)。

Symphony は、タスクを Issue Tracker で管理し、オーケストレーターが Issue ごとの作業環境に割り当てる

Symphony は、Issue Tracker からタスクを取得し、Issue ごとに独立したワークスペースとエージェントを割り当てるオーケストレーターの仕様である。実装例の WORKFLOW.md は、進捗・チェックリスト・検証結果を Issue の 1 つのコメント(Codex Workpad)に集約して更新し続けるよう指示し、作業範囲外の改善点は「file a separate Linear issue instead of expanding scope」と定めている。Linear のほかに GitHub Issues、Jira Cloud、Asana、GitLab のアダプターがある。README は「a low-key engineering preview」と明記しており、本番運用を想定したものではない(SPEC.md、WORKFLOW.md)。

実行環境と資格情報は、リポジトリとは別の基盤で管理する

記事「Securing persistent agents like OpenClaw at OpenAI」は、信頼できるゲートウェイとサンドボックス内で動作する信頼しないエージェントを分離すること、資格情報をエージェントから見えないようにする credential broker を置くこと、エージェントの識別情報を利用者の識別情報と分けることを挙げている(developers.openai.com)。会話の履歴、実行ログ、資格情報は、AGENTS.md やスキルとは性質が異なり、Git リポジトリの管理対象ではない。

ハーネスは、モデルの更新に合わせて削る対象でもある

記事「Rethinking skills and prompts for GPT-6 Astra」は、長すぎるスキルの説明文が切り詰められること、文書の読み込みを必須とする指示が誤字の修正には過剰であること、以前のモデル向けのテストの指示が不要なテストを招くことを挙げている。記事「Maintaining software with the GPT-6 family」は、AGENTS.md の指示を 1 つ選び、同じリポジトリの状態と同じモデルで同じタスクを再実行して変更前後を比較する方法を提案している。これは実験の報告ではなく、提案である(Rethinking skills、Maintaining software)。

これらを合わせると、OpenAI の事例が支持しているのは長期間有効な設計知識をコードと同じリポジトリに置くことである。タスクの状態と進捗は Issue Tracker に、実行中の計画は(公開 OSS では)ローカルに、実行ログと資格情報は別の基盤に置いている。図2 の類型にあてはめると、社内プロダクトは C と D の組み合わせ、Agents SDK は B である。

3AGENTS.md は短くし、手順はスキルに、決定は書き換えない ADR にする

成果物の種類ごとの扱いは、類型が違ってもほぼ共通している。

AGENTS.md には、コードからは読み取れないことだけを書く

調査したリポジトリのルートにある AGENTS.md は、5 行から 749 行まで幅があるが、半数以上は 100〜240 行に収まる(図3)。内容はコマンド、依存の方向、禁止事項である。Anthropic のドキュメントは CLAUDE.md を 1 ファイル 200 行未満にすることを目安とし、CLAUDE.md は「context, not enforced configuration」であるため、確実に禁止したい操作には PreToolUse フックを使うよう求めている(Claude Code docs)。

分量を増やしても効果は上がらない。ETH Zurich などによる評価研究(第 3 版、2026-09-29)は、AGENTS.md などのコンテキストファイルは一般にタスクの成功率を向上させないと結論している。LLM が生成したファイルでは成功率が約 0.5〜2 ポイント下がり、開発者が書いたファイルでは約 2.4 ポイント上がったが、いずれも統計的に有意ではない。一方で、推論コストは LLM が生成したファイルで 20〜23%、開発者が書いたファイルで最大 19% 増加した。リポジトリの概要説明については「Context files do not provide effective overviews」としている(arXiv:2602.11988v3)。

各プロジェクトのルールも同じ方向である。modelcontextprotocol/servers は「ルールは AGENTS.md に、手順は必要なときに読み込むスキルに」と分け、このファイルのルールはすべて現在のリポジトリについて正しい、と定めている。workers-sdk は、バージョン・ルールの一覧・件数を転記すると古くなるので、元の設定ファイルやドキュメントを参照するよう指示している(servers AGENTS.md、workers-sdk AGENTS.md)。

ルールは AGENTS.md に書き、CLAUDE.md はインポートの 1 行にする

sentry、supabase、tldraw、ruff、mastra、goose の CLAUDE.md は @AGENTS.md の 1 行だけである。Claude Code は、CLAUDE.md がなければ AGENTS.md を直接読み込み、両方ある場合は CLAUDE.md がインポートしたときにだけ AGENTS.md を読み込む(Claude Code docs)。スキルは、特定のツールに依存しない .agents/skills/ に実体を置き、.claude/skills をシンボリックリンクにする構成が広く使われている。スキルの対象は、リリース、PR の作成とレビュー、issue のトリアージ、テストの作成、動作検証に集中している。サブエージェント定義をまとまった数コミットしているのは、PostHog(11 個)と claude-code-action(レビュー用 5 個)程度である。

フックは用途を限定した検査にとどめ、エージェント設定は実行コードとしてレビューする

コミットされているフックは、編集後のフォーマット、対話型コマンドのブロック、セッション開始時のセットアップ程度で、leisen の 2 本のフックもこの水準に合っている。一方で、リポジトリにコミットされた .claude/settings.json や .mcp.json は攻撃対象にもなる。Check Point が報告した Claude Code の脆弱性は、Anthropic のアドバイザリでは表3 の 3 件で、いずれも修正済みである。Check Point は設定ファイルを実行コードと同じ水準でレビューするよう推奨している(Check Point Research)。

設計書は現在の状態を、ADR は決定時点の内容を記述する

cloudflare/agents は、設計書を「現在どう動作するか」を記述して随時更新する文書と位置づけ、RFC は決定後に更新せず、却下されたものも削除しないと定めている。手順は、提案する、Status を accepted / rejected に更新する、関連する設計書を更新する、の順である(design/AGENTS.md)。vercel/ai は、アーキテクチャに関わる変更の前に ADR を確認し、既存の ADR と矛盾する場合は作業を止めて人間に相談するよう AGENTS.md で指示し、ADR の起案手順をスキルとして定義している(vercel/ai AGENTS.md)。

完了した計画は、継続的に更新する対象にしない

完了した計画の扱いには 3 つの考え方がある。いずれの考え方でも、完了した計画を継続的に更新する対象とはしていない。

  • 完了済みのディレクトリに移して残す。OpenAI の社内プロダクトの docs/exec-plans/completed/。
  • 内容を現行仕様に反映し、残りをアーカイブする。OpenSpec。
  • 削除し、残すべき事実だけをコード・テスト・短い ADR に移す。「変更がリリースされたら、仕様の大半は削除すべきである」とする記事による(The Main Thread)。

公開 OSS の Agents SDK は、実行計画を gitignore した plans/ に書き、書き方を定めた PLANS.md だけをコミットしている(2 章)。

評価は定義をコミットし、実行結果はコミットしない

gemini-cli は evals/logs/ を、humanlayer は評価結果の出力先を gitignore している(gemini-cli、humanlayer)。日付付きの評価レポートをデフォルトブランチに置いている例は、調査した範囲にはなかった。

外部からのコントリビューションは、内容を理解している人間が責任を負う

ghostty は、メンテナ自身が AI を多用していると明記したうえで、外部のコントリビューターにだけ AI 利用の開示と内容の理解を求めている(AI_POLICY.md)。goose と cline は issue の承認を PR の前提条件とし、codex は外部からの PR を受け付けていない。開示の方法はプロジェクトによって異なる。ASF は Generated-by または Co-authored-by トレーラーを推奨している(ASF)。Linux カーネルは AI ツールの利用を Assisted-by タグで示すよう求めていたが、2026 年 10 月の Maintainers Summit でこの要件を削除すると決め、2026-11-15 時点の mainline の文書にはこのタグの記述がない(LWN、coding-assistants.rst)。

4並行開発では、タスクの割り当てを 1 か所に集約し、作業は worktree で隔離する

タスクを Issues で管理する場合の、複数のエージェントによる並行開発での割り当て・排他制御・依存関係の扱いを整理する。全体の流れは図4 のとおりである。以下の内容は、公式ドキュメントと clone したリポジトリのファイルで確認した。

割り当ては人間か単一のオーケストレーターが行い、エージェント同士にタスクの取得を競わせない

goose は、公開の Projects ボードでステータスが Ready になった issue だけをエージェントに実装させ、Ready でない issue を実装した PR は閉じる。OpenHands の ready-for-dev ラベルは「明確な受け入れ条件がある」ことを意味し、CI のワークフローがこのラベルを付けたのが書き込み権限以上を持つ人であることを検査する(issue-readiness-check.yml)。Symphony の仕様は「The orchestrator is the only component that mutates scheduling state.」と定め、同時に実行するエージェントの数に上限(既定値 10)を設けている。gastown では、Mayor と呼ぶ調整役のエージェントが作業担当のエージェントにタスクを渡す(SPEC.md、gastown README)。

GitHub の assignee は、タスクをアトミックに取得する手段にはならない

assignee を追加する API は、1 つの issue に最大 10 人まで追加でき、すでに設定されている担当者を置き換えない。更新系のリクエストでは条件付きリクエストが原則として使えない。したがって、複数のエージェントが同じ issue に自分を担当者として設定しても、どちらのリクエストも成功する(REST API: assignees、REST API のベストプラクティス)。エージェントの起動は、人間が 1 件ずつ指示する形が基本である。GitHub Copilot のクラウドエージェントは 1 つのタスクにつき 1 つの PR を作成し、Claude は issue や PR での @claude メンションで起動し、Linear では issue の delegate としてエージェントを設定する。

排他制御はロックではなく、作業環境の隔離とマージ時の検査で行う

タスクごとに git worktree かクラウド上のサンドボックスを用意し、エージェントは互いの作業ツリーに触れない。next.js は worktree を扱うツールの設定(conductor.json、.cursor/worktrees.json、.codex/environments/next.toml)をコミットし、humanlayer はタスク名ごとに worktree とブランチを作成するテンプレートを定義している。マージの直列化には GitHub のマージキューが使える。マージキュー用の merge_group トリガーは、zed、PostHog、goose、pydantic-ai、beads のワークフローにある(実際に有効になっているかは未確認)。

ロックが機能しなかった実例を Cursor が報告している。多数のエージェントを並行して動かす実験で、ファイルのロックを使うと「Twenty agents would slow down to the effective throughput of two or three」となり、楽観的並行制御に変えるとエージェントがリスクを避けて難しい作業に着手しなくなった。最終的に、計画を担当するエージェントと実装を担当するエージェントに役割を分けた(Cursor)。

エージェントが自律的に次のタスクを選ぶ構成では、専用のタスク管理の仕組みを使う

beads の bd update <id> --claim はタスクをアトミックに取得し、別のエージェントが先に取得していた場合は専用の終了コードを返す。Claude Code の agent teams(実験的な機能)は、共有のタスクリストを ~/.claude/tasks/{team-name}/ に保存し、「Task claiming uses file locking to prevent race conditions」としている(beads CLI_REFERENCE.md、Claude Code docs)。いずれも状態は Git リポジトリの外にある。Issues に置くのは「何を実装するか」「誰に割り当てたか」という粒度の情報にとどまる。

依存先の完了の判定方法は、仕組みによって異なる

「マージをもって完了とする」と定めた指針は見つからなかった。実装では、gastown の Refinery がマージ後に元のタスクを閉じ、Symphony ではブロック元の issue が終了状態になった時点で後続の issue が割り当て可能になる。一方、Claude Code の agent teams では、完了はエージェント自身の報告による。マージを待たずに進める方法として、依存先のブランチから後続のブランチを作成する stacked PR があり、pydantic-ai の PLAN.md は実装を stacked PR として順に提出する計画を記載している(PLAN.md)。

作業中に見つかった作業は、元のタスクに含めず、新しいタスクとして登録する

Symphony の WORKFLOW.md は「file a separate Linear issue instead of expanding scope」と指示し、新しい issue を元の issue に関連づける。beads には、作業中に見つかったタスクを元のタスクに関連づける discovered-from という依存関係の種類がある。gastown のドキュメントも、見つけた作業は自分で修正せずに登録するよう指示している(molecules.md)。

leisen は、assignee とラベルによる割り当てで足りる

leisen ではオーナーが唯一の割り当て担当であり、「1 タスク = 1 ブランチ = 1 PR」のルールもすでにある。割り当てる人が 1 人であれば、assignee がアトミックでないことは問題にならない。GitHub App の承認待ちや API キーの入手待ちといった人手による前提条件は、タスク間の依存関係と同じく「ブロックされている」状態として扱い、issue の依存関係か blocked ラベルで表す。コネクタのツール IF は connector-sdk と ADR で先に固定されているので、コネクタの実装は互いに並行して進められる。認可と監査に関わる変更にはレビューが必要なので、依存先の完了はエージェントの報告ではなくマージで判定するのが適している。

並行開発で実際に衝突しているのは、タスクの割り当てではなく、どの PR も書き換える CLAUDE.md の「現在のフェーズ」と backlog README である。タスクと進捗を Issues に移せば、この衝突の原因がなくなる。

5leisen の課題は文書の量ではなく、状態を管理する場所が決まっていないことにある

leisen の文書は 9,602 行で、ソースコード(31,380 行)とテストコード(31,510 行)の合計の約 15% にあたる。量だけを見れば、PostHog の 273 個のスキルや cloudflare/agents の 58 本の設計文書と比べて特に多いわけではない。違いは内容にあり、文書の約 6 割(約 5,800 行)が開発の経過と判断の記録である(棚卸し)。

毎セッション読み込まれる CLAUDE.md の本文の 69% が、進捗記録になっている

CLAUDE.md は 58 行で、行数だけなら 200 行の目安に収まる(図3)。しかし本文の大半は「現在のフェーズ」の節で、恒久的なルールは約 4,600 文字しかない(図5)。この節には、ADR-018 を Proposed とする誤りがある(実際は Accepted)。AGENTS.md や CLAUDE.md に書かれた指示はエージェントによく守られるので、誤った状況の記述はそのままエージェントの判断に影響する。

同じ事実を手作業で複数の文書に転記し、記述が食い違っている

MCP SDK のバージョンは 3 か所に 3 通りの値で書かれ、ADR-018 の Status は ADR 本体と CLAUDE.md で異なる(図6)。このほか、PR #14 がマージされたという記述は 8 ファイルにあり、サブエージェント定義には connector-sdk が v0.3(実際は v0.4)、ADR の次の番号が 017 と書かれている。backlog README が完了としている T-001 / T-002 / T-010 / T-014 は、各タスクのチェックボックスが未チェックのままである。workers-sdk が避けるよう指示している問題が、そのまま発生している。

ADR が、決定の記録と経過の記録を兼ねている

22 本のうち 12 本に追補があり、ADR-001 には追補が 9 回、日付が 15 種類ある。現在有効な決定内容を知るには、全文(合計 233,787 文字)を読む必要がある。cloudflare/agents の「RFC は決定後に更新しない」とは逆の運用である。

内部向けの率直な記述が、公開される文書に含まれている

実際の秘密情報は見つかっていない。懸念されるのは、次の記述が CLAUDE.md と利用者向け文書(docs/install.md など)に分散していることである。

  • T-003 レビューなどで未修正のまま残っている指摘を、minor-6 や H1 といった識別子で列挙した記述(minor-N が 17 ファイル 59 か所、H1 が 27 ファイル 63 か所)
  • 商用配布と有償支援に関する論点
  • 承認待ちの項目の一覧、オーナー個人の開発環境に関する記述

公開された ADR やバックログが攻撃に利用された事例は見つからなかった。これらの扱いはリスク評価の問題であり、実害が確認されているわけではない。

外部のコントリビューターを受け入れるための文書がない

CONTRIBUTING / SECURITY / issue テンプレート / CODEOWNERS がなく、フックによる検査は Claude Code を使わないコントリビューターには適用されない。コミットの 64% はエージェントが作者として記録され、71% に Co-Authored-By トレーラーが付いている。開発体制はオーナー 1 人とエージェントであり、ASF の推奨の範囲には収まっている。

OpenAI の社内プロダクトとの違いは、目次としての AGENTS.md、自動検査、進行中と完了済みの分離である

設計書・実行計画・技術的負債の一覧をリポジトリに置く点は、OpenAI の社内プロダクトと leisen で同じである。違いは、AGENTS.md を約 100 行の目次にとどめていること、文書の鮮度・相互リンク・構造を lint と CI で検査していること、進行中の計画と完了した計画をディレクトリで分けていることの 3 つである。また、OpenAI 自身もタスクの状態は Issue Tracker で管理する方式を公開しており、エージェントが GitHub の issue を読める構成であれば、タスクをリポジトリ内のファイルで管理する必要はない。

8完了した計画と評価結果の残し方変更せずにリポジトリに残す / PR と issue にだけ残す / 削除するbacklog は変更せずに残し、新しい計画と評価結果は PR と issue にだけ残す。複数の PR にまたがる変更で実行計画を書く場合は、Agents SDK と同様に gitignore したローカルの作業ファイルとし、決定事項だけを ADR に記録する

7削除すべきなのは ADR ではなく、ADR と CLAUDE.md に混在している作業の記録である

エージェントによる開発が進んでいるプロジェクトほど、リポジトリに置く文書を、いつ読んでも内容が正しい文書に絞っている。AGENTS.md のルール、スキル、ADR、現行の設計書がこれにあたる。特定の時点では正しかった記録(進捗、計画、評価結果、レビューでの指摘)は、日付と状態が自動的に記録される issue、PR、コミット、リリースで管理している。

すべてをリポジトリに置く leisen の構成は、エージェントにコンテキストを渡すという目的に対しては妥当だった。ただし、この構成が成立するのは、オーナー 1 人とエージェントという閉じた体制で、PR のたびにすべての文書を更新できる間だけである。記述の不一致がすでに生じていることから、その限界は超えている。leisen は認可と監査を強みとするプロダクトなので、ADR と脅威モデルを公開していること自体は、導入を検討する側にとって価値がある。

今回の調査で確認できなかった点が 2 つある。完了済みの計画を残すことがエージェントの作業の成功率を上げるのか下げるのかを測定したデータと、エージェントで開発されたプロジェクトが公開時に開発プロセスの文書をどう再編成したかの事例である。leisen の移行は、その最初の記録の 1 つになりうる。
