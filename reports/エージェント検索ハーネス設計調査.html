検索の仕様を探索 LLM に伝え、利用者が入力したキーワードを検索クエリまで保つ

leisen のエージェント検索ハーネス設計についての調査レポート。2026 年 11 月 25 日

leisen の検索精度が低い原因は、検索の回数が足りないことではありません。原因は 2 つあります。各ソースの検索の仕様が、Orchestrator の中で検索を行う LLM(以下、探索 LLM)に伝わっていないこと。そして、利用者が入力したキーワードが、最初の検索クエリに残っていないことです。回数の上限は、すでに外部の目安を上回っています。

これは、オーナーが挙げた 2 つの問題に対応します。以下、問題 a と問題 b と呼びます。問題 a は、探索 LLM がコネクタの先の検索実装を知らないままクエリを作ること。問題 b は、LibreChat から Orchestrator にクエリが渡る時点で、語を直接検索に入れるより結果が悪くなることです。

対策は 3 つあります。どれも、現行のツール IF を変えずに着手できます。

  1. A
    各ソースの検索の仕様を、探索 LLM に伝える空白区切りが AND か OR か、使える構文、語数の上限、並び順はソースごとに違います。この情報をコネクタに持たせ、Orchestrator が文章にして探索 LLM に渡します。この情報を「検索プロファイル」と呼ぶことにします。
  2. B
    利用者が入力したキーワードを、最初の検索クエリに必ず使うLibreChat 側の LLM が言い換えてもキーワードが失われないように、Orchestrator が利用者の発言から固有名詞などの語句をコードで抜き出し、最初の検索に必ず使います。
  3. C
    検索結果から、次に何をすべきかが分かるようにするスニペットには一致箇所を含めます。0 件や重複のときは、Orchestrator が状況に応じた指示を探索 LLM に返します。

図 1 は、現行の経路のどこで利用者が入力したキーワードと検索の仕様が失われているかを示します。印の位置が、上の A・B・C に対応します。

最初に行うのは計測です。既存の評価は LibreChat 側の LLM も実ソースの検索も通っていないので、現状ではどちらの問題も数値で確認できません。計測の方法は 6 章、作業の順番は 7 章にあります。

このレポートの設計案は、外部の実践と現行実装の読解からの推論です。組み合わせた構成の効果は実証されていません。根拠の強さは 9 章にまとめています。

2外部の実践は「短いキーワード、複数のクエリ、ソースごとの書き方」で一致している

クエリの書き方はバックエンドで決まり、ツール説明に書くのが一般的である

キーワード型の検索に渡すクエリは短くする、という指示は各社で揃っています。Anthropic の Research サブエージェント用プロンプトは「5 語未満」、Jina の node-DeepResearch は「2〜3 語、30 文字未満」、Perplexity は「数語のキーワード、年はフィルタで」と書いています。ニューラル検索の Exa だけは逆に「欲しいページを文で記述せよ」と指示します。つまり、キーワードか自然文かは照合方式で決まります。

キーワード検索を持つ公式 MCP サーバーは、クエリの書き方をツール説明で教えています。しかも、指示がソースによって正反対になることがあります。

表 2 の内容は、調査時に接続されていた実物のツール定義の観測です。公開文書ではなく、サーバー側で変わりえます。

5 つのバックエンドは、空白の解釈からして違う

leisen が接続する検索を並べると、全ソースに共通する指針は成り立たないことが分かります。たとえば Redmine に日本語の文をそのまま渡すと、空白がないので文全体が 1 つの語として部分一致にかけられ、ほぼ必ず 0 件になります。

回数は複雑さで決め、1 ターンに複数のクエリを並べる

検索の回数は固定せず、質問の複雑さに応じてモデルに見積もらせるのが共通の方法です(図 2)。止める条件も、判定できる形で書かれています。LangChain の open_deep_research は「十分に答えられる」「関連ソースが 3 件以上ある」「直近 2 回の検索が同じ情報を返した」の 3 つを即時停止の条件にしています。

一方、論文は「回数を増やせばよい」とは言っていません。最初の数ステップの後は新しい文書が出にくくなるという分析があり、文書の新規性を信号にして続行、方向転換、停止を選ぶ制御の仕組みは、検索回数を平均 14 回減らしながら精度を平均 3 ポイント上げました。質問を手掛かりに分け、手掛かりごとの短い検索の結果を統合し、最初の検索結果として渡すだけで、精度が 5〜11 ポイント上がったという報告もあります(いずれも査読前)。

0 件や失敗のときは、ツールの応答文で次の行動を指示する

Anthropic は、エラーの応答文でエージェントの行動を誘導できるとし、直し方を返すよう勧めています。smolagents の検索ツールは 0 件のとき「より一般的なクエリを試せ」と返します。Jina は失敗したクエリの一覧を次のプロンプトに差し戻し、重複した検索を検出すると「別の角度から考えよ」と返します。「同じクエリを繰り返すな」とプロンプトに書くだけでは弱く、委譲を調べた実験では重複回避の指示がほぼ無効でした。

委譲すると情報が失われる。利用者が入力したキーワードを残し、言い換えは別のクエリにする

問題 b と整合する実測があります。2026 年 11 月のプレプリントは、Web 検索を 1 つのエージェントで行う場合と委譲する場合を比べ、32 条件中 21〜22 条件で委譲が悪化したと報告しています。原因は、委譲する側のエージェントの書き直しがタスクを変えてしまうことと、委譲された側の失敗が委譲した側に伝わらないことでした。ただし「利用者の発言をそのまま委譲先に渡す」という緩和策は試されていません。また約 30B 級の Qwen3 だけは委譲が有利でした。

対話検索の研究は、代名詞と省略だけを解決して他の語を残す「最小限で忠実な書き換え」を支持しています。検索範囲を広げるための言い換えは別のクエリとして並行に実行し、利用者が入力したキーワードによる結果の重みを大きくします。LLM の知識だけで語を足す拡張は、LLM が知らない題材で失敗します。社内だけで使われる用語は、この条件に当てはまります。

ソースを都度検索する方式の弱さは、どの製品も LLM 側で補っている

本人の資格情報でソースを都度検索する方式は、Microsoft 365 Copilot のフェデレーテッドコネクタや Claude の enterprise search も採っています。補う場所は、専用のシステムプロンプト、ツール説明での構文の教育、ソースごとのクエリの作り直しで、ほぼ LLM 側です。ハーネスの違いが、検索エンジンの違いと同じくらい結果に影響するという報告もあり、同じモデルでハーネスを替えると正答率が 93.1% と 76.7% に分かれた例があります(査読前)。

3現行の leisen では、利用者が入力したキーワードと検索の仕様が途中で失われている

問題 a: 検索の仕様を伝える手段が、自由文 1,000 字しかない

ソースごとの検索の仕様を探索 LLM に伝えられる場所は、コネクタの summary(自由文、1,000 字で切られる)だけです。そして、どのコネクタもそこに構文を書いていません。esa の既定は英語 1 文の内容説明、Redmine は対象種別だけです。esa コネクタは in: や updated: を自分で組み立てており、LLM が title: や OR を書けばそのまま効く構造ですが、LLM はそれを知らされていません。

代わりに探索プロンプトに書かれているのは、全ソース共通の指針「多くのソースは空白で区切った語をすべて含む文書だけを返す」「名詞を 1〜2 語だけ」です。この指針は AND 部分一致の開発用コネクタでの失敗から作られたもので、実ソースでは検証されていません。

問題 b: 利用者が入力したキーワードは 2 か所で減る

1 か所目は UI 側 LLM です。ask の引数は自然文の question 1 本で、入力側の指示は「利用者の質問は ask ツールに渡してください」だけです。利用者の発言をそのまま入れよ、固有名詞を変えるな、という指示はありません。ask は会話履歴も受け取りません。2 か所目は探索プロンプトで、「質問文をそのまま入れるな、1〜2 語にせよ」と語を減らすよう指示しています。利用者が esa の検索欄に直接入力すれば目的の文書が見つかる語の組み合わせが、途中で減ります。

問題 b の説明は実装の読解からの推論です。UI 側 LLM が実際に question をどう書き換えているかの記録は、リポジトリにありません。

共通の指針が当てはまらないソースがあり、評価環境は実ソースより有利な条件になっている

Redmine コネクタは all_words=0 を送っています。Redmine のソースコードを読む限りでは OR になり、「語を足すほど絞り込まれる」という指針が逆になります。並び順は日付順なので、語を足すほど最近更新された無関係な Issue が上に並びます。プロンプトが勧める filters.container も、Redmine では指定するとエラーになり、1 ターンを失います。

評価に使っている開発用コネクタは、一致箇所を中心にしたスニペットを返し、タイトル一致で順位を付けます。「名詞 1〜2 語」は 7 文書のコーパスでは必ず上位に入りますが、数千件の実ソースでは目的の文書が上位 10 件に入らない方向に働きえます。

all_words=0 が実機で OR になるか AND になるかは未確認です。esa の検索が MCP 経由で公式ヘルプと同じ仕様で動くかも、実機では確かめていません。

4検索プロファイルを伝え、利用者が入力したキーワードを最初の検索に必ず使う構成にする

推奨する構成は、ask の中で探索 LLM が検索する現行の構成を保ち、最初の検索だけをコードで決まった手順として実行するものです(図 3)。出典の検証と run の記録という leisen の中核はそのまま残ります。

ask には利用者の発言をそのまま渡させ、言い換えを UI 側 LLM に任せない

まず引数を変えずに、ask の description に入力側の指示を足します。利用者の直近の発言を言い換え、要約、翻訳せずに入れること。固有名詞、ID、エラー文、引用符で囲まれた語句を一字も変えないこと。意味が通らないときだけ、指している対象を補うこと。Anthropic は、モデルが検索クエリに不要な年を付け足す癖をツール説明の修正で直した例を挙げています。

UI 側 LLM が指示に従わない場合への備えも用意します。Orchestrator が受け取った question から、引用符で囲まれた語句、英数字と記号の連なり(ID、エラーコード、ファイル名)、カタカナや漢字の連なりを機械的に抜き出し、最初の検索の 1 本に必ず使います。

次の段階として、利用者の発言をそのまま入れる引数(userMessage)、会話の前提(context)、変えてはならない語(keepTerms)を足す案があります。これは ADR-018 の変更になります。返り値には、試したクエリと、有用な結果がなかったソースを構造化して入れます。委譲の実験が示した「委譲先の失敗が委譲元に伝わらない」問題への対処です。

20B 級の UI 側モデルが description の指示に従うかは未検証です。辞書なしでの日本語の語の抽出の精度も、実装して確かめる必要があります。

検索プロファイルはコネクタが持ち、Orchestrator が文章にして渡す

ソースごとの検索の仕様は、コネクタというプラグイン境界が持つのが ADR-005 と整合します。Orchestrator のコアに esa や Redmine の構文を直書きすると、個社差分をコアに入れることになります。プロファイルの項目は、各社がツール説明に書いているものと同じです。空白区切りの既定、照合の単位、引用符の可否、演算子と修飾子、語数の上限と超過時の挙動、並び順、スニペットの種類、そして各項目が実機で確認済みかどうかです。

渡し方は 3 段階で進めます。

  1. IF を変えない。各コネクタの summary に検索の書き方を書き、探索プロンプトの共通の指針を「各ソースの検索の仕様に合わせる」に置き換える。
  2. SourceDescription に構造化した searchProfile を足す。列挙値と数値を中心にし、文章は Orchestrator がテンプレートから生成する。こうすると「外部のデータ」の自由文ではなく、Orchestrator 自身の文として渡せる。ADR が要る。
  3. 導入ごとの差を deployment.yaml で上書きする。Redmine の全文検索プラグインの有無、Slack の意味検索の可否など。

Redmine は、プロファイルを書く前にコネクタの挙動を決める必要があります。関連度のない日付順の検索で OR を既定にすると適合率が構造的に低くなるので、AND を既定にし、0 件のときに OR に切り替える順序が妥当だと考えます(実機での比較はしていません)。

クエリは、利用者が入力したキーワードで 1 本作り、言い換えは別のクエリにし、根拠のない語は足さない

現行の「名詞 1〜2 語」を次の規則に置き換えます。

  • 語数はソースのプロファイルに合わせる。関連度順のソースでは主題の名詞 2〜3 語を基本にし、1 語だけのクエリは、0 件だったときに次に試す形とする。
  • 最初のターンで、利用者が入力したキーワードをそのまま使ったクエリを必ず 1 本出す。
  • 表記の違う言い換え(長音の有無、英語と日本語、略語と正式名、複合語の分割)は、別のクエリとして同じターンに並べる。1 本に並べてよいのは、プロファイルが OR の記法を明示しているソースだけ。
  • 質問に複数の事柄があるときは、事柄ごとに分ける。
  • 社内だけで使われる用語を、LLM の知識で言い換えない。次の語は、1 回目の結果に実際に出てきた表記から拾う。
  • 期間や区画はクエリ語ではなく filters に入れる。

0 件、重複、切り捨ては、Orchestrator が制御メッセージで知らせる

Orchestrator は自分が出したクエリの形とソースのプロファイルを知っているので、コネクタの IF を変えずに次の判定ができます。語数がソースの上限を超えていた。クエリが文のままで空白がない。フィルタを指定していた。同じソースに同じクエリを既に実行していた。今回のヒットがすべて既出だった。試したクエリの一覧(ソース、クエリ、新しく得た文書の数)も毎ターン示します。

守る線は ADR-012 です。メッセージに書けるのは、クエリの形と、認可を通って返ってきた結果から計算できることだけです。「権限がないため 0 件」と「本当に 0 件」を区別する情報は出しません。

回数の目安はツール呼び出し数で示し、止める基準と続ける基準を書く

上限値は変えません。変えるのは、探索 LLM への伝え方です。1 ターンに複数の検索を並べてよいこと、単純な質問は 2〜4 回で終えてよいこと、複数の事柄を含む質問は 10 回前後を使ってよいことを伝えます。ローカルモデルでは時間の大半が推論なので、ターンを増やすより 1 ターンに並べる検索を増やす方が 120 秒の時間上限に合います。

  • 止める基準: 質問の各事柄について本文を読んだ裏付けがある。または、直近 2 回の検索が新しい文書を返さなかった。
  • 見つからないときに打ち切る基準: 利用者が入力したキーワードによる検索、語を減らした検索、表記を変えた検索がどれも有用な結果を返さなければ、探した範囲を書いて unresolved で提出する。
  • 続ける基準: 1 件も fetch せずに提出しようとしたとき、裏付けのない事柄が残っているときは、Orchestrator が 1 回だけ差し戻す。

結果は一致箇所が見える少量にし、判断の前に本文を読ませる

スニペットが本文の先頭だと、目的の文書が検索結果に含まれていても、探索 LLM にはそれが分かりません。esa の検索結果には本文が含まれているので、コネクタの中でクエリの語の周辺を切り出せます。IF は変わりません。GitHub の issue と PR も一致断片を取れます。esa のヒットにはカテゴリをタイトルと並べて見せます。

fetch は、有望な上位 2〜3 件を同じターンで並行に読んでから採否を決めるよう書きます。弱いモデルは全文を読むツールをほとんど使わないという結果があるので、プロンプトだけでなく前項の差し戻しで担保します。

一致箇所のスニペットが ADR-016 の規約の範囲に収まるかは、同 ADR の本文を今回読んでいないので確認が必要です。

結果の統合と再順位付けは Orchestrator の中で、順位だけを使って行う

複数のクエリの結果は (sourceId, documentId) で重複を除き、順位だけを使って統合します(rank fusion)。ソースごとにスコアの尺度が違い、そもそも返らないからです。利用者が入力したキーワードによるクエリの結果を 2 倍の重みにすると、言い換えで意味がずれた場合の影響を抑えられます。選別は、探索 LLM 自身に題名とスニペットの一覧から選ばせるのが第一候補です。Redmine のように日付順でしか返らないソースで特に価値があります。対象は認可済みのヒットだけなので、ADR-012 の境界は変わりません。

小型ローカルモデルには、手順をプロンプトではなくコードで固定する

27B 級のモデルを前提にするなら、プロンプトに手順を書き足すより、決まった手順をコードで実行する方が確実だと考えます。小型モデルの実力を測ったプレプリントでは、短い構造化されたツール利用は小型モデルで足り、長い計画は足りませんでした。計画、実行、提出に分解するプロンプトは、試したすべてのモデルで悪化しました。図 3 の「コードで実行する最初の検索」は、この解釈に基づきます。

この論文はコード側の固定を比較しておらず、検索ではなくツール操作の合成ベンチです。「コードで実行する方が確実」は推論です。

構成の選択肢は 4 つあり、現行の構成に、コードで実行する最初の検索を加える形を勧める

推奨は、案 3 を基本にし、案 2 の「コードによる並列検索」を最初の検索として Orchestrator の中に組み込む構成です。案 4 は、6 章の比較実験で「人が書いたキーワードを直接入れる」条件が大きく上回り続ける場合の次の候補として残します。案 1 は、UI 側 LLM が小型モデルである限り勧めません。

5プロンプト文面の例

以下は文面の例で、評価を経た確定版ではありません。制御メッセージを含むプロンプトの変更には評価レポートを添える規則です(packages/orchestrator/src/prompt.ts:15-16)。

ask の description

引数を変えない第 1 段階の例です。question の書き方の指示を足しています。

社内ナレッジ(接続済みのデータソース)を利用者本人の権限で検索し、出典付きで回答する。

question の書き方:
- 利用者の直近の発言を、言い換え・要約・翻訳をせずにそのまま入れる。
  固有名詞、ID、エラーメッセージ、引用符で囲まれた語句、英数字の表記は一字も変えない。
- 直近の発言だけでは意味が通らないとき(「それ」「さっきの件」など)に限り、
  指している対象を会話から補い、末尾に「補足: …」として足す。
- 利用者が言っていない条件(用途・期間・範囲)を足さない。
  利用者が検索語・対象のソース・期間を指定していれば、その指定をそのまま含める。
- このツールは過去の会話を覚えていない。1 回の呼び出しで質問が完結するように書く。

結果の本文と「出典」節は改変せず、そのまま利用者に提示する。リンクは「出典」節の URL だけを使う。
outcome が resolved 以外のときは、先頭の注意書きを省かない。応答には 1〜2 分かかることがある。

探索プロンプトの「探索の進め方」

現行の共通の指針を、ソースごとの検索の仕様を参照する指示に置き換え、最初のターンの検索の構成と停止の基準を足した案です。

# 探索の進め方
1. 最初の利用者メッセージの「利用者が入力したキーワード」(質問から抜き出した固有名詞・ID・語句)と、
   各ソースの「検索の仕様」を読む。検索の書き方はソースごとに違う。仕様に書かれていない
   記法(他のサービスの演算子など)は使わない。
2. 最初のターンでは、次の検索を 1 回の応答でまとめて呼ぶ。
   - 利用者が入力したキーワードを変えずに使った検索(主題を表す語を 2〜3 語。文や助詞は入れない)
   - 表記の違う言い換え(カタカナの長音の有無、英語と日本語、略語と正式名、
     複合語を分けた形)を、それぞれ別の検索として
   - 質問に複数の事柄があるときは、事柄ごとに別の検索として
   query に入れるのは、文書を書いた人が実際に書きそうな語だけにする。
   意味を知らない社内用語は推測で言い換えない。
3. 結果のタイトル・区画・スニペットを見て、有望な 2〜3 件を fetch で読んでから判断する。
   スニペットが本文の先頭だけのソースでは、スニペットに答えが見えなくても
   タイトルが合っていれば読む。
4. 次の検索の語は、ここまでの結果に実際に出てきた表記から選ぶ。同じソースに同じ query を
   繰り返さない。語を減らす・フィルタを外す・別のソースを試す、の順で広げる。
5. 次のどちらかになったら submit_answer を呼ぶ。
   - 質問の各事柄について、本文を読んだ裏付けの文書がある
   - 利用者が入力したキーワードでの検索、語を減らした検索、表記を変えた検索のいずれも
     新しい有望な文書を返さなかった(このときは探した範囲を書き、unresolvedReason を付ける)

ソースの検索の仕様

Orchestrator がプロファイルの列挙値から生成する文の例です。未確認の項目は「不明」と書きます。

[オーケストレーター] 各ソースの検索の仕様
- esa-main: 空白で区切った語をすべて含む記事を返す。別表記をまとめるときは「A OR B」。
  タイトルに絞るときは title:語、完全一致は "語句"。日付は filters を使う。
  順位はタイトルに語を含む記事が上。スニペットは本文の先頭で、一致箇所ではない。
  filters.container はカテゴリのパス(例: 開発/設計)。
- redmine: フィルタは使えない。語は部分一致で、先頭 5 語だけが使われる。
  順位は関連度ではなく更新の新しい順。語の組み合わせ方(すべて含む / いずれか含む)は不明。
  1〜2 語から始め、結果が多すぎるときに語を足す。
- github: 空白で区切った語をすべて含むものを返す。1 回の検索で issue・PR・コードが混ざって返る。
  言い換えは 1 つの query に並べず、別の検索に分ける。
  filters.container は owner/repo または組織名。

0 件と重複のときの制御メッセージ

権限や件数には触れません。

[オーケストレーター] redmine への検索「VPN 接続手順 申請 承認 期限 例外」は結果を返さなかった。
このソースは先頭 5 語だけを使う。語を 2 語以下に減らして検索し直す。
見つからなかったことは、文書が存在しない根拠にならない。

[オーケストレーター] esa-main への検索「経費精算」は 2 ターン目と同じ query で、新しい文書はなかった。
別の表記(expense、立替)か、別のソースを試す。

[オーケストレーター] ここまでの検索: esa-main「経費精算」→ 新しい文書 6 件 / esa-main「経費 締め日」→ 0 件 /
redmine「経費」→ 新しい文書 3 件。ツールを呼べるターンは残り 3 回。

6精度の低下は、区間ごとにクエリの作り手を入れ替えて測る

問題 a と b を分けて測るには、同じ質問と同じ正解文書に対して、検索に入力するクエリの作り手だけを入れ替えて比較します(図 4)。

実ソースの検索の仕様を模したフィクスチャと、クエリを記録するトレースを先に作る

現行の評価環境は AND 部分一致の 1 種類で、プロンプトはそれに合わせて調整済みです。開発用コネクタに検索の方式を切り替える設定を足し、esa 型(AND、タイトル優遇、本文の先頭を切り出したスニペット)、Redmine 型(部分一致、5 語上限、日付順)、GitHub 型(種別の混合)を模します。コーパスは 7 文書から数百件に増やします。同じ語を含む無関係な文書が多数ないと、適合率の問題は現れません。

実ソースの検索の仕様は、推測ではなく実測で確かめます。同じ文書に対して、文、名詞の AND、複合語、表記違い、6 語以上のクエリを実行し、どのクエリで見つかるかを記録する小さなスクリプトを、esa、GitHub、Redmine の実機に対して走らせます。

質問は 3 種に分け、失敗は「どの段階で最初に失敗したか」で分類する

質問セットは、既知項目検索(known-item search。題名や ID が分かっている 1 文書を探す質問)、複数文書の質問、答えられない質問の 3 種に分けます。最初の質問は、オーナーが把握している失敗(質問、期待した文書、直接入力して見つかった語)から作るのがよいと考えます。失敗は、次の状態のうちどれを最初に満たせなかったかで分類します。

  1. UI 側 LLM が ask を呼んだ
  2. question に利用者が入力したキーワードが残った
  3. 正しいソースを選んだ
  4. クエリが 1 件以上を返した
  5. 正解文書が上位 k 件に入った
  6. 正解文書を fetch した
  7. 回答が正解文書に基づいている
  8. 引用が正しい

この 4 条件の比較は公開の標準手法ではなく、「検索を先に IR 指標で切り分けよ」「多段のトレースでは、経路の中で最初に起きた失敗を見よ」という指針(Hamel Husain と Shreya Shankar の FAQ、Anthropic の評価の記事)から組み立てたものです。0 件率は「認可済みの結果が 0 件」と定義します(ADR-012)。

7進め方は、計測、文面、コネクタ、IF の順にする

1 から 6 は ADR なしで進められ、1 から 4 は人手による準備も要りません。7 以降は、1 から 4 を文面とコードで試して効果を確かめてから ADR を起こす方が、IF に入れる項目を絞れます。

8不変条件と ADR は、変更の置き場所を決めている

ソース固有の知識はコネクタに、導入先ごとの値は deployment.yaml に、仕組みそのものはコアに置きます。検索プロファイルという仕組みはソースの種類に依存しないので、コアに置けます。

Slack については、ADR-014 に関わる見落としやすい点が 1 つある

「検索結果に出た語で次のクエリを作る」方式を Slack に適用すると、Slack 由来の語(チャンネル名、人名、本文の語)がクエリに入ります。そのクエリは生クエリ表、「試したクエリ」の返り値、チャット UI の履歴に残りえます。これは Slack 由来データの永続化(ADR-014)に当たるおそれがあり、既にある未決事項「Slack 有効時にクエリ原文を生クエリ表に書く挙動」と合わせて、T-006 の前に決める必要があります。

ADR-016、007、011、013、015、017、019 の本文と脅威モデルの原文は今回読んでおらず、CLAUDE.md とコード内のコメント経由の把握です。プロファイルを Orchestrator 自身の文として渡す設計は本レポートの提案で、プロンプトインジェクション対策の観点でのレビューが要ります。

9根拠の弱い点

最初に確定させる事実は 3 つである

探索プロンプトの v3 は、開発用コネクタの AND 部分一致に合わせて最適化され、その環境で 40 回中 37 回合格しました。同じことを v4 で繰り返すと、測れる環境での得点だけが上がり、実ソースで見えている問題は動きません。実ソースの検索の仕様を模したフィクスチャと、区間ごとの比較実験が、以後のすべての変更の判定基準になります。

  1. Redmine の all_words=0 が実機で何を返すか。
  2. esa の MCP 経由の検索が空白をどう扱うか。
  3. UI 側 LLM が、question に利用者が入力したキーワードを残しているか。

調査ノートの全文は research_notes/エージェント検索ハーネス設計調査/、元の文章版は reports/エージェント検索ハーネス設計調査.md にあります。
