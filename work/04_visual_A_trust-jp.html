COLUMN 01

AI検索の導入でつまずくのは、検索ではなく権限です

全社の情報をAIに検索させようとした瞬間、これまで見過ごされてきた権限設定の問題が表面化します。

過剰共有が、AIで露呈する

放置された広すぎる共有設定のままAI検索を重ねると、役員資料や人事資料が「検索すれば出てくる」状態になります。問題はAIではなく、権限が最初から広すぎることです。

権限を持たないRAGは、経営資料が混ざる

全社データを一括で取り込み、利用者ごとの権限を持たない検索基盤では、一般社員が見るべきでない資料が回答に混ざります。元文書のアクセス権を回答にも引き継ぐ設計が要ります。

部署ごとの野良RAGは、統制できない

部署単位で作られた検索ボットが増えるほど、誰がどの社内データをどう検索しているのか、情シスから見えなくなっていきます。

COLUMN 02

権限を複製しない。可否の判断は、元のデータソースに任せる。

leisenは独自の権限データベースやACLのコピーを持ちません。検索のたびに、各データソースが検索する本人の資格情報に対してアクセス可否を判断します。権限の変更は即時に反映され、権限表の同期ズレによる事故が起きません。

利用者チャット／エージェント
→本人としてログイン
leisen Gateway認証・監査ログ・レート制御
（すべての呼び出しの単一経路）
→本人の資格情報でAPIを呼ぶ
Google Drive が可否を判断
Slack が可否を判断
GitHub が可否を判断
wiki（Confluence等） が可否を判断

返ってくるのは、定義上「その人が見てよい情報」だけ。leisen側に権限の複製・翻訳・同期は存在しません。

COLUMN 03

誰が・どのソースに・何を検索したか。全件、監査ログに残る。

すべての検索・取得はGatewayを通り、Gatewayを経由しないアクセス経路は作りません。監査・インシデント調査のとき、「誰の権限で・どのソースに・何を問い合わせ・何が返ったか」を全件たどれます。

# 監査ログの記録イメージ（項目は設計ドキュメントに基づく例） { "ts": "2026-08-28T09:12:44Z", "principal": "user:tanaka@example.co.jp", # 誰の権限で "source": "gdrive", "tool": "search", # どのソースに・どの操作で "query_ref": "q_8f31…", # 何を（生クエリは短期保持後に削除） "decision": "allowed-by-source", "results": 12 } # 何が返ったか

権限と監査のしくみは、設計ドキュメント（ADR）で公開しています。

COLUMN 04

回答には必ず出典リンク。原文までワンクリック。

回答は必ず原典への参照付きで返り、利用者はワンクリックで原文に到達できます。1回のキーワード一致で終わらせず、LLMが「粗く探す→結果を読む→検索し直す」を繰り返して絞り込むため、キーワードを何度も変えるのは人ではなくLLMの仕事になります。

① 粗く探す

質問から検索語を組み立て、権限のあるソースを横断して当たりをつけます。

② 読んで、検索し直す

ヒットした文書を読み、足りなければ言い換えて再検索。ヒットしない・多すぎるを機械側で吸収します。

③ 出典付きで答える

まとまった回答と、根拠になった原典へのリンクを返します。裏取りは1クリックです。

COLUMN 05

導入1件の構成は、deployment.yaml 1枚。

どのソースを繋ぎ、どの認可方式を使い、監査をどう設定するか——1社分の導入構成はひとつの設定ファイルで宣言します。設定スキーマとコードは公開されており、何がどこまで設定できるかを導入前に確認できます。

# examples/deployment.yaml（抜粋） deployment: name: your-company idp: adapter: keycloak # okta / entra-id も選択可 connectors: - id: gdrive enabled: true privateScopes: excluded # 個人領域は既定で除外 - id: slack enabled: true audit: failureMode: fail-closed # 監査に書けなければ止める
COLUMN 06

ソフトウェアはOSSで無償。導入支援とサポートが有償。

ライセンス費・ユーザー数課金はありません。費用が発生するのは、導入支援と運用サポートの役務だけ。小さく試すのに最低契約や有償PoCは要りません。

FAQ

よくある質問

オンプレ／自社クラウドで動きますか？

はい。OSSを自社環境（オンプレミスまたは自社契約のクラウド）にデプロイして使います。社内データが外部のSaaSに送られることはありません。

Slackのデータは保存されますか？

保存しない設計です。Slackは検索のたびにその場で参照し、本文もメタデータも基盤側に永続化しません（設計ドキュメントADR-014）。

既存のIdP（Okta / Entra ID）と繋がりますか？

IdP Adapterというプラグインで接続します。Keycloak・Okta・Entra IDの参照実装を提供予定で、認証は既存のSSOに乗ります。

検索インデックス（検索層）を後から足せますか？

はい。検索性能が十分に出ないソースや、検索のカスタマイズが必要な用途に向けて、後から検索インデックスを追加するオプションがあります。導入はインデックスなし（データソースとなる各ツールの検索機能を直接利用）で始まり、必要になったソースにだけ追加できます。

いまの環境のソースと権限構成から、一緒に確認します。

導入相談は、利用目的や利用傾向、環境などのアセスメントから始まります。設計ドキュメント（ADR）と導入プレイブックは、登録なしでそのまま読めます。
