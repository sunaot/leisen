01 / 課題

AI検索の事故は、AIが権限を破るから起きるのではない。

広すぎる権限が、AIで一気に表面化するから起きる。過去の共有リンク、継承されたままのフォルダ権限 — 普段誰も辿り着かない文書が、自然文の検索で見つかるようになる。権限総点検が終わるまで導入を止めるか、判定を毎回ソースに任せるか。

02 / 仕組み

権限のコピーは持たない。見てよいかは、毎回ソースが本人に対して判定する。

検索はすべて利用者本人の資格情報でソースAPIに対して実行。ACLの複製・同期・独自権限モデルは実装しない。ソースアクセスは全てGateway経由の単一経路で、迂回路はない。

権限を複製・同期する検索

  • ACLコピーの同期漏れ・反映遅れが構造的に発生
  • 導入前に全社の権限棚卸しが前提になる
  • 本文の中央コピー(インデックス)を常時保持

認可を委譲する検索(leisen)

  • 元のソースが毎回、本人に対して判定する
  • 異動・退職はソース側の権限変更が即座に効く
  • データもログも自社環境のみ。インデックス既定オフ
03 / 監査・検証

「守れている」ことを、監査ログとカナリア文書で検証し続ける。

全ツール呼び出しを記録(誰の権限で・どのソースへ・何を問い合わせ・何が返ったか)。監査は回答単位とツール呼び出し単位の2層。カナリア文書 = 特定テストユーザーに絶対に見えてはいけない文書を各ソースに常設し、ヒット0件を常時監視する。

不変条件はCIが検査する: 認可の委譲・全呼び出しの監査・userId必須キャッシュ。

04 / できること

散らばったままの社内情報に、出典付きで答える。

Google Drive・Slack・GitHub・wiki。集約も移行も不要 — LLMが複数ソースを本人権限で反復検索し、出典リンク付きで回答する。個社固有のソースはコネクタSDK(search / fetch / list / describe)で追加できる。個社差分は Connector / IdP Adapter / Search Backend の3境界だけで吸収する。

制約も明記する: Slackはオンデマンド検索のみ(本文・メタデータを永続化しない。API規約準拠)。構造化クエリ(DB・BI)はv1.0スコープ外。

05 / 運用

導入1件=設定ファイル1枚。同期パイプラインもインデックスも、最初から抱えない。

インデックスは、証拠が出るまで作らない(既定オフ)。監査ログの昇格判定レポートが「このソースはネイティブ検索では解決しない」と示したソースだけ、コネクタ単位で有効化する。可動部品が少ないから、専任1〜2名で回る。

07 / FAQ
Slackの本文は保存される?
されない。毎回オンデマンド検索し、本文もメタデータも永続化しない。
SaaS型(Glean等)との違いは?
データ・インデックス・監査ログが自社から出ない。権限の扱いを主張ではなくコードで確認できる。
審査用の資料は?
脅威モデル・監査設計・認可方式のADRを公開している。
