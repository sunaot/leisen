## Option A — 権限ゲート正面型
Summary: 「AI社内検索の本当の障害は権限」という情シスの実感(D-7/D-8)に正面から答え、権限透過と監査を主戦場にする。02のポジションの中心案。

- Target: 従業員数百〜数千人の情シス・セキュリティ責任者。Copilot/RAG検討で権限整理の壁に当たった、または野良RAG乱立を統制したい状況。検索流入(「エンタープライズサーチ 権限」「社内 RAG セキュリティ」)を想定。
- Core message:
  - H1: 「Google DriveもSlackも、本人の権限のまま横断検索。」
    - proposition: この基盤で検索すると、Google DriveやSlackなど複数のデータソースを一度に検索でき、結果に出るのは検索した本人が元のシステムで見られる情報だけである。だから全社に配っても権限外の情報は出ない。
    - structure / exemplar: operation→result / R-quicksol-41「社内ファイルサーバからクラウドまで 高速・高精度に横断検索」、R-neuron-40「オンプレもクラウドも横断検索！」
  - Sub: 「社内ナレッジをLLMで検索できるようにするOSS基盤。アクセス可否は元のデータソースが検索する本人の資格情報で判断し、すべてのツール呼び出しを監査ログに記録します。」
    - proposition: これはOSSのエンタープライズサーチ/社内RAG系基盤である。アクセスの可否判断は本体が行わず、元のデータソースが本人の資格情報に対して行う。全アクセスが監査ログに残る。だから情シスは権限の複製表を作らずに導入でき、事後の説明責任も果たせる。
  - Headline type / exemplar: outcome型(7/14で最多)/ R-quicksol-1「欲しい情報がすぐに見つかる 企業内検索システム」
- Argument logic: 促し(本人権限のまま横断検索)→ 課題の言語化(つまずくのは権限整理: D-7/D-8)→ 方式の証明(委譲のしくみ図解+監査ログ)→ 検索便益の事実記述(出典リンク・反復検索)→ 導入負担の低さ(deployment.yaml)→ 費用構造(OSS無償+支援有償)→ 相談へ。反論マップの順序は02の通り: 権限→監査→検索精度→データ主権→導入の手間→価格。

## Option B — OSSアーキテクチャ開示型
Summary: 起案者となる技術責任者・テックリードに向け、「コードと設定がすべて公開されている」こと自体を信頼の根拠にする。Onyx型(Line 3)の借用を最大化。

- Target: 技術選定の一次スクリーニングを行うテックリード・アーキテクト・CTO(数百〜数千人規模)。GitHub・技術記事・比較記事(「Glean 代替 OSS」「Onyx 比較」)からの流入。
- Core message:
  - H1: 「自社環境で動かす、OSSの社内ナレッジ検索基盤。」
    - proposition: これはSaaSではなく、自分の会社の環境にデプロイして動かすオープンソースの基盤であり、対象は社内ナレッジの検索である。だから社内データを外部に預けない検索環境を自分たちで持てる。
    - structure / exemplar: audience→offer(定義提示)/ R-narekan-44「『非IT企業』向けの、AIナレッジツール」、R-onyx-41「Onyx is the open-source AI chat connected to your docs, apps, and people.」
  - Sub: 「Gateway・コネクタ・検索層まで、コードと設定スキーマを公開。データは自社環境から出しません。Apache-2.0(予定)。」
    - proposition: アーキテクチャの全コンポーネントのコードが読め、社内データが外部サービスに送られない。ライセンスは企業利用の摩擦が小さいApache-2.0を予定している。だから導入前の技術・法務審査を自力で完了できる ※「出しません」の否定形はD-14(外部SaaSに預けたくない)でライセンス
  - Headline type / exemplar: audience→offer型 / R-narekan-44(対象の名指し→カテゴリ提示)
- Argument logic: 定義(OSS・自社環境)→ データの扱い(複製を持たない設計)→ 認可方式(委譲)→ コネクタの事前確認可能性(D-5)→ 導入の再現性(deployment.yaml)→ 監査→ GitHub/ドキュメントへ。

## Option C — 現場起案・移行不要型
Summary: 「情報が散在して探せない」という現場の痛み(D-9/D-10)から入り、「いまあるものを移さずそのまま検索」を約束する。起案者(DX推進・現場テックリード)が社内を説得するためのLP。

- Target: 情報探しに消耗している現場のDX推進担当・部門テックリード(数百〜数千人規模)。「社内 ナレッジ 検索 AI」等の課題語検索や紹介記事からの流入。情シアへの起案前段階。
- Core message:
  - H1: 「社内の情報は、移さず、そのまま検索。」
    - proposition: 既存のGoogle Drive・Slack・wiki等から内容を移行・転記せず、いまある場所に置いたまま横断検索の対象になる。だからナレッジ移行プロジェクトなしで検索できる状態が手に入る。
    - structure / exemplar: contrast / R-notepm-40「“属人化した情報”を“会社のナレッジ”に」、R-neuron-41「ファイル名だけでなく ファイルの中身まで全文検索！」
  - Sub: 「散らばったGoogle Drive・Slack・GitHub・wikiを、LLMにまとめて聞ける。回答は出典リンク付き、見られる範囲は本人の権限のまま。」
    - proposition: 複数ソースへの質問が1回で済み、回答から原文に飛べて、自分の権限外のものは出ない。だから探し回る時間が質問1回に置き換わり、勝手に見えてはいけない物が見える事故もない。
  - Headline type / exemplar: outcome型 / R-notepm-1「社内の知りたい、すぐ見つかる。」
- Argument logic: 痛みの承認(散在・探す時間: D-9/D-10)→ 約束(移さずそのまま)→ 検索体験(出典リンク・反復)→ 安心(権限そのまま=情シスを説得できる)→ 書き直し不要(D-9)→ 導入の現実性(プレイブック・OSS)→ 相談へ。
