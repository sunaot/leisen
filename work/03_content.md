前提: 3案とも Phase 2 の骨格(Line 2: 国内実績駆動型)と許容逸脱リスト(1〜6)の内側にある。実績系プルーフはすべてプレースホルダ(逸脱5)。製品名は「leisen(霊泉)」を仮使用(商標未確定)。

## Option A — 統制と検証(推奨)
Summary: 稟議を書く情シス/セキュリティ責任者に「権限事故を起こさず、データを外に出さずにAI検索を導入でき、守れていることを検証し続けられる」ことを約束する。

- Target: 数百〜数千人規模の国内企業の情報システム部門・セキュリティ責任者。生成AI検索を入れたいが、権限事故(D-1〜4)とデータ外部送信(D-5)で止まっている人。流入: 検索(「社内ナレッジ検索 AI」)・技術記事
- Core message:
  - H1: 「見えてはいけないものは、AIにも見えない。」
    - proposition: この基盤では、利用者本人の権限で見えない文書はAIの検索・回答にも決して現れない。だから権限事故の心配なしにAI検索を全社に開放できる。
    - structure / exemplar: situation→consequence(条件→帰結)/ R-glean-40(「権限を考慮している場合にのみ企業で機能します」)、R-credal-42("Agents only see what they need")。語彙はD-2「見えてはいけない情報」
  - Sub: 「leisen(霊泉)は、社内に散在するドキュメント・チャット・コードを、本人の権限のまま横断検索できるOSSの社内ナレッジ検索基盤。自社環境で動き、データも検索ログも外に出ません。」
    - proposition: 対象はドキュメント/チャット/コードの横断検索。認可は本人権限のまま。OSSで自社環境デプロイ。データとログの所在は自社。→ SaaS審査・稟議の主要論点が最初から消えている。
  - Headline type / exemplar: situation→consequence型はセットの見出しでは少数派だが、逸脱2で許可(Line 4借用)。カテゴリ認識語(社内ナレッジ検索/横断検索)はsubが負担(R-onyx-2, R-qast-2 の「subが説明を全負担」型: 3/17)
- Argument logic: 権限の約束(H1)→ なぜ約束できるか(認可を複製せず委譲する仕組み)→ 守れている証明(監査・カナリア)→ それで何ができるか(横断検索・出典付き回答)→ 運用が回るか(1枚設定・可動部品最小)→ 費用(OSS+支援)→ ask(相談/GitHub)

## Option B — エンジニア評価直行
Summary: 評価を任されたプラットフォームエンジニアに「アーキテクチャが正しいこと」をコードと設計文書で示し、GitHubへ直行させる。

- Target: 導入可否の技術評価を任されたプラットフォームエンジニア/アーキテクト。流入: GitHub/技術記事/OSSリスト
- Core message:
  - H1: 「ACLは同期しない。検索は、本人のトークンで。」
    - proposition: この基盤は権限リストの複製・同期を実装せず、すべての検索をユーザー本人の資格情報でソースAPIに対して実行する。→ 権限の二重管理と同期漏れという故障モードが設計上存在しない。
    - structure / exemplar: operation→result(対句)/ R-credal-43("Context in. ... out.")、R-credal-40。否定形だがD-1〜4(権限事故が採用判断を左右する高頻度・高強度の不満)が示す通り、この痛みは購買理由の中心 — 逸脱2の範囲
  - Sub: 「leisen(霊泉)は MCP Gateway+コネクタ群で社内ナレッジを権限透過検索するOSS基盤。1デプロイ=1社。全ツール呼び出しが監査ログに残る。自社環境で今日評価できる。」

## Recommendation
**Option A を推奨。** 理由: (1) Ring Dの最頻・最強の不満(権限事故・データ外部送信)に正面回答する唯一の案で、反論マップの buyer-only ギャップ(検証可能性)を使えるのはこの製品の実差分だけ。(2) ブリーフの事業目標(採用の摩擦最小化+導入支援パイプライン)に対し、稟議者と評価者の両方に導線がある(相談+GitHub)。(3) C の便益(探す時間)は A の中でセクション6として保持されており、包含関係にある。B は A の下層ページ(/developers や README)として共存させるのが自然。
