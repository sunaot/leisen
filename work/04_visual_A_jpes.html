なぜ止まるのか

AI検索の事故は、AIが権限を破るから起きるのではない。

広すぎる権限が、AIで一気に表面化するから起きる。何年も前の共有リンク、継承されたままのフォルダ権限 — 普段は誰も辿り着かなかった文書が、自然文の検索で一気に見つかるようになる。だから選択肢は2つ: 全社の権限総点検が終わるまでAI導入を止めるか、見てよいかの判定を、毎回データソース自身に任せるか。

仕組み

権限のコピーは持たない。
見てよいかは、毎回ソースが本人に対して判定する。

leisenの検索は、すべて利用者本人の資格情報でソースのAPIに対して行われます。ACLの複製・同期・独自の権限モデルはありません。返ってくるのは、定義上その人が見てよいものだけです。

権限を複製・同期する検索認可を委譲する検索(leisen)
権限の判定者検索システム側のACLコピー元のデータソースが、毎回、本人に対して判定
同期漏れ・反映遅れ構造的に発生(棚卸しが前提)発生しない(コピーが存在しない)
異動・退職の反映同期ジョブ待ちソース側の権限変更が即座に効く
データの所在本文の中央コピーを保持自社環境のみ。インデックスも既定で作らない
監査・検証

「守れている」ことを、
監査ログとカナリア文書で検証し続ける。

全ツール呼び出しを記録します — 誰の権限で・どのソースに・何を問い合わせ・何が返ったか。さらにカナリア文書(特定のテストユーザーには絶対に見えてはいけない文書)を各ソースに常設し、検索にヒットしないことを監視し続けます。権限逸脱ゼロを「導入時の一度きり」ではなく、常時の検証にします。

できること

散らばったままの社内情報に、出典付きで答える。

集約も移行も要りません。LLMが複数ソースを本人権限で反復検索し、出典リンク付きで回答します。答えの根拠には、ワンクリックで原文に到達できます。

Google DriveSlackGitHubwiki(Confluence / Notion 等)+ コネクタSDKで追加

※ Slackは規約に従いオンデマンド検索のみ(本文やメタデータを保存・インデックス化しません)。

運用

導入1件=設定ファイル1枚。
同期パイプラインもインデックスも、最初から抱えない。

構成は deployment.yaml 1枚で決まります。インデックスは既定オフ — 監査ログが「このソースはネイティブ検索では解決しない」という証拠を出したときだけ、そのソースに限って有効化します。可動部品が少ないから、専任1〜2名で運用が回ります。

# deployment.yaml — 導入1件はこのファイル1枚
deployment:
  name: your-company
idp:
  adapter: keycloak        # okta / entra-id / …
connectors:
  - id: gdrive
    enabled: true
    privateScopes: excluded  # 既定で除外
    searchLayer: { enabled: false }  # 既定オフ
  - id: slack
    enabled: true
audit:
  failureMode: fail-closed

よくある質問

稟議・審査の前に、よく聞かれること

Slackのメッセージは保存されますか?
されません。Slackは毎回オンデマンドで検索し、本文もパーマリンク等のメタデータも永続化しません(API利用規約に準拠した設計です)。
導入に必要なものは?
自社の実行環境(オンプレ/自社クラウド)、IdP(Okta / Entra ID / Keycloak等)、各データソースの管理者設定です。導入1件の構成は deployment.yaml 1枚で表現されます。
Glean などの SaaS 製品との違いは?
大きく2点。(1) データ・インデックス・監査ログが自社環境から出ないこと。(2) OSSなので、権限の扱いを主張ではなくコードと設計文書で確認できることです。
セキュリティ審査に使える資料はありますか?
脅威モデル・監査ログ設計・認可方式の設計判断(ADR)を公開しています。審査のための追加ヒアリングは導入支援でお受けします。

営業資料の代わりに、設計文書を公開しています。

まずは設計から確認してください。導入の相談は、環境と対象ソースが分かる方とお願いします。
