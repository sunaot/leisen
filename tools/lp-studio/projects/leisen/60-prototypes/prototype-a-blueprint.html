社内ナレッジのAI検索基盤(OSS・自社環境で導入)

権限を複製しない。
AIは、本人に見える情報だけで答える。

leisen(霊泉)は、Google Drive・Slack・GitHub・wiki に散らばる社内ナレッジを、LLMが横断検索するための基盤です。社員はチャットとAPIから質問でき、検索はつねに質問者本人の権限で行われ、アクセスの可否は元のデータソースが判断します。オープンソースとして自社環境に導入でき、ナレッジのコピーを外部に蓄積しません。

権限リストの複製・同期なし すべての検索を監査ログに記録 自社環境で完結・他社と混ざりません

Problem / なぜ止まるのか

社内AIが審査で止まる理由は、モデルの性能ではなく「権限の複製」にある

社内データをAIにつなぐとき、多くの実装は、アクセス権限のリストをAI側のデータベースへ複製し、同期し続けようとします。この方式は構造的に壊れます。

故障モード 01

複製した瞬間から古い

権限は毎日変わります。異動、退職、共有設定の変更。コピーした権限リストは、変わり続ける現実に追いつけません。

故障モード 02

例外ほど翻訳を誤る

DM、プライベートチャンネル、限定共有のフォルダ。例外的な共有ほど権限の翻訳が難しく、「見えないはず」の内容が回答に混ざる事故が実際に報告されています。

故障モード 03

収集の権限が広すぎる

サービスアカウントの全権でデータを集めてインデックスを作ると、元の権限がインデックスに反映されない「ザルRAG」構成になりやすい——実装現場で繰り返し指摘されている難所です。

権限外の情報がAIの回答に混ざる。 情報システム部門が社内AIを止めるのは、この一点に説明が付かないからです。leisenはこの構造を、権限を「うまく複製する」ことではなく、複製そのものをやめることで断ちます。

Design Invariants / 設計原則

3つの不変条件として実装する

leisenでは、以下は機能ではなく不変条件——違反するコードを書かないことをリポジトリのルールとして明文化した制約です。

一

権限を複製しない

検索・取得は、質問者本人の資格情報で各データソースのAPIに問い合わせます。アクセス可否の最終判断は、つねに元のデータソースが本人に対して下します。leisenは独自の権限モデルを持ちません。

invariant #1 — 認可は常にデータソースに委譲する
二

すべての検索を記録する

全ツール呼び出しはGatewayの単一経路を通り、「誰の権限で・どのソースに・何を問い合わせ・何が返ったか」が監査ログに残ります。Gatewayを迂回するアクセス経路は作りません。

invariant #2 — 全ツール呼び出しを監査ログに記録する
三

データを抱え込まない

インデックスも同期パイプラインも持たずに始められます。ナレッジのコピーを蓄積しないので、漏れる場所も、鮮度が腐る場所も増えません。検索層が必要になったソースだけ、実測に基づいて後から有効化します。

invariant #3 — 可動部品は実測が必要性を示したときだけ追加する

How it works / 動作の流れ

質問から回答まで

質問する

社員がチャットまたはAPIで、自然言語のまま質問します。

本人の権限で検索する

LLMがソースの当たりをつけ、質問者本人の資格情報で検索します。ヒットが薄ければ、言い換え・英日変換・期間指定を変えて粘り強く再検索します。

原典を読んで組み立てる

有望な文書だけ本文を読み、そこに書かれた固有名詞やリンクを手がかりにさらに辿ります。

出典付きで答える

回答には必ず原典リンクが付き、ワンクリックで原文に到達できます。確信が持てないときは、その旨と探索した範囲を明示します——権限のないソースは検索されないため、「どこまで探したか」を正直に示すことが回答の一部です。

正直な注記: 回答には10〜60秒かかります。検索のたびに、本人の権限で各ソースへ問い合わせているためです。この待ち時間は「権限の複製を持たない」ことの対価であり、leisenはこれを隠しません。

Sources & Protocol / 対応ソース

散らばったまま、つなぐ

利用密度の高いソースから接続します。初期対象として設計しているのは:

Google Drive Slack GitHub wiki(Confluence・Notion 等) 社内システム(順次)

コネクタは1ソースにつき1つのMCP(Model Context Protocol)標準サーバーとして実装され、統一インターフェースで追加できます。MCP標準のため、コネクタ群は将来、別のLLM製品・エージェント製品からもそのまま利用できます。

Slackは公式APIの利用条件に従い、取得したデータを保存しないオンデマンド検索として扱います(本文もメタデータも蓄積しません)。

Alternatives / 代替との関係

「Copilot でよくない?」——よい場合と、そうでない場合

正直に言えば、社内の情報が Microsoft 365 や Notion など1つのスイートにほぼ収まっているなら、そのスイート内蔵のAIが最適です。leisenの出番はありません。leisenが解くのは、Drive にも Slack にも GitHub にも wiki にもナレッジがある——スイートの外側をまたぐときの権限問題です。

スイート内蔵AI
(M365 Copilot / Notion AI 等)		自前RAG構築leisen
対象範囲そのスイートの内側つないだ範囲すべて複数ソース横断(10〜30種を想定)
権限の扱いスイート内の権限を継承(外側には届かない)権限フィルタを自前で設計・実装・保守複製せず、本人の権限でソースに委譲
運用負担小(ベンダー任せ)大(インデックス同期・鮮度・精度改善に専任)インデックスなしで開始。専任1〜2名で回る設計
データの置き場所ベンダーのクラウド自社設計に依存自社環境。ナレッジのコピーを蓄積しない
すでにRAGを内製している/しようとしているチームへ: leisenは「作るな」とは言いません。内製で最もつらい権限連携・コネクタ・監査を標準実装として引き受け、あなたのチームが探索品質とデータ整備に集中できるようにする、という分担の提案です。

Rollout / 導入の進め方

小さく入れて、実測で広げる

PoCで止まる最大の理由は、次に進む判断材料がないことです。leisenは導入の各段階が、次の段階の証拠を生むように設計されています。

STEP 1

設定1枚で宣言する

コネクタ・IdP・監査・プライバシー方針(DM等は既定で対象外)を deployment.yaml 1枚で宣言。導入担当が触るのは原則このファイルとソース側の管理画面だけです。

STEP 2

インデックスなしで開始

検索層はOFFで始めます。同期パイプラインがないので、初期の可動部品とセキュリティ審査の対象が最小になります。

STEP 3

監査ログで広げる

「どのソースで、何度探しても解決しないか」を監査ログが実測します。その証拠に基づき、必要なソースだけ検索層を有効化します。

# deployment.yaml(抜粋・骨子) deployment: name: your-company idp: adapter: keycloak # okta / entra-id / keycloak connectors: - id: gdrive privateScopes: excluded # 私的領域は既定で対象外 searchLayer: { enabled: false } # 実測に基づき有効化 audit: failureMode: fail-closed # 監査に書けなければ実行しない

専任1〜2名で運用が回り続けることを設計目標としています。導入プレイブック(アセスメント→PoC→全社展開→検索層判定)を同梱予定です。

Current Status / 限界と現在地

いま、できないことも書いておきます

leisenは現在、設計を確定し実装前の検証ゲートを通過している段階です。誇張しないこともこのプロジェクトの設計原則です。

  • 稼働実績・導入事例はまだありません。このページに導入ロゴや削減率が並んでいないのはそのためです
  • 回答まで10〜60秒かかります(即答型のUXではありません)
  • 各ソースの初回利用時に、本人によるアカウント接続(OAuth同意)が必要です
  • 検索精度は各ソースのネイティブ検索とLLMの反復探索に依存します。文書が存在しない・整備されていない領域は魔法のようには解決しません
  • DM・プライベートチャンネルは既定で検索対象外です(方針は設定で明示的に変更)

この段階から、一緒に検証してくれる企業を探しています

数百〜数千人規模で、ナレッジが複数のツールに分散している企業のデザインパートナーを募集しています。設計レビューへの参加と引き換えに、導入支援を提供します。権限・監査の要件が厳しい組織ほど、検証相手として歓迎します。

FAQ

よくある質問

回答の生成にLLMを使うなら、結局データは外に出るのでは?

回答生成にはクラウドのLLM API(Claude API 等)を利用します。LLMに送られるのは「質問者本人が閲覧権限を持つ検索結果」のみで、leisen自体はナレッジのコピーを保存・蓄積しません。モデル学習への利用有無は各LLMベンダーとの契約条件に従います。完全に閉じた環境が必要な場合の構成はご相談ください。

ライセンスと料金は?

OSSとして無償公開する予定です(ライセンスは Apache-2.0 を軸に最終決定中。確定次第ここに明記します)。開発元はSaaS運営を行わず、導入アセスメント・初期導入支援・運用サポートを事業とします。「OSSなのに相談CTAがある」のはこの事業構造のためです。

既存のSSO(IdP)と接続できますか?

Okta / Microsoft Entra ID / Keycloak を IdP Adapter として接続する設計です。各データソースへの接続は、ソースごとに本人のOAuth同意を経て、トークンは暗号化保管・失効管理されます(退職・異動時はIdPの無効化イベントに連動して失効させる設計)。

DMや個人的なファイルまで検索されてしまいませんか?

DM・プライベートチャンネルなどの私的領域は既定で検索対象外です。対象範囲の方針は deployment.yaml に明示的に記述し、監査ログの閲覧権限・保持期間とあわせて、導入時に労務・法務と合意して規程化することを標準の導入手順に含めています。

権限逸脱が絶対に起きないと保証できますか?

「絶対」は主張しません。leisenが約束するのは構造です: 権限の複製を持たないため、複製の陳腐化による漏洩経路が存在しません。加えて、特定ユーザーに見えてはならないカナリア文書を常設して非出現を継続検証する仕組みと、四半期のレッドチームテストを導入手順に組み込む設計です。
