# 検索の仕様の伝え方の比較(役割で分ける `split`): haiku、esa 型と Redmine 型(AND)、各 3 回(2026-11-26)

T-027 の `dev-search-eval` による計測。前回の計測(`docs/eval/2026-11-26-search-eval-spec-delivery-haiku.md`)の 3 通りの伝え方(`summary` / `both` / `profile`)に、4 つ目の伝え方 `split` を足して比べた。`split` は検索の仕様を役割で分ける: 検索プロファイルの項目で表せる仕様は検索プロファイルだけで伝え、`summary` には内容の説明と、検索プロファイルの項目で表せない補足だけを書く。ADR-025 の確認事項 9(`summary` から検索の仕様の記述を消すか)と T-030 の受け入れ条件の材料にする。

## 解釈

- esa 型の `split` は recall@1 で `summary` より高かったが、回ごとの範囲が重なり、同じ条件の `summary` が前回と今回で 3 ポイント動いている。改善と言い切れる差ではない。recall@5 と引用では差がない
- `split` では、前回の `profile` で減った `OR` の使用が一部戻った(12 回 → 23 回)。`split` の `summary` の補足に OR の結び付きの規則と例を戻したことと合う。ただし、自由文をすべて渡す `summary`(32〜33 回)と同じ水準までは戻っていない。OR の使用回数と recall の関係は確かめていない
- 検索プロファイルと重複する記述を `summary` から除いても(`split`)、自由文だけの場合(`summary`)より悪くなったという結果は、どちらの方式でも出なかった。前回の `profile`(補足も消した場合)と比べると、esa 型では recall@1 が高く、Redmine 型では同程度だった
- Redmine 型の補足(語の数え方・1 文字の語・フィルタ非対応)は、効く場面(6 語以上のクエリ、1 文字の語、フィルタの指定)がほとんど出なかったため、効果を測れていない

## ADR-025 の確認事項 9(`summary` から検索の仕様の記述を消すか)について

この結果から言えること:
- haiku・模擬の esa 型と Redmine 型・合成コーパスでは、検索プロファイルで表せる記述を `summary` から消し、表せない補足だけを残した場合(`split`)、recall と引用の割合は自由文だけの場合(`summary`)と同じ程度だった(esa 型の recall@1 は高かったが、ばらつきの範囲内)。悪くなったという結果はない
- 補足も含めてすべて消した場合(前回の `profile`)に esa 型で減った `OR` の使用は、補足を残すと一部戻った。消すのであれば、検索プロファイルの項目で表せない情報(esa 型の OR の結び付きの規則と例など)は `summary` に残す方が、探索 LLM に届く情報の欠けが少ない
- 検索プロファイルの制御メッセージを渡すときは、0 件の制御メッセージとソース一覧の前置きの読み直す先を、その制御メッセージと `summary` の補足に変えた。この変更を含めて `split` で悪くなった指標はなかった(変更だけの効果は分けて測っていない)

この結果から言えないこと:
- 消すべきか残すべきかの結論。差はばらつきと同じ程度で、1 つのモデル・模擬の方式・合成コーパスでの結果である
- 実ソースのコネクタ(connector-esa・connector-github・connector-redmine)の `summary` を同じように分けた場合の結果。実ソースの検索プロファイルは根拠が `documented` の項目が中心で、「実機では未確認」の句が付く。補足に何を残すかもコネクタごとに決める必要がある
- 他のモデル(sonnet、Anthropic API のネイティブのツール呼び出し、LM Studio の手元のモデル)での結果
- GitHub 型の補足の効果(今回は流していない)
- 語数の上限・通知・空白のない文の判定の効果(この計測でも出なかった)
- 0 件の制御メッセージと前置きの文言の変更だけの効果(`split` と同時に変えたため分けられない)

## 集計の問題(前回の指摘。直していない)

`claude -p` の応答が読めずに回答が `outcome: error` で終わった試行は、表の「エラー」(`case_error` の数)に数えられず、答えられない質問では「棄権」にも数えられる。今回の該当: esa 型 `summary` 5 件(`md-telework-vpn` 1・2 回目、`ki-eng-checklist` 2 回目、`md-new-member-setup` 3 回目、`un-book-subsidy` 3 回目)、esa 型 `split` 2 件(`ki-vpn-timeout` 1 回目、`ki-retry-policy` 3 回目)、Redmine 型 `summary` 1 件(`ki-inc-0412` 3 回目)、Redmine 型 `split` 3 件(`un-gym` 1 回目、`md-leave-handover` 2 回目、`ki-carryout-rule` 3 回目)。このうち答えられない質問で「棄権」に数えられたのは 2 件(esa 型 `summary` の `un-book-subsidy`、Redmine 型 `split` の `un-gym`)。正解のある質問の `outcome: error` の試行が recall@k・引用の割合にどう数えられるかは、この文書では確かめていない。

## 限界

- 1 つのモデル(haiku)、`claude -p` の構造化出力によるツール呼び出しの模擬での結果である。Anthropic API のネイティブのツール呼び出しとは挙動が違いうる
- 検索方式は開発用コネクタの模擬で、検索プロファイルは模擬の実装と一致する値(`tested`)である。補足も模擬の実装に合わせて書いたもので、実ソースの挙動とは限らない
- 前回の `both` / `profile` は別の時刻・別のコード(`7860c93`。`operator_ignored` の条件が広い)で流したもので、今回の `split` との比較は同時刻の比較ではない。同じ条件の `summary` が前回と今回で最大 7 ポイント動いた
- 合成コーパス(425 件)と 23 問。複数文書の質問は 7 問で、1〜2 問の違いが割合を大きく動かす
- 各組 3 回。回ごとの幅が平均の差と同じ程度で、回数を増やさないと差の有無を判断できない
- 条件 3 だけ。条件 4(UI 側 LLM を通す)は流していない
- 回答の内容の正しさは採点していない。測ったのは、正解文書が検索で返ったか、fetch したか、引用したかである
- 語数の上限と通知(`terms_dropped`)、修正後の `operator_ignored` が効く場面が出なかったため、その効果は測れていない
