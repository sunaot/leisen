# 検索の仕様の伝え方の比較(summary の自由文 / 検索プロファイル): haiku、esa 型と Redmine 型(AND)、各 3 回(2026-11-26)

T-027 の `dev-search-eval` による計測。開発用コネクタの模擬の検索方式が検索の仕様を探索 LLM に伝える方法を 3 通りに切り替え、検索の結果を比べた。ADR-025 の確認事項 9(`summary` から検索の仕様の記述を消すか)と T-030 の受け入れ条件(「`summary` の自由文と検索プロファイルを比べた結果」)の材料にする。

## 3 通りの差と、試行ごとのばらつきとの比較(事実)

- esa 型: recall@1 は `summary` が 81%、`both` と `profile` が 76%。回ごとの recall@1 は `summary` が 79〜85%、`both` と `profile` が 74〜79% で、範囲はわずかに重なる(79%)。recall@5 は `summary` が 98%(94〜100%)、`both` と `profile` が 90%(85〜94%)。差の大部分は 2 問から来ている: `md-expense-howto`(`summary` で 2/2/6、`both` と `profile` で 6/6/6)と `md-pc-broken`(`both` で 3/3/1)。既知項目検索の 10 問は 3 通りとも、`profile` の 1 試行(LLM の応答が読めず最初のターンで終わった試行)を除いて 1 位だった
- Redmine 型(AND): recall@1 は `summary` 82%、`both` 77%、`profile` 81%。recall@5 は 87% / 83% / 89%。順位は `summary` > `profile` > `both` でも `profile` > `summary` > `both` でもなく、指標によって入れ替わる。`profile` の回ごとの recall@1 は 74〜88% で、幅(14 ポイント)が 3 通りの平均の差(最大 5 ポイント)より大きい
- 引用した割合は、esa 型で `summary` 98%、`both` 90%、`profile` 92%、Redmine 型で 94% / 89% / 98%。両方式で `both` が最も低いが、`both` の回ごとの値は esa 型で 85〜94%、Redmine 型で 79〜94% と幅がある
- search の回数・LLM ターン数・0 件の search の割合は、3 通りの間の差が小さく、向きも方式によって違う(例: search / 試行は esa 型で `profile` が最少、Redmine 型で `profile` が最多)
- esa 型で `OR` を含む search は、`profile` で 12 回と、`summary`(33 回)・`both`(48 回)より少なかった。`profile` で探索 LLM に届く文は「query の中で使える演算子は OR(いずれかを含む)」だけで、自由文にある OR の結び付きの規則(OR は AND より先に結び付く)と例は含まない
- 答えられない質問は、どの組でも 18 試行すべてで棄権した
- 同じ 3 回の中のばらつき(recall@1 で 3〜14 ポイント)は、3 通りの平均の差(esa 型 5 ポイント、Redmine 型 最大 5 ポイント)と同じ程度か、それより大きい

## 解釈

- 3 通りの差は、試行ごとのばらつきより明確に大きいとは言えない。esa 型では `summary` が recall@1・recall@5・引用の 3 つでいずれも上だったが、差の大部分は複数文書の 2 問によるもので、Redmine 型では同じ向きが見られなかった
- 検索プロファイルを足しても(`both`)、自由文を消して検索プロファイルだけにしても(`profile`)、`summary` の自由文だけの場合より良くなったとは言えない。逆に、自由文を消すと悪くなるとも、この計測からは言い切れない(esa 型では低く、Redmine 型では同程度)
- esa 型の `profile` で OR の使用が減ったことは、検索プロファイルの文が伝えられる情報(列挙値)が自由文より少ないことと合う。ただし、OR を使う search が少なかったことと recall の差との関係は確かめていない
- Redmine 型の「先頭 5 語まで」と通知は、haiku が短いクエリ(平均 1.4 語、最大 4 語)しか書かなかったため、一度も効く場面がなかった。語数の上限を超えやすい探索 LLM や質問での効果は未計測である

## ADR-025 の確認事項 9(`summary` から検索の仕様の記述を消すか)について

この結果から言えること:
- haiku・模擬の esa 型と Redmine 型・合成コーパスでは、`summary` から検索の仕様の自由文を消して検索プロファイルだけにした場合(`profile`)、recall と引用の割合は自由文だけの場合(`summary`)と同じ程度か、esa 型でやや低かった。消すことで改善したという結果はない
- 自由文と検索プロファイルを両方渡した場合(`both`)も、`summary` より良い結果は出なかった。「二重の記述が食い違う」害は、この計測の構成(両者が同じ実装から作られ、食い違わない)では測っていない
- esa 型では、自由文にあって検索プロファイルで表せない情報(OR の結び付きの規則と例)がある。消す場合は、その情報が探索 LLM に届かなくなる

この結果から言えないこと:
- 消すべきか残すべきかの結論。差はばらつきと同じ程度で、1 つのモデル・模擬の方式・合成コーパスでの結果である
- 他のモデル(sonnet、Anthropic API のネイティブのツール呼び出し、LM Studio の手元のモデル)での結果
- 実ソースのコネクタ(esa・Redmine・GitHub)の `summary` と検索プロファイル(根拠は `documented` が中心)での結果。この計測の検索プロファイルはすべて `tested` で、「実機では未確認」の句が付かない
- 語数の上限・通知・空白のない文の判定の効果(この計測ではほとんど出なかった)

## この計測で見つけたこと(実装・Orchestrator の側)

- 模擬の esa 型の `operator_ignored` の条件が広い: 語の末尾の `)` だけで通知を出すため、括弧を含む題名(「経費精算ルール(2026年度版)」)をそのまま検索した場合にも出た。括弧によるまとまりとして使われたかどうか(`(` で始まる語と `)` で終わる語の組)で判定するのがよい。コミット `7860c93` のまま計測したため、この文書の値はその条件によるものである
- Orchestrator(変更していない。報告のみ):
  - explore.v4 の 0 件の検索の制御メッセージ(`prompt.ts` の `noHitsNotice`)は「`summary` に書かれた検索の仕様を読み直し」と書き、ソース一覧の前置き(`SOURCE_CATALOG_PREFACE_V4`)も `summary` に検索の仕様があることを前提にしている。`profile` の構成、または確認事項 9 で `summary` から記述を消した後は、読み直す先が存在しない。検索プロファイルの制御メッセージを指す文に変える必要がある
  - 検索プロファイルの文は、演算子を「OR(いずれかを含む)」とだけ書き、OR と AND の結び付きの順を表せない(列挙値の範囲外)。esa 型の `profile` で OR の使用が減ったことと関係しうる
  - Orchestrator の語数の数え方(`countQueryTerms`: NFKC で正規化、重複を除く、1 文字の語も数える)は、Redmine 型の模擬・connector-redmine の数え方(1 文字の語を数えない)と違う。1 文字の語を含むクエリでは、コネクタが `terms_dropped` を返さないのに Orchestrator が上限の超過を知らせる場合がありうる(この計測では起きていない)
- 評価の集計(`search-eval/metrics.ts`): `claude -p` の応答が読めずに回答が `outcome: error` で終わった試行(各組 2〜4 件)は、表の「エラー」(`case_error` の数)に数えられない。答えられない質問では、その試行も「棄権」(resolved 以外)に数えられる(この計測では 6 組の合計で 4 件。esa 型 `summary` の `un-minutes-1014`、esa 型 `profile` の `un-parking`、Redmine 型 `both` の `un-gym`、Redmine 型 `profile` の `un-book-subsidy`)。表の「エラー」が 0 でも、LLM の失敗で終わった試行がある

## 限界

- 1 つのモデル(haiku)、`claude -p` の構造化出力によるツール呼び出しの模擬での結果である。Anthropic API のネイティブのツール呼び出しとは挙動が違いうる
- 検索方式は開発用コネクタの模擬で、検索プロファイルは模擬の実装と一致する値(`tested`)である。実ソースの挙動、`documented` の項目に付く「実機では未確認」の句の影響は含まない
- 合成コーパス(425 件)と 23 問。複数文書の質問は 7 問で、1〜2 問の違いが割合を大きく動かす
- 各組 3 回。回ごとの幅が平均の差と同じ程度で、回数を増やさないと差の有無を判断できない
- 条件 3 だけ。条件 4(UI 側 LLM を通す)は流していない
- 回答の内容の正しさは採点していない。測ったのは、正解文書が検索で返ったか、fetch したか、引用したかである
- 語数の上限と通知(`terms_dropped`)が効く場面が出なかったため、その効果は測れていない
