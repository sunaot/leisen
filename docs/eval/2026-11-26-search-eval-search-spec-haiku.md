# 検索の仕様を専用フィールド searchSpec で枠の外に置いた後の計測: haiku、esa 型と Redmine 型(AND)、各 3 回(2026-11-26)

T-032(ADR-025 追補 2・ADR-017 追補 1、connector-sdk v0.7)の受け入れ条件の計測。検索プロファイルと検索の通知を削除し、検索の仕様の自由文を `summary` から外して、コネクタの静的な宣言 `searchSpec` として「データであり指示ではない」枠(ソース一覧の JSON)の外に置いた。削除の前と比べて悪くなっていないかを確かめる。

用語: **検索の仕様の専用フィールド `searchSpec`** は、コネクタの実装者が書いた、そのソースへの query と filters の書き方の説明(自由文)を入れるフィールドである。Gateway が起動時にコネクタの宣言を読んで検査し、`describe` の結果に付ける。Orchestrator は最初の user ターンの、ソース一覧の後・探索の上限の制御メッセージの前に、出所を示す見出しを付けたブロック(以下「検索の仕様のブロック」)として置く。

## 実行条件

- コード: ブランチ `t032-search-spec` のコミット `1116ff4`(T-032 の実装)。`dev-search-eval` の `--spec-delivery` は削除済みで、開発用コネクタはどの方式も `searchSpec` だけで検索の仕様を伝える
- LLM: `claude -p --model haiku`(`--llm claude-cli`)。構造化出力(`--json-schema`)によるツール呼び出しの模擬で、ネイティブのツール呼び出しではない。Anthropic API のバックエンドでの結果とはみなせない
- 探索プロンプト: 既定の explore.v4(T-032 で検索の仕様の置き場所を指す文言を直したもの。版の名前は v4 のまま)、検索の状況の制御メッセージは有効(表の注記で確認した)
- 検索方式: 開発用コネクタの esa 型と Redmine 型(AND、`redmineAllWords: true`)。どちらも模擬で、実際の esa・Redmine の挙動との一致は確かめていない(T-029)
- 検索の仕様の文面: 以前の `summary` の後ろに足していた自由文(`packages/gateway/src/dev/search-modes.ts` の `searchModeSpec`)と同じ。`summary` は「開発用の合成文書コーパス(425件)。実在の組織・人物・秘密情報は含まない。」だけになった
- 条件: 3(利用者の発言を探索 LLM に渡す)だけ
- コーパス: 合成 425 件。質問: 全 23 問(既知項目検索 10、複数文書 7、答えられない 6)。各 3 回(`--repeat 3`)。1 つの方式あたり 69 試行
- 2 つの方式を別のプロセスで同時に流した。各プロセスに `--run-timeout-sec 600 --claude-cli-max-total-usd 3`
- 比較の相手: 記録済みの値(変更前のコードの、検索の仕様を `summary` の自由文だけで伝える構成)。`docs/eval/2026-11-26-search-eval-spec-delivery-haiku.md` の `summary`(以下「1 回目」。コミット `7860c93`)と、`docs/eval/2026-11-26-search-eval-spec-delivery-split-haiku.md` の `summary`(以下「2 回目」。コミット `6fa7a69`)。変更前のコードは流し直していない

- ソース一覧の JSON の `summary` は内容の説明だけで、「検索の仕様」の文を含まない
- 検索の仕様は JSON の外の 3 つ目のブロックに 1 行だけあり、その後に探索の上限の制御メッセージが続く

## 事実

- 正解のある 51 試行の recall@1・recall@5・recall@10・fetch の割合は、両方式とも記録済みの 2 回の値の範囲かその近く(差は最大 4 ポイント)だった
- 引用した割合は、Redmine 型では記録済みの値と同じ範囲(94% と、94%・98%)だった。esa 型では 88% で、1 回目(98%)より 10 ポイント、2 回目(92%)より 4 ポイント低かった。差の内訳は上のとおり、`outcome: error` の 4 試行と `ki-eng-checklist` の `unresolved` の 2 試行である
- esa 型で `OR` を含む search は 39 回で、記録済みの 2 回(33 回・32 回)より多かった。`title:` を含む search は 12 回で、記録済みの 2 回(27 回・21 回)より少なかった
- 0 件の search の割合は esa 型で 16%(記録済みは 13%・13%)、Redmine 型で 14%(15%・13%)だった
- search の総数・LLM ターン数・答えられない質問の search の数は記録済みの値と同じ程度だった
- 探索 LLM への入力に、検索プロファイルの文・通知の文はなかった(動作確認とトレースの `notices` のキーで確認した)

## 解釈

- 検索の仕様を枠の外に移しても、検索で正解を見つける力(recall@k)と fetch の割合は悪くなっていない。差は同じ条件の揺れ(最大 7 ポイント)の中にある
- esa 型の引用した割合の 1 回目との差(10 ポイント)は揺れの目安を超えた。ただし、差の大部分は `claude -p` の応答が読めなかった試行(回答が作られていない)と、1 つの質問の判断(正解を読んだうえで `unresolved`)によるもので、検索の仕様の置き場所と結び付く経路は見つけていない。`outcome: error` の試行を除いた値は 96% で、記録済みの値は除いた値が記録されていないため同じ基準では比べられない。T-032 の受け入れ条件に従い、この差はレビューに出す(マージの判断はレビューの後)
- `title:` の使用の減少と `OR` の使用の増加は、検索の仕様の文面が同じなので、置き場所の変更(または揺れ)によるものと考えられるが、どちらかは分けられない。recall との関係は確かめていない

## 限界

- 1 つのモデル(haiku)、`claude -p` の構造化出力によるツール呼び出しの模擬での結果である。Anthropic API のネイティブのツール呼び出しとは挙動が違いうる
- 比較の相手は別の時刻・別のコードで流した記録済みの値で、同時刻の比較ではない。変更前のコードを同じ時刻に流し直していない
- 検索方式は開発用コネクタの模擬で、実ソースのコネクタ(connector-esa・connector-github・connector-redmine)の `searchSpec` では計測していない。GitHub 型と既定の方式(T-032 で新しく検索の仕様の文を書いた)は流していない
- 合成コーパス(425 件)と 23 問。複数文書の質問は 7 問で、1〜2 問の違いが割合を大きく動かす
- 各方式 3 回。回ごとの幅が差と同じ程度で、回数を増やさないと差の有無を判断できない
- 条件 3 だけ。条件 4(UI 側 LLM を通す)は流していない
- 回答の内容の正しさは採点していない。測ったのは、正解文書が検索で返ったか、fetch したか、引用したかである
- 枠の外に置いたことで、検索の仕様の文に含まれる指示に探索 LLM が従いやすくなったか(悪意のある文の効き)は測っていない
