## 3. 見えた問題

1. **検索語の盛りすぎ。** incident-contact の回答本文が示す検索語は「システム障害 連絡先 インシデント」「障害 連絡 エスカレーション」。検索が語の AND のため、文書にない語(「連絡先」「インシデント」「エスカレーション」)が1つでも入ると 0 件になる。「障害」1 語なら該当文書(タイトル「システム障害発生時の連絡フロー」)に当たっていた。モデルは言い換えを 1 つの query に並べれば候補が広がる(OR)と扱っている。expense-deadline の 2 回の 0 件も同じ原因と推定する(原文は「翌月10日までに申請する」で「締め日」を含まない。監査は検索語をハッシュでしか残さないため推定)
2. **list の誤読。** incident-contact で区画を指定した list を 4 回呼び、空の結果を「区画に文書がない」と解釈して上限に達した。list は区画だけを返す仕様だが、ツールの説明文(「区画を列挙する」「区画を辿るのに使う」)からは読み取れなかった
3. 初回ターンの遅さ(expense-deadline で describe から最初の search まで 22 秒)はプロンプト全体の読み込みと推定。2 問目以降の初回ターンは 7〜13 秒

## 4. v3 の変更

- 探索方針: 最初は質問の主題を表す名詞 1〜2 語で検索し、質問文や質問側の言い回しを入れない。多くのソースは語の AND なので言い換えの候補を 1 つの query に並べない。0 件ならまず語を減らして 1 語にし、言い換え・英日変換は別の search で試す
- list は区画だけを返し文書は返さない。区画内の文書は search の `filters.container` で探す。list の空の結果は文書がないことを意味しない
- 見つからなかったことを「存在しない」と断定しない
- 同じ趣旨をツールの説明文にも入れた(Orchestrator の USAGE_HINTS、Gateway の list の説明。入出力のスキーマは変えていない)

## 6. 限界

- v3 は同じ 4 問の結果を見て作ったため、この 4 問への合わせ込みを否定できない。v3 を作る前に見ていない質問(コーパスの残り 4 文書、表記ゆれ・英語の質問、複数文書にまたがる質問)を質問セットに足して測るのが次の確認(T-022)
- 合成コーパス 7 文書・4 問・1 モデル・各 1 回。ぶれ(`--repeat`)は未計測で、解決率の推定には使えない
- 開発用コネクタの検索は実ソースより単純(AND の部分一致のみ)。v3 の「名詞 1〜2 語」の効きは実ソース(GitHub の検索も語の AND)で改めて測る
- Claude API では未計測。プロンプトはモデル系統ごとに効きが変わりうる(ADR-017)
