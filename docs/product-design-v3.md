# 社内ナレッジ検索基盤 製品企画・設計書 v3

## 実装前レビュー(2026-07-05)の反映差分

本書は v1(`product-design.md`)・v2(`product-design-v2.md`)への差分である。2つの独立した設計レビューの統合・相互検証と外部事実の裏取りに基づき、コード実装開始前に確定すべき変更を定義する。変更のない箇所は v1/v2 を正とする。各項目の詳細は対応するADRを正とする。

---

## 1. 認可方式の再設計(ADR-010)

v1 §3.2 の「IdP起点のToken Exchange(RFC 8693)を基本方式、個別OAuthをフォールバック」は前提から見直す。Phase 1 の主要対象である Google Drive / Slack について、外部IdPトークンを各SaaSの本人アクセストークンへ交換する、公式に前提化できる汎用経路は確認できない(Google Workspace API は個別OAuth同意またはドメインワイド委任のみ。Slack user token は本人のOAuth承認フローのみ)。Microsoft Graph系では Entra ID on-behalf-of が有力だが、汎用基盤としては**ソース別 Auth Adapter を前提**とし、token exchange が成立するソースを例外として扱う。

帰結:

- **Token Vault を中核コンポーネントに昇格**する。個別OAuthリフレッシュトークンの暗号化保管(KMS連携)・ローテーション・失効を担い、IdPのdeprovisioningイベント(SCIM等)を受けて各SaaSトークンをrevokeする
- **初回同意UXを製品要件化**する(T-007/T-009)。未接続ソースの検索スキップと接続促しの導線。KPI「週次アクティブ30%」はこの摩擦と衝突するため、採用率はゲートではなく目標(target)として扱う(→ §8)
- ドメインワイド委任は「認可判定は本人に対して行われるが、資格情報はサービスアカウント資格情報」であり、不変条件1を「認可判定の主体」と「資格情報の形態」に分解して扱う。採用可否はソースごとにADRで明示する
- **T-000a(認可実現性マトリクス)を最初のタスク**とし、その成果でADR-010をAcceptedに更新する
- T-002のKeycloak E2Eは本丸(Drive/Slack)の認可経路を検証しない。CIの緑が与える過信を防ぐため、この限界をタスクとREADMEに明記する

## 2. 監査データモデルの2層化(ADR-011)

v1 §4.4 のツール呼び出し単位1層では「何回再検索しても未解決」を集計できない。**AnswerRun(会話/回答単位)と ToolInvocation(ツール呼び出し単位)の2層**に再設計する。呼び出し主体(人間チャット/自律エージェントのon-behalf-ofチェーン)を記録する。

重要な制約: **post-filtering前の候補件数を通常の監査ログに入れない**。返却0件に対して候補件数が残ると「その語にマッチする未認可文書が存在する」ことを漏らす(existence leak)。post-filter品質の可視化が必要な場合は、query/userId/docIdと結合できないバケット化・短期保持・高権限限定の分離テレメトリのみを許す。

rawQueryはqueryDigestで結合できる短期保持の別テーブルに置き、昇格判定レポート(T-014)が原文参照に使う(ダイジェストは人間が読めないため)。

## 3. 未認可候補の境界不変条件(ADR-012)

post-filteringの「返却前」の境界を確定する。未認可候補は Search Backend Adapter の内部にのみ存在し、Connector / Gateway / Orchestrator / LLM / 監査ログ / デバッグログ / メトリクスのいずれにも出さない(件数を含む)。候補取得→認可照会→K拡張はアダプタ内で完結させる。CLAUDE.md の不変条件に昇格済み。

## 4. プライバシー・保持・ログ閲覧方針(ADR-013、人間の決定待ち)

本人権限検索はDM・プライベートチャンネルを含み、認可上は正当だが、fetchedDocIds等のメタデータが中央監査ログに載る。就業規則・労使協議・個人情報保護の論点であり、次を**T-010(deployment.yaml)とT-001(監査スキーマ)より先に**決定する: (1) プライベートスコープの既定除外(deployment.yamlの `privateScopes: excluded | consent | included`、既定 excluded)、(2) プライベートスコープdocIdのログ上の扱い、(3) 監査ログの閲覧権限・目的・保持期間の規程化、(4) **チャット履歴の扱い**(回答への機密転写は権限剥奪に遡及しない。保持期間・エクスポート・共有禁止をT-009要件に追加)。

## 5. Slackの取り扱い(ADR-014)

外部事実(2026-02-17のSlack公式MCPサーバー/RTS API正式リリース、RTSドキュメントの「取得データの保存・コピー禁止・学習利用禁止」、API ToSの「第三者アプリによる他組織データの永続コピー・アーカイブ・インデックス作成禁止」)により、v1 §5.1 の「Slackは昇格の典型例」は成立しない。

- Slackは**オンデマンド検索ソース**として扱い、中央インデックス化(Phase 2 ingest)は契約・利用条件・導入形態を確認できた場合のみ検討する
- 保存禁止はingestに限らない。RTS経由で取得した本文・スニペットを監査ログ・評価ログ・キャッシュ・Source Catalog/マップ生成に永続化しない(不変条件7)
- T-006は**公式Slack MCPサーバー/RTS APIを第一候補**として評価する(ADR-001の「公式サーバーが認可要件を満たせば採用」の初の実例候補)
- **導入形態は要確認事項**: customer-owned internal app / vendor-managed single-tenant / Marketplace app の3類型のAPI Terms適合性を法務/Slackに確認する(人間タスク、v2 §7に追加)。ToSはCommercial Distributionの制約がテンプレート化されたcustom appにも適用されると明記し、適用除外は単一の第三者専用アプリのみ

## 6. 自律エージェントの権限委譲ポリシー(ADR-015)

v1 §4.1「呼び出し元エージェントの実行主体となる人間のトークンを引き回す」には監査(§2)に加えて同意モデルが必要。delegated agent execution policy として **human-in-the-loop / scheduled / autonomous** の区分、許可ソース、スコープ、TTL、再承認、監査上の表示を定義する。Phase 1では human-in-the-loop のみ許可し、他区分は既定拒否とする。

## 7. Source Catalog / 全社公開マップ(Phase 1.5、T-018)

v1 §4.3 の「describeを常時コンテキスト保持」は10〜30ソースでスケールしない。文書本文の要約ではない薄い Source Catalog(語彙・代表コンテナ・「何がありそうか」。本人権限フィルタ版と全社公開版を分離)を Phase 1.5 として追加する。全員可視情報のみで構成する全社公開マップは権限区画問題が存在せず(入力が全員可視なら要約漏洩が構造的に起きない)、Phase 3 パイプラインの低リスク検証を兼ねる。

## 8. 計画・タスク構成の差分

- **実装前ゲート**: T-000a(認可実現性マトリクス)、T-000b(プライバシー方針)、T-000c(脅威モデル)を最優先タスクとして追加。完了までT-003以降に着手しない
- **順序変更**: T-010(Deployment Profile)をT-003より前に。T-003は最初からdeployment.yamlの最小サブセットで書く(sources.yamlは廃止)
- **統合**: T-011(IdP Adapter)をT-002に統合。最初からIdpAdapter IFとして作る
- **前倒し**: T-017(delegated_identity認可スパイク)をQ2に新設。検索層の第一顧客(ファイル共有)の認可方式(KCD/RBCD)成立可否を早期確定する。文書検索モジュール本体はQ3を維持
- **追加コネクタタスク**: T-019(GitHub)、T-020(wiki)。v1ロードマップQ2「4〜6本」との不一致解消
- **KPIゲートの再構成**: 週次アクティブ30%は展開施策に左右される採用指標のためPhase移行ゲートから外し、目標として残す。ゲートには「利用があった範囲での解決率」「未解決の原因分布が取れていること」を残す
- **カナリア文書**: 特定テストユーザーに絶対に見えてはいけない文書を各ソースに常設し、ヒット非出現を継続検証する(T-013のセキュリティスイート、導入プレイブック標準工程)。権限逸脱検出を四半期イベントから常時監視に変える
- **Phase 3権限区画の再定義**: 「区画メンバー全員がアクセス可能な文書集合」の算出はACL評価の複製であり原則1と矛盾する。入力を「区画のIdPグループに明示的に共有されたコンテナ」に限定し、運用はオーナー承認制のCurated Mapから始める(Phase 3着手時にADR化)
- **MCP再利用の期待値**: 既存MCPサーバーは再利用候補として評価するが、Gatewayの監査・認可・Token Vault・未認可候補境界・deployment.yamlと整合しない場合はラップまたは自前実装を前提に見積もる(ADR-001追補)
- **人間の意思決定項目の追加**(v2 §7): Slack導入形態の法務確認、ADR-013のプライバシー方針、v2体制表の改訂とOSS公開時期の再検討(OSS化はrelease engineeringという追加製品であり、v1 §7.3の体制表が未改訂。Q2公開とQ3公開+Q2非公開パートナー提供の比較検討)、Buy比較表(Glean / M365 Copilot / Gemini Enterprise)とv2ターゲット顧客定義のday-0作成
- **ADR-009は欠番**とする(削除済み番号の再利用を避ける)

## 9. 工数の目安

ドキュメント整合と本差分の反映は完了済み(本コミット)。T-000a/b/cとADR-010/013の確定は、調査と関係者(情報セキュリティ・法務・労務)レビュー込みで1〜3週間程度を見込む。全体では2週間前後、レビュー往復を含め3〜4週間を計画値とし、「数日で終わる」前提で計画しない。
