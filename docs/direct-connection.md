# 直接接続との関係と leisen の位置づけ

Status: 分析メモ(設計判断ではない。決定事項は ADR を正とする)/ Date: 2026-10-09

エージェント(Claude・ChatGPT・Claude Code 等)から Slack / GitHub / Google Drive / Notion などへ
公式の MCP サーバーやコネクタで直接つなぐ場合(以下「直接接続」)と、leisen を経由する場合の違いを整理する。
「本人の資格情報で検索する」ことが leisen の前提であるため、直接接続でも同じことができてしまうのではないか、
という問いに答えるのが目的である。

## 結論

- **leisen を迂回しても権限は越えられない。** 直接接続も leisen も本人の権限で動く。迂回で失われるのは
  権限ではなく統制(文脈付きの監査、プライベートスコープの除外、Slack データの非永続化、LLM の送り先の選択、
  一括失効)である
- **leisen への同意は直接接続の許可にならない。** 同意は OAuth アプリ(クライアント)単位で行う。導入先が
  自社で登録した leisen のアプリだけを承認し、他のアプリをソース側の管理機能で止める構成は、主要なソースで取れる
- **経路を leisen 一本に完全に絞ることはできない。** 残る経路は、意図的な回避(規程と事後の検知で扱う)と、
  善意で日常的に使われる経路(技術で塞ぐ)に分けて扱う
- **leisen は万能の情報漏洩対策ではない。** 本人がアクセスできるデータを本人が意図的に持ち出すことは、
  元のソースでもできるので防げない。leisen が抑えるのは、意図しないデータ共有と、エージェントで増幅された
  横断的な取得であり、その統制を強めることにある。カジュアルな悪意への牽制として働く
- **読み取り専用であることが、広い範囲に強く効くのに比較的安全である理由になる。** ソースへの書き込みという
  副作用を持たないため、集めたデータを機能を絞ったエージェントで使う形にすれば、AI 活用のリスクの影響範囲を限定できる

## 1. 迂回で失われるのは権限ではなく統制

leisen は独自の権限モデルを持たず、認可をソースに委ねる(不変条件1、ADR-003 / ADR-010)。直接接続も同じく
本人の資格情報で動くため、どちらの経路でも見えるデータの範囲は変わらない。したがって迂回は権限逸脱ではない。

失われるのは次の統制である(詳細は §4 の比較表)。

- 質問 → 検索 → 取得 → 引用 → フィードバックを runId でつないだ監査(ADR-011 / ADR-019)
- DM・プライベートチャンネルの既定除外(ADR-013)
- Slack 由来データの非永続化(ADR-014、不変条件7)
- LLM の送り先の選択(ADR-017。ローカル LLM も可)
- Token Vault による一括失効(ADR-010)

不変条件2「Gateway を経由しないソースアクセス経路を作らない」が保証するのは、**leisen 自身が抜け道を作らない**
ことまでである。組織全体でソースへの経路が leisen だけになることは保証しない(threat-model §7)。

## 2. 許可は OAuth アプリ単位

ADR-010 の方式 A(本人の個別 OAuth)では、利用者は導入先が登録した leisen の OAuth アプリに同意する。
直接接続には、エージェント製品のコネクタや公式 MCP サーバーのクライアントという**別のアプリへの同意**が要る。
そのため、leisen だけを承認して他を止める構成が取れる。

| ソース | 管理者の制御(docs/auth-matrix.md の「管理者同意」行) | 直接接続を止められるか |
|---|---|---|
| Google Drive | アプリアクセス制御で、信頼済みに指定したアプリ以外をブロックできる | ◎ |
| Slack | アプリ承認制、`admin.apps.restrict`。公式 MCP の利用は Marketplace アプリか社内アプリに限られる(ADR-014) | ◎(アプリ承認制を使えるプランが前提) |
| GitHub | Org の OAuth App アクセス制限(新規 Org は既定でオン)、GitHub App のインストール承認 | ○(PAT は別に制限する) |
| Notion | Enterprise はコネクションの承認リストで管理できる | Enterprise なら ○、他プランは弱い |
| Microsoft 365 | `Files.Read.All` 等は admin consent が必須。利用者による同意を止める設定と組み合わせる | ○ |

止め方は**許可リスト**(leisen のクライアントだけを許可し、ほかはすべて拒否する)にする。どのエージェント
製品からの接続かを見分けて拒否リストで蹴る方式は成り立たない。ソースに見えるのは OAuth のクライアント ID で、
リモート MCP サーバーへの接続ではクライアントが動的に登録されることがあり、クライアント名は自己申告である。
利用者が自分でクライアントを作ることもできる。許可リストが効くのは、leisen のクライアントがサーバー側に
シークレットを持ちリダイレクト先が固定されていて、利用者が流用できないからである。許可リストで止めるのは
エージェントとソースの直接の接続であって、エージェント製品ではない。Claude Code 等から leisen
(`kp-ask serve`)へつなぐことは正規の利用である。

許可リストの抜け穴になりやすいのは、Google の「社内アプリを自動で信頼する」設定(社員が自社の GCP
プロジェクトで作ったクライアントが通る)と、Slack で利用者が自分で作ったアプリを入れられる設定である。

逆に言えば、**アプリ承認制を使っていない組織では、leisen の導入と関係なく今日すでに直接接続ができる。**
leisen が穴を開けるのではなく、導入を機に既存の穴を塞げるかどうかの問題である。導入チェックリストの
項目は docs/install.md §10「直接接続の統制」に置いた。

## 3. 塞ぎきれない経路の分類

OAuth アプリの承認制で塞げない経路が残る。誰がどんな動機で使うかで扱いを分ける。

| 経路 | 使う人 | 扱い |
|---|---|---|
| ソースのセッショントークンの流用、規約外の自作アプリ | 回避だと自覚しているリテラシーの高い少数 | 利用規程と事後の検知。性質は SaaS の利用規約違反・社内規程違反 |
| GitHub の個人アクセストークン(PAT) | 開発者が日常的に使う。公式の GitHub MCP サーバーも PAT で設定できる | **技術で塞ぐ**: Org で classic PAT を禁止し、fine-grained PAT を承認制にする |
| ブラウザを操作するエージェント(ブラウザ拡張、computer use) | 公式製品として善意で使われる。本人の Web セッションで動くため、ソースからは本人と区別できない | **技術で塞ぐ**: ブラウザ拡張の許可リスト、エージェント製品の組織管理設定 |
| エクスポート・コピー&ペーストで LLM に渡す | 最も多い。ふつうの利用者が行う | 利用規程と、leisen の方が便利な状態を作ること |

規程で抑えられるのは意図的な回避である。善意で便利だから使われる経路は、規程があっても違反だと
認識されにくいため、導入チェックリストで技術的に塞ぐ側に入れる。

本人の資格情報で本人に見えるデータにアクセスすることは、トークンの流用を含め、一般には法律上の
不正アクセスにはあたらず、SaaS の利用規約・社内規程の問題として扱われる(法的評価は導入先で確認する)。
規程に経路を明記しておく意味はここにある。

## 4. 体験の比較

| 観点 | 直接接続 | leisen 経由 |
|---|---|---|
| 初期設定 | エージェント製品の数 × ソースの数だけ OAuth 同意が要る | SSO と、ソースごとに 1 回の同意。どのエージェントからも同じ入口(`kp-ask serve`、ADR-018) |
| 横断検索 | エージェントごとに寄せ集める。品質はエージェント次第 | Orchestrator が横断して探索し、出典を検証してから回答する(ADR-017) |
| DM・プライベート | 本人に見えるものはすべて対象 | 既定で除外(ADR-013) |
| Slack データ | エージェント製品側の規約に従って保存されうる | 永続化しない(ADR-014) |
| 監査 | ソースごとのネイティブ監査ログに分散。「何を聞いたか」は残らない | 質問から引用までを runId でつないで記録(ADR-011 / ADR-019) |
| 失効 | トークンが各ベンダーに分散する | Token Vault で一括失効(ADR-010) |
| LLM の送り先 | 製品ごとに固定 | 設定で選べる(ローカル LLM も可。ADR-017) |
| 文書経由のインジェクション | エージェント次第 | 出典の検証、回答本文の URL 除去(TM-D2) |
| 自律・定期実行 | 制限なし | Phase 1 は拒否(ADR-015) |

## 5. leisen が防ぐもの・防がないもの

**防がないもの**: 本人がアクセスできるデータを、本人が意図的に持ち出すこと。悪意を持った本人は、元の
ソースの UI やエクスポートで個別に持ち出せる。leisen はこれを止める立場にない(threat-model §7)。

**抑えるもの**:

- **意図しないデータ共有**: DM・プライベートチャンネルの既定除外(ADR-013)、Slack 由来データの非永続化
  (ADR-014)、会話の共有リンクの無効化(TM-G4)、回答本文からの URL 除去による持ち出しの防止(TM-D2)
- **エージェントで増幅された横断的な取得**: 手作業では手間のかかる、複数ソースにまたがる大量取得が
  エージェントで容易になる。leisen では取得がすべて利用者ごとに監査に残り、自律・定期実行は既定で拒否される
  (ADR-015)。Orchestrator には反復回数とツール呼び出し件数の上限がある(TM-D3)。ただし、この上限は
  Orchestrator を通らない Gateway への直接の呼び出しにはかからず、Gateway のレート制御はソース API の
  クォータを守るためのソース単位のもので、利用者単位の上限はない。現状の抑止は記録が残ることが中心である
- **統制の強化**: 文脈付きの監査(誰が何を聞き、何を根拠に答えたか)と一括失効

監査は、すべての取得を見張る仕組みとしてではなく、**公認された経路で文脈付きの記録が残る**ことに価値がある。
ソース側のネイティブ監査ログにはアクセスの事実は残るが、問いと答えのつながりは残らない。この記録は
昇格判定(T-014)の入力にもなる。万能の対策ではないが、記録が残ることがカジュアルな悪意への牽制になる。

なお、取得の偏り(短時間に多数のソースを横断する、特定の利用者の取得量が突出する等)を監査ログから
見つけるクエリは、まだ `docs/audit-queries.md` にない。利用者単位の取得量の上限も Gateway にない。
エージェントによる横断的な取得を抑えることを leisen の価値として掲げるなら、この 2 つが次の候補になる。

## 6. 読み取り専用であることの意味

コネクタのツール IF は `search` / `fetch` / `list` / `describe` の読み取りだけで(ADR-016)、ソースに
求めるスコープも読み取り系に限る(`drive.readonly`、`search:read.*`、`Files.Read.All` 等。auth-matrix.md)。
leisen 経由のエージェントは、ソースの内容を変える・メッセージを送る・権限を変えるといった副作用を起こせない。

このため、社内の広い範囲に横断的に効く一方で、誤動作やインジェクションの影響は情報の読み出しに限られる。
エージェントの危険は「機密データへのアクセス」「信頼できない内容の取り込み」「外部への送信手段」の 3 つが
揃うと大きくなる。leisen は前の 2 つを持つが、3 つ目をソースへの書き込みとして持たず、回答本文の URL 除去で
送信の経路も細くしている。

集めたデータを、書き込みや外部送信の手段を持たない機能を絞ったエージェントで使う形にすれば、AI 活用の
リスクの影響範囲を限定できる。書き込みや外部送信の手段を持つエージェントに leisen をつなぐと、この性質は
エージェント側で崩れる。リファレンス構成の LibreChat で、利用者が MCP サーバーを追加できないようにし
(`interface.mcpServers.create: false`)、接続先を許可リストで限っている(`mcpSettings.allowedDomains`)設定は、
この性質を保つ役にも立つ(docs/ui-librechat.md)。

副作用がゼロではない点も残る。検索クエリはソース側の検索履歴やログに残るため、インジェクションが検索クエリに
機密を載せて攻撃者に見える場所へ書き出す経路がある(TM-D3)。

## 7. 迂回を誘う要因と打ち手

leisen が直接接続より不便、あるいは制限が強いと、それが迂回の動機になる。

| 要因 | 打ち手 |
|---|---|
| 最初の同意の手間 | 初回同意 UX(ADR-010 決定3)と、未接続ソースの接続を促す導線 |
| DM・プライベートの除外 | `consent` モード(ADR-013。同意状態の持ち方が未設計のため現在は指定できない。#42、ADR-016 追補2)の設計の検討材料に迂回のリスクを加える |
| 自律・定期実行の拒否(Phase 1) | 解放(ADR-015)の判断材料に、直接接続へ需要が流れるリスクを加える |
| 使い慣れたエージェントから使えない | `kp-ask serve` を MCP サーバーとして配布し、エージェント製品の組織管理機能でカスタムコネクタとして登録する(ADR-018) |

「leisen で禁止 = 組織として禁止」が成り立つのは、直接接続を塞いだ場合だけである。塞がずに leisen の制限だけを
強めると、利用は統制の弱い直接接続へ流れる。
