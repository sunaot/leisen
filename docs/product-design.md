# 社内ナレッジ検索基盤 製品企画・設計書

段階的アーキテクチャ: Phase 1 フェデレーテッド Agentic Search → Phase 2 選択的インデックス補強 → Phase 3 権限区画別ナレッジレイヤー

---

## 1. 概要

### 1.1 目的

社内の事業・サービス開発にまつわるナレッジを、LLM が API 経由で検索・利用できる状態にする。人間の利用者は LLM(チャットまたはエージェント)を経由して問い合わせる。LLM エージェントそのものが自律的に社内知識を参照して業務を遂行することも、同じ基盤の上で成立させる。

### 1.2 スコープ

対象組織規模は数百〜数千人。データソースは Google Drive / Slack / GitHub / SaaS wiki(Confluence, Notion 等)/ 社内 DB・業務システムなど 10〜30 種類程度を想定する。数万人規模の組織、および全社横断のコンプライアンス検索(eDiscovery)は非スコープとする。

### 1.3 成功の定義

本基盤の成否は検索アルゴリズムの精度ではなく、次の 3 点で測る。第一に、権限逸脱による情報漏洩がゼロであること。第二に、利用者が「社内のことは Claude 等に聞けば大体わかる」と感じる状態(週次アクティブ率とタスク解決率で計測)に到達すること。第三に、専任 1〜2 名で運用が回り続けることである。

---

## 2. プロダクト原則

段階的に機能を積み上げていく過程で、判断がぶれないよう次の 4 原則を不変条件として置く。

**原則 1: 認可は常にデータソースに委譲する。** 本基盤は独自の権限モデルを持たない。アクセス可否の最終判断は、必ず元のデータソースが検索者本人の認証情報に対して下す。Phase 2 でインデックスを持つ場合も、返却前にソース側の認可を照会することでこの原則を守る。権限の複製・翻訳・同期を正とする設計は採用しない。

**原則 2: 可動部品を最小にする。** 同期パイプライン、インデックス、生成物は、それぞれが劣化・故障し運用負債になる。追加する場合は「実測データが必要性を示したとき」に限る。Phase 2 と Phase 3 の機能は、Phase 1 の利用ログという証拠に基づいて投資判断する。

**原則 3: 検索品質はエージェントの反復で稼ぐ。** 単発クエリの精度を上げるより、LLM が粗い検索を複数回試行し、結果を読んで再検索する探索ループの質に投資する。ネイティブ検索が貧弱なソースでも、反復である程度吸収できることを前提とし、吸収しきれない場合のみインデックスで補強する。

**原則 4: すべての検索行為を監査可能にする。** 誰の権限で・どのソースに・何を問い合わせ・何が返ったかを全件記録する。これはセキュリティ要件であると同時に、Phase 2 以降の投資判断に使う最重要のプロダクトデータである。

## 3. 全体アーキテクチャ

### 3.1 共通基盤(全 Phase で不変)

```
利用者/エージェント
   │  (チャットUI / API)
   ▼
[Agent Orchestrator]  … 探索戦略、ツール選択、回答合成
   │
   ▼
[MCP Gateway]         … 認証・認可の要。全ツール呼び出しの単一経路
   │  ├─ Token Exchange (IdP: Okta / Entra ID)
   │  ├─ 監査ログ (全リクエスト/レスポンス記録)
   │  └─ レート制御・タイムアウト管理
   │
   ├──▶ [Connector: Google Drive]   ネイティブ検索API
   ├──▶ [Connector: Slack]          ネイティブ検索API
   ├──▶ [Connector: GitHub]         ネイティブ検索API
   ├──▶ [Connector: Wiki]           ネイティブ検索API
   ├──▶ [Search Layer]              Phase 2で追加(弱いソースのみ)
   └──▶ [Knowledge Layer]           Phase 3で追加(権限区画別マップ)
```

コンポーネント間の接続プロトコルは MCP(Model Context Protocol)に統一する。これにより、社内基盤としてのコネクタ群が、将来別の LLM 製品・エージェント製品からもそのまま利用できる。

### 3.2 認証・認可フロー(全 Phase 共通)

> **改訂(2026-07-05、ADR-010)**: 本節の「Token Exchange を基本方式」は見直し中。Phase 1 主要対象(Google Drive / Slack)では外部IdPトークンからの交換経路を前提化できず、実際の主経路は個別 OAuth となる。ソース別 Auth Adapter + Token Vault を前提とし、詳細は `product-design-v3.md` §1 と ADR-010 を正とする。以下は元の記述(歴史的経緯として残置)。

権限透過の実現方式は IdP を起点とした token exchange とする。

1. 利用者はチャット UI に IdP(Okta / Entra ID)で SSO ログインする
2. Agent Orchestrator は利用者のセッショントークンを保持する
3. MCP Gateway はツール呼び出し時、OAuth 2.0 Token Exchange(RFC 8693)または各 SaaS の on-behalf-of フローで、対象データソース用の利用者本人のアクセストークンを取得する
4. コネクタはそのトークンでソース API を呼ぶ。したがってソースが返す結果は、定義上その利用者が見てよいものに限られる

サービスアカウントによる全件アクセスは、Phase 2 のインデックス構築など明示的に必要な箇所を除き禁止する。トークンのキャッシュは利用者×ソース単位で短期(トークン有効期間内)に限る。

### 3.3 技術スタック想定

| 領域 | 選定 | 理由 |
|---|---|---|
| プロトコル | MCP | エコシステム標準。コネクタの再利用性 |
| IdP 連携 | Okta / Entra ID + RFC 8693 | 既存 SSO 資産の活用 |
| Orchestrator | Claude API 等 + 自前の薄い制御層 | エージェントループは LLM 側の能力に委ね、制御層は薄く保つ |
| 監査ログ | 構造化ログ → データウェアハウス | Phase 2 以降の投資判断データを兼ねる |
| 検索層 (Phase 2) | 着手時に選定 | 実データでのPoCを経て判断(v2/ADR-006で詳細化) |
| マップ生成 (Phase 3) | LLM バッチパイプライン | 後述 |

## 4. Phase 1: フェデレーテッド Agentic Search

期間目安: 開始〜6 ヶ月。目標: 主要 4〜6 ソースへの権限透過検索を全社提供し、利用実態データを蓄積する。

### 4.1 機能要件

チャット UI および API から自然言語で問い合わせると、LLM が適切なソースを選択し、本人権限で検索・閲覧し、出典リンク付きで回答する。回答には必ず原典への参照を含め、利用者がワンクリックで原文に到達できること。API 利用時(エージェント連携)は、呼び出し元エージェントの実行主体となる人間のトークンを引き回す。

### 4.2 コネクタ設計

コネクタは 1 ソースにつき 1 MCP サーバーとし、次のツールインターフェースを共通化する。

- `search(query, filters)` — ソースのネイティブ検索を叩く。フィルタ(期間、作成者、スペース等)はソースが対応する範囲で公開する
- `fetch(document_id)` — 文書本文の取得。長文はページング
- `list(container_id)` — フォルダ/チャンネル/リポジトリ等の列挙。検索が弱いソースでの探索的走査に使う
- `describe()` — そのソースに何があるか(スペース一覧、主要フォルダ構造)のメタ情報。エージェントの初手選択を助ける

初期対象ソースは利用密度の高い順に 4〜6 個(典型的には Google Drive、Slack、wiki、GitHub)。コネクタは公式 MCP サーバーが存在すればそれを利用し、認可要件(本人トークン)を満たさない場合のみ自前実装する。

### 4.3 探索戦略(Orchestrator の設計)

エージェントには次の探索方針をシステムプロンプトとして与える。

1. 質問からソースの当たりをつける(`describe` の情報を常時コンテキストに保持。10ソース超では Source Catalog に置換する — T-018、v3 §7)
2. まず広いキーワードで 1〜2 ソースを検索し、結果のスニペットを読む
3. ヒットが薄ければ、類義語・英日変換・期間フィルタを変えて最大 N 回(初期値 6)再検索する
4. 有望な文書は `fetch` で本文を読み、そこに書かれた固有名詞・リンクを手がかりにさらに辿る
5. 回答には根拠文書を必ず引用し、確信が持てない場合はその旨と探索した範囲を明示する

反復回数・レイテンシ・コストのバランスは運用パラメータとして調整可能にする。

### 4.4 監査ログ設計(Phase 2 への布石)

> **改訂(2026-07-05、ADR-011)**: 本節の単層モデルは AnswerRun / ToolInvocation の2層モデルに再設計された。post-filtering 前の候補件数は記録しない(existence leak 対策、ADR-012)。rawQuery は短期保持の別テーブル。詳細は ADR-011 を正とする。

全ツール呼び出しについて、利用者・タイムスタンプ・ソース・クエリ・ヒット件数・fetch した文書 ID・最終回答の引用文書・利用者フィードバック(解決した/しない)を記録する。特に「どのソースで、何回再検索しても解決しなかったか」を集計できるスキーマにする。これが Phase 2 の昇格判断の直接の入力になる。

### 4.5 Phase 1 の既知の限界と受容

Slack のようにネイティブ検索が貧弱なソースでは精度が出ない。横断的な俯瞰(「この事業領域で何が決まっているか」)に弱い。ソース API のレート制限とレイテンシ(1 問あたり 10〜60 秒)がかかる。これらは Phase 2 / 3 で解決する前提で、Phase 1 では受容する。

### 4.6 Phase 1 の完了条件と KPI

> **改訂(2026-07-05、v3 §8)**: 週次アクティブ利用率は展開施策に左右される採用指標のため、Phase 移行のゲートからは外し目標(target)として扱う。ゲートには解決率と未解決原因分布の取得可能性を用いる。

- 週次アクティブ利用率: 対象部門の 30% 以上
- 利用者評価によるタスク解決率: 60% 以上
- 権限逸脱インシデント: 0 件(レッドチームテストを四半期実施)
- ソース別の未解決率レポートが出力できていること(Phase 2 の判断材料)

## 5. Phase 2: 選択的インデックス補強

期間目安: 6〜12 ヶ月。目標: 実測で検索品質が律速しているソースに限定して検索層を追加し、権限の正しさを維持したまま解決率を引き上げる。

### 5.1 昇格基準(どのソースを補強するか)

インデックス構築は無条件には行わない。Phase 1 の監査ログから、次の条件を満たすソースのみ「昇格」させる。

- 未解決クエリに占めるそのソース起因の割合が高い(目安: 上位 2 ソースに集中している)
- 失敗原因が「文書は存在するのにネイティブ検索で到達できない」であることをサンプリング調査で確認済み
- エージェントの反復回数を増やしても解決率が改善しない(探索戦略の調整では吸収不能)

典型的には検索 API を持たない社内システムが昇格対象になる。**Slack は昇格判定の対象外とする(改訂 2026-07-05、ADR-014)**: RTS API と API Terms により中央インデックス化が原則不可となったため、オンデマンド検索ソースとして扱う。

### 5.2 検索層アーキテクチャ

```
[Connector: 昇格ソース]
   │ search() の実装が切り替わる(インターフェースは不変)
   ▼
[Search Layer]
   ├─ Ingest Pipeline: サービスアカウントで全件取得 → 正規化 → チャンク
   ├─ Index: BM25 + ベクトル(ハイブリッド)
   └─ AuthZ Filter: 返却前にソース認可APIを本人トークンで照会
```

重要な設計判断は、コネクタのツールインターフェース(`search`/`fetch`)を変えずに、内部実装だけをネイティブ検索から検索層に差し替えることである。Orchestrator と利用者からは Phase 1 と同じに見える。

### 5.3 認可設計: post-filtering と recall 劣化対策

原則 1 に従い、インデックスに ACL を複製・同期する方式は取らない。代わりに検索層はまず権限を無視して上位 K 件を取得し、返却前に各文書についてソースの認可 API を本人トークンで照会し、閲覧可能なもののみ返す(post-filtering)。

post-filtering の既知の問題は、上位 K 件の大半が権限外だった場合に返却件数が枯れる recall 劣化である。対策を 3 段で設ける。

1. **適応的 K 拡張**: 返却件数が閾値未満なら K を段階的に広げて再照会する(上限あり)
2. **粗い事前フィルタ**: 権限そのものではなく「明らかに到達不能な区画」(利用者が所属しない Slack ワークスペース、参加履歴のないプライベートチャンネル群)をインデックス側のメタデータで粗く除外する。これは認可の代替ではなく候補削減の最適化であり、最終判断は常に認可 API 照会が行う
3. **認可照会のキャッシュ**: 利用者×文書の照会結果を短 TTL(目安 5〜15 分)でキャッシュし、照会コストを抑える。TTL は「権限剥奪から反映までの許容遅延」としてセキュリティポリシー上明文化する

### 5.4 Ingest パイプラインの運用設計

サービスアカウントによる全件クロールは Phase 2 で初めて導入する例外である。差分同期(変更通知 webhook があれば利用、なければ定期クロール)、削除伝播(ソースで消えた文書はインデックスからも消す。目標反映時間を SLO 化)、鮮度メトリクス(インデックス遅延の p95)をダッシュボード化し、劣化を検知できる状態を維持する。パイプラインは昇格ソース数に比例して増えるため、昇格は常に「最小限」を守る。

### 5.5 Phase 2 の完了条件と KPI

- 昇格ソース起因の未解決率が昇格前比で 50% 以上改善
- post-filtering 起因の空振り率(適応拡張しても閾値未満)が 5% 未満
- インデックス鮮度 SLO(例: p95 で 15 分以内)の達成
- 権限逸脱インシデント: 0 件(post-filtering 経路を重点にレッドチーム)

## 6. Phase 3: 権限区画別ナレッジレイヤー

期間目安: 12〜18 ヶ月。目標: 「探せば見つかる」から「聞けば俯瞰できる」へ。エージェントの初手品質と、横断的・要約的な質問への回答力を引き上げる。

### 6.1 コンセプト

Phase 1/2 は文書粒度の検索であり、「◯◯事業の現在のアーキテクチャ方針は」「この半年で決まった重要な意思決定は」といった俯瞰質問には弱い。Phase 3 では、LLM がバッチで生成・更新する構造化ナレッジマップ(領域別の要約+原典リンク集)を追加し、エージェントの探索の起点とする。

マップは検索の代替ではなくナビゲーションである。エージェントは「マップで領域と主要文書を把握 → Phase 1/2 の検索で原典に降りる」という 2 段探索を行う。網羅性は引き続き検索側が担保するため、マップの圧縮による情報劣化は俯瞰の初手に限定され、致命的にならない。

### 6.2 最重要設計: 権限区画(Permission Cohort)

> **改訂(2026-07-05、product-design-v3.md §8)**: 本節の「代表権限(区画メンバー全員がアクセス可能な文書集合)」の自動導出は、ACL評価の複製に当たり不変条件1と矛盾する。現行方針では入力を「区画のIdPグループに明示的に共有されたコンテナ」に限定し、運用はオーナー承認制のCurated Mapから始める(Phase 3着手時にADR化)。以下の「代表権限トークン」「人事マスタ/IdPグループからの自動導出」を含む記述は旧設計であり、そのまま実装しないこと。Phase 3はまだ着手しない。

マップの要約は複数文書の内容を混ぜるため、全社 1 枚のマップは必然的に権限漏洩を起こす。これを構造的に防ぐため、マップは権限区画ごとに独立生成する。

権限区画とは「アクセス可能な文書集合がほぼ同質な利用者グループ」であり、実務上は部門・事業部・プロジェクトの単位に一致させる。設計ルールは次の通り。

- 各マップは、その区画の代表権限(区画メンバー全員がアクセス可能な文書集合)のみを入力として生成する。区画内の一部の人しか見られない文書はマップに入れない
- マップ自体へのアクセス制御は IdP のグループに紐付ける
- 区画の定義は人事マスタ/IdP グループから自動導出し、組織変更に追随させる
- 全社公開情報のみで構成する「全社マップ」を 1 枚別途持ち、区画横断の共通レイヤーとする

この設計により「要約が機密を漏らす」問題は、入力文書集合の段階で遮断される。

### 6.3 マップ生成パイプライン

1. **入力収集**: 区画の代表権限トークンで、対象ソースから主要文書(更新頻度・参照数・リンク被参照数でスコアリングした上位)を取得
2. **構造化生成**: LLM が領域ツリー(事業 → プロダクト → コンポーネント/テーマ)を生成し、各ノードに 3〜10 行の要約と原典リンク 3〜10 件を付与。前回版との差分生成とし、変更のあった領域のみ更新
3. **検証**: 生成物中の全リンクの到達性チェック、要約と原典の整合性を別 LLM で照合(hallucination 検査)、機密キーワードのスクリーニング
4. **人間レビュー**: 各区画に 1 名のマップオーナー(その部門の従来のナレッジ管理担当を兼務)を置き、週次更新分を承認する。全自動化はしない
5. **配信**: 承認済みマップを MCP の `describe` 拡張としてエージェントに提供

更新頻度は週次を基本とし、区画ごとに調整可能とする。

### 6.4 マップの利用設計

Orchestrator の探索戦略を次のように更新する。利用者の質問を受けると、まず本人が属する区画のマップ(+全社マップ)を参照して領域を特定し、マップ記載の原典リンクを `fetch`、不足があれば Phase 1/2 の検索に降りる。俯瞰型の質問はマップだけで回答が完結する場合もあるが、その際もマップの生成日時を回答に明示し、鮮度の限界を利用者に開示する。

### 6.5 Phase 3 の完了条件と KPI

- 俯瞰型クエリ(分類器でタグ付け)の解決率が Phase 2 比で有意に改善
- 探索の平均ツール呼び出し回数・レイテンシが 30% 以上短縮(初手の質の改善効果)
- マップ経由回答の hallucination 率(サンプリング監査)が閾値未満
- マップオーナーの週次レビュー負荷が 30 分/週以内に収まること(運用持続性)

## 7. 横断設計

### 7.1 評価基盤

Phase 1 の開始時点から、社内質問の評価セット(実クエリからサンプリングし、正解文書を人手で付与した 100〜300 問)を構築・維持する。探索戦略の変更、コネクタ追加、Phase 昇格のたびに回帰評価を実施し、解決率・引用正確性・レイテンシ・コストを比較する。この評価セットが「Phase 2/3 に進むべきか」「Glean 等の購入に切り替えるべきか」の共通のものさしになる。

### 7.2 セキュリティ・監査

- レッドチームテスト(権限外文書の取得試行、プロンプトインジェクション経由の権限昇格試行)を四半期実施
- **カナリア文書による常時検証(追加 2026-07-05)**: 特定テストユーザーに絶対に見えてはいけない文書を各ソースに常設し、ヒット非出現を継続検証する。権限逸脱の検出を四半期イベントから常時監視に変える(T-013、導入プレイブック標準工程)
- 検索対象文書に含まれる指示的テキストによるインジェクション対策として、ツール結果はデータとして扱う旨のプロンプト防御と、Gateway での出力フィルタ(権限外ソースへの追加呼び出し検知)を実装
- 監査ログの保持期間・閲覧権限は情報セキュリティ部門と合意の上ポリシー化

### 7.3 体制とコスト概算

| 時期 | 体制 | 主業務 |
|---|---|---|
| Phase 1 | エンジニア 2 名 + PM 0.5 名 | Gateway/コネクタ構築、探索戦略チューニング |
| Phase 2 | 同上(継続) | 検索層構築、Ingest 運用 |
| Phase 3 | エンジニア 2 名 + PM 0.5 名 + 区画オーナー(兼務、各 30 分/週) | マップパイプライン、レビュー運用 |

ランニングコストの主要因は LLM API(探索の反復呼び出し)で、利用者数×利用頻度に比例する。Phase 3 はマップによる初手改善で 1 問あたりのツール呼び出しが減るため、利用拡大とコスト増を部分的に相殺する構造を持つ。

## 8. ロードマップ

| 四半期 | マイルストーン |
|---|---|
| Q1 | 共通基盤(Gateway、token exchange、監査ログ)+ コネクタ 2 本。1 部門でクローズドβ |
| Q2 | コネクタ 4〜6 本。全社公開。評価セット v1。KPI 計測開始 |

| Q5 | 全社マップ + パイロット 2 区画でマップ生成・レビュー運用開始 |
| Q6 | 区画マップ全社展開。探索戦略のマップ統合。効果測定 |

各 Phase の移行はロードマップ上の日付ではなく、前 Phase の完了条件(KPI)の達成をゲートとする。

## 9. リスクと意思決定ポイント

**Build vs Buy の再判定(Q2 末)**: Phase 1 の実測で「未解決の主因が横断検索の欠如であり、昇格対象が 3 ソース以上」と判明した場合、自前の Phase 2 拡張より Glean 等の permission-aware 検索製品の購入が合理的になる可能性がある。その場合も本設計の Gateway・監査ログ・評価基盤はそのまま活き、購入製品は「大きな 1 コネクタ」として組み込める。この可換性こそ Gateway を単一経路とする設計の狙いである。

**主要リスク一覧**:

| リスク | 影響 | 対策 |
|---|---|---|
| ソース API のレート制限で全社利用が頭打ち | 中 | Gateway でのキャッシュ・スロットリング、ベンダーとの上限交渉 |
| post-filtering の認可照会がソース API に負荷 | 中 | 短 TTL キャッシュ、照会のバッチ化 |
| マップレビューの形骸化 | 中 | レビュー負荷の KPI 化、負荷超過時は更新頻度を落とす |
| プロンプトインジェクション経由の情報引き出し | 高 | 7.2 の多層防御 + 四半期レッドチーム |
| 探索レイテンシへの利用者不満 | 低〜中 | ストリーミング表示、進捗の可視化、Phase 3 での初手短縮 |
