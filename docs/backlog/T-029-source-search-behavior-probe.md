# T-029: 実機での検索の仕様の確認(Redmine の `all_words`、esa の MCP 経由の AND と OR、各ソースの日本語の扱い)

## 依存
T-026(esa コネクタ、実チームで接続確認済み)、Redmine コネクタ(ADR-024)、T-025(自分の GitHub で試す開発用設定)。結果は T-027(フィクスチャの検索方式)、T-028(`summary` の記述、Redmine の AND / OR)、ADR-025(検索プロファイルの `basis`)に反映する

## 前提(人手)
- 実機と資格情報: esa(導入先のチームの owner の許可と OAuth クライアント。既存の手元の構成)、Redmine の実機(版と全文検索プラグイン `redmine_full_text_search` の有無を記録する。本人の個人 API キー、`mock_env` の開発用経路)、GitHub(本人の fine-grained PAT、T-025)
- 確認用の文書: 各ソースに、確認のための文書を用意するか、既存の文書のうち確認に使ってよいものを人が選ぶ。実在の業務の内容を確認の記録に残さないため、確認用に作った文書を推奨する
- Slack は対象外(T-006 未実装。ADR-014 により取得データを確認の記録に残せない)

## 背景
`reports/エージェント検索ハーネス設計調査.md`(以下「レポート」)の「根拠の弱い点」は、次を実機未確認とした。いずれも探索 LLM に伝える検索の仕様の中心であり、推測のまま書くと、今の全ソース共通の指針(AND の部分一致の開発用コネクタで作った一般化)と同じ誤りを繰り返す。

- Redmine の `all_words=0` が OR になるか AND になるか。コネクタは `all_words: "0"` を送る(`packages/connector-redmine/src/redmine.ts:213`)。Redmine のソースではトークンの結合が `all_words ? ' AND ' : ' OR '` なので意図は OR と読めるが、コントローラがこのパラメータを「存在すれば真」と解釈する実装だった可能性(調査ノートの記憶に基づく指摘)があり、版や全文検索プラグインの有無でも変わりうる
- esa のリモート MCP の `esa_search_posts` 経由で、公式ヘルプ(docs.esa.io/posts/104)と同じ仕様で動くか。空白の AND の厳密さ、「表記の揺れを考慮した検索」の範囲、`OR` と後置の修飾子を混ぜたときの優先順位、日本語の扱い、`sort: best_match` の中身
- GitHub の検索 API の日本語クエリの分かち書きと AND の厳密さ

## 内容
- **調査用スクリプト**: 同じ確認用の文書に対して、次の形のクエリを実行し、その文書が結果に入ったか・何位か・返った件数(返却されたヒットの数。総件数は取らない)を記録する。Gateway を経由してコネクタの `search` を本人の資格情報で呼ぶ(不変条件 1・2。ソースの API を直接呼ばない)
  - 文(質問文)、文節、名詞を空白で区切った AND、複合語(例: 経費精算)、複合語の構成語(経費 精算)、表記違い(長音の有無、全角と半角、英語)、6 語以上のクエリ、`OR` を含むクエリ、引用符、修飾子(esa の `title:` など)
  - Redmine は `all_words=0` と `all_words=1` の両方(コネクタの外から指定できない場合は、調査用に限り切り替える手段をスクリプト側に持つ。コネクタの本番のコードは変えない)
  - esa は `OR` を含む query に filters(`in:` など)を付けた場合と、括弧で包んだ場合
- **記録の扱い**: 記録に残すのは、クエリの形(確認用の文書のために作った語)、確認用の文書の documentId、順位、返却件数、ソースの版とプラグインだけにする。実在の業務の文書のタイトル・本文・スニペットは記録しない。生クエリ表・監査は通常どおり Gateway が書く(保持期間に従う)
- **結果の反映**:
  - `docs/eval/` か `docs/spikes/` に結果のレポートを書く(ソースごと、クエリの形ごとの表。確かめた日付と版)
  - Redmine の結果を ADR-024 の「帰結」か「残る確認事項」に、esa の結果を ADR-023 に追記する
  - T-027 のフィクスチャの検索方式、T-028 の `summary` の記述を、結果に合わせて直す(別の PR でよい)
  - ADR-025 が Accepted になっていれば、検索プロファイルの該当項目の `basis` を `tested` にする(T-030)

## 受け入れ条件
- [ ] 調査用スクリプトがリポジトリにあり、Gateway 経由で本人の資格情報だけを使う(モックでのユニットテストで、資格情報が本人のものだけであることと、ソースの API を直接呼ばないことを確かめる)
- [ ] スクリプトが記録に業務の文書のタイトル・本文・スニペットを書かないことのテストがある
- [ ] Redmine の `all_words=0` と `all_words=1` の挙動を、版と全文検索プラグインの有無とともに記録したレポートがある
- [ ] esa の MCP 経由の検索で、空白の AND、`OR`、引用符、`title:`、`OR` と後置の修飾子の組み合わせ、日本語の複合語と構成語の結果を記録したレポートがある
- [ ] GitHub の日本語の複合語・構成語・文のクエリの結果を記録したレポートがある
- [ ] 結果が ADR-024 / ADR-023 に追記されている

## 判断が必要な点
- **確認用の文書の用意**: 確認用に作る(推奨)か、既存の文書を使うか。既存の文書を使う場合、記録に残してよい範囲を人が決める
- **Redmine の実機**: 確認に使う Redmine の版。導入先で使われている版と、OAuth2 に対応した版(6.1 以降とされる。ADR-024)のどちらを優先するか

## 限界
- 確かめられるのは調べた版・設定・チームでの挙動である。導入先ごとの違い(Redmine のプラグイン、Slack のプラン)は、ADR-025 の deployment.yaml の上書きで表す
- 公式 MCP(esa)はβで、仕様がサーバー側で変わりうる(ADR-023)。確かめた日付を記録に残す
