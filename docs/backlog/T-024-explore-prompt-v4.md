# T-024: 探索プロンプト v4(検索の仕様の参照、利用者が入力したキーワードの保持、制御メッセージ、複数文書の質問の分解、止める基準と続ける基準)

## 依存
T-007(Orchestrator)、T-022(v3 の汎化確認。改訂の根拠は `docs/eval/2026-10-09-t022-generalization.md` §4・§5)。2026-11-25 の拡張分は T-027(評価の仕組み)で判定し、T-028(コネクタの `summary` への検索の仕様の記載)と組み合わせて測る

## 前提(人手)
- 実走には LLM が要る(オーナーの手元の LM Studio。v3 の計測と同じモデルを基準にする)
- 新しい質問の書き手を決める(下記「判断が必要な点」)

## 背景
v3 は 20 問 × 2 回で 37 / 40 合格した。不合格の 3 件はすべて複数文書の質問で、原因は、質問を事柄ごとの検索に分解できていないこと。2 つ目の事柄が質問文に明示されていないと届かず、見つけたヒットを読まずに打ち切ることもあった。また、文書にない質問は正しく unresolved になるが、上限(6 ターン)まで探し続け、所要時間が全種類で最も長い(中央値 77.8 秒)。

T-022 の 20 問は v4 の改訂の材料になるため、v4 の効きの評価には使えない(回帰の確認には使う)。

## 内容
- **新しい質問を先に固定する。** v4 のプロンプトを書く前に、別のコミットで新しい質問を `examples/eval/` に足す(既存の 20 問とは別ファイルにするか、種類に「held-out」を表す印を付けて区別する)。複数文書の質問を中心にし、文書にない質問と、1 文書の質問(表記ゆれ・英語を含む)も入れる
  - 複数文書の質問は、2 つ目の事柄が明示されているものと、明示されていない(質問から推して探す)ものの両方を入れる
  - 必要なら合成コーパス(`examples/fixtures/dev-corpus.yaml`)に文書を足す。足した文書も質問と同じコミットで固定する
- **`prompts/explore.v4.md`** を追加し、`EXPLORE_PROMPT_VERSION` を `explore.v4` に上げる。v3 から引き継ぐ防御の文言(インジェクション・URL・出典)はテストで固定したまま残す。改訂の候補:
  - 複数の事柄を聞く質問は、事柄ごとに分けて検索する(並行に呼んでよい)。1 つの事柄の文書が見つかった後も、残りの事柄を探す。見つかったヒットは fetch してから判断する
  - 見つからないときの打ち切り: 1 語の検索・区画を絞った検索がいずれも 0 件なら、上限まで探さずに unresolved で答える。早く打ち切ると表記ゆれの立て直しを損なうおそれがあるため、回帰で確かめる
- **v3 との比較の手段**: 同じ質問を v3 と v4 で流す。v3 のコミットで dev-eval を流すか、開発用にプロンプトの版を指定する手段(本番では使えないもの)を足す
- 評価レポートを `docs/eval/` に書く(v3 と v4 の比較、種類別、Gateway の監査から読んだ呼び出し順、不合格の原因の分類)

## 受け入れ条件
- [ ] 新しい質問が、v4 のプロンプトより前のコミットで固定されている(履歴で順序を確かめられる。計測後に質問・期待値を差し替えない)
- [ ] 新しい質問には、複数文書の質問(2 つ目の事柄が明示されているもの・いないものを各 2 問以上)、文書にない質問(2 問以上)、1 文書の質問(表記ゆれ・英語を含む 2 問以上)がある
- [ ] `prompts/explore.v4.md` と版の更新があり、v3 から引き継ぐ防御の文言と v4 で足した方針の文言がテストで固定されている
- [ ] 新しい質問で v3 と v4 を `--repeat 2` で比べた結果がレポートにある(合否、種類別、ターン数、所要時間)
- [ ] T-022 の 20 問で v4 を `--repeat 2` で流し、回帰がないことを確かめている(特に表記ゆれ・英語の合格と、文書にない質問で作り話をしないこと)
- [ ] 文書にない質問のターン数・所要時間の変化を報告している
- [ ] v4 が v3 より良くならない場合は v3 のままにし、採用しない判断とその根拠をレポートに残す

## 2026-11-25 の拡張(オーナー方針)

`reports/エージェント検索ハーネス設計調査.md`(以下「レポート」)を受けたオーナーの方針(2026-11-25)により、v4 の範囲を広げる。探索 LLM(Orchestrator の中で `search` / `fetch` を呼ぶ LLM)はモデルによらず検索に十分な性能を持つものとして扱い、クエリは探索 LLM が書く。ハーネスの役割は次の 4 つで、いずれも IF を変えずに行う(IF の変更は ADR-025 / ADR-026 で扱い、T-030 / T-031 で実装する)。コードで実行する最初の検索(キーワードのコード抽出、クエリの整形、並列検索の自動実行)、順位による結果の統合、LLM による選別の別呼び出し、古い結果の圧縮、小型モデル向けの補助は範囲外とする。

### 拡張する内容
- **検索の仕様を伝える**: 探索プロンプトと `USAGE_HINTS`(`packages/orchestrator/src/tools.ts:25-33`)の全ソース共通の指針「多くのソースは、空白で区切った語をすべて含む文書だけを返す」「名詞を 1〜2 語だけ」(`prompts/explore.v3.md:12-13`)を、「ソース一覧に書かれた各ソースの検索の仕様に合わせる。仕様に書かれていない記法(他のサービスの演算子など)は使わない」に置き換える。各ソースの仕様の記述そのものは T-028 がコネクタの `summary` に書く。Redmine では使えない `filters.container` を一律に勧める記述を直す
- **利用者が入力したキーワードを残す指示**:
  - `ask` の description と `instructions`(`packages/orchestrator/src/server/tools.ts:206-240`)に入力側の指示を足す。利用者の直近の発言を言い換え・要約・翻訳せずに `question` に入れる、固有名詞・ID・エラーメッセージ・引用符で囲まれた語句を一字も変えない、直近の発言だけで意味が通らないときに限り指している対象を補う、利用者が言っていない用途・期間・範囲を足さない、`ask` は過去の会話を覚えていない、応答に時間がかかることがある。引数は変えない(ADR-018 決定 1 のまま)
  - 探索プロンプトに、最初のターンでは利用者が入力したキーワードを変えずに使った検索を必ず 1 本出すこと、表記の違う言い換え(長音の有無、英語と日本語、略語と正式名、複合語を分けた形)は別の検索として同じターンに並べること、文書を書いた人が実際に書きそうな語だけを query に入れること、意味を知らない社内用語を推測で言い換えないこと、次の検索の語はここまでの結果に実際に出てきた表記から選ぶことを書く
- **0 件・重複のときの制御メッセージ**: Orchestrator が、自分が発行したクエリの形と返った結果から次を判定し、`[オーケストレーター]` で始まる制御メッセージ(ツール結果の外)で返す
  - 0 件だった(クエリが文のままで空白がない、フィルタを指定していた、などの形の手掛かりを添える。ソースの仕様に依存する判定(語数の上限など)は、T-028 の記述を Orchestrator が解釈できないため、ADR-025 の検索プロファイルが入るまで行わない)
  - 同じソースに同じ query を既に実行していた
  - 今回のヒットがすべて既出の文書だった
  - 毎ターン、ここまでの検索の一覧(ソース、query、新しく得た文書の数)と残りのツールターン数を示す
  - 文面は「見つからなかったことは、文書が存在しない根拠にならない」を保つ。権限や件数には触れない(ADR-012。新しく得た文書の数は返却済みのヒットから数えるので抵触しない)
- **止める基準と続ける基準**:
  - 上限(`maxIterations` 既定 6、120 秒)は変えない。1 ターンに複数の検索を並べてよいこと、単純な質問は 2〜4 回の呼び出しで終えてよいこと、複数の事柄を含む質問は 10 回前後を使ってよいことを伝える
  - 止める基準: 質問の各事柄について本文を読んだ裏付けの文書がある、または直近 2 回の検索が新しい文書を返さなかった。見つからない側は、利用者が入力したキーワードでの検索、語を減らした検索、表記を変えた検索がいずれも有用な結果を返さなければ、探した範囲を書いて unresolved で提出する(上の「見つからないときの打ち切り」を置き換える)
  - 続ける基準: ヒットを 1 件も fetch せずに提出しようとしたとき、Orchestrator が 1 回だけ差し戻す
- 変更する制御メッセージの文言はプロンプトの一部として扱う(`packages/orchestrator/src/prompt.ts:15-16`)。評価レポートを添付する

### 拡張分の受け入れ条件
- [ ] 探索プロンプトと `USAGE_HINTS` から全ソース共通の「多くのソースは AND」「名詞を 1〜2 語だけ」の指針がなくなり、ソースごとの検索の仕様を参照する指示になっている(テストで文言を固定)
- [ ] `ask` の description と `instructions` に入力側の指示があり、引数のスキーマが変わっていないことがテストで固定されている
- [ ] 0 件・同じ query の繰り返し・既出の文書だけ、の 3 つの制御メッセージと、検索の一覧の制御メッセージに、それぞれユニットテストがある。制御メッセージが権限・件数・未認可の文書に触れないことのテストがある
- [ ] fetch せずに提出しようとしたときの差し戻しが 1 回だけであることのテストがある
- [ ] T-027 の質問セットと検索方式(少なくとも esa-like と redmine-like)で、v3 と v4 を比べた結果がレポートにある。T-028 の `summary` の記述の有無も条件として分けている
- [ ] T-027 の 4 条件のうち条件 3 と 4 で、キーワードの保持率を `ask` の description の改訂の前後で比べた結果がレポートにある

## 判断が必要な点
- **新しい質問の書き手**: A: オーナー / B: v4 を書かない別のセッション・人が書き、計測前に固定する / C: v4 を書くセッション(T-022 と同じ手当てで)。v4 の改訂者が書くと、改訂で直る形の質問に寄りやすい
- **打ち切りを入れるか**: 所要時間の短縮と、表記ゆれの立て直しの損失の兼ね合い。計測の結果を見て決める(入れない判断もありうる)
- **合格ライン**: ここでは決めない(#20 の「最低ラインの置き場所」と T-008 で決める)
