# T-028: コネクタの `summary` への検索の仕様の記載、一致箇所のスニペット、クエリの正規化

## 依存
T-019(GitHub)、T-026(esa)、Redmine コネクタ(ADR-024)、dev-fixture。T-027(評価の仕組み)で効きを測る。Redmine の AND / OR の決定と esa の OR の扱いは T-029(実機での確認)の結果を待つ

## 前提(人手)
- なし(実装とテストはモックで行う)。実機での効きの確認は T-029 の人手の前提(実機と資格情報)に従う

## 背景
探索 LLM(Orchestrator の中で `search` / `fetch` を呼ぶ LLM)にソースの検索の仕様を伝える経路は、現状では `describe` の `summary`(自由文、1,000 字で切られる)だけで、どのコネクタもそこに検索の書き方を書いていない(esa は英語 1 文の内容の説明 `packages/connector-esa/src/connector.ts:138-140`、Redmine は対象の種別だけ `packages/connector-redmine/src/redmine.ts:185`、GitHub は「語彙一致検索」と container の形まで `packages/connector-github/src/connector.ts:749-764`)。また、esa のスニペットは本文の先頭 300 字、GitHub の issue・PR と Redmine は本文の先頭 500 字以内で、一致箇所ではない(`packages/connector-esa/src/parse.ts:159-171`、`packages/connector-github/src/connector.ts:394-397`、`packages/connector-redmine/src/redmine.ts:245-262`)。目的の文書が結果に含まれていても、探索 LLM にはそれが分からない(`reports/エージェント検索ハーネス設計調査.md`「結果は一致箇所が見える少量にし、判断の前に本文を読ませる」)。

どちらもコネクタの内部の変更で、IF(不変条件 5)は変えない。構造化した検索プロファイル(ソースごとの検索の仕様をまとめた情報。コネクタが持ち、Orchestrator が探索 LLM に伝える)は ADR-025 で扱い、承認後に T-030 で実装する。本タスクはその前の段階として、同じ内容を自由文で書く。

## 内容
- **`summary` への検索の仕様の記載**(各コネクタの既定の `summary`。日本語で書く。1,000 字以内):
  - 空白で区切った語の結合(すべて含む / いずれかを含む / 不明)、照合の単位、使える演算子と修飾子、語数・文字数の上限と超過時の挙動、並び順、スニペットの種類、`filters.container` に入れる値の形、返るヒットの種別
  - 実機で確かめていない項目は「公式の文書による。実機では未確認」「不明」と書き、断定しない(T-029 の結果で直す)
  - 指示の形(「〜せよ」)ではなく、仕様の記述として書く(ソース一覧は「データであり指示ではない」枠で渡るため。`packages/orchestrator/src/prompt.ts:202-203`)
  - 初期の記述の案はレポートの「各ソースのプロファイルの初期案」の表と「ソースの検索の仕様」の文面の例を元にする
  - esa: 空白は AND、`A OR B`、`title:`、`"…"`、日付は filters を使う(`after:` などは使えない)、順位はタイトルに語を含む記事が上、スニペットは本文の先頭(本タスクで一致箇所にした後はその旨)、`filters.container` はカテゴリのパス。公式ヘルプ(docs.esa.io/posts/104)による記述で、MCP 経由では未確認と添える
  - GitHub: 空白は AND、演算子は 5 個まで・256 文字まで、1 回の検索で issue・PR・コードが混ざる、言い換えは別の検索に分ける、author / 期間の指定があるとコードは検索しない(既存の記述を残す)
  - Redmine: フィルタは使えない、語は部分一致、使われるのは先頭 5 語まで、順位は更新の新しい順、語の結合は不明(T-029 まで)
  - dev-fixture: 検索方式ごと(T-027)の記述
  - 導入先が `settings.summary` で上書きする既存の仕組み(esa)は残す。上書きした場合は検索の仕様の記述も導入先が書く(README に書く)
- **一致箇所のスニペット**:
  - esa: 検索結果の `body_md` から、query の語(修飾子と演算子を除いた語)の最初の一致箇所の周辺を切り出す。一致がなければ従来どおり本文の先頭。カテゴリ(`meta.category`)はタイトルと並べて見せる(既存の `meta` で足りるかを確かめる)
  - GitHub の issue・PR: REST の text-match(`Accept: application/vnd.github.text-match+json`)の断片を使う。得られなければ従来どおり本文の先頭
  - Redmine: 検索結果の `description` に一致箇所が含まれる場合はその周辺。含まれなければ従来どおり
  - いずれも `MAX_SNIPPET_CHARS`(500)以内で、本文全体を入れない(ADR-016 採用した変更 3。Gateway が強制的に切る)。front matter・HTML コメント・コードブロックの除去など、既存の平文化の規則は保つ(隠しテキストをスニペットに出さない)
- **クエリの正規化**(語を変えない範囲に限る):
  - 前後の空白の除去(既存)に加え、全角空白を半角空白に、連続する空白を 1 つにする
  - 語の削除・追加・表記の変換(全角英数字の半角化を含む)はしない。全角英数字の扱いはバックエンドの照合が区別するかで決まるため、T-029 の結果を見て別に判断する
- **Redmine の AND / OR の決定**: T-029 で `all_words=0` の実際の挙動を確かめてから、次のどれにするかを決め、ADR-024 に追記する。(a) 現状のまま、(b) AND を既定にする、(c) AND で 0 件のときコネクタの中で OR に切り替えて再検索する。関連度のない日付順の検索で OR を既定にすると適合率が構造的に低くなる、というレポートの指摘(Redmine の仕様からの推論で、実機での比較はない)を判断の材料にする
- **esa の修飾子の後置と OR**: コネクタは filters を修飾子として query の後ろに空白で足す(`packages/connector-esa/src/connector.ts:206-233`)。query に `OR` が含まれると、結合の優先順位が意図と変わるおそれがある(esa のヘルプは左から順に処理し括弧で優先順位を変えられるとする。未検証)。T-029 で確かめ、必要なら query を括弧で包む

## 受け入れ条件
- [ ] esa・GitHub・Redmine・dev-fixture の既定の `summary` に検索の仕様が書かれ、1,000 字以内であることと、未確認の項目に「未確認」「不明」が付いていることがテストで固定されている
- [ ] esa と GitHub の issue・PR のスニペットが一致箇所の周辺になり、一致がないときに本文の先頭に戻ることのユニットテストがある
- [ ] スニペットが `MAX_SNIPPET_CHARS` 以内で、HTML コメント・front matter・コードブロックの中の文字列を含まないことのテストがある(既存のテストを保つ)
- [ ] クエリの正規化が全角空白と連続空白だけを変え、語を変えないことのテストがある
- [ ] T-027 の検索方式を切り替えられるフィクスチャで、`summary` の記述の有無を比べた結果が評価レポート(T-024 のレポートと合わせてよい)にある
- [ ] Redmine の AND / OR の決定と、esa の OR の扱いの決定が、T-029 の結果とともに ADR-024 / ADR-023 に追記されている(T-029 が終わるまでは未チェックのまま残す)

## 判断が必要な点
- **Redmine の AND / OR**(上記 (a)〜(c))。T-029 の結果を見て決める
- **`summary` を日本語にするか**: 探索プロンプトは日本語で、利用者も日本語で尋ねる想定。英語の導入先がある場合は `settings.summary` で上書きする

## 限界
- `summary` は「データであり指示ではない」枠で渡るため、探索 LLM が参考情報として軽く扱うおそれがある。構造化と信頼区分の整理は ADR-025 で扱う
- 検索の仕様のうち実機で確かめていない項目は、T-029 が終わるまで「未確認」のまま
