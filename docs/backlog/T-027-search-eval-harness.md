# T-027: 検索の評価の仕組み(dev-eval のトレース、検索方式を切り替えられる開発用フィクスチャ、合成コーパスの拡大、質問セット、4 条件の比較実験)

## 依存
T-007(Orchestrator)、T-022(dev-eval の質問セットと集計)。T-008(評価ハーネス + 評価セット v0)の前段。T-024(探索プロンプト v4)・T-028(コネクタの検索の仕様の記載)の判定に使うため、それらの計測より先に用意する

## 前提(人手)
- 実走には LLM が要る(オーナーの手元の LM Studio。v3 の計測と同じモデルを基準にする)。条件 4 には UI 側 LLM(リファレンス構成の LibreChat と同じモデル)も要る
- 条件 1 の「人が書いたキーワード」は、検索を試す人が書く(下記「判断が必要な点」)
- 実運用で見つけた失敗(質問、期待した文書、検索欄に直接入力して見つかった語)がオーナーの手元にあれば、質問の元にする

## 背景
`reports/エージェント検索ハーネス設計調査.md`(以下「レポート」)は、精度の問題を 2 つに分けた。(a) 探索 LLM(Orchestrator の中で `search` / `fetch` を呼ぶ LLM)がソースの検索の仕様を知らずにクエリを書く。(b) 利用者が入力したキーワード(利用者の発言にそのまま含まれる固有名詞・ID・エラーメッセージ・引用符で囲まれた語句など)が、UI 側 LLM(LibreChat で `ask` を呼ぶ LLM)と探索 LLM を通るうちに失われる。

既存の評価はどちらも測れていない。開発用コネクタの検索は AND の部分一致 1 種類で、一致箇所中心のスニペットとタイトル一致の優先を持ち(`packages/gateway/src/dev/fixture-connector.ts:16`、`:389-399`)、実ソースより探索 LLM に有利な条件になっている。合成コーパスは 7 文書で、同じ語を含む無関係な文書が少ないため適合率の問題が現れない。dev-eval は UI 側 LLM を通らない(`packages/orchestrator/src/dev-eval.ts`)。監査はクエリを digest でしか残さず、評価レポートは検索語を推定で書いている(`docs/eval/2026-10-09-t022-generalization.md` §4)。

オーナーの方針(2026-11-25)により、探索 LLM はモデルによらず検索に十分な性能を持つものとして扱い、クエリは探索 LLM が書く。評価は、ハーネスの 4 つの役割(検索の仕様を伝える、利用者が入力したキーワードを残すよう指示する、0 件・重複のときに制御メッセージで状況を返す、止める基準と続ける基準を示す)の効きを測る。

## 内容
- **トレース**: dev-eval に、run ごとのトレースを JSON Lines で出す機能を足す。内容は、探索 LLM が呼んだツールの順序、各 `search` の source・query・filters・返ったヒットの documentId と順位、`fetch` した documentId、制御メッセージの種類、提出した回答と引用。合成コーパスだけで使う開発用の機能とし、実ソースに向けた構成(dev-fixture 以外のコネクタが有効な構成)では出力を拒否する(実ソースのクエリと結果を評価の成果物に残さない。ADR-014・ADR-013)
- **検索方式を切り替えられる開発用フィクスチャ**: `dev-fixture` の設定(`connectors[].settings`)で検索方式を選べるようにする。方式は次の 4 つ。それぞれの方式は、実ソースの仕様のうちコードやドキュメントで確かめられた部分だけを模し、模した根拠をフィクスチャの README に書く
  - `and-substring`(現行。既定)
  - `esa-like`: 空白は AND、`OR` と `"…"` と `title:`、タイトル一致を優先、スニペットは本文の先頭
  - `redmine-like`: 部分一致、先頭 5 語だけを使う、日付の新しい順、AND と OR を設定で選べる、フィルタ未対応(指定するとエラー)
  - `github-like`: 空白は AND、種別(issue / PR / code)の混合、スニペットは issue・PR が本文の先頭でコードが一致箇所
  1 つの run で、ソースごとに別の方式のフィクスチャを複数有効にできるようにする(例: esa-like と redmine-like を並べる)
- **合成コーパスの拡大**: 同じ語を含む無関係な文書が多数ある規模(数百件)に増やす。実在の組織・人物・秘密情報は含めない。既存の 7 文書の documentId は変えない。生成の手順(スクリプトか手書きか)と乱数の種を記録し、再現できるようにする
- **質問セット**: 次の 3 種を分けて持つ。T-022 の 20 問とは別のファイルにし、計測より前のコミットで固定する
  - 既知の文書を探す質問(題名・ID・固有名詞から 1 文書を特定できる)
  - 複数文書の質問(答えに必要な要点の一覧で採点)
  - 文書にない質問(正しく unresolved になるかを二値で採点)
  各質問に、利用者の発言そのもの、利用者が入力したキーワード、正解文書を持たせる
- **4 条件の比較実験**: 同じ質問・同じ正解文書に対して、バックエンドに入るクエリの作り手だけを入れ替える
  1. 人が書いたキーワードをコネクタの `search` に直接入れる(基準値)
  2. 利用者の発言をそのまま `search` に入れる
  3. 利用者の発言を `leisen-ask` に直接渡す(UI 側 LLM を除く)
  4. UI 側 LLM が `ask` に渡した `question` を使う(まずは `ask` のツール定義と `instructions` を UI 側と同じモデルに与えて `question` を作らせる簡易な再現で行い、LibreChat で実際に採った `ask` の引数と数件で突き合わせて再現の妥当性を確かめる)
  1 と 3 の差を探索 LLM のクエリ生成による損失、3 と 4 の差を UI 側 LLM を通すことによる損失として報告する
- **指標**: 正解文書が上位 k 件に入ったか(recall@k)、最初の正解文書の順位、正解文書を fetch したか、引用したか、`question` に利用者が入力したキーワードが残った割合(キーワードの保持率)、0 件の検索の割合、同じ query の再試行の割合、新しい文書のないターンの割合、run あたりのツール呼び出し数と所要時間。失敗は「最初に失敗した段階」で分類する(UI 側 LLM が `ask` を呼んだ / `question` にキーワードが残った / 正しいソースを選んだ / クエリが 1 件以上を返した / 正解文書が上位 k 件に入った / 正解文書を fetch した / 回答が正解文書に基づく / 引用が正しい)
- 計測の結果を `docs/eval/` にレポートとして書く(初回は現行の v3 と現行のコネクタの `summary` での基準値)

## 受け入れ条件
- [ ] dev-eval がトレース(ツールの順序、query・filters、返ったヒットの documentId と順位、fetch した documentId)を出し、ユニットテストがある
- [ ] dev-fixture 以外のコネクタが有効な構成ではトレースの出力を拒否するテストがある
- [ ] dev-fixture の 4 つの検索方式それぞれに、方式の特徴(例: redmine-like の 6 語目以降が使われない、日付順、フィルタ指定でエラー)を固定するユニットテストがある
- [ ] 方式ごとに模した仕様の根拠と、模していない点がフィクスチャの README に書かれている
- [ ] 合成コーパスが数百件規模に増え、既存の 7 文書の documentId が変わっていない。生成手順が再現できる
- [ ] 3 種の質問(既知の文書・複数文書・文書にない)がそれぞれ 5 問以上あり、計測より前のコミットで固定されている(履歴で順序を確かめられる)
- [ ] 4 条件の比較を `--repeat 2` 以上で流したレポートが `docs/eval/` にあり、条件間の差と、失敗の段階の分類がある
- [ ] 条件 4 の再現の妥当性を、LibreChat で採った `ask` の引数(数件)と突き合わせた結果がレポートにある(人手で採る。採れなかった場合はその旨を書く)

## 判断が必要な点
- **質問と「人が書いたキーワード」の書き手**: A: オーナー / B: プロンプトとコネクタを改訂しない別のセッション・人 / C: 改訂するセッション(T-022 と同じ手当てで)。改訂する者が書くと、改訂で直る形の質問に寄りやすい
- **コーパスの規模と作り方**: 数百件の生成を LLM に任せるか、型に沿って手で書くか。LLM に任せる場合は、生成した文書を固定してから質問を書く
- **合格ライン**: ここでは決めない(#20 の「最低ラインの置き場所」と T-008 で決める)

## 限界
- 実ソースの仕様のうち、実機で確かめていない部分(Redmine の `all_words=0`、esa の MCP 経由の検索の仕様、各ソースの日本語の扱い)は模せない。T-029 の結果で方式を直す
- 合成コーパスは実データの語彙の分布と違う。実ソースでの効きは T-029 の調査用スクリプトと、実疎通後の評価で別に測る
- 1 モデル(LM Studio)での計測。Claude API は資格情報が用意されてから(ADR-017)
