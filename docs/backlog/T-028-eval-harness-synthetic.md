# T-028: 評価ハーネス(合成コーパスでの実験環境。ADR-026 決定 8)

## 依存
T-027(エージェント定義の識別子とファイルからの読み込み)、T-022(dev-eval と質問セット)。T-008(実データの評価)と T-024(探索プロンプト v4)の前段

## 前提(人手)
- ADR-026 が Accepted になっていること(「人間に確認してほしい点」6: 実験環境をこの ADR に含めるか)
- 実走には LLM が要る(オーナーの手元の LM Studio。T-022 の計測と同じモデルを基準にする)
- 採用の条件を決める(下記「判断が必要な点」)

## 背景
dev-eval は `leisen-ask` を子プロセスで起動し、試行ごとに合否を 1 つ返して Markdown の表にする。失敗の原因を調べる記録がなく、T-022 では不合格の原因を推定で分類した。試せる単位は質問セット全体だけで、1 run に約 1 分かかる。

公開されている Eval 実装(SWE-bench、HumanEval、Aider、IFEval、BFCL、τ-bench、SimpleQA、AlpacaEval / MT-Bench、Zed)の調査(2026-11-23)に照らすと、次の点が足りない。

| 足りない点 | 参考にした実装 |
|---|---|
| 判定の結果が合否 1 つしかない | Zed の個別のアサーション、Aider の編集形式の遵守率 |
| 質問の期待値に「してはいけないこと」がない | SWE-bench の FAIL_TO_PASS と PASS_TO_PASS |
| 「答えなかった」と「間違えた」を区別していない | SimpleQA の 3 値の採点 |
| 集計の式が決まっていない | τ-bench の pass^k |
| 失敗を下の層のテストへ移す手順がない | Zed の 3 つの層 |

用語(検査、試行、実験環境)は ADR-026「用語」の定義に従う。

## 内容

### 評価ハーネスの本体
- 非公開の別パッケージ(`packages/eval`)。dev-eval の判定と集計(`packages/orchestrator/src/dev-eval.ts`)をここへ移し、`leisen-ask` の子プロセス起動をやめる
- Gateway を同一プロセスで起動し、開発用コネクタ(合成コーパス)だけを接続する。外部の Gateway の URL は受け取らない。テストの `packages/orchestrator/test/helpers/harness.ts` と同じ構成を使う
- エージェント定義 × 質問 × 試行回数の組み合わせを実行する。保存済みの試行は再実行しない(中断後の再開)。並行数を指定できる(ローカルのモデルでは 1)
- 候補のエージェント定義をファイルから読み込む
- 入力に含まれる日付を固定する

### トレース
- ランタイムのコールバック(ADR-026 決定 8)を実装し、試行ごとにトレースをファイルに保存する
- トレースにトークン・資格情報・`AuthContext` が入らないことをテストで固定する

### 検査
検査は名前と種類を持ち、トレースと期待値だけから合否を返す。

| 種類 | 最初に用意する検査 |
|---|---|
| 形式 | 催促なしで提出した / 引数が壊れた呼び出しがない / 検証で落ちた出典がない / 無害化での除去がない / 上限に達していない |
| 達成 | 期待した outcome だった / 期待した文書を引用した(どれか 1 つ、すべて)/ 回答が期待する語を含む |
| 禁止 | 回答本文に URL が残っていない / 引用してはいけない文書を引用していない / 文書にない質問に答えていない / 回答が含んではいけない語を含まない |

- 達成の検査のうち文書に関するものは、段階ごとに分ける: 正解の文書が検索でヒットした / fetch された / 引用された
- 試行の結果は 4 値にする: 正解 / 誤答 / 回答せず(resolved を期待した質問に unresolved で答えた)/ エラー(環境に由来する失敗)
- 保存済みのトレースを、検査だけ実行し直して判定し直すコマンドを用意する
- LLM による採点は扱わない

### 質問の形式と合成コーパス
- 質問ごとに、達成の期待値と禁止の期待値の両方を書ける形式にする(引用してはいけない文書、回答が含んではいけない語)。既存の 20 問の ID と期待値は変えず、禁止の期待値を足す場合は計測の前に別のコミットで固定する
- 質問セットに役割を持たせる: 改善を測るための質問(ホールドアウト)と、回帰を確かめるための質問
- 答えが 1 つに定まらない質問は、定まる形に書き直すか、質問セットから外す(T-022 の multi-newcomer-vpn の注記を参照)。書き直した質問は新しい ID にする
- 禁止の検査のために、合成コーパスに文書を足す: 正解に似ているが誤りの文書、古い内容の文書(RS-6)、指示を埋め込んだ文書(RS-3 / RS-4)、質問者の権限では見えない文書(RS-1)

### 集計と比較
- 試行結果を JSONL に追記する。記録する項目は ADR-026 決定 8 の表のとおり(エージェント定義の識別子、質問の ID、モデル、試行回、コーパスと質問セットのハッシュ、ランタイムのコミット、`tools/list` のハッシュ、検査の集合の版、集計の式の名前)
- 集計: 検査の種類ごとの通過率、質問ごとの pass^k(k 回すべて合格する確率。試行回数 n から推定する)、4 値の内訳、ターン数・ツール呼び出し数・トークン数・所要時間。式はコードで固定する
- 比較: 2 つのエージェント定義の試行結果を、質問ごと・検査の種類ごとに対比する。記録した版が一致しない結果どうしは、比較を拒否するか、一致しない項目を明示する

### 確率的テスト(ターン単位の評価)
- トレースから、探索の途中の状態(質問、ソース一覧、そこまでのツール呼び出しと結果)を取り出して保存する
- 保存した状態を、指定したエージェント定義の文言で組み立て直し、LLM に 1 ターンだけ応答させて検査する。検索語の検査は、返ってきた語でコーパスを検索して確かめる
- T-022 の不合格(2 つ目のヒットを fetch せずに打ち切った)を、最初の確率的テストにする

### 手順の文書化
- 広い評価で見つけた失敗を、原因によって確率的テストか決定的テスト(`ScriptedLlmClient`)に移す手順を、`packages/eval/README.md` に書く
- エージェント定義を変更する PR、既定の対応表を変更する PR に添付する評価レポートの作り方を書く(T-008 の受け入れ条件 3 の前段)

## 受け入れ条件
- [ ] 評価ハーネスが、外部の Gateway を起動せずに、質問セットを指定したエージェント定義で実行できる
- [ ] 同梱の v3 を既存の 20 問で実行した結果が、T-022 の計測と同じ判定基準で再現できる(合格の定義を変えた場合は、新旧の対応をレポートに書く)
- [ ] 試行結果に、検査ごとの結果と、ADR-026 決定 8 の表の項目がすべて記録されている
- [ ] 形式の検査が、warnings の文言ではなくトレースのイベントから計算されている
- [ ] resolved を期待した質問で、「回答せず」と「誤答」が区別されて集計される
- [ ] 質問セットに、引用してはいけない文書を持つ質問、指示を埋め込んだ文書に当たる質問、古い内容の文書に当たる質問が、それぞれ 2 問以上ある
- [ ] pass^k の推定がユニットテストされている(n 回中 c 回合格のときの値)
- [ ] 保存済みのトレースから、LLM を呼ばずに判定し直せる
- [ ] 確率的テストが 1 件以上あり、同じ状態からの 1 ターンを指定した回数だけ実行して通過率を出せる
- [ ] 評価ハーネスが開発用コネクタ以外を接続できないこと、トレースに秘密情報が入らないことがテストされている
- [ ] 実行環境の CLI が、評価ハーネスのパッケージとトレースのコールバックに依存していない(`npm run lint:imports` に検査を足す)
- [ ] 失敗を下の層へ移す手順と、評価レポートの作り方が README にある

## 判断が必要な点
- **採用の条件**: 案は「禁止の検査は全試行で通ることを条件にし、達成の検査は現在の既定との比較で判断する」。T-022・T-024 で未決の合格ライン(issue #20)と合わせて決める
- **試行回数**: 案は、質問セット全体で k = 3〜5、回数が要る振る舞いは確率的テストで測る。手元のモデルで 20 問を 5 回ずつ流すと約 1.5 時間かかる(1 run の中央値 52 秒)
- **禁止の期待値と足す文書の書き手**: T-022・T-024 と同じ論点(エージェント定義を書くセッションが書くと、通りやすい形に寄る)
- **サンプリングの設定**: 現在は temperature・seed を送っていない。評価のときだけ固定するか、既定のまま回数で測るか

## 限界
- 合成コーパスと開発用コネクタ(AND の部分一致)での評価。実ソースでの効きは T-008 / T-025 で測る
- 確率的テストは、途中までの履歴が別のエージェント定義で生成されたものになる。採用の判断には使わない
- 権限外の文書の検査は、合成コーパスでの確認にとどまる。実際の権限境界の合否判定は T-008(テストアイデンティティが要る)
- LM Studio 側のサンプリングの設定と量子化は記録できない。同じモデル名でも条件が同一とは限らない
