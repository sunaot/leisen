# ADR-026: Orchestrator のランタイムとエージェント定義の分離(既定と固定、実験環境)

Status: Proposed(人間レビュー待ち)/ Date: 2026-11-16 / 改訂: 2026-11-26(番号を ADR-023 から ADR-026 に変更。main で ADR-023〜025 が先に使われたため。決定 8 を、公開されている Eval 実装の調査に照らして改訂: 検査、評価の 3 つの層、試行結果に記録する版)

置き換える決定(Accepted になり、実装されてから効力を持つ):
- ADR-017 決定4 のうち、プロンプトの置き場所(`packages/orchestrator/prompts/`)と版の識別(`EXPLORE_PROMPT_VERSION`)。system prompt を固定部だけにすること、ソース一覧を最初の user ターンに置くこと、文言の変更に評価レポートを添付することは引き継ぐ

ADR-017 は全体としては Proposed のままである。

## 用語

この ADR で導入する語を定義する。

| 用語 | 定義 |
|---|---|
| エージェント定義 | 1 種類のエージェントの挙動を決める一式。LLM に渡す自作の文言、ループの上限、提出物の検証規則の種類を含む。データだけで構成し、コードを含まない。名前と内容のハッシュで識別する |
| ランタイム | エージェント定義を読み込んで探索ループを実行する Orchestrator の部分。不変条件に関わる処理を持ち、エージェント定義によって変わらない |
| 試行 | 1 つの質問を、1 つのエージェント定義・コーパス・モデルの組み合わせで 1 回実行すること。評価結果の最小の記録単位 |
| 検査 | 試行の結果を判定する最小の単位。名前と種類(形式・達成・禁止)を持ち、トレースと期待値から合否を 1 つ返す |
| 実験環境 | エージェント定義の候補を評価するための環境。合成コーパスだけを対象とする |
| 実行環境 | 利用者に回答を提供する環境。`leisen-ask` と `leisen-ask serve` |

「探索」は従来どおり、LLM がツールを繰り返し呼ぶ処理(探索ループ)だけを指す。プロンプトの試行錯誤は「実験」と呼ぶ。

## 文脈

探索プロンプトの調整(T-022、T-024)を進める中で、次の問題が明らかになった。

**LLM に渡す文言が 5 か所に分かれており、バージョン名がその一部しか指していない。** `EXPLORE_PROMPT_VERSION`(現在 `explore.v3`)が指すのは 1 つ目だけである。

| 場所 | 内容 |
|---|---|
| `packages/orchestrator/prompts/explore.v3.md` | system prompt の固定部 |
| `packages/orchestrator/src/prompt.ts` | 催促、最終ターンの指示、データの前置き、上限の通知 |
| `packages/orchestrator/src/tools.ts` | `USAGE_HINTS`(ツールの使い方の指針) |
| `packages/orchestrator/src/answer.ts` | `submit_answer` の説明 |
| `packages/gateway/src/proxy/tools.ts` | Gateway が返すツールの説明 |

**バージョンの切り替えにコードの編集が要る。** `EXPLORE_PROMPT_VERSION` は定数で、`leisen-ask` にも dev-eval にも切り替える手段がない。T-024 は「v3 のコミットで dev-eval を流すか、開発用に版を指定する手段を足す」としている。

**失敗の原因を調べる記録がない。** 監査ログは検索語をハッシュでしか残さない。T-022 の評価レポートは、不合格の原因を「語は推定できない」としたうえで推定で分類している。監査ログが検索語を隠すのは設計どおりであり、調査用の記録は別に要る。

**導入企業が動作を固定する手段がない。** プロンプトを改訂すると、アップグレードした全導入先の挙動が変わる。精度を優先する導入先には最良のものを既定で提供したいが、動作の変更に社内の承認が要る導入先は、特定のバージョンに固定できる必要がある(2026-11-16 オーナーの方針)。

**検索以外のエージェントを今後開発する。** 取得した情報を加工するエージェントを予定している。検索のための文言と検証規則が `Orchestrator` クラスに直接書かれた現在の構造では、種類の違うエージェントを同じ仕組みで動かせない。

## 決定

### 1. Orchestrator をランタイムとエージェント定義に分ける

```
実験環境(合成コーパス、トレースあり、候補のファイルを読める)
  評価ハーネス ─→ ランタイム + エージェント定義(候補)─→ 判定 ─→ 試行結果
        │
        │ 採用を決めたエージェント定義をリリースに同梱
        ▼
実行環境(実データ、トレースなし、同梱の定義だけ)
  ランタイム + エージェント定義 ──→ Gateway ──→ コネクタ
```

実験環境と実行環境は、同じランタイムのコードを使う。実験環境の結果が実行環境で成り立つための条件である。

### 2. エージェント定義に入れるもの

エージェント定義はデータだけで構成する。コードは入れない。

| 項目 | 現在の場所 |
|---|---|
| 名前、形式のバージョン、対象とするモデルの系統 | (新設) |
| system prompt の固定部 | `prompts/explore.v3.md` |
| 制御メッセージ(上限の通知、催促、最終ターンの指示) | `src/prompt.ts` |
| LLM に渡すツールの説明(`search` / `fetch` / `list` / `describe`) | Gateway の説明に `USAGE_HINTS` を連結 |
| 提出用ツールの説明 | `src/answer.ts` |
| ループの上限(`maxIterations`、`maxToolCallsPerTurn`、`maxToolCallsPerRun`、`maxTokensPerTurn`) | `orchestratorSettingsSchema` |
| 提出物の検証規則の種類 | (新設。当面は「run 内で受け取った文書に限る出典の検証」の 1 種類) |

LLM に渡すツールの説明は、エージェント定義の文言だけを使う。Gateway の説明は連結しない。Gateway の説明は、Orchestrator を通さずに接続する MCP クライアントのためのものとする。これにより、Gateway の説明を変更しても、Orchestrator 経由の挙動は変わらない。ツールの引数の形は Gateway の `tools/list` の値をそのまま使う(コネクタのツール IF は変更しない。不変条件 5)。

ループの上限は、`deployment.yaml` の値(`orchestrator.maxIterations`)を上限として扱い、エージェント定義の値がそれを超える場合は `deployment.yaml` の値を使う。`deployment.yaml` の上限は費用と API 呼び出しの増幅を抑えるためのもの(TM-D3)であり、エージェント定義で緩められてはならないためである。`costLimitPerQuery`、`runTimeoutMs`、`finalTurnTimeoutMs`、`pricing` は従来どおり導入先の設定とする。

モデル ID と effort はエージェント定義に入れず、従来どおり LLM バックエンドの設定に置く。エージェント定義は、対象とするモデルの系統だけを持つ。

### 3. ランタイムに固定するもの

次の処理はランタイムが持ち、エージェント定義では変更も無効化もできない。

- run API への開始・終了の申告と fail-closed(ADR-019)
- すべてのツール呼び出しを Gateway 経由にすること(不変条件 2)
- Gateway が認証した利用者との照合(`user_mismatch`)
- ソース一覧・ツール結果・ツールエラーを「固定の前置き」と「データ本体の JSON」に分けて渡す構造と、その前置きの文言(セキュリティレビュー 2026-09-27 H3)
- `permission_denied` と `not_found` を区別せずに LLM に渡すこと(TM-B2)
- 提出物の検証規則の実装。エージェント定義は種類を選ぶだけで、検証なしは選べない
- 回答本文の無害化(`src/sanitize.ts`)
- 時間・費用・ツール呼び出し件数の上限の強制と、上限を超えた呼び出しに返す固定の文言
- 利用者に見せる文言(出典がない場合の注意、失敗の文言)

### 4. 識別と置き場所

エージェント定義は `<名前>@sha256:<ハッシュ>` で識別する。ハッシュは、LLM の挙動に影響する内容の全体を正規化した値から計算する。

置き場所は `packages/orchestrator/definitions/` とし、`prompts/` は廃止する。現在の v3 は、LLM に渡る内容が 1 バイトも変わらない形でエージェント定義に移す。文言を固定している既存のテストは、移行後もそのまま通す。v2 は移さない。

### 5. 既定と固定

`deployment.yaml` で、同梱されたエージェント定義から選ぶ。

```yaml
orchestrator:
  agents:
    search:
      definition: default                  # 既定
      # definition: explore.v3@sha256:…    # 固定
```

| | 既定 | 固定 |
|---|---|---|
| 使われる定義 | そのリリースで最良と評価されたもの | 指定したもの |
| アップグレード時 | 変わりうる | 変わらない |

既定は、リリースに同梱する対応表(モデルの系統 → エージェント定義)で決める。最良の文言はモデルによって違うためである(ADR-017 決定4 はバックエンド別の派生を認めている)。どの系統にも当てはまらないモデルには、対応表の「その他」の行を使う。起動ログには、決まったエージェント定義の識別子を 1 行出す。

次の場合は起動を拒否する。既定への切り替えは行わない。黙って切り替えると、固定したという前提が崩れるためである。

- 指定した名前のエージェント定義が同梱されていない
- 同梱された内容のハッシュが、指定と一致しない
- エージェント定義の形式のバージョンに、ランタイムが対応していない
- 指定したエージェント定義が、取り下げの一覧に入っている

実行環境の CLI(`leisen-ask`、`leisen-ask serve`)は、同梱されたエージェント定義だけを使う。任意のファイルから読み込む手段は持たない。したがってエージェント定義は ADR-005 のプラグイン境界ではなく、不変条件 8 の「3 つのプラグイン境界」は変わらない。

固定が保証するのはエージェント定義の同一性だけである。モデル、ランタイム、ソース側の検索の挙動は、固定の対象に含まれない。ランタイムのセキュリティ修正は、固定している導入先にも適用する。この範囲は運用者向けの文書に明記する。

### 6. 既定の変更と過去のエージェント定義の扱い

既定の対応表を変更する PR には、評価レポートを添付する。プロンプト変更の PR に対する現在の規則を、対応表の変更に広げる。

過去のエージェント定義は、リリースに残す。残したエージェント定義には、形式の検証と脚本テスト(`ScriptedLlmClient`)での動作確認を行う。精度は再計測しない。

エージェント定義に問題が見つかった場合(例: インジェクションへの防御の文言の不備)に備えて、リリースに取り下げの一覧を持つ。

### 7. どのエージェント定義で動いたかを AnswerRun に記録する

Orchestrator は `POST /runs` で、エージェント定義の識別子を申告する。Gateway は形式だけを検証し、pending の AnswerRun に記録する。

- `answerRunRecordSchema` に `agentDefinition`(識別子の文字列。`null` 可)を足す。この項目を持たない過去のレコードは `null` として読む
- 値は Orchestrator の申告であり、Gateway は内容を検証できない(`iteration` と同じ扱い)
- 識別子は名前とハッシュだけで、利用者・質問・ソースに由来する情報を含まない

これにより、導入企業はいつ・どのエージェント定義で動いていたかを監査ログから示せる。昇格判定レポートでの定義ごとの集計は、後続のタスクとする。

### 8. 実験環境

評価ハーネスを、非公開の別パッケージに置く。dev-eval の判定と集計はそこに移す。評価ハーネスは実行環境にない機能を 2 つ持つ。

**候補のエージェント定義をファイルから読み込む。** 同梱前の候補を試すためである。

**トレースを保存する。** ランタイムは、探索の経過を通知する任意のコールバックを、ライブラリの API として持つ。実行環境の CLI はこのコールバックを指定しない。通知する内容は次のとおりとする。

- 各ターンの要求と応答、ツール呼び出しの引数と結果、所要時間
- ランタイムがモデルの出力の乱れを吸収した事象: 提出の催促、引数が壊れた呼び出し、検証で落ちた出典、無害化での除去、上限への到達と実行しなかった呼び出し

後者を含めるのは、形式の検査(下記)を warnings の文言ではなくイベントから計算するためである。

トレースには検索語と文書の本文が入るため、次の制限を置く。

- 評価ハーネスは、Gateway を同一プロセスで起動し、開発用コネクタ(合成コーパス)だけを接続する。外部の Gateway の URL は受け取らない
- コールバックに渡す内容には、トークン・資格情報・`AuthContext` を含めない(不変条件 6)
- 実データを対象とするトレース(T-008、T-025)は、この ADR では認めない。別の ADR で決める

評価ハーネスの試行も、Gateway と監査を通る(不変条件 2)。同じ経路を通すことで、実行環境との差を作らない。

**判定は検査の集合として定義する。** 試行ごとに合否を 1 つだけ返す形にはしない。検査は種類を持ち、検査ごとの結果を試行結果に記録する。

| 検査の種類 | 意味 | 検索エージェントでの例 |
|---|---|---|
| 形式 | 出力がランタイムの求める形を守ったか | 催促なしで提出した、ツールの引数が壊れていない、出典が検証で落ちていない |
| 達成 | その質問で達成すべきこと | 期待した文書を引用した、期待した outcome だった |
| 禁止 | その質問でしてはいけないこと | 回答本文に URL が残る、無関係な文書を引用する、文書にない内容を答える、権限外の文書を引用する |

検査はトレースと期待値だけから結果を出す。LLM と Gateway を呼ばない(LLM による採点を行う検査は例外とし、採点に使ったモデルを記録する)。これにより、検査を改訂したときに、保存済みのトレースを判定し直せる。検索と加工の違いは、検査の集合の違いとして扱う。

環境に由来する失敗(LLM・Gateway の障害、タイムアウト)は、検査の不合格と区別して記録する。

**試行結果はデータとして保存し、比較レポートはそこから生成する。** 試行結果には、試行を特定する値と、結果の比較ができるかを判断するための版を記録する。

| 記録するもの | 理由 |
|---|---|
| エージェント定義の識別子、質問の ID、モデル、試行回 | 試行を特定する |
| コーパスのハッシュ、質問セットのハッシュ | 質問や文書を変えた前後の結果を混ぜない |
| ランタイムのコミット | ランタイムの変更による差を切り分ける |
| Gateway の `tools/list` のハッシュ | ツールの引数の形が変わると結果が変わる |
| 検査の集合の版、集計の式の名前 | 判定と集計を変えた前後の結果を混ぜない |

入力に含まれる日付は固定する。

**評価は 3 つの層で行い、上の層で見つけた失敗を下の層のテストにする。**

```
広い評価(実モデル。質問セット全体を run 単位で実行する)
   │ トレースを読んで、失敗の原因を特定する
   ├─ モデルの出力が原因 ─→ 確率的テスト(実モデル。ターン単位で、同じ状態から多数回実行する)
   └─ 実装が原因 ─────────→ 決定的テスト(モデルなし。ScriptedLlmClient による脚本テスト)
```

エージェント定義を採用するかの判断は、広い評価で行う。確率的テストは、途中までの履歴が別のエージェント定義で生成されたものになるため、個別の振る舞いの回帰確認に使う。

質問の形式、集計の式、採用の条件は、この ADR では決めない。評価ハーネスのタスク(T-028)で決める。

### 9. この ADR の対象外

- 加工のエージェント。書き込みの有無、成果物の保存、検索との連結は未決であり、別の ADR で決める
- 導入企業が自作したエージェント定義の読み込み
- エージェント定義にコードを含めること。探索ループの構造を変える場合は、ランタイムに方式を足し、エージェント定義からそれを選ぶ
- プロンプトの自動最適化

## 理由

- 1・2: LLM の挙動を決める入力を 1 つの単位にまとめないと、評価結果がどの入力に対するものかを特定できない。データだけに限るのは、コードを含めるとランタイムの内部の関数やデータ構造まで互換性の対象になり、ランタイムを変更しにくくなるためである
- 2(ツールの説明): Gateway の説明を連結したままでは、Gateway のアップグレードで固定した導入先の挙動が変わる
- 3: エージェント定義は頻繁に差し替える。差し替えのたびに不変条件の確認をやり直さずに済むよう、不変条件に関わる処理はエージェント定義から到達できない場所に置く
- 5: 既定と固定の両方を持つのは、精度を優先する導入先と、動作の変更を管理したい導入先の両方に応えるためである。同梱されたものからの選択に限ることで、個社差分を `deployment.yaml` の中に収める(不変条件 8)
- 7: 固定の機能は、実際にどの定義で動いたかを後から確かめられなければ、導入企業にとって証明にならない
- 8: 文言の差し替えとトレースを実行環境の CLI に持たせると、本番で誤って有効になる経路ができる。別パッケージに置けば、実行環境からは構造上使えない
- 8(検査): 合否を 1 つにまとめると、失敗が出力の形式によるものか、内容によるものか、してはいけないことをしたのかを区別できない。区別できないと、文言で直すのか、ランタイムのコードで吸収するのかを決められない。公開されている Eval 実装(SWE-bench の FAIL_TO_PASS と PASS_TO_PASS、Aider の編集形式の遵守率、Zed の個別のアサーション)も、この区別を記録している
- 8(3 つの層): 層を試行の大きさではなく失敗の原因で分けると、失敗を見つけたあとの手順が決まる(Zed の構成)。決定的テストはすでにあり、評価の構造に含めていなかっただけである

## 帰結

- `deployment.yaml` のスキーマ(`orchestrator` セクション)、監査スキーマ(`answerRunRecordSchema`)、run API(`POST /runs` の本文)が変わる
- `Orchestrator` の `systemPrompt` オプションは、エージェント定義を受け取るオプションに置き換わる
- Gateway のツールの説明は、Orchestrator 経由の LLM には渡らなくなる。Gateway の list の説明に入れた v3 の趣旨(区画だけを返す)は、エージェント定義の側にも同じ内容を持つ
- 過去のエージェント定義を残すため、次の変更には慎重さが要る: 制御メッセージを出す箇所の削除、提出用ツールの形式の変更、検証規則の種類の削除。追加は互換性を保てる
- ランタイムと Gateway の内部(run API の申告、監査、無害化、認証、資格情報)の変更は、これまでどおり行える
- 同じエージェント定義を新旧のランタイムで評価すれば、ランタイムの変更による精度の低下を検出できる
- T-024(探索プロンプト v4)の「v3 との比較の手段」は、この ADR の決定 1・2・4・8 の実装(T-027、T-028)で満たす
- 実装のタスクは T-027(決定 1〜7)と T-028(決定 8)に分ける

## 不変条件との関係

| 不変条件 | 関係 |
|---|---|
| 1(認可の委譲) | 変更なし。エージェント定義は資格情報に関与しない |
| 2(全ツール呼び出しの監査) | 変更なし。実験環境の試行も Gateway を通る(決定 8) |
| 3(未認可候補) | 変更なし。トレースに入るのは、LLM に渡った認可済みの結果だけである |
| 5(ツール IF) | 変更なし。変えるのは LLM に渡す説明だけで、Gateway の `tools/list` は変えない |
| 6(秘密情報) | コールバックに資格情報を渡さない(決定 8) |
| 7(Slack の非永続化) | トレースは合成コーパスに限る(決定 8)。AnswerRun に足す識別子は Slack に由来しない(決定 7) |
| 8・9(個社差分、コア化の基準) | 同梱された定義からの選択に限る(決定 5)。プラグイン境界は増やさない |

## 却下した案

- **`leisen-ask` に `--prompt-file` を足す。** バージョンの切り替えだけは解決する。トレース、比較、識別の問題は残り、開発用の差し替えが実行環境の CLI に入る
- **エージェント定義を 4 つ目のプラグイン境界にする。** 導入企業が自作の定義を読み込めるようになるが、不変条件に関わらない範囲に限る検証が要り、サポートの範囲が広がる。2 社以上で需要が再現してから検討する(不変条件 9)
- **エージェント定義にコードを含める。** 探索の方針を自由に書けるが、ランタイムの内部が互換性の対象になる
- **モデル ID をエージェント定義に含める。** 固定の範囲は広がるが、同じ文言を別のモデルで使うたびに定義が増える。導入先が使えるモデルは契約と環境で決まるので、導入先の設定に残す
- **固定の指定が解決できないときに既定へ切り替える。** 起動はできるが、固定したはずの動作が黙って変わる
- **エージェント定義の識別子を ToolInvocation に記録する。** run の中で定義は変わらないので、run 単位の AnswerRun に 1 回記録すれば足りる

## 人間に確認してほしい点

1. **データの前置きの文言をランタイムに固定してよいか(決定 3)。** 安全側としてランタイムに置いた。モデルの系統ごとに文言の調整が要ると分かった場合は、エージェント定義に移す。移す場合は、前置きが空でないことを形式の検証で確かめる
2. **effort を LLM バックエンドの設定に残してよいか(決定 2)。** effort は文言の効き方に影響するので、エージェント定義に「推奨する effort」を持たせる案がある
3. **過去のエージェント定義を何バージョン分残すか(決定 6)。** 固定を使う導入先が現れるまで決めなくてよいと考える
4. **どの系統にも当てはまらないモデルに「その他」の行を使ってよいか(決定 5)。** ローカルのモデルでは系統を判定できないことが多い。明示の指定を必須にする案もある
5. **AnswerRun の `agentDefinition` を Orchestrator の申告のままにしてよいか(決定 7)。** 侵害された Orchestrator は偽の識別子を申告できる。範囲は ADR-019 の既知の限界(その利用者の run の結果を偽れる)と同じである
6. **実験環境(決定 8)をこの ADR に含めてよいか。** 文書の本文をローカルに保存する経路を新設するため、別の ADR に分ける選択もある
7. **`leisen-ask` を `--config` なしで起動した場合は既定とする。** 現在も `--config` は任意である
