# ADR-008: 検索モダリティの分離と文書検索モジュールの適用範囲

Status: Accepted / Date: 2026-07-04

## 文脈
データソース候補の広い検討(オフィス業務・開発業務)により、現行のコネクタ+検索層の枠に収まらないソース群が特定された。設計に反映する。

## 決定

### 1. 検索は2モダリティに分離する
- **文書検索モジュール**: 全文(BM25系)+ベクトルのハイブリッドを1索引で提供する。「全文はこのソース、ベクトルはあのソース」とは分けず、同一索引内のシグナル重みで吸収する(ベクトル単独は固有名詞・ID・エラーコードの完全一致に弱いため)
- **構造化クエリモダリティ**: DB・ログ基盤・BIは索引を引く問題ではなく自然言語→クエリ変換(text-to-SQL/text-to-query)である。Connector IF(search/fetch/list/describe)に押し込まず、Orchestratorレベルの別モダリティとして扱う。**v1.0スコープ外**とし、監査ログでDB・ログ系の未解決クエリが実証されてから再訪する(証拠駆動の原則)

### 2. 文書検索モジュールの適用順序(ADR-006の明確化)
汎用モジュールとして1本開発するが、適用には確定順序がある:
1. **第一の顧客(確定)**: index-requiredクラス=ファイル共有/オブジェクトストレージ上のOffice・PDF等。組み込む先の製品が存在せず、本プロジェクトが自前で検索を持つ必然があるのは事実上このクラスのみ
2. **第二の顧客(証拠駆動)**: degradedソース(Slack, wiki, チケット等)。各導入の昇格判定レポート(T-014)に基づく

### 3. バックエンド選定は着手時に行う
文書検索モジュールのエンジン選定は本ADRの範囲外。検索層着手時(Q3)にPoCでゼロから判断する(ADR-006)。現時点では抽象境界の存在のみを確定する。

### 4. 前処理はingestパイプラインのプラガブルな前段とする
OCR(スキャン)、文字起こし(録画・録音)、テキスト抽出(Office/PDF)は文書検索モジュールの手前の前処理段。設定はdeployment.yamlのコネクタ設定内部で表現し、**SDKの型(ConnectorCapabilities)は拡張しない**。消費者がQ3の検索層のみでありADR-007の却下基準(期限圧力のない確定は過剰設計)に該当するため。paradigm等の予約フィールド追加案も同理由で却下。

### 5. ソースコードは文書検索モジュールの対象外
コード検索の本質はシンボル解決・ASTであり文書索引と目的が異なる。Phase 1ではGitHub等のネイティブ検索(degraded)で対応し、専用索引はコア外(contrib/または外部ツール連携)とする。

## スコープ外の明記
既存OSS製品(Redmine, GitLab等)への検索エンジンbuilt-in(redmine-fulltext-search型)は各製品コミュニティの領分であり、本プロジェクトはコネクタ経由でその成果を利用する側に立つ。
