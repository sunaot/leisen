# 社内ナレッジ検索基盤 製品企画・設計書 v2

## OSS + 複数社シングルテナント導入モデルへの改訂

本書は v1(`product-design.md`)の改訂版である。**実装前レビュー(2026-07-05)の反映差分は `product-design-v3.md` を併読すること。**v1 の A→C→D 段階構成・プロダクト原則・認可設計は維持しつつ、次の前提変更に伴う差分を定義する。変更のない箇所は v1 を正とする。

**前提の変更**: 単一企業の社内基盤 → OSS として公開し、複数社がそれぞれ自社環境にシングルテナントで導入する。開発元は SaaS 運営を行わず、導入支援・サポートを事業とする。

---

## 1. プロダクトの再定義

### 1.1 提供物は「ソフトウェア + 導入方法論」である

v1 では成果物は「自社で動く基盤」だったが、v2 では次の 3 点セットになる。

1. **OSS コア**: Gateway、コネクタ群、Orchestrator、汎用検索層、管理レポート。コード変更なしに設定だけで各社導入が完結することを製品品質の定義とする
2. **リファレンスデプロイ**: Docker Compose / Helm による再現可能な導入構成、アップグレード・マイグレーション手順
3. **導入プレイブック**: アセスメント → PoC → 全社展開 → 検索層有効化判定 → ナレッジレイヤー、の標準工程。導入支援ビジネスの中身そのもの

### 1.2 「汎用性」の規律

複数社対応で最も危険なのは、個社要件の無秩序なコア取り込みである。次の規律を置く。

- 各社差分は **設定(Deployment Profile)とプラグイン(後述の 3 つの拡張点)だけ** で吸収する。コアに if 文で個社分岐を入れない
- 2 社以上で再現した要件のみコア化する。1 社だけの要件はその会社のプラグイン/フォークとして実装し、導入支援の役務で対応する
- マルチテナント機構(テナント ID、テナント間分離)は実装しない。1 デプロイ = 1 社を不変条件とし、これにより v1 の認可設計(本人トークン委譲、post-filtering)がそのまま成立する

### 1.3 事業モデル

収益は導入アセスメント、初期導入支援、運用サポート契約(アップグレード追随、昇格判定の伴走)、個社コネクタの受託開発。OSS の採用数がパイプラインの源泉であるため、**採用の摩擦を最小化することが事業上の最優先**となり、これがライセンス選定(後述)の判断軸になる。

## 2. アーキテクチャの差分

### 2.1 Deployment Profile(新規・最重要)

導入 1 件の全構成を単一の宣言的設定で表現する。これが「汎用インデックス基盤 + 導入単位ごとのコネクタ/インデックス有効化」の実現手段である。

> この例は v3(ADR-010/013/014)を反映した現行方針。旧版にあった `tokenExchange: rfc8693` 前提と「Slackのみ searchLayer 有効化」は撤回済み。設定スキーマの正は T-010 と `examples/deployment.yaml` とする。

```yaml
# deployment.yaml(骨子)
deployment:
  name: acme-corp
idp:
  adapter: keycloak            # プラグイン選択: okta / entra-id / keycloak / ...
auth:
  # 認可方式はソース別(ADR-010)。token exchange / user OAuth / DWD /
  # delegated identity のどれが使えるかは T-000a のマトリクスで確定する
  sourceAdapters:
    gdrive: user-oauth
    slack: user-oauth
connectors:
  - id: gdrive
    enabled: true
    privateScopes: excluded    # 既定除外(ADR-013)
    searchLayer:
      enabled: false           # 既定OFF。昇格判定後にtrueへ(ADR-006)
  - id: slack
    enabled: true
    privateScopes: excluded    # DM/private は既定OFF(ADR-013)
    searchLayer:
      enabled: false           # ADR-014: Slackは原則オンデマンド検索のみ。中央インデックス化しない
orchestrator:
  maxIterations: 6
  costLimitPerQuery: ...
audit:
  sink: stdout                 # 収集基盤は各社の運用に委ねる
  failureMode: fail-closed     # 監査書き込み失敗時の既定(ADR-011)
  rawQueryRetentionDays: 30    # 生クエリ短期保持(ADR-011)
```

設定スキーマはバージョン管理し、アップグレード時のマイグレーションツールを製品の一部として提供する。**導入支援エンジニアが触るのは原則このファイルと IdP/ソース側の管理画面だけ**、という状態を目指す。

### 2.2 プラグイン境界を 3 つに確定する

| 拡張点 | 役割 | 同梱リファレンス実装 |
|---|---|---|
| Connector | ソース検索・取得(v1 の SDK) | Google Drive, Slack |
| IdP Adapter | 認証と、ソース別認可方式(token exchange / user OAuth / DWD / delegated identity)の吸収(ADR-010) | Keycloak(自己ホスト可能な OSS を参照実装に), Okta, Entra ID |
| Search Backend | 検索層のインデックス・クエリ抽象 | 着手時(Q3)に選定(ADR-006) |

Connector SDK には optional capability として **`ingest()`(全件/差分クロール)と変更フィード** を追加する。検索層の有効化は「そのコネクタが ingest capability を実装している場合のみ可能」という型レベルの制約にする。これにより v1 の不変条件(ツール IF の安定性、search の内部実装差し替え)を保ったまま、検索層が汎用モジュール化される。

### 2.3 汎用検索層: 製品開発は前倒し、有効化は各社で証拠駆動

v1 との最大の差分。v1 では検索層は「昇格ソースが判明してから作る」だったが、複数社では弱いソースが会社ごとに異なるため、**検索層モジュール自体は最初からコアのオプション機能として開発する**。一方で「証拠駆動ゲート」は消滅するのではなく、**各社の導入ロードマップに移動する**。

- 全導入は検索層 OFF で開始する(導入プレイブックの標準)
- v1 T-001 の「ソース別未解決率」は、社内分析からコマンド/管理画面のレポート機能(**昇格判定レポート**)に昇格し、導入各社の管理者と導入支援エンジニアが有効化判断に使う
- 有効化は deployment.yaml のコネクタ単位フラグで行い、Ingest 開始・初期インデックス構築・post-filtering 稼働までを製品の標準手順として自動化する

認可設計は v1 ADR-003(ACL 非同期、post-filtering + 適応的 K 拡張 + 短 TTL 認可キャッシュ)を変更なく踏襲する。シングルテナントなのでテナント間分離は不要だが、代わりに **「インデックスは deployment.yaml から常に再構築可能」** を運用不変条件とし、各社での障害復旧・アップグレードを単純化する。

### 2.4 Phase 3(ナレッジレイヤー)の差分

権限区画(Permission Cohort)の定義は各社の IdP グループ体系に依存するため、区画導出ルールを設定スキーマ化し、マップオーナーの週次レビューを製品内ワークフロー(差分表示と承認)として実装する。プロンプト・領域ツリー粒度は業種で振れるため、**デザインパートナー 2〜3 社との共同検証を Phase 3 開発の前段に置く**。ここは v1 の「区画単位生成で漏洩を入力段階で遮断する」原則をそのまま適用できる(シングルテナントなので社間の考慮は不要)。

### 2.5 アップグレードとマイグレーション(新規の品質要件)

OSS では運用が各社に渡るため、後方互換性が製品品質になる。semver 運用、設定スキーマ・監査ログスキーマ・インデックススキーマそれぞれのバージョンとマイグレーションツール、リリースノートでの breaking change 明示、少なくとも 1 メジャー前からの直接アップグレード保証、を release engineering の要件とする。

## 3. OSS プロジェクト運営

### 3.1 ライセンス(要意思決定 → ADR-004)

SaaS 事業を行わない前提では、他社によるクラウドサービス化は直接の脅威ではなく、むしろ採用拡大が導入支援パイプラインを太らせる。したがって **Apache-2.0 を推奨**する(特許条項があり企業採用の摩擦が最小)。防御を優先するなら AGPL-3.0 だが、国内企業の社内導入でも法務審査の障壁になりやすく、事業モデルと整合しない。BSL 等のソースアベイラブルは「OSS として公開」の趣旨から外れるため対象外。**最終決定は人間(経営判断)。**

### 3.2 セキュリティ運営

認可を扱うソフトウェアであるため、SECURITY.md と脆弱性報告窓口(非公開報告 → 修正 → 開示の手順)、リリース成果物の署名、依存関係の自動監査(CI)、v1 のレッドチーム項目を公開のセキュリティテストスイートとして同梱、を公開時の必須要件とする。

### 3.3 その他の運営要素

コントリビューションは DCO 方式(CLA より軽く採用摩擦が小さい)。個社コネクタの受け皿として `contrib/` 階層(コア外・ベストエフォート保守)を設ける。テレメトリは実装するとしてもオプトイン・既定 OFF・内容公開を厳守(信頼が事業の核のため)。ドキュメントは導入ガイド/リファレンスアーキテクチャ/コネクタ・アダプタ開発ガイドの 3 部構成で、これ自体が導入支援の営業資料を兼ねる。プロジェクト名と商標は導入支援ブランドの中核になるため早期に確保する(人間タスク)。

## 4. 改訂ロードマップ

自社(開発元)を導入 0 号として dogfood し続けることを前提とする。

| 四半期 | 製品(OSS) | 導入・事業 |
|---|---|---|
| Q1 | コア(Gateway/SDK/監査)+ Deployment Profile + コネクタ 2 本 + Keycloak アダプタ | 自社導入(0 号)で Phase 1 検証 |
| Q2 | **OSS 公開(v0.x)**: ライセンス・SECURITY・docs 整備。IdP アダプタ 3 種 | デザインパートナー 1 社目の導入支援開始。導入プレイブック v1 |
| Q3 | 汎用検索層モジュール(backend 抽象 + ingest capability + post-filtering)+ 昇格判定レポート | 0 号・1 社目の監査ログで昇格判定の実証 |
| Q4 | 検索層の本番品質化(初期構築・再構築ツール、鮮度 SLO 計測) | パートナー 2〜3 社目。検索層有効化 1 社目 |
| Q5 | Phase 3 機能(区画設定スキーマ、マップ生成、レビューワークフロー) | パートナー 2〜3 社と Phase 3 共同検証 |
| Q6 | v1.0(後方互換性保証の開始) | 有償サポート契約の定型化 |

ゲート原則は「各社の導入が次段階に進む条件は当該社の KPI 達成」(v1 の Phase 完了条件を導入プレイブックに移植)と「コア機能の GA 条件は 2 社以上での本番実績」の二本立てになる。

## 5. バックログへの影響

Phase 1 タスク(T-001〜T-009)は全て有効。ただし T-002/T-004 は IdP Adapter 抽象を前提に読み替える。追加タスクは T-010 以降として backlog に追記済み: Deployment Profile スキーマ(T-010)、IdP Adapter 抽象 + Keycloak 参照実装(T-011)、リファレンスデプロイ(T-012)、OSS 公開準備(T-013)、昇格判定レポート(T-014)。検索層モジュール(T-1xx 系)は Q3 着手時に詳細化する。

## 6. リスク差分

| リスク | 影響 | 対策 |
|---|---|---|
| 個社要件のコア汚染 | 高(長期の保守負債) | 「2 社ルール」と contrib/ 階層、PR テンプレートでの汎用性チェック |
| 導入先での誤設定による権限事故 | 高(プロジェクトの信頼毀損) | deployment.yaml の静的検証、導入時セキュリティチェックリスト、危険設定の起動時拒否 |
| アップグレード追随の放棄(塩漬け導入) | 中 | マイグレーションツール、サポート契約への誘導、LTS ポリシー |
| OSS 化による競合の学習 | 低〜中 | 事業の核を「導入方法論と伴走」に置く。コードは追随できても導入実績は追随しにくい |
| コミュニティ対応コスト | 中 | 公開当初は「ソース公開・課題受付・ロードマップ非公約」の低コミット運営から開始 |

## 7. 人間の意思決定が必要な項目

ライセンス最終決定(3.1)、プロジェクト名・商標、デザインパートナー候補の選定と契約形態(無償支援と引き換えに要件・評価データ提供)、脆弱性報告窓口の体制、**Slack導入形態3類型のAPI Terms適合性の法務/Slack確認(ADR-014)**、**プライバシー・保持・ログ閲覧方針(ADR-013)**、**体制表の改訂とOSS公開時期の再判断(v3 §8: OSS化はrelease engineeringという追加製品であり本書は体制を未改訂。Q2公開とQ3公開+Q2非公開パートナー提供を比較する)**、**Buy比較表(Glean / M365 Copilot / Gemini Enterprise)とターゲット顧客定義のday-0作成**。いずれも OSS 公開より前に確定が必要。

## 追補(2026-07-04): 検索層の構造の確定 — ADR-008

データソース候補の広域検討と批判的検証の結果、検索層の構造を次の通り確定した。詳細は各ADRを正とする。

**検索の2モダリティ分離(ADR-008)**。文書検索モジュール(全文+ベクトルのハイブリッド1索引、前処理[OCR/文字起こし/テキスト抽出]はingestパイプラインのプラガブルな前段)と、構造化クエリモダリティ(DB・ログ・BIへのtext-to-query、Orchestratorレベルの別機構)を分離する。後者はv1.0スコープ外とし、監査ログの証拠で再訪する。ソースコード検索(シンボル/AST)も文書検索の対象外(ネイティブ検索+コア外)。

**文書検索モジュールの適用順序**。第一の顧客はindex-requiredクラス(ファイル共有/オブジェクトストレージ)で確定 — 本プロジェクトが自前検索を抱える必然があるのは事実上このクラスのみであり、「可動部品最小」の原則と整合する。degradedソース(Slack, wiki, チケット等)への適用は各導入の昇格判定(T-014)に従う。

**バックエンド選定**。文書検索モジュールのエンジン選定は検索層着手時(Q3)にPoC(T-016)でゼロから判断する。現時点で候補を確定せず、設計としては Search Backend の抽象境界の存在のみを確定する。

**ロードマップへの反映**: Q3の「汎用検索層モジュール」は「バックエンドPoC(T-016)→ファイル共有向け文書検索モジュール(T-015と結合)→degraded昇格対応」の順に具体化する。
