1結論の要約

  • leisen は、オブザーバビリティの基盤を提供しない。leisen が責任を持つのは、シグナルの定義と、その意味の一貫性である。保存、検索、可視化、アラートは、導入先が運用する監視基盤に委ねる。
  • 品質の観測とは、目的と時間軸が異なる。品質の観測は「十分に良いか」を日から四半期の単位で評価し、改善につなげる。オブザーバビリティは「いま何が起きているか、なぜか」を秒から分の単位で把握し、障害の検知と原因の特定に用いる。シグナルはオブザーバビリティが所有し、品質の観測はその集計値を利用する。
  • 一般的な APM の標準的な動作は、この製品では情報漏えいの経路となる。自動計装が収集する HTTP ヘッダー、リクエスト本文、エラーメッセージには、トークン、質問の原文、Slack 由来のデータが含まれる。除外設定による対処ではなく、許可したシグナルのみを出力する方式を採る。
  • 監査ログを運用に転用しない。監査ログと運用データは、目的、保持期間、アクセス制御が異なる。同一の出来事を、発生した時点で目的別に 2 つの記録として出力し、一方から他方を導出しない。運用時の調査と監視は、構造化運用ログのみを入力とする。
  • APM の利用が制約される分、代替となる機能を組み込みで提供する。エラー発生箇所コード、処理の経過を含むリクエストの要約、診断コマンドとレディネス、検査コマンド、プローブである。いずれもスキーマの項目または CLI であり、監視基盤の機能は持たない。
  • オブザーバビリティを、監査とも品質の観測とも異なる独立した層としてモデル化する。監査は証跡となるレコードを、オブザーバビリティは稼働状況を表すシグナルを、品質の観測は評価のための指標を扱う。計装はオブザーバビリティ層に属し、コアロジックの境界(入口と出口)でのみ行う。モジュール、設定、コマンドを 3 者で分け、依存の向きを import 境界の検査によって保証する(10 章)。
  • 構成は 3 層とする。組み込み(追加の基盤なしで常に動作する)、ブリッジ(導入先の監視基盤へ任意で連携する)、開発・評価専用(合成データを用いる環境に限り、内容を含む詳細なトレースを許可する)である。
  • アラートは、不変条件の違反と利用者への影響に直結する少数の条件に限定する。それ以外は、定期的なレポートの確認によって対応する。ツールの導入よりも、見直しの手順を先に定める。
  • 最初に行うべきことは、APM を接続する場合の指針を導入手順に記載することである。現時点の最大のリスクは、監視の不足ではなく、導入先が標準設定の APM エージェントを接続することによる情報漏えいである。

2品質の観測との関係

本文書で用いる語のうち、構造化運用ログ、レコーダー、計測デコレーター、計測コンテキスト、スパン、計装は、「品質の観測計画」2 章の定義に従う。本文書で新たに用いる語は次のとおりである。

目的と担い手の違い

構造化運用ログはオブザーバビリティが所有するシグナルであり、品質の観測は、その集計値を入力として利用する。計装はオブザーバビリティ層にのみ置き、品質の観測は稼働中のプロセスに計装を持たない(10 章)。同じシグナルであっても、利用の仕方は目的に応じて異なる。たとえばタイムアウト超過率は、品質の観測では週次の推移として設定値の妥当性の評価に用い、オブザーバビリティでは直近数分間の値を依存先の障害の検知に用いる。

3前提: この製品に固有の制約

一般的な Web サービスと異なる点が 4 つあり、運用ツールの利用方法を制約する。

4責任分界

leisen は 1 デプロイ = 1 社の OSS であり、運用は導入企業が担う。監視基盤は導入先ごとに異なるため、leisen がその機能を持つと、個社差分がコアに混入する(不変条件 8)。責任の範囲を次のように定める。

この分界において、leisen が最も重視すべきものはシグナルの定義の安定性である。導入先のダッシュボードとアラートは、イベントの種別と分類コードに依存する。これらを変更すると導入先の監視が機能しなくなるため、コネクタ IF や監査スキーマと同様に、変更を管理する対象とする。

5監査ログと運用データの分離

監査ログには、ツール呼び出しの順序、所要時間、エラー分類が記録されている。これを運用時の調査に利用すれば、新たなデータを出力せずに済む。しかし、監査ログはアプリケーションの要件(不変条件 2)として記録するものであり、運用への転用は適切ではない。本章では、その理由と、分離の原則を定める。

両者の性質の違い

転用した場合の問題

  • 目的外利用となる。ADR-013 が認める閲覧目的は、セキュリティインシデントの調査、権限逸脱の検出、昇格判定・運用改善(集計値の利用を原則とする)、法令および社内規程に基づく正式な調査である。性能の調査のために個別の run の経過を参照することは、いずれにも該当しない。
  • アクセス制御が形骸化する。運用担当者が日常的に監査ログを必要とするようになると、指名制と閲覧の記録が負担となり、制御を緩める方向の要求が生じる。
  • 不要な個人データを参照することになる。性能の調査に利用者の識別子は不要であるが、監査ログを参照すれば必ず含まれる。
  • スキーマが 2 つの要求の影響を受ける。運用上必要な項目を監査レコードに追加することになり、監査のスキーマが、本来の目的と関係のない理由で変更される。

分離の原則

  1. 同一の出来事を、目的別に 2 つの記録として出力する。出力は、出来事が発生した時点で、それぞれ独立に行う。一方の記録から他方を導出しない。
  2. 運用時の調査、監視、アラートは、構造化運用ログとヘルスチェックのみを入力とする。監査ログ、生クエリ表、分離テレメトリは入力としない。
  3. 運用上の項目を、監査レコードに持たせない。運用上の必要から項目を追加する場合は、構造化運用ログのスキーマに追加する。既存の latencyMs と retryCount は、この原則に照らして見直しの対象とする(後述)。
  4. 構造化運用ログに、証跡としての役割を持たせない。構造化運用ログは欠落を許容するため、説明責任の根拠としては用いない。

この原則は、オブザーバビリティに適用する。品質の観測は、回答品質と利用状況の指標について、引き続き監査ログの集計値を入力とする。これは ADR-013 が認める「昇格判定・運用改善」の目的に当たり、利用率のように利用者の識別子を必要とする指標を含むためである。運用品質の指標は、構造化運用ログのみを入力とし、監査ログからは暫定的にも算出しない。このため、構造化運用ログを早期に実装する(品質の観測計画 7 章、12 章)。

既存の監査レコードの見直し

監査レコード(ToolInvocation)の latencyMs と retryCount は、ADR-011 の決定 1 によって定められた項目であるが、いずれも説明責任のための情報ではなく、運用上の情報である。過去の決定であっても、分離の原則に適合しない場合は、今後の変更として見直す。

削除は監査スキーマの変更であり、ADR-011 の追補として起票する(論点 O6)。既に記録されたレコードの読み取りを維持するため、読み取り側は当該の項目を任意として扱う必要がある。評価レポート(docs/eval)には監査ログから所要時間を参照した記述はないが、テストコードと導入先の独自の集計における利用は確認していない。

セキュリティインシデントの調査において、監査ログから特定の利用者の呼び出しの経過を確認することは、監査の本来の目的であり、この原則に反しない。その場合は、ADR-013 の手続きに従って閲覧を記録する。

63 層の構成

第 3 層を設ける理由は、本番環境の制約と、開発者の必要が相反するためである。本番環境では内容を含むデータを出力できないが、探索プロンプトやコネクタの改善には、質問に対してどの検索語を用い、何が返され、どの文書を取得したかを追跡する必要がある。開発環境では合成コーパスのみを扱うため、この制約は当てはまらない。現在は dev-eval の出力と監査ログを照合して調査しているが、開発専用トレースによって、この作業を 1 つのトレースの参照に置き換えることができる。

7シグナルの種類ごとの扱い

本番環境でトレースを提供しないことによる影響は、障害調査において、1 件のリクエストの処理経過をスパン単位で追跡できない点にある。これは、リクエストの要約イベントに処理の経過(スパンの種類、所要時間、結果の分類の列)を含めることで補う。利用者からの問い合わせに対応する場合は、リクエスト参照 ID によって該当する要約イベントを特定する(9 章)。監査ログは、この調査には用いない(5 章)。

8APM・監視ツールを接続する場合の指針

導入先が既存の APM や監視ツールを leisen に接続することは、想定される。その際に不変条件が損なわれないよう、導入手順(docs/install.md)に次の指針を記載する。

自動計装のエージェントを、収集項目を限定したうえで接続することは、技術的には可能である。ただし、設定の誤りや製品の更新によって収集項目が変わるおそれがあり、leisen 側からその状態を検証する手段がない。このため、指針としては「標準設定での接続を行わない」とし、限定した接続は導入先の責任において行うものと位置付ける。

9組み込みで提供する運用機能

3 章と 8 章のとおり、leisen では APM の利用が制約される。これによって得られなくなる機能のうち、不変条件を維持したまま代替できるものは、leisen が組み込みで提供する。いずれも、構造化運用ログのスキーマの項目、または、ファイルを入力とする CLI として実現する。

シグナルとの関係による分類

組み込みの運用機能は、新しい種類のシグナルを追加するものではない。7 章のシグナルのうち、構造化されたイベントログとヘルスチェックの 2 種類を拡張するもの、それらを利用するもの、および能動的に確認を行うものに分類できる。

稼働中のプロセスへの計装を必要とするのは、シグナルの拡張に当たる 4 つのみである。これらを、コアロジックを変更せずに実現する方法は 10 章で述べる。それ以外は、プロセスの外部で動作する CLI であり、コアロジックに影響しない。

エラー発生箇所コード

現在、エラーは分類コードに正規化して記録しており、メッセージは記録しない。このため、internal_error が発生した場合に、発生した箇所を特定する手段がない。APM であればスタックトレースによって特定できるが、メッセージには値が含まれうるため利用できない。

代替として、例外を送出した箇所を示す固定の識別子を、エラー分類とともに構造化運用ログに出力する。識別子は、事前に定義したコード、または関数名と行番号とする。値とメッセージを含まないため不変条件に抵触せず、同一の箇所で発生したエラーを集計できる。

処理の経過を含むリクエストの要約

リクエストの要約イベントに、ターンアラウンドタイムと内訳に加えて、処理の経過を含める。経過は、スパンの種類、所要時間、結果の分類を、発生順に並べたものである。利用者、run、クエリ、文書の識別子は含めない。これにより、「検索が 3 回連続して失敗した後に、探索の上限に達した」といった経過を、監査ログを参照せずに確認できる。

利用者からの問い合わせに対応するには、該当するリクエストを特定する必要がある。このために、リクエスト参照 ID を設ける。応答(回答およびエラーの表示)に乱数の識別子を含め、同じ値をリクエストの要約イベントに記録する。利用者が問い合わせの際にこの値を提示した場合に限り、運用担当者は該当するイベントを特定できる。監査ログには記録しないため、運用担当者がこの値から利用者を特定することはできない。

診断コマンドとレディネス

現在は、設定の検証(leisen-gateway validate)と、Keycloak に対する確認(auth-check)がある。これを拡張し、IdP、LLM バックエンド、各ソース、KMS、監査ログの書き込み先への到達性を一括して確認する診断コマンドとする。導入時の疎通確認と、障害時の切り分けに用いる。

現在の /healthz は、プロセスが稼働していることのみを示す。これとは別に、依存先の状態を反映するレディネスのエンドポイントを設ける。応答は状態の区分のみとし、依存先の名称、アドレス、エラーの内容は含めない。

検査コマンドとプローブ

検査コマンドは、直近の構造化運用ログを読み取り、11 章のアラートの条件を判定して、終了コードで結果を返す。監視基盤を運用していない導入先でも、定期実行と通知の仕組み(cron とメールなど)のみで、最低限の検知を行える。

プローブは、固定した質問を定期的に実行し、利用者体感のターンアラウンドタイムと回答の合否を記録する。カナリア検証と仕組みを共用する。LLM の呼び出しコストを伴うため、実行頻度は導入先が定める。

組み込みでは提供しないもの

  • ダッシュボード、メトリクスの保存、通知の配信。導入先ごとの差異が大きく、提供すれば監視基盤そのものを実装することになる(4 章)。
  • 監査ログから run の経過を再構成する運用機能。監査ログの運用への転用に当たる(5 章)。

10オブザーバビリティ層のモデルと実現方式

監査、オブザーバビリティ、品質の観測は、いずれも稼働中の出来事を記録して利用する点で類似する。しかし、目的と要求される性質が異なるため、同じ仕組みの一部として実装すると、5 章で述べた転用と同じ問題が生じる。本章では、オブザーバビリティを独立した層として定め、コアロジックを変更せずに実現する方式を示す。

3 つの関心事の区別

品質の観測は、長期の推移を必要とする。構造化運用ログの保持期間は短いため、品質の観測は、集計した結果を品質スナップショットとして自ら保持する。これにより、オブザーバビリティの保持期間を、品質の観測の都合によって延ばす必要がなくなる。

境界での計装

オブザーバビリティ層は、コアロジックの内部には計装を置かず、境界でのみ観測する。境界は、入口と出口の 2 種類である。

いずれも、構成処理(Gateway の bootstrap/、Orchestrator の bin/)において適用する。コアロジックは、包まれていることを認識しない。計装の方式の比較と、現状のコードとの差分は、品質の観測計画 9 章に記載している。入口のデコレーターは、本文書で追加するものである。コアロジックが例外を送出せずにエラーを結果として返却する場合、ミドルウェアと出口の計測デコレーターのいずれからも観測できないため、入口で結果を観測する必要がある。

シグナルの拡張の実現方式

診断コマンドは、構成処理を利用してポートの実装を生成し、到達性を確認する。コネクタの呼び出しには利用者の資格情報が必要であるため、利用者を伴わない確認は、接続先への到達性の確認にとどまる。認可を含む確認は、テスト用のアイデンティティを指定して行う。

プローブは、サーバーのプロセスの外部で、クライアントとして動作する。プローブによるリクエストは、利用者によるリクエストと同じ経路で処理されるため、統計に混入する。区別のために、リクエストの要約イベントに、通常のリクエストかプローブによるリクエストかを示す属性を設ける。この属性は、利用者の識別子ではない。

モジュールの構成と依存の向き

3 つの関心事を、コード上でも区別できるようにする。名称は案であり、ADR-020 の命名規則に従って確定する。

設定とコマンドも、関心事ごとに分ける。deployment.yaml には、既存の audit の節とは別に observability の節を設け、構造化運用ログの出力先、保持期間、レディネスの有無を定める。コマンドは、サーバーの起動、オブザーバビリティ(診断、検査、プローブ、診断用の出力)、品質の観測(レポートの生成)で、サブコマンドの系統を分ける。運用担当者は、設定の節とコマンドの系統によって、どの関心事を操作しているかを判別できる。

この構成により、「計測デコレーター」「レコーダー」「計測コンテキスト」は、オブザーバビリティ層の構成要素として位置付けられる。品質の観測計画では、これらを品質の観測のための仕組みとして導入したが、所有はオブザーバビリティ層に置き、品質の観測は出力されたシグナルを利用する立場とする。

11アラートと定期的な見直し

アラートは、直ちに対応が必要な条件に限定する。対象は、不変条件の違反と、利用者への影響に直結する事象である。件数を絞るのは、通知が多いと重要な通知が見落とされるためである。

上記以外の指標(エラー率の内訳、キャパシティ使用率、コスト、再接続要求率など)は、アラートの対象とせず、品質の観測の運用レポートによって定期的に確認する。

ツールを導入しても、それだけでは運用の品質は向上しない。次の見直しの手順を、ツールの選定より先に定める。

  • 週次: 運用レポートを確認し、対応が必要な事項を backlog に登録する。発生したアラートについて、対応の要否が正しかったかを見直し、不要な通知の条件を調整する。
  • リリースおよび設定変更の前後: スパン別の所要時間、タイムアウト超過率、ターンアラウンドタイムを比較する。カナリア検証を実行する。
  • 障害の発生後: 検知までの時間と、原因の特定に要した時間を記録する。既存のシグナルでは特定できなかった場合に限り、シグナルの追加を検討する。

12リファレンスデプロイの常時稼働

leisen の開発者は、導入先のデータを参照できない。共有用集計(品質の観測計画 Q5)によって機能別の利用量と導入構成は把握できるが、運用時の挙動を直接に確認する手段はない。このため、OSS プロジェクト自身が、合成コーパスを用いたリファレンスデプロイを常時稼働させることを提案する。

一方で、稼働させ続けるための運用負荷と、LLM の利用コストが発生する。合成監視の実行頻度と利用するモデルによってコストは大きく変わるため、実施の可否と規模は論点 O2 として判断する。

15前提と未検証事項

  • 本文書の位置付け: 現時点の見解をまとめた分析であり、決定事項ではない。構造化運用ログのスキーマ、開発専用トレース、シグナルの変更管理は、ADR によって定める。
  • 前提: 導入先には、監視基盤を運用している企業と、運用していない企業の双方が存在する。導入先への聞き取りは行っていない。本文書の内容は、構造化運用ログと計測デコレーターが「品質の観測計画」の案のとおりに実装されることを前提とする。
  • 確認済みの事項: ヘルスチェックのエンドポイント(/healthz)が Gateway と Orchestrator に存在し、利用者に関する情報を返さないこと。開発用コンポーネントを本番環境で拒否する仕組み(dev_only_in_production)が存在すること。stderr の出力規則が docs/install.md §7.1 に定められていること。
  • 未検証の事項: 個々の APM 製品の自動計装が、標準設定でどの項目を収集するか(製品とバージョンによって異なる)。OpenTelemetry Collector によるファイルの取り込みとメトリクスへの変換の構成。開発専用トレースの出力先を切り替える実装の規模。リファレンスデプロイを常時稼働させた場合の LLM の利用コスト。
  • 組み込みの運用機能に関する未検証の事項: 正規化したエラー(GatewayError など)が、元の例外を原因として保持しているか。スタックトレースのフレームから、ビルド後のコードの位置を安定した識別子として取り出せるか。入口のデコレーターを適用できる形で、コアロジックの公開メソッドが構成処理から参照されているか。レディネスの判定に、依存先への問い合わせをどの頻度で行うか。リクエスト参照 ID を、MCP の応答および LibreChat の画面でどのように利用者へ提示できるか。
  • 対象外: 監視基盤の製品の選定。導入先の当番体制と障害対応の手順。利用者向けの画面(LibreChat)の監視。
