1比較の範囲と、ここまでの経緯

Leisen は、利用者本人の資格情報でソース API を呼び、結果を本人に返す(不変条件 1)。ソース API を呼ぶのは Gateway のコネクタであり、Gateway を通らない経路は作らない(不変条件 2)。したがって「個人認可の仕組み」とは、本人がソースに与えた同意を、Gateway が本人のために使える形にする仕組みのことである。問題になるのは、同意の結果として得られるトークン(多くのソースでは長命の更新トークン)を、どこに置き、どう運び、どう取り消すかである。

ここまでの検討では、次の順に議論が進んだ。ADR-010 は本人ごとの OAuth(方式 A)が主経路であると確定し、Token Vault を中核部品とした。「資格情報の置き場所」では、トークンをサーバー側に永続化せずローカルに寄せられないかという問いに対し、bearer token の性質(所持が権限、使用点では必ず平文、複製は遠隔から消せない)から選択肢を整理し、端末が保持して毎回提示する案と、それを Gateway の鍵で暗号化する案(以後 ESC: encrypted self-contained credential)を挙げた。本書はそれらを、保管しない方式(IdP トークン方式)も含めた 4 つに揃えて並べ、要件に対して評価し、論点を設定する。

比較する 4 方式は次のとおり。名前は本書内の呼び名で、括弧内は前の文書での記号である。

  • Gateway の Token Vault(V1): Gateway が更新トークンを暗号化して保管する
  • IdP トークン方式(L4): 保管せず、本人の IdP トークンを呼び出しのたびにソースのトークンへ交換する(Entra ID の On-Behalf-Of、策定中の ID-JAG)
  • キーチェーンと MCP クライアント方式(L2): MCP クライアントが端末の OS 保護領域に更新トークンを保持し、呼び出しのたびに平文で Gateway に提示する
  • ESC 方式(L3): 同じく端末が保持するが、トークンは Gateway の鍵で暗号化されており、Gateway だけが復号できる。Gateway を MCP の認可サーバーにして、発行するアクセストークンそのものを ESC にする形(2.5 節)を含む

ブラウザの localStorage に置く案は、保持者がブラウザになるだけで、仕組みとしては「キーチェーンと MCP クライアント方式」か「ESC 方式」のブラウザ版である(参照構成の LibreChat をそのまま使う場合は成立せず、UI の改造が要る)。本書では 4 方式の中で扱う。

24 つの方式の実現方法

図1 に、長命の秘密(更新トークン、またはそれに相当するもの)がどこに置かれ、1 回の呼び出しで何が動くかを示す。以下、方式ごとに仕組みを説明する。

2.1Gateway の Token Vault

Gateway が接続ページを持ち、OAuth のコールバックで受け取った更新トークンを、KMS の鍵で封筒暗号化して保管する。キーは userId と sourceId の組(不変条件 4)。呼び出しのたびに Gateway が保管庫から取り出して復号し、期限切れなら更新し、更新トークンのローテーションは Gateway が直列化する。本人による解除と IdP での利用停止(SCIM 等)を受けて、Gateway がソースの失効 API を呼び、保管庫から消す。端末と中継者には IdP トークンしか流れない。RFC 10017 が業務アプリに推奨する Backend for Frontend を、ソース API に対して Gateway が担う形である。

2.2IdP トークン方式

ソースのトークンを保管しない。Gateway は要求に添えられた本人の IdP トークンを、ソースの認可サーバーで短命のアクセストークンに交換し、その要求の処理に使う。交換の根拠は IdP とソースの間の事前の信頼関係で、現時点で確実に成立するのは Entra ID の On-Behalf-Of(SharePoint / OneDrive)だけである。IETF で策定中の Identity Assertion JWT Authorization Grant(ID-JAG、Cross-App Access)が広がれば、方式 A のソースの一部もここに移れる。本人の同意は管理者の一括同意(admin consent)で済み、利用者に接続の操作はない。失効は IdP のセッションと利用停止に追随する。

2.3キーチェーンと MCP クライアント方式

Gateway の接続ページで OAuth を行う点は Token Vault と同じだが、得た更新トークンを Gateway は保管せず、MCP クライアント(Claude Code、Claude Desktop など)に渡す。クライアントは端末の OS 保護領域(macOS の Keychain、Windows の DPAPI、Linux では権限 0600 のファイル)に保持し、呼び出しのたびに _meta 等で Gateway に提示する。Gateway は要求の間だけ使い、更新が起きたら新しいトークンを応答で返す。ブラウザ UI でこの形を取る場合、保持者はブラウザの localStorage になり、UI のフロントエンドとバックエンドの改造が要る。CLI ツールが長年取ってきた形(AWS の SSO キャッシュ、Claude Code の資格情報ファイル)と同じで、守っているのは他ユーザーとディスクの盗難からだけである。

2.4ESC 方式

保持者と提示の流れはキーチェーン方式と同じで、提示するものが違う。Gateway はコールバックで得たトークンを、自分の鍵で暗号化し(JWE。本人の sub と sourceId を付加データとして結び付ける)、暗号文だけをクライアントに返す。クライアントはこれを保持し、毎回提示する。中継者には暗号文しか見えず、端末から盗まれても Gateway 以外では開けず、Gateway に対しても同じ本人の IdP トークンがなければ受け付けない。Gateway が持つのは鍵と拒否リスト(cid または sub)だけで、秘密は永続化しない。更新で新しいトークンが得られたら、新しい暗号文を応答で返す。先例は、認可サーバーが発行する自己完結型トークン(RFC 6819 §3.1)、暗号化した Cookie セッション、Kubernetes の Sealed Secrets である。

2.5ESC 方式の具体化: Gateway を MCP の認可サーバーにする

ESC 方式には「クライアントが暗号文を保持し、毎回提示し、更新後は差し替える」というクライアント側の振る舞いが要る。既存の MCP クライアントには、サーバーが返した任意の値を保持して次の呼び出しに添える仕組みがないため、これを _meta で運ぶなら Leisen が実装を持つクライアント(leisen-ask の CLI)に限られる。この制約を外すのが、Gateway を MCP の認可サーバー(RFC 9728 / 8414 のメタデータ、認可エンドポイント、トークンエンドポイント)にし、発行するアクセストークンそのものを ESC にする形である。標準の MCP クライアントは、アクセストークンの保持・再送・更新を OAuth の手順として実装しているので、追加の対応なしに ESC を運ぶ。LibreChat も MCP サーバーごとの OAuth に対応しており、この形では改造なしに標準のクライアントとして使える。ただし LibreChat は利用者ごとのトークンを自分の DB に保存するので、暗号文の置き場所は端末ではなく UI サーバーになる(鍵は Gateway にあり、平文を得るには両方の侵入が要る)。

Gateway が持つ状態

この形は、認可サーバーの作りとして「状態を持たない(自己完結型)」側を選ぶことにあたる。Keycloak のように発行したトークンの控えを DB に持つのではなく、トークンの中に必要な情報を入れて自分の鍵で暗号化し、提示されたときに開いて検証する。Gateway が持つのは鍵と、秘密を含まない少量の状態である。表1 の「Gateway が持つ状態」の行と、次の内訳を参照。

  • 永続: 鍵(KMS)、拒否リスト(cid または sub。秘密ではない)、使用済みの更新トークンの識別子(再利用検知。秘密ではない)、MCP クライアントの登録と機密クライアントのシークレット(利用者の資格情報ではなく、LEISEN_ORCHESTRATOR_CREDENTIAL と同種)、監査(値は含めない)
  • 一時: 使用中の平文(要求の間だけメモリ)、同意直後のトークン(認可コードがトークンに引き換えられるまでの数十秒。認可コード自体を暗号化した自己完結型にすればゼロにできる)、run 内の更新の直列化(run の間)、ローテーション差分の保留(次項。数分)
  • 持たない: ソースの更新トークンの控え。V1 との差はこの一点で、鍵を持つことと使用点で平文を扱うことは同じである

更新トークンのローテーションを標準の OAuth の枠で扱う

ESC の中身(ソースのアクセストークンと更新トークン)は、Gateway が呼び出しの途中で更新する。しかし通常の OAuth では、発行済みのトークンの中身は変わらないという前提があり、変わる状態は認可サーバー側に置く(Auth0 の Token Vault が状態を持つ作りなのはこのためである)。クライアントが新しいトークンを受け取るのは、認可フローのやり直し、refresh_token グラント、トークン交換のいずれかをクライアント自身が出したときだけで、資源サーバーの応答に添えたトークンをクライアントは保存しない。一方で、資源サーバーは 401 invalid_token を返すことでクライアントに更新を引かせることができ、MCP のクライアント SDK もこの動きを実装している。

この原則に沿うと、ローテーションは図2 の手順で扱える。ローテーションしないソース(Google、ローテーション無効の Slack)では保留は不要で、更新トークンがローテーションするソース(GitHub)でだけ、数分の保留という小さな状態が生じる。

Orchestrator の経由は交換で扱う

クライアントが Orchestrator 宛てに得たトークンを Orchestrator が Gateway へそのまま渡すと、MCP の認可仕様が禁じる passthrough と同じ形になる。「ESC は中継者に無意味だから渡してよい」という解釈は、暗号化が消すのが「読める」ことだけで、仕様が守ろうとしている混乱した代理・audience の束縛・中継者の方針の迂回には答えていない。「Orchestrator と Gateway を一つの認可ドメインとみなす」解釈は筋が通る(同じ運用者が同じイメージで配備する部品であり、仕様が想定する上流の第三者 API ではない)が、どちらの解釈も ADR-018 決定 8 の直接転送という未確定の受容を前提に積み上げている。正攻法は、Orchestrator がクライアントのトークンと自分の資格情報(LEISEN_ORCHESTRATOR_CREDENTIAL)を Gateway のトークンエンドポイントに出し、Gateway 宛ての短命トークンに引き換える(RFC 8693)ことである。交換のときに Gateway が ESC を復号し、Gateway 宛ての短命トークンに ESC を含めなければ、Orchestrator 以降に長命の秘密は流れない。認可サーバー化を引き受けるなら、この差分は小さい。

3Leisen における個人認可の要件

評価の軸を、Leisen の不変条件と ADR、および「資格情報の置き場所」で整理した要件の衝突から導く。表2 に要件と出所を示す。要件は互いに衝突するため(たとえば再同意の少なさは長命の秘密を要求し、盗難耐性は短命を要求する)、どの方式も全部は満たさない。

4評価

表3 に 4 方式を要件ごとに評価する。記号は ◎ 満たす、○ 条件付きで満たす、△ 部分的、× 満たさない。記号だけで判断せず、各欄の条件を読む。

4.1読み方

評価を要件の束で読むと、4 方式は次のように位置づけられる。

IdP トークン方式は、成立するソースでは最善である
長命の秘密がどこにもなく、同意の操作もなく、失効は IdP に追随する。制約は R10 だけで、現時点では Microsoft 365 に限られる。ID-JAG の対応ソースが増えれば、他の方式から移すべきソースが増える。他の 3 方式は「IdP トークン方式が使えないソースのための方式」として評価するのが正確である。
Token Vault は、要件を最も広く満たす既定である
唯一の弱点は、運用者が全員分の秘密を預かること(R7 の Gateway 侵入、R12)で、それ以外の要件はすべて満たす。素の LibreChat を含むすべてのクライアントで動く(R6)のはこの方式だけである。
キーチェーンと MCP クライアント方式は、要件の 3 つを同時に落とす
R7(盗難耐性)、R8(直接接続の統制)、R9(中継者の信頼)を落とす。この 3 つはどれも「平文のソーストークンが Gateway の外にある」ことから来ている。中継者の信頼は判断で受容できるが、R8 は本人に対する統制であり、受容すると docs/direct-connection.md の前提(Leisen のアプリだけを許可リストに入れれば直接接続を止められる)が崩れる。この方式を選ぶなら、その帰結を導入チェックリストと利用規程に書く必要がある。
ESC 方式は、Token Vault と同じ統制を保ちながら、運用者が秘密を持たない
R7 〜 R9 を Token Vault と同等に満たし、保管庫がない。認可サーバー化すれば R6 も標準のクライアントで満たす。代償は 4.3 節にまとめる。得るものは「Gateway の DB に利用者の資格情報が存在しない」ことに絞られ、運用者が復号できること、使用点で平文を扱うこと、鍵の漏えいの影響範囲は V1 と同じかそれ以上である。Token Vault を置き換える方式ではなく、「本人の資格情報をサーバーに永続化しない」が要件として現れた導入のための別実装と見るのが適切である。

4.2評価が前提に依存する点

表3 のいくつかの欄は、設計上の前提で評価が変わる。これらが 5 章の論点になる。

  • R6 のクライアント対応。既存の MCP クライアントには、サーバーが返した任意の値を保持して次の呼び出しに添える仕組みがない。Gateway が MCP の認可サーバーになり、発行するアクセストークンそのものを ESC にすれば、標準のクライアントがトークンを保持・再送・更新する仕組みをそのまま使える。この前提の有無で ESC 方式の R6 は △ から ○ に変わる。表3 は認可サーバー化を前提に評価している。LibreChat を使い続けることもできるが、暗号文の置き場所が UI サーバーの DB になり、接続の体験は後退する(4.3 節)。
  • R4 の責任分担。IdP での利用停止がソース側の失効に届くかは、ソースごとの経路(Slack の自動失効、Google の管理者失効、GitHub の SCIM)に依存し、Token Vault でもこれは前提である。Gateway からの能動的な失効を「必須」とするか「追加の防御」とするかで、ESC 方式の R4 の評価が変わる。
  • R9 の受容。ADR-018 決定 8 は IdP トークンの直接転送を採り、再確認事項として残っている。中継者を同じ信頼ドメインとみなす判断をすれば、キーチェーン方式の R9 は受容できる。ただし R7 と R8 は中継者の信頼とは別の問題で、その判断では解消しない。
  • ブラウザ UI の前提。素の LibreChat を参照構成とする限り、ESC をブラウザ(端末)に置く形は成立しない。認可サーバー化すれば LibreChat は標準のクライアントとして使えるが、暗号文は UI サーバーの DB に置かれる。UI を改造するか自前の UI を持つなら、ESC をブラウザに置く形が加わる。

4.3ESC 方式(認可サーバー化)のトレードオフ

盗難耐性と保管庫の有無だけで比べると、ESC 方式は Token Vault と同等以上に見える。別の観点で比べると、明確に不利になる点が 5 つある。

標準の OAuth クライアントは、ツールの応答でトークンを差し替えられない
2.5 節のとおり、Gateway が呼び出しの途中で更新したソースのトークンは、クライアントが refresh_token グラントを出すまで届かない。更新トークンがローテーションするソース(GitHub)では、401 で引かせる手順と数分の保留が要る。ソースによっては小さな状態が戻ってくる設計であり、V1 にはこの問題がない。
「質問の中で接続する」体験が成り立たない
新しいソースを接続すると ESC を作り直す必要があり、クライアントが OAuth をやり直す(再接続する)ことになる。標準の MCP クライアントは接続時と 401 のときにしか OAuth を始めないので、未接続の案内から接続して同じ質問を自動で再実行する導線は、「設定で MCP サーバーを再接続する」に後退する。V1 では接続ページでソースを足せば次の呼び出しから効く。
認可サーバーという大きな攻撃面を自前で持つ
認可エンドポイント、トークンエンドポイント(認可コード、更新、交換)、PKCE、動的クライアント登録、メタデータ、リダイレクト URI の検証、クライアント認証、失効エンドポイント。ADR-018 がこれを避けたのは量だけでなく、認可サーバーの不具合がそのまま成りすましにつながるからである。スタックには既に Keycloak があり、認可サーバーを二重に持つことになる。MCP の認可仕様はまだ動いており(2026-07-28 版、SDK v2 への移行待ち)、作り直しの可能性がある。
本人認証の層が入れ替わる
今は MCP クライアントが IdP のトークンを持ち、Gateway がそれを検証する(ADR-010 追補の iss / typ / azp / aud 検証、auth-check、allowedClients)。認可サーバー化すると、クライアントが持つのは Gateway 発行のトークンになり、IdP トークンは認可エンドポイントでの本人認証にだけ使われる。既存の検証の契約、LibreChat の設定、リファレンス構成の realm 設定が一通り変わる。ADR-018 決定 8 の再確認事項は決着するが、移行の作業は小さくない。
鍵の漏えい時の回復が全員の再同意になる
V1 では鍵を替えて保管庫を再暗号化すれば利用者には見えない。ESC では配布済みの暗号文が全部無効になり、全員が全ソースに再同意する。鍵の定期ローテーションにも同じ制約がかかる(旧鍵の猶予期間の間に全クライアントが更新を通ることが前提)。さらに、中継者のログや DB に残った暗号文も鍵の漏えいで平文になるため、被害範囲は暗号文が通過した場所すべてに広がる。

運用で効いてくる点もある。接続状態が中央になく、利用者ごとの未接続の理由を Gateway から調べられない。端末ごとの同意がソース側の認可一覧に積み上がる(Google は OAuth クライアントごと・アカウントごとに更新トークンの上限があり、超えると古いものが黙って無効になる)。IdP での利用停止時に Gateway がソースへ失効を依頼できず、拒否リストを ESC の最長寿命以上の期間持ち続ける。接続中のソース全部のトークンが毎回の Authorization ヘッダに載る。E2E テストと CI に認可サーバーのフローが入る。

判断の分かれ目は、「本人の資格情報をサーバーに永続化しない」が要件なのか好みなのかである。導入先の方針として必須であれば、上の問題を引き受けてでも採る価値がある。そうでなければ、最初の 2 点(ソースによる状態の復活と、接続体験の後退)だけで Token Vault が勝る。

5今後の論点

検討を進めるために設定する論点を、依存関係とともに挙げる。図3 に依存関係を示す。上流の論点ほど先に決める。

A. Gateway を MCP の認可サーバーにするか
RFC 9728 / 8414 のメタデータとトークンエンドポイントを Gateway に実装し、発行するアクセストークンそのものを ESC にすれば、標準の MCP クライアントと LibreChat が追加対応なしに ESC を保持・再送・更新する(2.5 節)。ADR-018 はこれを避けて IdP トークンの直接転送を選んだ。ESC 方式の実現性はこの判断にほぼ依存する。認可サーバー化しない場合、ESC 方式は leisen-ask の CLI など Leisen が実装を持つクライアントに限られる。認可サーバー化する場合の代償は 4.3 節(攻撃面、本人認証の層の入れ替え、接続体験の後退)。
B. 中継者の信頼ドメイン
UI サーバーと Orchestrator を Gateway と同じ信頼ドメインとみなすか。「ESC は中継者に無意味だから渡してよい」「Orchestrator と Gateway は一つの認可ドメイン」のどちらの解釈も、中継者の侵入単独に対してはリスクを拡大しないが、仕様適合の根拠としては弱く、鍵の漏えいと組み合わさる事象では中継者に残った暗号文の分だけ拡大する(2.5 節、4.3 節)。認可サーバー化するなら、Orchestrator に LEISEN_ORCHESTRATOR_CREDENTIAL で Gateway 宛てのトークンへ交換させる(RFC 8693)のが正攻法で、ADR-018 決定 8 の再確認事項は「直接転送をやめる」形で決着する。
C. 失効の責任分担
IdP での利用停止に対して、Gateway からソースへ能動的に失効を依頼することを必須とするか、ソース側の経路(SCIM 等)を一次とし Gateway の依頼を追加の防御とするか。後者なら、ESC 方式の R4 は Token Vault と同等に扱える。いずれにせよ GitHub の SCIM 連携などソース側の前提は導入チェックリストに残る。
D. ブラウザ UI の前提
素の LibreChat を参照構成とし続けるなら、ブラウザ経路は Token Vault(と IdP トークン方式)で固定される。UI を改造するか自前の UI(T-009)を持つなら、ブラウザに ESC を置く形が加わる。この判断は個人認可の範囲を超えて UI 戦略の判断でもある。
E. Token Store の IF と並立
Gateway のコネクタに渡す Credential の供給元を Token Store の IF で抽象化し、Token Vault と ESC を実装として並立させるか。ADR-005 の 3 つのプラグイン境界に 4 つ目を足すか、Auth Adapter の内側に収めるかを含む。
F. ESC の詳細設計
暗号方式と形式(JWE)、sub と sourceId の結び付け、最長寿命、拒否リストの単位と保持期間、接続ページから保持者への受け渡し(ワンタイムコードの引き換え、URL モードの入力要求の再開、別オリジンへの postMessage)、MCP 上での載せ方(_meta か、A の場合はアクセストークン)。
G. 鍵の運用
Token Vault でも ESC でも Gateway は master key を持つ。ESC では鍵の漏えいが配布済みの全件に及び、鍵を替えると全員が再同意になる。KMS の非エクスポート鍵、世代管理と猶予期間、漏えい時の手順をどこまで要求するか。
H. ローテーションと並行呼び出し
Orchestrator は 1 つの run で複数の呼び出しを並行させる。更新トークンがローテーションするソース(GitHub)で競合しないよう、Gateway が run の間だけ更新後のトークンを持つか。クライアントへの差分の受け渡しは、標準の OAuth の枠では「401 で引かせ、refresh_token グラントで渡す」形になり(図2)、差分の保留の上限(MCP のアクセストークンの寿命)と、保留が切れた場合に再同意に倒すことを決める。保留を長くするほど Token Vault に近づく。
I. 接続状態と計測
Gateway が保管庫を持たない方式では、「接続中のソース一覧」や未接続の判定、昇格判定の接続率を、保持者の提示と監査の事象(接続、提示、拒否)から導くことになる。どの事象を監査に残すかの定義。
J. 既定と検証計画
上の論点を踏まえた決定。現時点の見立ては次のとおり。(1) IdP トークン方式を成立するソース(M365)で先に実装し、ID-JAG の対応ソースを調査して auth-matrix を改訂する。(2) 方式 A のソースの既定は Token Vault とし、ブラウザ UI 経路はこれで固定する。(3) ESC 方式は、「本人の資格情報をサーバーに永続化しない」が導入先の要件として現れた場合の別実装と位置づけ、A(認可サーバー化)の判断と合わせて leisen-ask の CLI で PoC を行い、図2 の手順の挙動(GitHub のローテーション)と接続体験の後退の程度を測ってから採否を決める。(4) キーチェーン方式(平文)は、R8 を受容しない限り採らない。

本書の評価は、「資格情報の置き場所」で整理した前提(使用点は Gateway、呼び出しは中継者を経る、bearer token の性質)に基づく。前提のうち不変条件 2 を緩める(端末常駐エージェントがソースを直接呼ぶ)場合は、監査と未認可候補の境界(ADR-012)の設計が変わるため、本書の範囲外とした。
