探索の調整を繰り返せる構造にする
ランタイムとエージェント定義の分離、評価ハーネスの設計

Orchestrator が LLM にツールを繰り返し呼ばせて回答を作る処理は、現状では、プロンプトを書き換えて質問セット全体を流し直す方法でしか調整できません。1 回の run に約 1 分かかり、失敗の原因を調べる記録もありません。

この文書は、その調整を小さな単位で繰り返せるようにする設計を解説します。設計の柱は 2 つです。1 つは、Orchestrator をランタイムとエージェント定義に分け、評価したエージェント定義を変更せずに利用者向けの環境へ持っていくことです。もう 1 つは、評価の判定を検査の集合として定義し、広い評価で見つけた失敗を、より小さく速いテストへ移していくことです。

設計は ADR-026(Proposed、人間レビュー待ち)に記録しており、実装は T-027 と T-028 に分けています。

1現状では、試せる単位が質問セット全体しかなく、失敗の原因を追えない

現在の評価は dev-eval で行っています。dev-eval は質問セットを読み、質問ごとに leisen-ask を子プロセスとして起動し、結果を Markdown の表にします(図1)。

この構造には、調整を繰り返すうえでの問題が 4 つあります。

LLM に渡す文言が 5 か所に分かれており、バージョン名がその一部しか指していない

評価レポートに出る explore.v3 は、表1 の 1 行目だけを指します。残りの 4 か所を変えても、バージョン名は変わりません。そのため、2 つの評価結果の差がどの文言の差によるものかを特定できません。

表1LLM に渡す文言の置き場所
場所内容
packages/orchestrator/prompts/explore.v3.mdsystem prompt の固定部
packages/orchestrator/src/prompt.ts催促、最終ターンの指示、データの前置き、上限の通知
packages/orchestrator/src/tools.tsUSAGE_HINTS(ツールの使い方の指針)
packages/orchestrator/src/answer.tssubmit_answer の説明
packages/gateway/src/proxy/tools.tsGateway が返すツールの説明

バージョンの切り替えにコードの編集が要る

EXPLORE_PROMPT_VERSION は定数です。Orchestrator には systemPrompt オプションがありますが、leisen-ask と dev-eval からは指定できません。T-024 も「v3 のコミットで dev-eval を流すか、版を指定する手段を足す」としています。

失敗の原因を調べる記録がない

T-022 の評価レポートは、不合格の原因を「監査は検索語をハッシュでしか残さないため語は推定できない」としたうえで、推定で分類しています。監査ログが検索語を隠すのは設計どおりです。調査のための記録は、監査ログとは別に持つ必要があります。

評価の単位が run 全体しかない

T-022 の計測では、1 run の所要時間の中央値は 52 秒でした。20 問を 2 回ずつ、合計 40 run を順に実行しています。複数文書の質問は 6 run で 3 回の合格でした。この回数では、プロンプトを改訂して結果が変わっても、改訂の効果と偶然を区別できません。

run、探索ループ、質問セット、合成コーパス、監査ログは、リポジトリの既存の定義のまま使います。ADR-026 で新しく導入する用語は表2 のとおりです。

「探索」は従来どおり、LLM がツールを繰り返し呼ぶ処理(探索ループ)だけを指します。プロンプトやハーネスの試行錯誤は「実験」と呼びます。

3Orchestrator を、変えない部分と差し替える部分に分ける

調整のたびに差し替えるものを 1 つにまとめ、エージェント定義とします。不変条件に関わる処理はランタイムに残し、エージェント定義からは変更も無効化もできないようにします(図2)。

この分け方には、3 つの判断が含まれています。

エージェント定義にはコードを入れない

コードを入れると、ランタイムの内部の関数やデータ構造までが互換性の対象になり、ランタイムを変更しにくくなります。探索ループの構造を変える実験をしたい場合は、ランタイムに新しい方式を足し、エージェント定義からそれを選ぶ形にします。

LLM に渡すツールの説明は、エージェント定義だけが持つ

現在は、Gateway が返す説明に USAGE_HINTS を連結して LLM に渡しています。このままでは、Gateway をアップグレードしただけで LLM の挙動が変わります。ADR-026 では、Orchestrator が LLM に渡す説明をエージェント定義の文言だけにします。Gateway の説明は、Orchestrator を通さずに接続する MCP クライアントのためのものになります。ツールの引数の形は、従来どおり Gateway の tools/list の値を使います。

検証規則は、種類だけをエージェント定義で選ぶ

出典の検証は検索に固有の処理ですが、作り話の引用やインジェクションで誘導された引用を落とす安全上の役割もあります。そのため、実装はランタイムが持ち、エージェント定義は種類を選ぶだけとします。検証なしは選べません。

ループの上限には例外があります。deployment.yaml の orchestrator.maxIterations は、費用と API 呼び出しの増幅を抑えるための値です。エージェント定義の値がこれを超える場合は、deployment.yaml の値を使います。

4実験環境で評価したエージェント定義を、変更せずに実行環境へ持っていく

試行錯誤を行う場と、利用者に回答を提供する場を分けます。両方の環境で同じランタイムのコードを使い、実験環境で採用を決めたエージェント定義を、内容を変えずにリリースへ同梱します(図3)。

同じランタイムを使うのは、実験環境の結果が実行環境でも成り立つための条件だからです。

実験環境だけが持つ機能は 2 つあります。候補のエージェント定義をファイルから読み込むことと、トレースを保存することです。これらを実行環境の CLI に持たせると、本番で誤って有効になる経路ができます。そのため、評価ハーネスは別のパッケージに置き、表3 の 3 つの手段で経路を閉じます。

表3実験環境の機能が実行環境で有効にならないようにする手段
手段内容
依存の向き実行環境のパッケージ(@leisen/orchestrator、@leisen/gateway)は評価ハーネスを import しない。npm run lint:imports で検査する
CLI の入口leisen-ask と leisen-ask serve は、エージェント定義をファイルから読むオプションと、トレースを出力するオプションを持たない
配布するイメージdeploy/Dockerfile の runtime ステージに、評価ハーネスのパッケージを含めない

評価ハーネスを隠すことは目的ではありません。リポジトリは公開するので、誰でも clone して実行できます。防ぐのは、設定の誤りで本番に入ることです。

トレースのコールバックは、ランタイムのライブラリ API として実行環境のパッケージに含まれます。@leisen/orchestrator をライブラリとして組み込む利用者は、コールバックを指定できます。自分でコードを書いて指定する場合は、誤って有効になる状況には当たらないので許容します。ただし、実データで使うと不変条件 7 に抵触しうることを、ライブラリの文書に明記します。

トレースには検索語と文書の本文が入ります。そこで、評価ハーネスは Gateway を同一プロセスで起動し、開発用コネクタだけを接続します。外部の Gateway の URL は受け取りません。実データを対象とするトレースは、ADR-026 では認めていません。

5導入先は、最良の既定を使うか、特定のエージェント定義に固定するかを選べる

精度を優先する導入先には、そのリリースで最良と評価されたエージェント定義を既定で提供します。一方で、企業での利用では、動作が固定され、変更を管理できることも重要です。そこで、deployment.yaml で特定のエージェント定義に固定できるようにします。

orchestrator:
  agents:
    search:
      definition: default                  # 既定
      # definition: explore.v3@sha256:…    # 固定
表4既定と固定の違い
既定固定
使われる定義そのリリースで最良と評価されたもの指定したもの
アップグレード時変わりうる変わらない
向いている導入先精度を優先する動作の変更に社内の承認が要る

既定は 1 つのエージェント定義ではなく、モデルの系統からエージェント定義への対応表で決めます。最良の文言はモデルによって違うためです。対応表を変更する PR には、評価レポートを添付します。

選べるのは、リリースに同梱されたエージェント定義だけです。導入企業が自作した定義を読み込む機能は持ちません。したがって、エージェント定義は ADR-005 のプラグイン境界には当たらず、不変条件 8 の「3 つのプラグイン境界」は変わりません。

指定を解決できない場合は、起動を拒否する

次のいずれかに当たる場合、Orchestrator は起動しません。既定への切り替えは行いません。黙って切り替えると、固定したという前提が崩れるためです。

  • 指定した名前のエージェント定義が同梱されていない
  • 同梱された内容のハッシュが、指定と一致しない
  • エージェント定義の形式のバージョンに、ランタイムが対応していない
  • 指定したエージェント定義が、取り下げの一覧に入っている

固定が保証するのは、エージェント定義の同一性だけである

エージェント定義を固定しても、動作のすべてが固定されるわけではありません(表5)。この範囲は、運用者向けの文書に明記します。ランタイムのセキュリティ修正は、固定している導入先にも適用します。

表5エージェント定義を固定しても変わりうるもの
変わりうるもの理由固定する手段
モデルエイリアスの指す先が変わる。ローカルのモデルを入れ替えるモデル ID を日付付きのスナップショットで指定する
ランタイムアップグレードで無害化や検証の実装が変わるリリースのバージョンを固定する
ソース側の検索の挙動SaaS 側の変更なし

導入企業が、いつ・どのエージェント定義で動いていたかを後から示せるように、AnswerRun にエージェント定義の識別子を記録します。値は Orchestrator が POST /runs で申告し、Gateway が監査ログに書きます。

6判定は、合否 1 つではなく検査の集合にする

現在の dev-eval は、試行ごとに合格・不合格・エラーのどれか 1 つを返します。これでは、失敗が出力の形式によるものか、内容によるものか、してはいけないことをしたためなのかを区別できません。区別できないと、文言で直すのか、ランタイムのコードで吸収するのかを決められません。

ADR-026 では、判定を検査の集合として定義し、検査ごとの結果を試行結果に記録します(図4)。

表6検査の種類と、検索エージェントでの例
種類意味例
形式出力がランタイムの求める形を守ったか催促なしで submit_answer を呼んだ。ツールの引数が壊れていない。出典が検証で落ちていない
達成その質問で達成すべきこと期待した文書を引用した。期待した outcome だった。回答が期待する語を含む
禁止その質問でしてはいけないこと回答本文に URL が残る。無関係な文書を引用する。文書にない内容を答える。権限外の文書を引用する

3 つの種類は、公開されている評価の実装に由来します。SWE-bench は、修正で通るようになるべきテストと、壊してはいけないテストを分けています。Aider は、正答率とは別に、指定した編集形式を守れた割合を報告しています。

形式の検査は、ランタイムが吸収した回数を表す

ランタイムの催促、出典の検証、無害化は、モデルの出力の乱れをコードで吸収する処理です。形式の検査の通過率は、その吸収が必要なかった割合を表します。文言の改訂で乱れを減らし、残りをコードで吸収するという分担を、数値で追えるようになります。

このために、トレースには各ターンの要求と応答に加えて、ランタイムが吸収した事象(催促、壊れた引数、検証で落ちた出典、無害化での除去、上限への到達)を含めます。現在の dev-eval は上限への到達を warnings の文言で判定していますが、これをトレースのイベントからの計算に改めます。

「答えなかった」と「間違えた」を区別する

現在は、resolved を期待した質問に unresolved で答えた場合も、誤った文書を引用して答えた場合も、同じ不合格です。Leisen では、誤った回答より「見つからなかった」と答えるほうが望ましいので、この 2 つは区別します。試行の結果は、正解・誤答・回答せず・エラーの 4 値にします。エラーは、LLM や Gateway の障害など、環境に由来する失敗です。

質問には、達成すべきことと、してはいけないことの両方を書く

現在の質問の期待値は、outcome と引用すべき文書だけです。そのため、無関係な文書を一緒に引用しても合格します。質問ごとに、引用してはいけない文書や、回答が含んではいけない語を書けるようにします。あわせて、合成コーパスに、正解に似ているが誤りの文書、古い内容の文書、指示を埋め込んだ文書、質問者の権限では見えない文書を足します。

7評価は 3 つの層で行い、見つけた失敗を下の層のテストにする

評価の層は、試行の大きさではなく、失敗の原因で分けます。こう分けると、失敗を見つけたあとに何をするかが決まります(図5)。この構成は、Zed がコード編集エージェントの評価で採っているものです。

表73 つの層の比較
層モデル1 回の所要時間用途現状
広い評価実モデル約 1 分(1 run)エージェント定義を採用するかの判断dev-eval がある
確率的テスト実モデル数秒(1 ターン)個別の振る舞いの回帰確認未実装
決定的テスト使わない1 秒未満実装の不具合の回帰確認脚本テストがある

確率的テストは、探索の途中の 1 ターンだけを繰り返す

探索は、検索語を決める、0 件のあとに言い換える、ヒットした文書を fetch するか決める、探索を打ち切るか決める、といった個別の判断の連続です。確率的テストでは、トレースから探索の途中の状態(質問、ソース一覧、そこまでのツール呼び出しと結果)を取り出し、評価したいエージェント定義の文言で組み立て直して、LLM に 1 ターンだけ応答させます。

判定は機械的に行えるものが多くあります。検索語であれば、返ってきた語で実際にコーパスを検索し、正解の文書がヒットするかを確かめます。T-022 の不合格のうち「2 つ目のヒットを fetch せずに打ち切った」は、その状態からの 1 ターンを多数回実行するテストになります。

この方法には限界があります。途中までの履歴は別のエージェント定義で生成されたものなので、評価対象のエージェント定義が実際に到達する状態とは限りません。そのため、採用の判断は広い評価で行い、確率的テストは個別の振る舞いの回帰確認に使います。

8安定性は、平均の合格率ではなく「毎回合格するか」で測る

T-022 の計測を質問ごとに並べると、図6 のようになります。試行の合格率は 40 回中 37 回で 92.5% ですが、2 回とも合格した質問は 20 問中 18 問で 90% です。

導入企業にとって意味があるのは、同じ質問に毎回正しく答えられるかです。そこで、τ-bench が使っている pass^k(同じ質問を k 回実行して、すべて合格する確率)を主な指標にします。集計の式はコードで固定し、試行結果と一緒に記録します。公開されている評価の実装では、集計の式が公開先ごとに違い、結果を比較できなくなった例があるためです。

費用の制約もあります。手元のモデルで 20 問を 5 回ずつ流すと、約 1.5 時間かかります。質問セット全体では k を 3〜5 にとどめ、回数が要る振る舞いは、1 回が数秒で済む確率的テストで測る分担とします。

9試行結果には、比較できるかを判断するための版を記録する

試行結果は JSONL に追記し、比較レポートはそこから生成します。2 つの結果を比べてよいかを後から判断できるように、試行を特定する値に加えて、表8 の版を記録します。

表8試行結果に記録するもの
記録するもの理由
エージェント定義の識別子、質問の ID、モデル、試行回試行を特定する
コーパスのハッシュ、質問セットのハッシュ質問や文書を変えた前後の結果を混ぜない
ランタイムのコミットランタイムの変更による差を切り分ける
Gateway の tools/list のハッシュツールの引数の形が変わると結果が変わる
検査の集合の版、集計の式の名前判定と集計を変えた前後の結果を混ぜない

ランタイムのコミットを記録すると、同じエージェント定義を新旧のランタイムで評価して、ランタイムの変更による精度の低下を検出できます。現在はこの確認の手段がありません。

入力に含まれる日付は固定します。現在は最初の user ターンに実行日が入るため、別の日の試行は入力が異なります。

11実装は ADR-026 の承認のあと、T-027、T-028 の順に進める
