1結論の要約

  • A は妥当。ただし A と B の差は「境界を作るか作らないか」ではない。共通 IF(継ぎ目)はどちらでも作る(ADR-022 決定 3)。差は、その IF の実装を誰が供給でき、どう解決されるかである。
  • A を「Token Store 一枚の enum」として作ると後で詰まる。個社差分が出るのは、その下の 2 層(鍵の包み方 = KMS、暗号文の置き場 = DB 等)である見込みが高い(推測)。enum はこの 2 層に分けて置くのがよい(A')。
  • B へ進む条件は「2 社目の要望」ではなく、もっと狭い。下位層の組み込み追加で吸収できない差分が出たときだけで、その場合も Token Store 全体ではなく「暗号文しか見ない保管バックエンド」だけを外に開くのが安全である(B'')。
  • ESC(Gateway の鍵で暗号化した資格情報を端末が持つ方式)は、A でも B でも「差し替え」では入らない。採るならコアの変更になる。

2文脈: この問いは設計のどこにあるか

用語と現状のコード

「Auth Adapter」は ADR-010 決定 1 の「ソース別 Auth Adapter」で、コード上は CredentialProvider(packages/gateway/src/idp/types.ts:92-100)にあたる。これは IdpAdapter の共通骨格 CredentialResolvingIdpAdapter に束ねられ、userId × sourceId のキャッシュ越しに呼ばれる(idp/adapter.ts:15-54、idp/cache.ts:38-44)。「Token Vault」は、本人の更新トークンを暗号化して預かる保管庫である。

つまり ADR-005 の「3 つのプラグイン境界」のうち、コードを外から読み込めるのは Connector だけである。issue #23(open、方針コメントは確認できなかった)がこの不一致を指摘し、ADR-005 の改訂方向として「(A) 動的プラグインとコア内の差し替え口を分けて書く /(B) IdP・資格情報方式・監査も module で動的に読む /(C) 閉じた列挙を正とする」を挙げている。

関係する決定

問いの位置

確認事項 3 は ADR-022 の中では小さく見えるが、issue #23 の「プラグイン境界とは何か」の最初の具体例になる。ここでの決め方が、IdP Adapter・監査 sink・LLM バックエンド(ADR-017 確認事項 7)の扱いの前例になる。

3論点: 「境界を決める」とは何を決めることか

「境界」という語は少なくとも 3 つの別のものを指しうる。混ぜると議論がずれる。

  1. 継ぎ目(seam): コア内部の IF。テストの差し替えと実装の並立のため。A でも B でも作る。
  2. 設定の選択点: deployment.yaml のどのキーで何を選べるか。
  3. コードの供給境界: コア以外の者が書いたコードを Gateway に入れられるか。ADR-005 の「プラグイン境界」が本来指すのはこれ。

A と B の差は 3 だけである。そのうえで、決めることは次の 10 点に分解できる。

論点 2 について補足する。Node には同一プロセス内の隔離がないので、module で読み込んだコネクタも技術的にはプロセスの環境変数とメモリに届く(ADR-021 帰結「module の明示そのものは、引き続き設定から任意のコードを読み込む経路」、文脈「混入したコードはそれらに届く」)。したがって B は「悪意あるコードの到達範囲」を新しく広げるわけではない。B が変えるのは次の 2 点である。

  • 設計上の正規のデータの流れとして、全員分の長命の秘密が外部コードを通ること。コネクタが受け取るのは「いまの呼び出しの本人 1 人・1 ソースの短命トークン」だけである。
  • 正しさの責任が外に出ること。暗号化の誤り、userId を含まないキー、ログへの混入は、IF の外からコアが検査できない。

4選択肢の空間

層の分解(選択肢を並べる前提)

「Token Store」は一枚ではない。責務で 4 つの層に分かれる(以下、L1 〜 L3b)。

現行の TokenVault IF(types.ts:142-154)は L2 と L3b を 1 つに混ぜている。revoke のコメントは「ソース側の revoke エンドポイント呼び出しと保管削除」で、保管の IF がソース API の呼び出しまで含む。この形のまま外に開くと、外部コードが平文とソースの失効 API の両方を持つことになる。

選択肢

E が不成立な理由は次の 5 点である。

  1. コネクタは動的に読み込む唯一の境界で、そこへ長命の秘密を設計として流すことになる(ADR-021 文脈)。
  2. コネクタの契約は「factory の中でソース API を呼ばない」「connector-sdk にのみ依存」で、資格情報は AuthContext で受けるだけ(plugins.ts:24-34)。変えるならコネクタ IF の変更で ADR が要る(不変条件 5)。
  3. 退職時の一括失効(TM-C4)と接続事象の監査(ADR-022 決定 7)を Gateway で一元化できない。
  4. OAuth クライアントのシークレットをサーバー側に固定する前提(ADR-022 決定 6、docs/direct-connection.md §2)が崩れる。
  5. userId を含むキー(不変条件 4)の保証がコネクタごとになる。

ESC と方式 B はどこに収まるか

  • 方式 B(都度交換)は L1 の別実装で、Token Store を使わない(idp-adapter-guide.md の方式表、auth-matrix.md §12.1)。確認事項 3 の対象外。
  • ESC を ADR-022 決定 5 は「Token Store の別実装」と呼ぶが、L3 の差し替えでは入らない。理由は 2 つある。
    • 現行の retrieve(userId, sourceId) は「要求に添えられて届く暗号文」を表現できない。ESC が収まる継ぎ目は L1(getCredential(identity)。Identity が提示物を運ぶ)である。検討メモ 10-15 §5.5 も「保管庫から取り出されるか、要求に添えられてくるかの違い」と書いている。
    • ESC は Gateway の MCP 認可サーバー化(確認事項 1)と一体で、authenticate()、接続ページ、失効の経路まで変わる(ADR-022 評価の要点)。1 つの IF の裏に閉じない。

したがって ESC は A でも B でも「プラグインとして後から足す」ことはできず、採るならコアの変更になる。「B にしておけば ESC を外で作れる」という期待は成り立たない。A を選ぶことで ESC の道が狭まることもない。

5A と B の位置付けと評価

図1 は、主な案が 4 つの層のどこをコアに持ち、どこを設定で選び、どこを外部コードにするかを並べたものである。A、A'、A'' はコードの供給者がコアだけのまま、選択点の置き方が違う。B は全層を外へ開き、B'' は L3b だけを開く。

論点ごとの評価

B が勝つのは論点 6 だけで、その利点は B''(L3b だけ開く)や A''(プログラム登録)でほぼ同じだけ得られる。B は「必要な柔軟性に対して開く範囲が広すぎる」案と位置づけられる。

A の弱点の正体

A の弱点は「最初の 2 社が別のクラウドを使う」ときに現れる(推測。KMS はクラウドごとに異なるため起こりやすい)。このとき選べるのは次の 3 つで、どれを採るかは未決である。

  1. 不変条件 9 を「要件 = KMS で鍵を包むこと」の単位で読み、KMS の種類は同じ要件の変種として組み込みを足す。
  2. A'' のプログラム登録口で導入先が自前の KeyProvider を注入する。
  3. フォーク(ADR-005 帰結の「contrib/ またはフォーク」。現在リポジトリに contrib/ はない)。

推奨

  1. A を採る。具体形は A'(Vault のロジックはコア 1 実装、KeyProvider と保管バックエンドを別々の組み込み enum で選ぶ)。テスト用を兼ねて A'' の注入口を assembleGateway に置くかは、公開契約になる点を踏まえて ADR で決める。
  2. この決定の意味は「Token Store を継ぎ目として持つが、コードの供給境界にはしない」である。ADR-005 の境界は 3 つのまま。ADR-005 の改訂は issue #23 でまとめて行う。
  3. B は Token Store 全体としては採らない。将来開くなら暗号文しか見ない保管バックエンド(B'')に限る。

6B へ移る判断基準

次のいずれかが成立したら見直す。「2 社目が出た」だけでは移らない(2 社で再現したなら組み込みに足せばよい)。

逆に、L2(Vault のロジック)を外に開くトリガーは見当たらない。失効連動・本人照合・監査事象は全社共通の統制で、差し替える理由が個社差分ではないため。

7A を選ぶいま、やっておくこと

後で B'' に移る、あるいは他の案に変える場合に、やり直しを小さくするための配慮である。

  1. IF を層で分ける。現行 TokenVault(types.ts:142-154)を、L2(コアの具象。ソースへの失効依頼を含む)と L3a KeyProvider・L3b 保管(狭い IF)に分ける。L3b は不透明なバイト列と userId / sourceId のキーだけを扱い、平文もソース API も知らない形にする。これで将来 B'' に移るとき IF を作り直さずに済む。
  2. L3b の IF に最初から必要な操作を入れる。更新トークンのローテーションの直列化には比較交換(版つきの置き換え)が、一括失効と定期突合(TM-C4)には userId での列挙と保有者の列挙が要る。現行 IF にはどちらもない。
  3. Token Store は CredentialProvider に注入し、IdpAdapter 実装には渡さない。組み立ては assemble.ts で行う。IdP Adapter が将来外部コードになっても Vault に触れない。deprovisioning の処理(キャッシュ破棄 invalidateUser と Vault の一括失効。types.ts:120-125)はコア側で束ねる。
  4. 設定は導入単位で 1 か所に置き、方式の選択と分ける。例(メモの例示であり既存スキーマではない): 
    credentials:
  tokenStore:
    keyProvider: { kind: aws_kms, keyId: "..." }    # L3a の enum
    storage:     { kind: postgres, urlEnv: "..." }  # L3b の enum
connectors:
  - id: gdrive
    auth: { provider: oauth_individual }            # L1 の選択(既存の位置)
    kind の判別共用体にしておけば、後で module を足す変更は追加で済む。秘密は環境変数名で参照する(schema.ts 冒頭の規律、不変条件 6)。スキーマ変更なので版と移行関数が要る(ADR-005 帰結)。
  5. 起動時拒否を先に決める。開発用の鍵(ローカルの鍵ファイル等)は本番で拒否(検討メモ 10-14 §4)。方式 A のコネクタがあるのに tokenStore が未設定なら拒否。方式 B だけの導入では tokenStore を要求しない。
  6. 契約テストを IF と一緒に書く。ユーザー間の分離(不変条件 4)、暗号文以外が保管に渡らないこと、Slack 由来の識別子が保管されないこと(不変条件 7、ADR-022 決定 7)。組み込み実装が増えても、将来外に開いても同じテストを当てられる。
  7. import 境界を機械的に守る。packages/audit と同じく npm run lint:imports で、L3 の実装が proxy/ やコネクタを import しないことを検査する(推測: 既存スクリプトの拡張で足りる)。
  8. ADR に語彙を書く。ADR-022 決定 3 の確定時に「Token Store は ADR-005 のプラグイン境界ではなく、コア内の差し替え口である。実装の追加は不変条件 9 に従う」と明記し、issue #23 の方向 A(動的プラグインとコア内の差し替え口を分けて書く)と揃える。idp/factory.ts:4-5 と schema.ts:225-226 の「コア改変を要しない」という既存コメントは実態と合っていない(issue #23 の指摘どおり)ので、同じ誤りを Token Store で繰り返さない。
