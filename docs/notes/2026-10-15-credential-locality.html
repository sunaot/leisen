1問い

前回の検討では、本人ごとの OAuth を使うソース(Google Drive、Slack、GitHub など)で、更新トークンを保管して自動更新し、退職時に一括で失効させる機能を「必須」とし、その置き場所としてサーバー側の Token Vault を既定にした。これに対して次のコメントがあった。

サーバー側でやらないでもっとローカルに寄せられるといいのになぁと思うんですけどねぇ。Web ブラウザーのローカルストレージとかだとアレなんですかねぇ。

この問いは「ブラウザの localStorage は危ないか」という個別の話に見えるが、実際には秘密をどこに置き、どこで使い、どう取り消すかという一般的な問題の一例である。本書は、まずこの問題がなぜ難しいのかを構造として説明し(2 章)、解決手段を直交する軸で整理し(3 章)、標準・製品・事故の実例でそれぞれの軸がどう現れたかを確かめ(4 章)、そのうえで Leisen においてローカルに寄せる案を列挙して評価する(5 章)。

先に結論を述べる。ブラウザの localStorage に更新トークンを置く構成は、ブラウザアプリ向けの OAuth のベストプラクティス(RFC 10017、BCP 212)が「業務アプリには推奨しない」とする構成であり、Leisen ではそれ以前に経路上成り立たない(ソース API を呼ぶのは Gateway であり、ブラウザではない)。一方で「サーバーに秘密を永続化しない」こと自体は、端末側の機密保管(MCP クライアントの OS 保護領域)と、Gateway の鍵で封緘した資格情報をクライアントが持ち歩く形で、MCP クライアント向けには成り立つ。ブラウザのチャット UI 向けには、サーバー側の保管が残る。

2問題の構造: なぜ「置き場所」が難しいのか

2.1bearer token: 持っている者が本人

OAuth のアクセストークンと更新トークンは、既定では bearer token である。提示した者が誰であれ、トークンが有効ならソースは要求に応じる。これは「鍵を持っている者がドアを開けられる」のと同じで、トークンの所持が権限そのものになる。ソースは本人を認証しているのではなく、同意の際に発行した秘密の所持を確かめているだけである。

したがって、資格情報の問題は本質的に「秘密の複製をどこに何個置くか」の問題になる。複製が多いほど盗まれる場所が増え、複製が少ないほど使える場所が限られる。

2.2使用点の必然: 暗号化は使う場所では効かない

保管を暗号化しても、トークンはソース API を呼ぶ瞬間には必ず平文になる。これを「使用点」と呼ぶ。暗号化が守れるのは、保存先(ディスクやストレージ)が盗まれる場合と、鍵と暗号文が別々に盗まれる場合だけで、使用点を乗っ取った攻撃者には効かない。使用点の乗っ取りとは、同じプロセス・同じオリジン・同じユーザー権限でコードを実行されることであり、ブラウザでは XSS、端末ではマルウェア、サーバーでは侵入がそれにあたる。

この帰結は単純だが重要である。秘密を置ける場所の候補は、ソース API を実際に呼ぶ主体に限られる。呼ぶ主体と違う場所に置けば、使うたびにそこへ運ぶ必要があり、運ぶ経路が新たな使用点と経路の露出を生む。Leisen では不変条件 2(すべてのソースアクセスは Gateway を通る)により、ソース API を呼ぶ主体は Gateway である。これが 5 章の議論の出発点になる。

2.3信頼境界の問題: 公開クライアントと同一オリジン

OAuth 2.0(RFC 6749)はクライアントを「機密クライアント」と「公開クライアント」に分ける。機密クライアントは秘密を守れる環境(サーバー)で動き、公開クライアントは守れない環境(ブラウザ、ネイティブアプリ)で動く。この区別は実装の巧拙ではなく、環境の定義である。ブラウザは利用者が自由にコードを検査・改変できる環境であり、そこに置いた秘密は利用者本人にも、本人になりすましたコードにも読める。

ブラウザの信頼の単位はオリジン(スキーム・ホスト・ポートの組)である。同じオリジンで動く JavaScript はすべて同じ主体として扱われ、localStorage も IndexedDB も Cookie(HttpOnly でないもの)も区別なく読める。XSS とは「攻撃者のコードが同じ主体になる」ことであり、これに対して同じ主体が持つ秘密を暗号で守る方法は原理的にない。RFC 10017 は、ブラウザ内の保管先を一つずつ検討したうえで「いずれの選択肢もトークンの持ち出しを完全には防げない」と結論している(8.5 節)。

端末のネイティブアプリでも構図は同じである。macOS の Keychain や Windows の DPAPI はディスク上の暗号化とアプリ単位のアクセス制御を提供するが、同じユーザー権限で動くマルウェアは、鍵を読むのではなく正規のアプリに代わって復号を頼むことができる。Chrome が 2024 年に導入した App-Bound Encryption が、数週間のうちに複数のインフォスティーラーに迂回された経緯は、使用点が端末にある限りこの構図から逃れられないことを示している(4.3 節)。

2.4失効の問題: 複製に対する取り消しは到達を保証できない

bearer token の検証は、ソースがトークンの有効性を自分の記録で確かめる(オンライン)か、署名と期限だけで確かめる(オフライン、自己完結型の JWT など)かのどちらかである。オフライン検証は速く可用性が高いが、失効が期限まで届かない。オンライン検証は即時に失効できるが、毎回の照会が要る。これは分散システムのキャッシュ無効化と同じ構造で、一貫性と可用性・遅延のトレードオフである。

さらに、失効はあくまで発行元が受け付けを拒むことで実現する。複製された秘密を遠隔から消すことはできない。退職者の端末に残ったトークンは、発行元(ソース)が拒むまで有効であり、保管側ができるのは「自分の持つ複製を消す」ことと「発行元に失効を依頼する」ことだけである。失効を依頼するには複製を手元に持っている必要がある(Google の tokens.delete や Slack の auth.revoke はトークンかその識別子を要求する)。つまり、一括失効の能力は、秘密を中央で持つことと表裏一体である。

2.5中継の問題: 混乱した代理

秘密を使用点以外に置くと、使うたびに運ぶことになる。運ぶ経路に中継者(チャット UI のサーバー、Orchestrator)がいれば、中継者はその秘密を読める。中継者が自分の判断でなく、渡されたトークンの権限で下流を呼ぶ構造は「混乱した代理(confused deputy)」と呼ばれ、下流が中継者を信頼する根拠が崩れる。MCP の認可仕様が「MCP サーバーはクライアントから受け取ったトークンを上流へそのまま渡してはならない」と定め、トークンの audience 検証(RFC 8707)を必須にしているのは、この問題への対処である。Leisen の参照構成は IdP トークンをチャット UI から Orchestrator、Gateway へ直接転送しており(ADR-018 決定 8、再確認事項として残る)、これと同じ経路にソースのトークンを乗せれば、問題は二重になる。

3解決手段の設計空間

解決手段は製品や機能の名前で語られがちだが、整理すると五つの直交する軸に分解できる(表2)。実際の製品はこの軸の組み合わせであり、軸ごとに選択肢とトレードオフが決まっている。

3.1保管場所と使用点の組み合わせ

五つの軸のうち、設計の形を最も強く決めるのは A(保管場所)と E(使用点)の組み合わせである。図2 はこの二軸の平面に、代表的な構成を配置したものである。対角線上(保管場所と使用点が一致する構成)は秘密を運ぶ必要がなく、対角線から離れるほど運ぶ経路が長くなる。

Leisen の制約を図2 に当てはめると、選べるのは「中間サーバー」の列(と、ソースが対応する範囲で「ソース側で交換」の列)に限られる。その列の中で、保管場所をサーバーから端末側へ動かすと、対角線から外れて「毎回提示」の形になる。ローカルに寄せる問いは、毎回提示の経路をどう安全にするかという問いに置き換わる。これが 5 章の L2・L3 の論点である。

3.2結び付けと失効が軸を補う

保管場所の弱さは、残りの軸で部分的に補える。送信者制約(C)は「盗んだトークン単体では使えない」状態を作り、保管場所がブラウザや端末でも被害を限る。ただし RFC 10017 が指摘するとおり、結び付けは「トークンの保管の問題を鍵の保管の問題に移す」だけであり(9.2 節)、使用点を乗っ取った攻撃者は鍵を取り出さずに署名を依頼できる。短命化(B)と継続評価(D)は、盗まれた複製が有効な時間を縮める。これらは置き場所の選択を代替するのではなく、どの置き場所を選んでも併用する手段である。

4実例: 標準・製品・事故

3 章の軸がどのように現れるかを、標準、製品、事故の順に見る。製品は「その設計がどの軸をどう選んだか」、事故は「どの困難が現実になったか」の例である。

4.1標準: RFC 10017(BCP 212)OAuth 2.0 for Browser-Based Applications

2026 年 8 月に発行されたこの BCP は、ブラウザで動く OAuth クライアントの構成を三つに分け、「安全性の高い順」に並べている。

Backend for Frontend(BFF、6.1 節)
サーバー側の機密クライアントがトークンを保持し、ブラウザには HttpOnly Cookie のセッションだけを渡す。すべてのリソース要求をサーバーが代理する。「業務アプリ、機密を扱うアプリには強く推奨する」。
Token-Mediating Backend(6.2 節)
サーバーが機密クライアントとしてトークンを取得し、アクセストークンだけをブラウザに渡す。更新トークンはブラウザに出ない。「BFF が使えない事情があるときに限って選ぶ」。
Browser-Based OAuth Client(6.3 節)
ブラウザが公開クライアントとして全フローを行い、トークンを自分で持つ。「これまでに述べたすべての攻撃に脆弱」であり、「業務アプリ、機密を扱うアプリ、個人データを扱うアプリには推奨しない」(6.3.4.3 節)。

保管先については 8 章で一つずつ検討し、結論は一貫している。Cookie を JavaScript から書く方法は「推奨しない」(8.1 節)。Service Worker は「完全に隔離された環境」を提供するが、永続ストレージ(IndexedDB)はメインウィンドウと共有であり、さらに悪意のあるコードが Worker の登録を解除できるため「このパターンは推奨しない」(7.4.1.1 節)。メモリ上の変数は現在の実行文脈に露出を限るが、ページを再読み込みすると消え、prototype 汚染で破れる(8.4 節)。localStorage は「悪意のある JavaScript からの不正アクセスを防がない」(8.5 節)。そして「ブラウザのストレージがディスク上で暗号化されている保証はない」(8.6 節)。

XSS 攻撃者にできることは四つに分類されている(5.1 節)。一度きりの窃取、継続的な窃取、新しい認可フローの実行による独立したトークンの取得、ブラウザを踏み台にした代理要求である。このうち三つ目については「フロントエンドにこれを防ぐ現実的な仕組みはない」と明記されている。表3 に構成ごとの帰結をまとめる。

この BCP が示すのは、ブラウザという環境では「保管先の工夫」が限界に達しており、解決は保管先ではなく使用点をサーバーに移す(BFF)ことだという判断である。Leisen の Gateway は、この意味でソース API に対する BFF に相当する。

4.2製品: 端末側に秘密を置く設計

ssh-agent: 鍵は出さず、署名だけを提供する

端末側保管の最も成功した例は ssh-agent である。秘密鍵はエージェントのメモリに置かれ、ディスクには書かれず、外部には出ない。クライアントはエージェントに「この内容に署名してほしい」と頼み、署名結果だけを受け取る。これは軸 C の送信者制約を端末常駐プロセスで実現した形で、「秘密を運ばずに所持を証明する」設計の原型である。

ただし、この設計の限界も同じ例に現れている。エージェント転送(agent forwarding)を使うと、リモートホストの root はソケット経由で署名を依頼でき、鍵を盗まずに利用者になりすませる。2026 年 8 月には、エージェントをロックすると要求の出所の検査が無効になる不具合(OpenSSH 10.4、10.5 で修正)も報告された。「鍵が外に出ない」ことと「署名能力が悪用されない」ことは別であり、後者は使用点の問題である(2.2 節)。

CLI ツール: OS 保護領域か、権限 0600 のファイルか

開発者向け CLI は、端末に長命の資格情報を置く設計を長く続けてきた。Claude Code は macOS では Keychain の項目に、Linux と Windows では ~/.claude/.credentials.json(権限 0600)にアクセストークンと更新トークンを置く。AWS の Identity Center は ~/.aws/sso/cache に既定で平文の JSON を書き、研究者は ~/.aws/credentials と同じ重要度で守るべきだと指摘している。MCP の mcp-remote ブリッジも権限 0600 のトークンファイルを使う。いずれも「同じユーザー権限で動くプロセスには読める」前提であり、守っているのは他ユーザーとディスク盗難からだけである。Keychain を使う場合でも、2026 年に報告された Claude Code の例のように、項目のアクセス制御の設定次第で任意のプロセスから読める状態になりうる(報道ベースであり一次資料は未確認)。

ブラウザと OS: 端末の鍵への結び付け

端末側で盗難耐性を上げる最近の取り組みは、保管先の暗号化から、端末の鍵への結び付け(軸 C)に重心を移している。Chrome の App-Bound Encryption(2024 年 7 月、Chrome 127)は Cookie の復号を SYSTEM 権限のサービスに結び付けたが、数週間のうちに Lumma、Vidar、StealC などが迂回を主張し、Elastic は COM 経由の復号依頼、リモートデバッグ、プロセス注入の三系統を文書化した。Google 自身が「突破不能ではなく、攻撃のコストを上げ検知しやすくする」ものだと述べている。これを受けた Device Bound Session Credentials(DBSC、2026 年 4 月に Windows の Chrome 146 で公開)は、TPM や Secure Enclave の持ち出せない鍵でセッションを結び付け、短命の Cookie を鍵の所持証明のたびに再発行する。Microsoft Entra の Token Protection も同じ発想で、端末に結び付いた Primary Refresh Token から発行されたセッションだけを受け付ける。いずれも「盗んだトークンを別の端末で使う」攻撃を無効にするが、端末そのものを乗っ取った攻撃者には効かない。

4.3製品: サーバー側に秘密を置く設計

Auth0 の Token Vault は、外部プロバイダのアクセストークンと更新トークンを接続ごとの tokenset として保管し、アプリは Auth0 の更新トークンを RFC 8693 のトークン交換でプロバイダのアクセストークンに引き換える。アプリは利用者に再認可を求めずにプロバイダの API を呼べる。AI エージェント向けに、エージェントがプロバイダの資格情報を直接扱わないことを売りにしている。これは軸 A をサーバー、軸 E を「サーバーが交換を仲介」にした構成で、図2 の「サーバーが交換を仲介」に相当する。Leisen の V1 案(内蔵の保管)は同じ軸の選択を、外部サービスに依存せず Gateway の中で行うものである。

サーバー側保管の対極にあるのがパスワードマネージャの「ゼロ知識」設計で、サーバーは暗号文だけを持ち、鍵は利用者の端末で主パスワードから導出する。これは軸 A のサーバー保管と軸 E の端末使用を組み合わせたもので、サーバー侵入では平文が漏れない。LastPass の 2022 年の事故は、この設計の帰結を正確に示した。攻撃者は暗号化された保管庫をサーバーから得たが、決定的だったのは DevOps 技術者の自宅 PC に仕込んだキーロガーで、MFA 通過後に主パスワードを使用点で捕らえたことだった。ゼロ知識設計は保存先と鍵を分けることに成功していたが、使用点(2.2 節)は守れなかった。

4.4製品: 保管しない設計

保管しない設計は、IdP とソースの間に事前の信頼関係があるときだけ成り立つ。Entra ID の On-Behalf-Of は、アプリが受け取った IdP のトークンを Microsoft Graph 向けのトークンに都度交換する。IETF で策定中の Identity Assertion JWT Authorization Grant(ID-JAG、draft-ietf-oauth-identity-assertion-authz-grant、2026 年 5 月に -04)は、RFC 8693 のトークン交換と RFC 7523 の JWT グラントを組み合わせ、ソースの認可サーバーが SSO で信頼している IdP の発行するアサーションを根拠にアクセストークンを発行する。Cross-App Access と呼ばれるこの方式が広がれば、方式 A のソースの一部が「保管なし」に移れる。現時点では対応ソースの調査が要る。

4.5事故: 困難が現実になった例

四件に共通するのは、失われた秘密が端末または経路上の bearer token であり、暗号化や MFA が「使用点の後ろ」で無力だったことである。業界の対応は、保管先の暗号化を強めることではなく、結び付け(DBSC、Token Protection)、短命化、継続評価(CAE、Shared Signals)へ向かっている。これは 3.2 節の「結び付けと失効が軸を補う」という見方と一致する。

5Leisen でローカルに寄せる選択肢と評価

5.1前提: 使用点は Gateway、呼び出し元はブラウザではない

Leisen の参照構成では、ソース API を呼ぶのは Gateway のコネクタである(不変条件 2)。利用者からソースまでの経路は、ブラウザ → チャット UI のサーバー(LibreChat) → Orchestrator → Gateway → コネクタ → ソースであり、MCP クライアント(Claude Code 等)から使う場合は、クライアント → Orchestrator(leisen-ask serve) → Gateway → ソースである。どちらの経路でも、ブラウザや端末が Gateway を直接呼ぶのではなく、間に一つか二つの中継者がいる。

この前提から、ブラウザの localStorage に置いたトークンが Gateway に届く経路は存在しない。LibreChat は別オリジンのサーバーアプリであり、ブラウザの localStorage を読めない。Gateway の接続ページが自分のオリジンの localStorage や Cookie にトークンを書いても、ソースへの呼び出しは Orchestrator 経由で来るため、その Cookie が付くことはない。つまり「ブラウザのローカルストレージ」は、Leisen では安全性を論じる以前に配線として成り立たない。成り立たせるには、チャット UI を Gateway を直接呼ぶ SPA に作り替える必要があり、それは RFC 10017 が業務アプリに推奨しない構成(6.3 節)をわざわざ選ぶことになる。

ローカルに寄せる案として意味があるのは、したがって次の形に限られる。秘密はMCP クライアント(端末)が保持し、呼び出しのたびに Gateway へ提示し、Gateway はその要求の間だけ使って永続化しない。これは RFC 10017 の Token-Mediating Backend を裏返した形であり、図2 の「毎回提示」の位置にある。問題は、提示の経路に中継者がいることと、提示する秘密が bearer であることの二つで、L3 はこの二つに答える案である。

5.2案の列挙

L0 ブラウザの localStorage に更新トークンを置き、呼び出しに添える
5.1 節のとおり、参照構成では Gateway に届かない。届かせるために UI を SPA 化しても、RFC 10017 6.3 節の構成になり、XSS で更新トークンが長期に盗まれ(表3)、中継者に平文が見え、退職時に Gateway から失効できない。不採用。
L1 チャット UI のサーバー(LibreChat)のセッションに保管する
「サーバーに置かない」という動機を満たさない。Token Vault が Gateway から UI サーバーへ移るだけで、監査(不変条件 2)と失効が Gateway の外に出る。UI が複数になれば保管も分散する。不採用。
L2 MCP クライアントが OS 保護領域に保持し、毎回 Gateway に提示する
Claude Code や Claude Desktop が MCP サーバーのトークンを端末に(Keychain、暗号化ファイル)保持しているのと同じ場所に、ソースのトークンも保持する。呼び出しのたびに _meta 等で Gateway に渡し、Gateway はその要求の処理が終われば捨てる。CLI 向けの既存の慣行(4.2 節)と整合する。弱点は、平文が Orchestrator を経由すること(2.5 節)、端末ごとに同意が要ること、退職時に Gateway が失効を依頼できないこと(複製を持たない)、更新トークンのローテーション(GitHub は更新のたびに新しい更新トークンを発行する)を端末側で確実に永続化しないと資格情報を失うこと、並行する呼び出しで更新が競合すること。
L3 封緘資格情報: クライアントが保持するが、Gateway の鍵で封緘されている
L2 の提示形式を変える。Gateway は接続ページの OAuth コールバックで得たトークンを、自分の公開鍵で封緘(暗号化し、userId と sourceId と発行時刻を結び付けて署名)し、暗号文だけをクライアントに返す。クライアントはこれを保持し、毎回提示する。Gateway だけが開封でき、中継者には暗号文しか見えない。盗まれても Gateway 以外では使えず、Gateway に対しても本人の IdP トークンと一緒でなければ受け付けない(封緘内の userId と IdP トークンの sub の一致を必須にする)。失効は、Gateway が秘密を持たない拒否リスト(userId、または封緘 ID)で行う。Gateway の秘密鍵が V1 の KMS 鍵と同じ位置づけの master key になる。更新で新しいトークンが得られたら、新しい封緘を応答の _meta で返し、クライアントが差し替える。ローテーションと並行更新の問題は L2 と同じく残る。
L4 保管しない(OBO、ID-JAG)
ソースが対応する範囲で最善。現時点では Microsoft 365 のみ確実で、ID-JAG の対応状況は調査中。
V1(参考)Gateway 内蔵の Token Vault(前回の既定案)
Gateway が KMS で封筒暗号化して保管し、更新・失効・並行制御をすべて Gateway が行う。

5.3失効の経路

ローカル寄せの最大の代償は失効である。図4 は IdP で利用者を停止したときに、各案でどの経路で失効が届くかを示す。V1 では Gateway が複製を持つので、ソースに失効を依頼できる。L2 と L3 では Gateway に複製がなく、ソース側の停止(Slack はアカウント無効化で自動失効、Google は管理者の失効、GitHub は SCIM 連携)に頼る。これは前回の認可実現性マトリクスが「失効の一次経路はソースごとに異なる」と整理したとおりで、ソース側の経路は L2・L3 でも V1 でも必要であり、V1 が加えるのはGateway からの能動的な失効である。L3 では端末に残った封緘は Gateway 以外では使えないため、Gateway の拒否リストが即時に効く。L2 では端末に平文の複製が残り、ソース側の失効までの間は本人(または端末を得た者)が使える。

5.4評価

5.5読み方

表5 を要件(表1)に戻して読むと、次のようになる。

  • ブラウザのチャット UI では、サーバー側の保管が残る。UI が別オリジンのサーバーアプリである以上、端末側に置いた秘密は Gateway に届かない。残る選択肢は、Gateway が持つ(V1)か、UI サーバーが持つ(L1)かであり、監査と失効の観点で V1 が勝る。
  • MCP クライアントでは、L3 が「サーバーに秘密を永続化しない」構成として成り立つ。クライアントは既に MCP サーバーのトークンを端末に保持しており、封緘を同じ場所に置くことは既存の慣行と整合する。中継者に暗号文しか見せず、盗まれても Gateway と本人の IdP トークンがなければ使えない点で、L2 や L0 より明確に強い。代償は、端末ごとの同意と、ローテーションの取りこぼしで再同意になることである。
  • L3 は V1 を置き換えるものではなく、Token Store の別実装である。Gateway の視点では、資格情報が「保管庫から取り出される」か「要求に添えられてくる」かの違いであり、コネクタに渡す Credential は同じ形になる。前回の検討で提案した Token Store の共通 IF が、この二つを両立させる境界になる。
  • 保管なし(L4)が最善であることは変わらない。ID-JAG の対応状況の調査は、ローカル寄せの議論とは独立に進める価値がある。

L3 の封緘形式は、本セッションの実行環境が外部サービスに対して渡す「封緘された秘密」(sealed secret: 受け手の鍵で暗号化され、経路上の誰にも読めず、受け手だけが使える値)と同じ考え方である。この形は MCP の認可仕様が禁じる「トークンの passthrough」にはあたらない。中継者が渡すのは中継者自身には使えない暗号文であり、Gateway は自分宛てに封緘された値だけを開封するからである。ただし、仕様上の位置づけ(_meta に載せるか、独自ヘッダか)は ADR で決める必要がある。

6結論と未決事項

「ローカルに寄せる」という希望は、安全性の議論に入る前に、Leisen の構造(使用点が Gateway にあり、呼び出し元が中継者を経る)によって形を限定される。ブラウザのストレージは配線として成り立たず、端末側に置く案は「毎回提示する」形に限られる。その形の中で、平文を提示する L2 は中継の問題と端末の平文の問題を抱え、Gateway の鍵で封緘して提示する L3 はその両方に答える。L3 は MCP クライアント向けに「サーバーに秘密を永続化しない Token Store」として検討する価値があり、ブラウザ UI 向けには V1 が残る。

本書は分析であり、次の点を決めるには ADR が要る。

  1. Token Store を共通 IF とし、V1(Gateway 保管)と L3(封緘をクライアントが保持)を実装として並立させるか。ADR-005 のプラグイン境界との関係。
  2. L3 の封緘形式: 暗号化と署名の方式、userId と sourceId の結び付け、IdP トークンの sub との照合、鍵ローテーションと猶予期間、拒否リストの保持期間。
  3. L3 で封緘を運ぶ位置(MCP の _meta、独自ヘッダ)と、MCP の passthrough 禁止との整理。ADR-018 決定 8 の IdP トークン直接転送の再確認と合わせて扱う。
  4. 更新トークンのローテーションを端末側が取りこぼした場合の扱い(再同意に倒すか、Gateway が短期間だけ最新の封緘を控えるか。後者は V1 に近づく)。
  5. ID-JAG(Cross-App Access)に対応するソースの調査と、auth-matrix の改訂。

本書で引用した製品の挙動(Claude Code の保管先、AWS SSO キャッシュ、Chrome ABE の迂回、DBSC の提供状況)は 2026 年 10 月時点の公開情報による。Silverfort が報告した Claude Code の Keychain の設定に関する指摘は、本セッションから一次資料に到達できず、報道の要約に基づく。
