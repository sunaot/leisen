個人の認可の実現方式

日付 2026-10-14 状態 検討中(ADR 起案前) 関連 ADR-005 / ADR-010 / ADR-013 / ADR-014 / ADR-018 / T-004 / auth-matrix

利用者本人の資格情報で各ソースにアクセスする仕組みを、利用者の体験、管理者の負担、安全性の 3 つの面から比べます。目標は、Claude のコネクタ(設定で「接続」を押し、OAuth に同意すれば使える)と同等以上の体験を、Leisen の不変条件を守ったまま実現することです。

0結論

  1. 接続は質問の中で求める。未接続のソースがあれば部分的な回答と接続ボタンを返し、許可が済んだら同じ質問を自動でやり直す。設定画面での事前接続は補助の導線にする。
  2. 接続の画面は Gateway が持つ。どのチャット UI や MCP クライアントから使っても同じ導線になり、保管・失効・監査が Gateway の中で完結する。
  3. 操作の要らない方式に寄せられるソースは寄せる。SharePoint / OneDrive は Entra ID の On-Behalf-Of で利用者の操作が要らない。IdP 起点のアクセス許可(ID-JAG)に対応したソースがあれば同じ扱いにできるので、調査する。
  4. 本人ごとの OAuth を使うソースでは、Token Vault の機能は必須。ただし実装先は差し替えられるようにし、既定は内蔵の保管(KMS で暗号化)とする。Keycloak の identity brokering は検証してから判断する。
  5. leisen を通さない直接接続は、権限は越えないが統制が抜ける経路として扱う。leisen への同意は OAuth アプリ単位なので直接接続の許可にはならない。ソース側のアプリ許可リストと Gateway の allowedClients で塞ぎ、塞げない経路は規程で扱う。接続の設計では、トークンを Gateway の外に出さないことと、leisen の方が便利な体験にすることで迂回の動機を消す。

1前提と制約

Claude のコネクタが簡潔に見える理由

Claude の体験が短いのは、裏の作業が済んでいるからです。OAuth クライアントの登録と各社の審査(Google の Restricted scope など)を Anthropic が済ませているため、利用者は同意画面を 1 度通るだけで済みます。Leisen は 1 デプロイ = 1 社で、アプリの登録と承認は導入企業が行います(Slack は類型 (a) で確定)。そのため、利用者の体験と管理者の体験を分けて評価します。

一方で Leisen には、Claude にない有利な条件が 2 つあります。社内 IdP の SSO がすでに通っていること、そして利用者が何を聞こうとしているかが分かった状態で接続を求められることです。

4Token Vault の検討

Token Vault は、本人ごとの OAuth で得たトークンを暗号化して保管し、更新し、失効させる部品です(ADR-010 決定 2)。要るかどうかは方式で決まります。

方式ごとの要否

方式該当ソース保管理由
A. 本人の OAuthGoogle、Slack、GitHub、Confluence、Notion要同意で得たトークンを次回以降も使うには、どこかに保管するしかない
B. token exchangeSharePoint / OneDrive不要毎回 IdP のトークンから交換する。失効は IdP のセッションに追随する
ID-JAG要調査不要B と同じく毎回交換する
C. 委譲された身元SMB、S3、社内 DB不要方式ごとに ADR が要る(T-017)

保管しない場合の再同意(方式 A)

保管しない場合、アクセストークンの寿命が切れるたびに同意をやり直すことになります。下の図は、9 時から 18 時まで使い続けた場合の同意の回数です。

前提: 「保管しない」は、更新トークンを捨ててアクセストークンだけを使う運用。Gateway のメモリにだけ持つ運用では、再起動やスケールアウトのたびに全員が許可し直す。Slack の user token はトークンのローテーションを有効にしない限り期限がない。Confluence(1 時間)や Notion の寿命は実装時に確認する 要確認。

保管しない代わりにチャット UI やブラウザにトークンを持たせる案は成り立ちません。MCP 仕様が禁じるトークンの中継にあたり、Gateway を通らない経路ができやすく(不変条件 2)、退職時の一括失効もできなくなります。

Token Vault が満たすべき要件

暗号化して保管TM / T-004

KMS の鍵でデータ鍵を包む封筒暗号化。開発用はローカルの鍵ファイルでもよいが、本番では拒否する。

本人単位で分ける不変条件 4

キーは userId と sourceId の組。ユーザー間で共有しない。

値を外に出さない不変条件 6

ログ・監査・エラーには値を出さず、redactAuthContext() を通す。

自動で更新する体験

更新トークンで静かに更新し、更新トークンのローテーションにも追随する。Credential.expiresAt の意味を T-004 で確定する。

退職時に一括失効TM-C4

IdP の利用停止(SCIM 等)を受けて、その人の全ソースのトークンを失効させる。Slack の tokens_revoked などソース側の通知も取り込む。

本人が解除できる体験

接続中のソース一覧から本人が解除できる。解除・失効・接続は監査に記録する(不変条件 2)。

Slack の識別子を残さない不変条件 7

トークン応答に含まれる Slack のユーザー ID などは保管しない。本人照合は接続時に済ませて捨てる。

失効を体験に変えるT-004

失効やスコープ不足はエラーではなく「再接続」の導線として返す。

5推奨構成

部品の配置

接続の流れ 呼び出し 任意の実装 利用停止による失効

Token Store を新しいプラグイン境界にするか、Auth Adapter(または IdP Adapter)の内側に収めるかは ADR で決めます(ADR-005 は境界を Connector / IdP Adapter / Search Backend の 3 つに限っている)。

接続の流れ(Google Drive が未接続の場合)

接続ボタンは、クライアントが対応していれば MCP の URL モードの入力要求で出し、対応していなければ回答のリンクで出します(2026-07-28 版仕様の MRTR での扱いは要確認)。OAuth 要求には PKCE、IdP セッションに結び付けた state、login_hint を付けます。

ソースごとの手間の段階

操作なし

管理者の設定だけで使える

  • SharePoint / OneDrive(OBO)
  • ID-JAG 対応ソース 要調査

保管不要。ドメインワイド委任もここに入るが、ADR で例外承認した場合に限る。

1 回の許可

質問の中で 1 度だけ許可する

  • Google Drive、Slack(公開)、GitHub
  • Confluence、Notion

Token Vault が必要。管理者の事前承認と SSO で警告とログインが消える。

追加の許可

必要になったときに範囲を広げる

  • Slack の private チャンネル・DM
  • 既定で外している範囲(privateScopes)

最初の許可は狭く。広げるのは本人の判断に任せる。

Claude のコネクタにはない安全策

本人の照合

接続直後に、ソース側のアカウントと IdP の本人が一致するかを確かめる。私用アカウントの誤接続を拒否する。

セッションへの結び付け

state を IdP セッションに結び付け、PKCE を使う。他人が始めた接続を自分のものとして完了させられない。

接続も監査に残す

接続・解除・失効を Gateway の監査に記録する。トークンの値は記録しない。

退職時の一括失効

IdP の利用停止で全ソースのトークンを失効させる。GitHub は SCIM 連携を導入の前提にする。

6leisen を通さない直接接続の扱い

エージェント(Claude・ChatGPT・Claude Code など)から、公式の MCP サーバーやコネクタで各ソースへ直接つなぐ場合の扱いです。既存の分析(docs/direct-connection.md)と導入チェックリスト(docs/install.md §10.1)を、個人の認可の設計とつなげて整理します。

権限

迂回しても権限は越えない

直接接続も leisen も本人の資格情報で動くので、見えるデータの範囲は同じ。失われるのは統制(文脈付きの監査、プライベートの既定除外、Slack データの非永続化、LLM の送り先の選択、一括失効)。

同意

同意は OAuth アプリ単位

利用者が leisen に与えた同意は、leisen のアプリへの同意。エージェント製品のコネクタは別のアプリなので、leisen への同意で直接接続が許されることはない。

範囲

経路を完全に一本にはできない

不変条件 2 が保証するのは、leisen 自身が抜け道を作らないことまで。組織全体の経路を絞れるかは、導入先のソース側の設定で決まる(threat-model §7)。

個人の認可の設計に入れること

接続ページは機密クライアントで許可リストの前提

leisen の OAuth クライアントはシークレットをサーバー側に持ち、リダイレクト先を固定する。利用者がこのクライアントを流用できないことが、ソース側の許可リストを成り立たせる。

トークンを Gateway の外に出さない不変条件 2

Token Vault の値をチャット UI やエージェントへ返す API を作らない。作った時点で、leisen の同意で得たトークンによる直接接続の抜け道になる。

同意画面で正規の経路と分かるように安全性

同意画面に出るアプリ名・発行元を導入先の名義で明確にし、利用規程に「承認してよいのはこのアプリだけ」と書く。似せたアプリへの同意を防ぐ。

迂回の動機を体験で消すdirect-connection §7

直接接続は「エージェントの数 × ソースの数」だけ同意が要る。leisen はソースごとに 1 回、しかも質問の中で済む。leisen が不便だと、利用は統制の弱い直接接続へ流れる。

アプリ承認制を使っていない組織では、leisen の導入と関係なく今日すでに直接接続ができます。leisen が穴を開けるのではなく、導入を機に既存の穴を塞げるかどうかの問題です。止め方は許可リストにします。ソースに見えるのはクライアント ID だけで、クライアント名は自己申告のため、拒否リストでエージェント製品を見分ける方法は成り立ちません。

8未決事項と次の作業

  1. ADR の起案:接続画面を Gateway が持つこと、本人照合、接続事象の監査スキーマ、Token Store の位置付け(新しいプラグイン境界か、Auth Adapter の内側か)。認可方式と監査に関わるため人のレビューが要る。
  2. ID-JAG / Cross App Access の調査:対応ソースがあれば auth-matrix を改訂し、「操作なし」の段階と保管不要のソースを増やす。
  3. Keycloak identity brokering の検証:外部トークンの保存・自動更新・失効の連動が V2 として成り立つかを小さく確かめる。
  4. 接続リンクと ADR-018 の両立:回答本文から URL を除く規則と、接続ボタンのリンクをどう両立させるか。リンクは設定から組み立てた信頼できる値だけにする。
  5. 直接接続の統制との接続:「Token Vault の値を外に返す API を作らない」「接続ページは機密クライアント」を ADR の決定に入れ、導入チェックリスト §10.1 から参照する。利用者単位の取得量の上限と、取得の偏りを見つける監査クエリ(direct-connection §5 で次の候補とされたもの)の扱いも決める。
  6. T-004 の受け入れ条件の追加:接続の段階ごとの監査事象、再接続の回数、Slack の識別子を保管しないことのテスト。
