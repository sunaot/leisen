1結論の要約

  • 評価単位は 13 コンポーネントとする。いずれも単体で実行する手段をすでに備えている。モック IdP、開発用コネクタ、LLM のスタブ、GitHub API のフェイクが整備されており、コンポーネントを分離して検証する基盤はある。不足しているのは、各コンポーネントに共通の指標を適用する仕組みである。
  • 現在計測できているのは、不変条件と機能の正しさに偏っている。不変条件の検査、監査ログ、1,747 件のテストは充実している。一方、運用時の性能と信頼性は監査ログの latencyMs と errorClass のみ、内部品質は型検査と 2 つの import 境界検査のみ、回答品質は合成コーパス 7 文書に対する 20 問のみで計測している。
  • 品質特性は 4 カテゴリに整理する。不変条件(合否判定)、回答品質、運用品質(性能・信頼性)、内部品質(保守性・テスト容易性)である。ISO/IEC 25010 は対応表として参照し、指標体系そのものには採用しない。
  • 評価は、CI で実行する適応度関数と、プラグイン境界ごとの適合性テストスイートを基盤とする。回答品質は評価ハーネス(dev-eval を T-008 に拡張)で計測し、シナリオベースのアーキテクチャレビューは四半期ごとに人手で実施する。
  • 運用時の観測経路は 3 系統に限定する。監査ログ(既存)、構造化運用ログ(新設。利用者・クエリ・文書を識別するフィールドをスキーマに定義しない JSONL)、分離テレメトリ(ADR-011 で決定済み、書き込み先が未実装)である。運用品質の指標は構造化運用ログのみから算出し、監査ログからは暫定的にも算出しない。このため、構造化運用ログを早期に実装する。OpenTelemetry と Prometheus はコアに組み込まず、構造化運用ログからのエクスポーターとして contrib に置く。
  • 可視化は静的レポートを標準とする。開発時は CI のジョブサマリとリポジトリ内のスコアカード、運用時は JSONL から HTML を生成する CLI(昇格判定レポートと同じ方式)を用いる。Grafana などによる常時監視は、compose の overlay として任意で追加する構成とする。
  • 時間に関する指標を、タイムアウト設定と対応付けて計測する。コード上には 13 種類の期限設定があり、実装方式と超過時のエラー分類が統一されていない。スパン別の所要時間の基本統計量、タイムアウト使用率、タイムアウト超過率、ターンアラウンドタイムとその内訳を指標として追加した(8 章)。
  • 計装はコアロジックの外側に配置する。計測は横断的関心事であるため、ポートに対する計測デコレーターと、リクエスト単位のミドルウェアを構成処理で適用し、コアロジックは計測用のモジュールを import しない構造を推奨する。監査ログの記録は不変条件 2 に基づくコアの責務であり、計測とは区別して扱う(9 章)。
  • 可視化は、閲覧するロールごとにレポートを分ける。ロールは、参照できる観測経路が異なる単位として、導入企業側に 4、OSS 側に 2 を定め、関心事項とアクセス制御に基づいて 5 種類のレポートに整理した(10 章)。この検討により、品質カテゴリには含まれない利用状況指標(利用率、利用量、コスト)と、可用性、保持期間の遵守などの指標を追加した。
  • 最初に着手するのは、指標定義表とスコアカード v0、および構造化運用ログの ADR である。本日時点の計測値を 11 章に示す。構造化運用ログと分離テレメトリは不変条件 3・6・7 に関わる新しい出力経路であるため、実装前に ADR を起票する。

4現状の評価

各コンポーネントを 4 つの品質カテゴリ(5 章で定義)に照らし、現在の計測手段を整理した。記号の意味は次のとおりである。◎ 継続的に計測している、○ 手段はあるが手動または部分的、△ 設計または文書のみ、× 手段がない。

課題

  1. 運用時のデータが監査ログに集中している。ToolInvocation にはレイテンシ、エラー分類、リトライ回数が記録されている。一方、ツール呼び出しに至らない事象(認証エラー、/runs や認可サーバーへのリクエスト、同時実行数の上限による拒否、起動時の警告)は、stderr への非構造化ログとして出力されるか、記録されていない。このため、P3・P4・P11 は単体で運用品質を計測できず、要件 R2 を満たしていない。
  2. 分離テレメトリは決定済みだが、書き込み先が実装されていない。保持期間(14 日)と削除処理の対象としては実装されているが、proxy/gateway.ts には「書き込み先が未実装のため、現在は落とす処理だけを行う」というコメントが残っている。プライベート領域の除外件数や、Phase 2 で必要になる空振り率を記録する手段がない。
  3. LLM の使用量が永続化されていない。ターン数、トークン数、コストの概算、打ち切り理由は、回答の出力と dev-eval にしか現れない。運用開始後に、コストと探索効率の推移を追跡できない。
  4. 回答品質の評価が開発環境と本番環境で分断されている。開発環境では合成コーパスに対する合否、本番環境では利用者フィードバックを用いており、両者をつなぐ評価がない。権限プロファイルを固定した評価(T-008)とカナリア文書による検証(threat-model §5)は設計段階にとどまり、要件 R5 を満たしていない。
  5. 内部品質の検査対象が 2 つの境界に限られている。CI が検査するのは、型と、audit および run の import 境界のみである。lint、カバレッジ、パッケージ全体の依存方向、複雑度は計測していない。CLAUDE.md が定める「any の使用は理由コメント必須」は、ツールによる検証が行われていない。
  6. 共有される定数とプロトコル定義が Gateway パッケージに置かれている。Orchestrator の 7 ファイルと昇格判定レポートの 2 ファイルが、@leisen/gateway から定数、ヘッダー名、runId のデコード処理を import している。コンポーネントを単体で評価する際に Gateway 全体(MCP SDK、yaml)への依存が発生するため、依存方向の検査を導入すると最初に検出される項目になる。
  7. 利用状況の指標と、閲覧者ごとの提供形態が定義されていない。設計書 4.6 節は週次アクティブ利用率を KPI として挙げているが、算出手段がない。また、既存のレポートは昇格判定レポートのみであり、運用管理者、監査担当、セキュリティ担当がそれぞれ何を参照するかが整理されていない。
  8. 所要時間が、タイムアウト設定と対応する単位で記録されていない。ToolInvocation の latencyMs は、レート制限の判定、資格情報の取得、コネクタの呼び出し、結果の射影を合算した値である。資格情報の取得(既定 10 秒)とコネクタの呼び出し(既定 30 秒)のどちらに時間を要したかを区別できない。認証(IdP への問い合わせ)と監査ログの書き込みは含まれない。
  9. 期限の実装方式と、超過時のエラー分類が統一されていない。期限は AbortSignal.timeout、Promise と setTimeout の競合、AbortController、MCP SDK のオプションの 4 通りで実装されており、超過時の分類も timeout、run_timeout、llm_timeout などに分かれている。設定値と実際の所要時間を同じ箇所で取得できないため、設定値の妥当性を検証する手段がない。
  10. 計測の処理が、コアロジックの中に記述されている。所要時間の計測と監査レコードの組み立ては Gateway.handleToolCall の内部にあり、LLM の使用量の集計は探索ループの内部状態(RunState)が担っている。計測項目を追加するたびに、コアロジックの変更が必要になる。
  11. テストは量的には十分だが、有効性を計測していない。テストコードの行数は実装コードとほぼ同等である(27,756 行に対し 29,504 行)。認可分岐のテストを最優先とする方針はあるが、認可分岐に欠陥を混入させた場合にテストが失敗するかどうかは検証していない。

判定: 個別の欠陥ではなく、設計上の課題である。個々の指標が不足しているのではなく、監査ログ以外について「どのデータを、どの経路に、どのコンポーネントが出力するか」が定義されていない。したがって目標は、指標の追加ではなく、「各コンポーネントについて 4 カテゴリの指標を、不変条件に違反せずに、3 系統の経路のいずれかへ出力できる状態にすること」と設定する。

5観測対象: 品質特性と指標

品質モデルの選択肢

カテゴリ別の指標

「データソース」が既存のものは、新規の計装なしで取得できる。新設のものは 7 章の経路を前提とする。追加 は、10 章のロール別の検討によって追加した指標である。表の末尾の利用状況指標は品質カテゴリではないが、指標定義表で併せて管理する。運用品質の指標は、構造化運用ログのみをデータソースとする。監査ログは、回答品質、利用状況、不変条件の指標に限って用いる(7 章)。

指標として採用しないもの: 検索の候補件数、フィルタリング前後の件数比、利用者別の利用回数や解決率。前二者は不変条件 3 に、後者は ADR-013 が禁じる目的外利用(人事評価、日常的な行動監視)に該当する。利用状況指標は集計値としてのみ出力し、利用者を単位とする一覧は生成しない。空振り率が必要な場合は、分離テレメトリのバケット(0 / 1-10 / 11+)のみを使用する。

6評価方法

現行設計の評価には、一度限りの評価と、継続的に実行する検査の 2 種類がある。4 章は前者を今回実施した結果である。本章では、継続的な評価の方法を選定する。

適合性テストスイートの対象境界

適合性テストスイートは connector-sdk と並ぶテスト用パッケージとして配置し、各実装のテストから呼び出す構成を想定している。コネクタ IF 自体は変更しないため、不変条件 5 に基づく ADR は不要である。ただし、IF の解釈を固定する項目(例:「存在しない文書と権限のない文書とで応答を区別できないようにする」)が既存の ADR に明記されていない場合は、ADR-016 への追補が必要になる。

7観測手段

運用時の観測経路

監査ログと運用データは、目的、保持期間、アクセス制御が異なるため、監査ログを運用上の計測に利用することは適切ではない(「オブザーバビリティの位置付け」5 章)。運用品質の指標は、同一の出来事を監査レコードとは別に構造化運用ログへ出力し、そこから算出する。構造化運用ログが実装されるまでの間も、監査ログからの算出は行わない。暫定の手段を設けると、監査ログに依存する集計処理が残り、後からの分離が困難になるためである。このため、構造化運用ログの実装を、実施計画の早い段階に置く(12 章)。

回答品質と利用状況の指標は、引き続き監査ログの集計値を入力とする。解決率、利用率などは、run の結果と利用者の識別子に基づく指標であり、監査ログが本来記録する内容から算出されるためである。

分散トレーシングについて補足する。run 内のツール呼び出しは、runId と iteration によってすでに順序付きで関連付けられており、監査ログがトレースに相当する役割を果たしている。プロセスが Orchestrator と Gateway の 2 つに限られる現在の構成では、トレースコンテキストの伝搬を別途導入する利点は小さい。

3 系統の役割分担

OpenTelemetry へのブリッジ

OpenTelemetry をコアに組み込まない理由は、属性に任意の値を設定できるためスキーマによって要件 R1 を保証できないこと、および収集基盤が前提となること(要件 R4)の 2 点である。いずれもコアの外側で変換を行えば解消するため、構造化運用ログから OpenTelemetry へのブリッジを提供する余地は残しておく。実装は、対応を求める導入先が現れた時点で行う(不変条件 9)。

ブリッジを後から追加できるようにするため、構造化運用ログのスキーマを定める際に次の 2 点を満たす。いずれも追加の実装を要しない。

  • OpenTelemetry のデータモデルに対応付けられる構造とする。スパンの完了イベントには、スパンの種類、開始時刻、所要時間、結果の分類を持たせる。これらは OpenTelemetry のスパン、またはヒストグラム型のメトリクスに変換できる。
  • 属性を、取りうる値が有限のものに限る。スパンの種類、sourceId、エラー分類、LLM バックエンドの種別などである。これは要件 R1 を満たすための制約であると同時に、メトリクスのラベルとしても適切な条件である。

ブリッジを提供しても、次のものは得られない。

  • プロセスをまたぐトレース。Orchestrator と Gateway のスパンを 1 つのトレースとして関連付けるには、トレースコンテキストの伝搬をコアに組み込む必要がある。本計画ではこれを行わないため、ブリッジ後もプロセス単位の表示となる。
  • 同一リクエストに属するスパンの関連付け。関連付けには、リクエスト単位の識別子をイベントに持たせる必要がある。個々のスパンのイベントには識別子を付与せず、内訳と処理の経過は、リクエストの要約イベント(8 章)にまとめて記録する。リクエスト参照 ID(Q8)を設ける場合も、記録するのはこの要約イベントのみとする。

監査ログと分離テレメトリは、ブリッジの対象としない。監視基盤に取り込むと、ADR-011 と ADR-013 が定める閲覧のアクセス制御を迂回することになるためである。

障害の検知と原因の特定を目的とする運用時の活動(オブザーバビリティ)、および APM などの運用ツールの扱いは、本計画の対象外とし、対になる文書「オブザーバビリティの位置付け」(docs/notes/2026-11-15-observability-positioning.html)にまとめた。

開発時の計測手段

8時間に関する指標: タイムアウトとターンアラウンドタイム

運用時には、各種のタイムアウト設定が実際の所要時間に対して妥当かどうか、超過がどの程度発生しているか、利用者が回答を得るまでにどれだけの時間を要しているかが、重要な判断材料となる。本章では、これらに関する現状の実装を確認したうえで、指標を定義する。

これまでの記載で不足していた点

タイムアウト設定の現状

コードから確認できた期限の設定は次のとおりである。値は既定値であり、多くは設定で変更できる。

現状の設定から読み取れる課題

  • 内側の期限が外側の期限と同じ値になっている箇所がある。OpenAI 互換バックエンドの LLM 呼び出しの期限(120 秒)は、run 全体の期限(120 秒)と等しい。LLM 呼び出し 1 回で run の時間をすべて消費しうる。コネクタ呼び出しの期限(30 秒)と connector-github の API 呼び出しの期限(30 秒)も既定値が等しく、どちらが先に発火するかによってエラー分類が変わる可能性がある。
  • 超過した呼び出しの実際の所要時間が記録されない。Gateway はコネクタ呼び出しの超過時に timeout を返すが、下流の処理は中断されずに継続する。この処理が最終的に何秒で完了したかは、どこにも記録されない。期限をどこまで延長すれば成功するかを判断する材料がない。
  • 期限のない区間がある。監査ログの書き込みには期限がなく、fail-closed の設定下では、書き込みの遅延がそのままツール呼び出しの遅延となる。リクエスト本文の受信は Node の既定値に依存している(minor-6)。
  • 期限に近い値で分布が打ち切られる。期限を超えた呼び出しは期限の時点で打ち切られるため、所要時間の p99 や最大値は設定値に張り付き、本来の分布を表さない。所要時間の統計量は、タイムアウト超過率と併せて解釈する必要がある。

指標の定義

ターンアラウンドタイムとその内訳は、利用者と run の識別子を持たないイベントとして構造化運用ログに記録する(Q1 の暫定方針)。1 件のリクエストに含まれる複数のスパンを集約する必要があるため、プロセス内の計測コンテキストで集約し、リクエストの完了時に要約を 1 件出力する。実現方式は 9 章で述べる。

9計装の実現方式

計測は運用の基礎となるが、検索や認可といったアプリケーションのコアロジックではなく、横断的関心事である。コアロジックへの変更を最小限に抑え、疎結合に実現する方式を検討する。

現状の構造

コードを確認した結果は次のとおりである。

  • ポートと構成処理は分離されている。Connector、IdpAdapter、CredentialProvider、LlmClient、GatewayClient、AuditSink はいずれもインターフェースとして定義されており、実装の生成と組み立ては Gateway の bootstrap/ と Orchestrator の bin/ に集約されている。構成処理で実装を別のオブジェクトで包むことができる。
  • エラーは分類コードに正規化されている。GatewayError、ConnectorError、LlmError はいずれも分類コードを持つ。呼び出しの外側から、メッセージを解析せずに結果を分類できる。
  • 時刻の取得は、多くのクラスで注入可能である。Gateway、資格情報、探索ループなどは now を引数として受け取る。
  • 計測はコアロジックの内部で行われている。Gateway.handleToolCall は、runId の検証、ツールの実行、所要時間の算出、監査レコードの組み立て、監査ログへの書き込み、生クエリ表への書き込みを 1 つのメソッドで行う。Gateway.execute は、認可に関わる検査、レート制限、資格情報の取得、期限付きのコネクタ呼び出し、結果の射影を順に行う。
  • イベントを外部に通知する仕組みはない。Gateway と探索ループには、処理の進行を通知するフックやオブザーバーがない。探索ループは、LLM の使用量と警告を内部状態(RunState)に蓄積し、結果として返却する。
  • 期限の実装は 4 通りある(8 章)。期限を適用する処理と、所要時間を取得する処理が分離しており、共通の抽象がない。

目標とする構造

監査と計測は、いずれも呼び出しを記録する点で類似するが、位置付けが異なる。監査ログの記録は不変条件 2 が定めるコアの責務であり、fail-closed の設定下では、記録の失敗が呼び出しの失敗となる。計測は、失敗しても処理の結果に影響を与えてはならない。この違いに基づき、目標とする構造を次のように定める。

  • コアロジックは、ポートと監査のみに依存する。計測のためのモジュール(レコーダー、計測デコレーター)を import しない。この依存関係を import 境界の検査(適応度関数)で保証する。
  • ポートの呼び出しは、計測デコレーターで計測する。構成処理において、各ポートの実装を計測デコレーターで包む。計測デコレーターは、構成時に適用される期限の値を受け取り、所要時間、期限、結果の分類を記録する。
  • リクエスト全体は、ミドルウェアで計測する。HTTP サーバーのリクエストハンドラーをミドルウェアで包み、ターンアラウンドタイムと応答の状態を記録する。ミドルウェアは計測コンテキストを開始し、処理中に計測デコレーターが記録したスパンを集約する。
  • 出力はレコーダーに一本化する。計測デコレーターとミドルウェアは、引数として利用者の資格情報やクエリを受け取るが、レコーダーの strict スキーマにはそれらのフィールドがないため、出力には含まれない(要件 R1)。
  • 計測の失敗は、処理に影響させない。レコーダーへの書き込みで例外が発生した場合は、計測デコレーターの内部で処理し、呼び出し元に伝播させない。

実現方式の選択肢

推奨は、B と C を主たる方式として実装し、G で利用者体感を補完する構成である。H は、暫定の手段としても採用しない。監査ログを運用上の計測に利用しないためである(7 章)。計装(計測デコレーター、ミドルウェア、レコーダー)はオブザーバビリティ層に属し、品質の観測は、出力された構造化運用ログの集計値を利用する(「オブザーバビリティの位置付け」10 章)。B と C は、いずれもコアロジックを変更しない。D は、期限の実装を共通の関数に置き換える範囲で先行し、制御全体をコアロジックの外に移すかどうかは Q7 として判断する。E は、B と C の適用後も計測できない箇所が残った場合にのみ用いる。

現状との差分

計測デコレーターが扱えない点が 2 つある。1 つは、期限を適用する処理が計測デコレーターの外側にある場合(Gateway のコネクタ呼び出し)である。この場合、計測デコレーターは下流の処理の完了を観測できるが、外側で期限が発火したことは直接には分からないため、構成時に受け取った期限の値と所要時間を比較して超過を判定する。もう 1 つは、共有されるインスタンス(LlmClient)の呼び出しを、どのリクエストに属するものとして集約するかである。これは計測コンテキストによって解決する。

10可視化手段

可視化は、提供形態(どのような手段で表示するか)と、閲覧するロール(誰に何を表示するか)の 2 点から整理する。ロールごとに、関心事項だけでなく、参照を許可される観測経路が異なるためである。

想定するロールと関心事項

ロールは、参照を許可される観測経路が異なる単位として定める。類似の製品(エンタープライズサーチ、社内向け AI アシスタント)の導入体制を参考に、導入企業側に 4、OSS 側に 2 のロールとした。小規模な導入では 1 人が複数のロールを兼ねるが、アクセス制御の単位として区別する。

経営層・予算責任者、法務・労務・プライバシーの担当者、各データソースの管理者、ヘルプデスクは、ロールとして定めない。これらの関係者は、観測経路を直接参照せず、いずれかのロールが生成したレポートの集計値を受け取る立場にあり、独自のアクセス制御を必要としないためである。レポートの配布先として、「ロール別レポートの構成」の表に記載する。利用者は、レポートではなく既存の画面(回答に付随する出典と確信度、接続ページ)によって情報を得るため、対象外とする。

ロールの検討による指標の追加

各ロールの関心事項を 5 章の指標と照合した結果、次の指標が不足していたため追加した(定義は 5 章の表に記載)。

提供形態の選択肢

ロール別レポートの構成

ロールごとの表示を実現する方法には、(a) 全指標を 1 つのレポートに掲載し、各ロールが必要な箇所を参照する、(b) 入力とする観測経路ごとにレポートを分割する、(c) ダッシュボードにロールベースのアクセス制御を実装する、の 3 案がある。(a) は、監査ログを入力とする部分と分離テレメトリを入力とする部分が同一のファイルに混在し、ADR-011 と ADR-013 のアクセス制御を満たせない。(c) は認可の仕組みをコアに追加することになる。(b) であれば、アクセス制御を「どの CLI を、誰が、どのファイルに対して実行できるか」というファイルシステム上の権限に帰着できるため、(b) を推奨する。

スコアカードは、行にコンポーネント、列に 4 つの品質カテゴリを配置し、カテゴリごとに代表指標 1 つと前回からの変化を表示する。不変条件の列は数値ではなく合否で表示し、1 件でも違反があれば当該行全体を警告表示とする。利用状況指標はコンポーネントの品質を表すものではないため、スコアカードには掲載しない。アラート(カナリアトークンの検出、監査ログへの書き込み不能)は可視化ではなく、threat-model §5.3 が定める通知経路の対象であるため、本計画の範囲外とする。

13推奨案の妥当性検証

変更シナリオ

前提に対する反例

  • 「運用品質は監査ログからすべて算出できる」は成立しない。認証エラーとなったリクエストは利用者を特定できないため、監査ログに記録されない。LLM の応答時間は Gateway を経由しない。起動に失敗したプロセスは監査ログを出力できない。この 3 点が、構造化運用ログを新設する根拠である。
  • 「構造化運用ログは利用者と関連付けられない」は、識別子のフィールドを持たないだけでは保証されない。利用者が 1 名しかいない時間帯や、特定の 1 名しか利用しないソースでは、タイムスタンプと sourceId から利用者を推定できる。保持期間を短く設定したうえで、タイムスタンプの粒度と sourceId の扱いを ADR で定める必要がある。
  • 「計測デコレーターによって、すべての期限設定を計測できる」は成立しない。run 全体の期限は探索ループの内部で適用されており、ポートの呼び出しに対応しない。リクエスト本文の受信の期限は Node のランタイムが適用する。runId の有効期間は処理の期限ではない。前者はミドルウェアが返却された結果から取得し、後二者は計測の対象外とする。
  • 「コンポーネント単体で同一の指標を取得できる」は、回答品質については成立しない。探索ループの回答品質は、LLM とコーパスの組み合わせに依存し、コンポーネント単体の値としては定まらない。回答品質は「プロンプトのバージョン × モデル × コーパス」の組み合わせに対して記録する。

14前提と未検証事項

  • 確認済みの事項: パッケージ構成、行数、テストの件数と実行時間、CI のジョブ構成、lint-imports.mjs の検査対象、監査スキーマ、proxy/gateway.ts の TODO コメント、dev-eval の評価結果(docs/eval)、パッケージ間の import。
  • コードの確認のみで、実行による検証を行っていない事項: 認証エラーとなったリクエストが監査ログに記録されないこと。レート制限による拒否が ToolInvocation に rate_limited として記録されること。コネクタ共通の適合性テストが存在しないこと(検索したが該当するものは見つからなかった)。
  • 時間に関する未確認の事項: 8 章の表で「未確認」とした、超過時のエラー分類。connector-github に実際に渡される期限の値(既定値どうしが等しいことのみ確認した)。回答のストリーミング送信の有無(ストリーミングを行う場合は、最初の応答までの時間を別の指標として定義する必要がある)。AsyncLocalStorage による計測コンテキストの実行時のオーバーヘッド(実測していない)。diagnostics_channel のうち TracingChannel の安定度(採用する場合は、対象の Node のバージョンで確認する)。
  • OpenTelemetry へのブリッジに関する未確認の事項: OpenTelemetry Collector のファイル読み取り用レシーバーによって JSONL を取り込み、メトリクスへ変換する構成は、動作を確認していない。採用時に、対象とする Collector のバージョンで検証する。
  • 計測していない指標: カバレッジ、ミューテーションスコア、依存方向の違反件数、PR ごとの変更の局所性。対応するツールが導入されていないため、値がない。段階 0〜1 で、11 章の表に列を追加して記録する。
  • 前提: 運用は導入企業の情報システム部門が担い、常時監視の基盤を持たない導入先が存在する。実 SaaS、実 IdP、実 KMS、Claude API との疎通は人手の前提条件が満たされておらず、運用品質の実測値はリファレンスデプロイと開発用コネクタでしか取得できない。
  • ロールに関する前提: 10 章のロールは、類似製品の一般的な導入体制から想定したものであり、導入先への聞き取りは行っていない。実際の導入先でロールの分担が異なる場合は、レポートの配布先のみを変更し、レポートの種類と入力は変更しない。監査閲覧担当とセキュリティ担当の権限は ADR-011 と ADR-013 の定めに従った。それ以外のロールの参照範囲は、本計画における提案である。
  • 本文書の位置付け: 分析および企画であり、決定事項ではない。3 章の論点が決定した時点で、構造化運用ログと分離テレメトリについては ADR に、合意した設計要件と用語については設計書に反映する。
