1結論の要約

  • 評価単位は 13 コンポーネントとする。いずれも単体で実行する手段をすでに備えている。モック IdP、開発用コネクタ、LLM のスタブ、GitHub API のフェイクが整備されており、コンポーネントを分離して検証する基盤はある。不足しているのは、各コンポーネントに共通の指標を適用する仕組みである。
  • 現在計測できているのは、不変条件と機能の正しさに偏っている。不変条件の検査、監査ログ、1,747 件のテストは充実している。一方、運用時の性能と信頼性は監査ログの latencyMs と errorClass のみ、内部品質は型検査と 2 つの import 境界検査のみ、回答品質は合成コーパス 7 文書に対する 20 問のみで計測している。
  • 品質特性は 4 カテゴリに整理する。不変条件(合否判定)、回答品質、運用品質(性能・信頼性)、内部品質(保守性・テスト容易性)である。ISO/IEC 25010 は対応表として参照し、指標体系そのものには採用しない。
  • 評価は、CI で実行する適応度関数と、プラグイン境界ごとの適合性テストスイートを基盤とする。回答品質は評価ハーネス(dev-eval を T-008 に拡張)で計測し、シナリオベースのアーキテクチャレビューは四半期ごとに人手で実施する。
  • 運用時の観測経路は 3 系統に限定する。監査ログ(既存)、構造化運用ログ(新設。利用者・クエリ・文書を識別するフィールドをスキーマに定義しない JSONL)、分離テレメトリ(ADR-011 で決定済み、書き込み先が未実装)である。OpenTelemetry と Prometheus はコアに組み込まず、構造化運用ログからのエクスポーターとして contrib に置く。
  • 可視化は静的レポートを標準とする。開発時は CI のジョブサマリとリポジトリ内のスコアカード、運用時は JSONL から HTML を生成する CLI(昇格判定レポートと同じ方式)を用いる。Grafana などによる常時監視は、compose の overlay として任意で追加する構成とする。
  • 最初に着手するのは、新規の計装を必要としないスコアカード v0 である。本日時点の計測値を 9 章に示す。構造化運用ログと分離テレメトリは不変条件 3・6・7 に関わる新しい出力経路であるため、実装前に ADR を起票する。

2設計要件、用語定義、コンポーネント構成

選択肢を比較する前に、計測基盤自体が満たすべき設計要件を定める。以降の選択肢は、この 5 項目を基準に評価する。

用語定義

本計画では、既存の語彙では表せない概念を次のとおり導入する。いずれも計測対象、計測経路、成果物を区別するために必要なものであり、合意した時点でプロジェクト共通の用語として設計書に登録する。「不変条件」「監査ログ」「分離テレメトリ」「プラグイン境界」「run」は既存の定義(CLAUDE.md、ADR-005、ADR-011、ADR-019)のまま用いる。

コンポーネント構成

評価単位とするコンポーネントは次の 13 個である。境界は、既存のパッケージとディレクトリ、ADR-005 が定める 3 つのプラグイン境界、ADR-017 の LLM クライアント境界に合わせた。新たな分割は導入していない。

3意思決定が必要な論点

結論によって推奨案の構成が変わる論点のみを挙げる。いずれも既存の資料からは判断できなかった。以降の章は、暫定方針を前提として記述している。

4現状の評価

各コンポーネントを 4 つの品質カテゴリ(5 章で定義)に照らし、現在の計測手段を整理した。記号の意味は次のとおりである。◎ 継続的に計測している、○ 手段はあるが手動または部分的、△ 設計または文書のみ、× 手段がない。

課題

  1. 運用時のデータが監査ログに集中している。ToolInvocation にはレイテンシ、エラー分類、リトライ回数が記録されている。一方、ツール呼び出しに至らない事象(認証エラー、/runs や認可サーバーへのリクエスト、同時実行数の上限による拒否、起動時の警告)は、stderr への非構造化ログとして出力されるか、記録されていない。このため、P3・P4・P11 は単体で運用品質を計測できず、要件 R2 を満たしていない。
  2. 分離テレメトリは決定済みだが、書き込み先が実装されていない。保持期間(14 日)と削除処理の対象としては実装されているが、proxy/gateway.ts には「書き込み先が未実装のため、現在は落とす処理だけを行う」というコメントが残っている。プライベート領域の除外件数や、Phase 2 で必要になる空振り率を記録する手段がない。
  3. LLM の使用量が永続化されていない。ターン数、トークン数、コストの概算、打ち切り理由は、回答の出力と dev-eval にしか現れない。運用開始後に、コストと探索効率の推移を追跡できない。
  4. 回答品質の評価が開発環境と本番環境で分断されている。開発環境では合成コーパスに対する合否、本番環境では利用者フィードバックを用いており、両者をつなぐ評価がない。権限プロファイルを固定した評価(T-008)とカナリア文書による検証(threat-model §5)は設計段階にとどまり、要件 R5 を満たしていない。
  5. 内部品質の検査対象が 2 つの境界に限られている。CI が検査するのは、型と、audit および run の import 境界のみである。lint、カバレッジ、パッケージ全体の依存方向、複雑度は計測していない。CLAUDE.md が定める「any の使用は理由コメント必須」は、ツールによる検証が行われていない。
  6. 共有される定数とプロトコル定義が Gateway パッケージに置かれている。Orchestrator の 7 ファイルと昇格判定レポートの 2 ファイルが、@leisen/gateway から定数、ヘッダー名、runId のデコード処理を import している。コンポーネントを単体で評価する際に Gateway 全体(MCP SDK、yaml)への依存が発生するため、依存方向の検査を導入すると最初に検出される項目になる。
  7. テストは量的には十分だが、有効性を計測していない。テストコードの行数は実装コードとほぼ同等である(27,756 行に対し 29,504 行)。認可分岐のテストを最優先とする方針はあるが、認可分岐に欠陥を混入させた場合にテストが失敗するかどうかは検証していない。

判定: 個別の欠陥ではなく、設計上の課題である。個々の指標が不足しているのではなく、監査ログ以外について「どのデータを、どの経路に、どのコンポーネントが出力するか」が定義されていない。したがって目標は、指標の追加ではなく、「各コンポーネントについて 4 カテゴリの指標を、不変条件に違反せずに、3 系統の経路のいずれかへ出力できる状態にすること」と設定する。

5観測対象: 品質特性と指標

品質モデルの選択肢

カテゴリ別の指標

「データソース」が既存のものは、新規の計装なしで取得できる。新設のものは 7 章の経路を前提とする。

指標として採用しないもの: 検索の候補件数、フィルタリング前後の件数比、利用者別の利用回数ランキング。前二者は不変条件 3 に、後者は ADR-013 が禁じる目的外利用に該当する。空振り率が必要な場合は、分離テレメトリのバケット(0 / 1-10 / 11+)のみを使用する。

6評価方法

現行設計の評価には、一度限りの評価と、継続的に実行する検査の 2 種類がある。4 章は前者を今回実施した結果である。本章では、継続的な評価の方法を選定する。

適合性テストスイートの対象境界

適合性テストスイートは connector-sdk と並ぶテスト用パッケージとして配置し、各実装のテストから呼び出す構成を想定している。コネクタ IF 自体は変更しないため、不変条件 5 に基づく ADR は不要である。ただし、IF の解釈を固定する項目(例:「存在しない文書と権限のない文書とで応答を区別できないようにする」)が既存の ADR に明記されていない場合は、ADR-016 への追補が必要になる。

7観測手段

運用時の観測経路

分散トレーシングについて補足する。run 内のツール呼び出しは、runId と iteration によってすでに順序付きで関連付けられており、監査ログがトレースに相当する役割を果たしている。プロセスが Orchestrator と Gateway の 2 つに限られる現在の構成では、トレースコンテキストの伝搬を別途導入する利点は小さい。

8可視化手段

スコアカードは、行にコンポーネント、列に 4 つの品質カテゴリを配置し、カテゴリごとに代表指標 1 つと前回からの変化を表示する。不変条件の列は数値ではなく合否で表示し、1 件でも違反があれば当該行全体を警告表示とする。アラート(カナリアトークンの検出、監査ログへの書き込み不能)は可視化ではなく、threat-model §5.3 が定める通知経路の対象であるため、本計画の範囲外とする。

9ベースライン計測(2026-11-15)

新規の計装なしで取得できる内部品質の値を、2026-11-15 に本リポジトリで計測した(npm ci と npm run build の後、パッケージごとに npm test を実行)。行数は、src 配下の .ts ファイルと *.test.ts ファイルの合計である。

この結果から次のことが分かる。テストコードの比率は、パッケージ間でおおむね均一である。テストの実行時間は orchestrator が全体の約 6 割を占めており、テスト容易性の観点では最初に調査すべき対象となる。1,000 行を超えるファイルが 3 つあり、いずれも複数の責務を持ちやすいコンポーネント(認可サーバー、探索ループ、GitHub コネクタ)に属している。行数は品質の直接的な指標ではないため、閾値は設定せず、推移のみを記録する。

11推奨案の妥当性検証

変更シナリオ

前提に対する反例

  • 「運用品質は監査ログからすべて算出できる」は成立しない。認証エラーとなったリクエストは利用者を特定できないため、監査ログに記録されない。LLM の応答時間は Gateway を経由しない。起動に失敗したプロセスは監査ログを出力できない。この 3 点が、構造化運用ログを新設する根拠である。
  • 「構造化運用ログは利用者と関連付けられない」は、識別子のフィールドを持たないだけでは保証されない。利用者が 1 名しかいない時間帯や、特定の 1 名しか利用しないソースでは、タイムスタンプと sourceId から利用者を推定できる。保持期間を短く設定したうえで、タイムスタンプの粒度と sourceId の扱いを ADR で定める必要がある。
  • 「コンポーネント単体で同一の指標を取得できる」は、回答品質については成立しない。探索ループの回答品質は、LLM とコーパスの組み合わせに依存し、コンポーネント単体の値としては定まらない。回答品質は「プロンプトのバージョン × モデル × コーパス」の組み合わせに対して記録する。

12前提と未検証事項

  • 確認済みの事項: パッケージ構成、行数、テストの件数と実行時間、CI のジョブ構成、lint-imports.mjs の検査対象、監査スキーマ、proxy/gateway.ts の TODO コメント、dev-eval の評価結果(docs/eval)、パッケージ間の import。
  • コードの確認のみで、実行による検証を行っていない事項: 認証エラーとなったリクエストが監査ログに記録されないこと。レート制限による拒否が ToolInvocation に rate_limited として記録されること。コネクタ共通の適合性テストが存在しないこと(検索したが該当するものは見つからなかった)。
  • 計測していない指標: カバレッジ、ミューテーションスコア、依存方向の違反件数、PR ごとの変更の局所性。対応するツールが導入されていないため、値がない。段階 0〜1 で、9 章の表に列を追加して記録する。
  • 前提: 運用は導入企業の情報システム部門が担い、常時監視の基盤を持たない導入先が存在する。実 SaaS、実 IdP、実 KMS、Claude API との疎通は人手の前提条件が満たされておらず、運用品質の実測値はリファレンスデプロイと開発用コネクタでしか取得できない。
  • 本文書の位置付け: 分析および企画であり、決定事項ではない。3 章の論点が決定した時点で、構造化運用ログと分離テレメトリについては ADR に、合意した設計要件と用語については設計書に反映する。
