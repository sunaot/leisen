1結論の要約

  • 部品は 13 個に分けられ、どれも単独で動かす手段をすでに持っている。モック IdP、開発用コネクタ、台本どおりに応答する LLM、偽の GitHub API があり、局所化の土台はできている。足りないのは、部品ごとに同じ物差しを当てる仕組みである。
  • いま測れているのは「約束」と「機能の正しさ」に偏っている。不変条件の検査、監査ログ、1,747 件のテストは厚い。運用時の性能と可用性は監査の latencyMs と errorClass だけ、構造の品質は型検査と 2 境界の import 検査だけ、回答の質は合成 7 文書の 20 問だけで測っている。
  • 観点は 4 面に整理する。約束(不変条件。合否で扱う)、回答の質、運用の質、構造の質。ISO/IEC 25010 は対応表として持ち、物差しそのものにはしない。
  • 評価は「CI で回る適応度関数」と「プラグイン境界ごとの適合キット」を土台にする。回答の質は評価ハーネス(dev-eval から T-008 へ)、設計の筋書きレビューは四半期に人が行う。
  • 観測の経路は 3 本に限る。監査ログ(既存)、運用イベント(新設。型に置き場がないことで不変条件を守る JSONL)、分離テレメトリ(ADR-011 で決定済み、書き込み先が未実装)。OpenTelemetry と Prometheus はコアに入れず、運用イベントからの変換として contrib に置く。
  • 可視化は静的レポートを標準にする。開発時は CI のサマリとリポジトリ内のスコアカード、運用時は JSONL から HTML を出す CLI(昇格判定レポートと同じ型)。Grafana などの常時監視は compose の overlay として任意にする。
  • 最初の一歩は、新しい計装なしで出せるスコアカード v0。今日の時点の値は 9 章に載せた。運用イベントと分離テレメトリは不変条件 3・6・7 に触れるので、実装の前に ADR を起こす。

案を並べる前に、計測の仕組みそのものが満たすべき性質を置く。以降の選択肢はこの 5 つで評価する。

部品の地図

答えによって案の形が変わるものだけを挙げる。どれも材料からは決められなかった。以降の章は、それぞれ推奨側の答えを仮に置いて書いている。

4現状の診断

部品を 4 つの観点(5 章で定義)に当て、いま何で測れているかを並べた。記号は、◎ 継続して測れている、○ 手段はあるが手動または一部、△ 文書や設計だけ、× 手段がない。

ずれの一覧

  1. 運用時の信号が監査に寄っている。ToolInvocation には所要時間、エラー分類、再試行回数がある。ツール呼び出しに至らない事象(認証での拒否、/runs や認可サーバーへの要求、同時実行の上限による断り、起動時の警告)は stderr の自由文か、記録がない。性質 S2 に対して、P3・P4・P11 は単独で運用の質を測れない。
  2. 分離テレメトリは決定済みで、書き込み先がない。保持日数(14 日)と削除の対象は実装されているが、proxy/gateway.ts に「書き込み先が未実装のため、現在は落とす処理だけを行う」と残っている。プライベート領域の除外件数や、Phase 2 の空振り率を置く場所がない。
  3. LLM 側の使用量が残らない。ターン数、トークン、費用の概算、打ち切りの理由は回答の出力と dev-eval にだけ出る。運用が始まると、費用と探索効率の推移を追えない。
  4. 回答の質の物差しが 2 つに分かれ、間がない。手元は合成コーパスの合否、本番は利用者のフィードバック。権限プロファイルを固定した評価(T-008)とカナリア検証(threat-model §5)は設計だけで、性質 S5 が満たされていない。
  5. 構造の品質は 2 境界しか見ていない。CI は型検査と、audit と run の import 境界だけを検査する。lint、網羅率、依存の向き全体、複雑度の計測はない。CLAUDE.md の「any は理由コメント必須」は道具で確かめていない。
  6. 共有の語彙が Gateway パッケージに置かれている。Orchestrator の 7 ファイルと昇格判定レポートの 2 ファイルが @leisen/gateway から定数、ヘッダー名、runId の復号を import している。依存の向きを測り始めると最初に出てくる項目で、部品を単独で評価するときに Gateway 全体(MCP SDK、yaml)が付いてくる。
  7. テストは多いが、何を守っているかは測っていない。テストの行数は実装とほぼ同じ(27,756 行 対 29,504 行)。認可分岐を最優先で書く方針はあるが、その分岐を壊したときにテストが落ちるかは確かめていない。

判定: 局所の不具合ではなく構造の問題。個々の指標が欠けているのではなく、「どの信号を、どの経路に、誰が書くか」が監査以外で決まっていない。目標は「指標を増やす」ではなく、「部品ごとに 4 面の指標を、3 本の経路のどれかに、約束を破らずに置けるようにする」と言い直す。

5何を観測するか: 品質の観点

観点の立て方の選択肢

4 面の指標

「出どころ」が既存のものは、新しい計装なしで取れる。新設は 7 章の経路を前提にする。

置かない指標: 検索の候補件数、絞り込み前後の比、利用者別の利用回数の順位。前の 2 つは不変条件 3 に、最後は ADR-013 の目的外利用に当たる。空振り率が要るときは分離テレメトリのバケット(0 / 1-10 / 11+)だけを使う。

6どう評価するか: 評価の方法

「いまの設計をどう評価するか」には、1 回きりの診断と、続けて回る検査の 2 つがある。4 章は前者を今回分として行った結果で、ここでは続け方を選ぶ。

適合キットを当てる境界

キットは connector-sdk の隣にテスト用のパッケージとして置き、各実装のテストから呼ぶ形を想定している。コネクタ IF そのものは変えないので、不変条件 5 の ADR は要らない。IF の解釈を固定する項目(たとえば「存在しない文書と権限のない文書の応答を同形にする」)が既存の ADR に書かれていない場合だけ、ADR-016 への追記が要る。

11案を揺さぶる

変化の筋書き

反例を作ってみた主張

  • 「運用の質は監査から全部出せる」は成り立たない。認証で拒否した要求は利用者が確定せず監査に入らない。LLM の待ち時間は Gateway を通らない。起動に失敗したプロセスは監査を書けない。この 3 つが運用イベントを足す根拠になっている。
  • 「運用イベントは利用者と結び付かない」は、欄を持たないだけでは成り立たない場合がある。利用者が 1 人の時間帯、sourceId が 1 人しか使わないソースの場合、時刻と sourceId から推定できる。保持を短くし、時刻の粒度と sourceId の扱いを ADR で決める必要がある。
  • 「部品だけで同じ指標が取れる」は、回答の質では成り立たない。探索ループの質は LLM とコーパスの組で決まり、部品単独の値にならない。回答の質は「プロンプトの版 × モデル × コーパス」の組に対して記録する。

名前

「テレメトリ」は ADR-011 で分離テレメトリの意味に使われているので、新しい経路をテレメトリやメトリクスと呼ばない。この計画で使う名前は 4 つ: 監査ログ、運用イベント、分離テレメトリ、品質スナップショット。「ログ」だけの呼び方は stderr の人向けの出力に限る。

12仮定と、確かめていないこと

  • 観測したもの: パッケージ構成、行数、テストの件数と所要時間、CI のジョブ、lint-imports.mjs の境界、監査の型、proxy/gateway.ts の TODO、dev-eval の結果(docs/eval)、パッケージ間の import。
  • コードを読んだだけで、動かして確かめていないもの: 認証で拒否した要求が監査に入らないこと。流量制限の拒否が ToolInvocation に rate_limited として入ること。コネクタ共通の適合テストがないこと(検索して見つからなかった)。
  • 測っていないもの: 網羅率、変異検出率、依存の向きの違反数、PR ごとの変更の局所性。道具が入っていないので値がない。9 章の表に列を足す形で段階 0〜1 で埋める。
  • 仮定: 運用は導入企業の情シスが行い、常時の監視基盤を持たない導入先がある。実 SaaS、実 IdP、実 KMS、Claude API との疎通は人手の前提待ちで、運用の質の実測値は参照デプロイと開発用コネクタでしか取れない。
  • この文書の位置付け: 分析と企画であり、決定ではない。3 章の問いに答えが出た時点で、運用イベントと分離テレメトリは ADR に、合意した性質と名前は設計書に写す。
