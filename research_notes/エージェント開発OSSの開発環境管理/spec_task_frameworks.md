## Key question 1: What taxonomy of artifacts emerges, and which are recommended to be version-controlled with the code versus ephemeral or external?

### Takeaway
Across tools and practitioner write-ups, five artifact classes recur: (1) short always-loaded rules files (AGENTS.md / CLAUDE.md / steering / constitution), (2) durable knowledge and decisions (docs/, ADRs, current-state specs), (3) per-change plans/specs/tasks, (4) session state and agent-written memory, (5) tool configuration. Classes 1, 2 and 5 are near-universally committed to the repo; class 3 is where the approaches diverge (keep forever, archive, or discard); class 4 is mostly machine-local or external, except in long-running harnesses that deliberately put progress files in the working tree.

### Cited Findings

#### 1a. Rules / context files (AGENTS.md and equivalents)
- AGENTS.md is described as "A simple, open format for guiding coding agents", plain Markdown with no required fields; the site states it "is now stewarded by the Agentic AI Foundation under the Linux Foundation" and is copyrighted by "AGENTS.md a Series of LF Projects, LLC" (opened) — [agents.md](https://agents.md/)
- Origin per the site: collaboration including OpenAI Codex, Amp, Jules (Google), Cursor and Factory; adoption claim "over 60k open-source projects" based on a GitHub code search (opened) — [agents.md](https://agents.md/)
- Tools listed as reading AGENTS.md: Codex, Jules, Factory, Aider, goose, opencode, Zed, Warp, VS Code, Devin, UiPath Autopilot & Coded Agents, Junie (JetBrains), Amp, Cursor, RooCode, Gemini CLI, Kilo Code, Phoenix, Semgrep, GitHub Copilot coding agent, Ona, Windsurf, Augment Code. Aider and Gemini CLI need configuration to read it (opened) — [agents.md](https://agents.md/)
- Nested files: put an AGENTS.md in each subproject; the nearest file in the directory tree wins; explicit user chat prompts override everything. The site says the main OpenAI repo had 88 AGENTS.md files at time of writing. Recommended content: project overview, build/test commands, code style, testing instructions, security considerations (opened) — [agents.md](https://agents.md/)
- The agents.md site does not mention CLAUDE.md; for legacy filenames it recommends renaming and symlinking (`mv AGENT.md AGENTS.md && ln -s AGENTS.md AGENT.md`) (opened) — [agents.md](https://agents.md/)
- Claude Code now reads AGENTS.md natively: the memory docs say Claude "can also read a repository's AGENTS.md files in place of CLAUDE.md". By default AGENTS.md is read only when there is no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` in the working directory or above; if both exist, only the CLAUDE.md files load unless CLAUDE.md imports AGENTS.md. Requires Claude Code v2.1.277 or later (opened) — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Claude Code layering: project instructions at `./CLAUDE.md` or `./.claude/CLAUDE.md` (shared via source control), user-level `~/.claude/CLAUDE.md`, modular rules in `.claude/rules/*.md` with optional `paths` frontmatter so they load only when matching files are touched; rules directory supports symlinks for sharing across projects (opened) — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Size guidance from Anthropic: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence"; imports organise a file but do not reduce context cost; the docs state these files are "context, not enforced configuration" and say to use a PreToolUse hook to block an action regardless of what the model decides (opened) — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Effectiveness study (ETH Zurich / LogicStar.ai; Gloaguen, Mündler-Sasahara, Müller, Raychev, Vechev; v1 12 Feb 2026, v3 29 Sep 2026): tested SWE-bench tasks with LLM-generated context files and a new issue set from repos with developer-committed context files. Abstract: "we find that providing context files does not generally improve task success rates", inference cost rises by over 20% on average, "instructions in the context files are well followed by coding agents", "repository overviews, although popular and recommended by model providers, are not helpful", and "any attempts to improve performance should be rigorously evaluated before deployment" (opened, abstract page only) — [arXiv:2602.11988](https://arxiv.org/abs/2602.11988)
- Secondary summaries of the same paper say LLM-generated files reduced success in 5 of 8 settings while human-written files fared somewhat better, and that the ICLR version's abstract is worded more negatively ("tend to reduce task success rates") (snippet; per-setting numbers not verified against the PDF) — [arXiv:2602.11988](https://arxiv.org/abs/2602.11988); [ICLR 2026 virtual page](https://iclr.cc/virtual/2026/10021142)
- OpenAI's harness-engineering team rejected a single large AGENTS.md for four stated reasons: context is scarce (large files crowd out task-relevant material), too much guidance becomes no guidance, monolithic manuals rot, and a single blob cannot be mechanically checked for coverage, freshness, ownership or cross-links. AGENTS.md is instead a short map pointing into `docs/` (opened via translation) — [npaka translation of OpenAI "Harness engineering"](https://note.com/npaka/n/nb4c5488e82fd?hl=en); original at [openai.com](https://openai.com/index/harness-engineering/)
- The AGENTS.md in that project is described as roughly 100 lines (snippet of secondary coverage; the translation I opened does not give a line count) — [InfoQ coverage](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex)
- Stripe (Minions, part 2, 19 Feb 2026): unconditional global rules are used sparingly because otherwise "the agent's whole context window would fill with rules before the agent even starts"; most context comes from rule files scoped to subdirectories or file patterns and attached automatically as the agent moves through the filesystem. Stripe standardised on Cursor's rule format and syncs those rules into a format Claude Code can read, so Minions, Cursor and Claude Code share one set of guidance without duplication (opened) — [Stripe: Minions part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)
- Anthropic context-engineering guidance (29 Sep 2025): aim for "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome"; context is "a finite resource with diminishing marginal returns" ("context rot"); Claude Code is a hybrid in which "CLAUDE.md files are naively dropped into context up front" while glob/grep retrieve files just in time (opened) — [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

#### 1b. Durable knowledge: docs as system of record
- OpenAI harness-engineering repository layout (opened via translation):
  ```
  AGENTS.md
  ARCHITECTURE.md
  docs/
  ├── design-docs/        (index.md, core-beliefs.md, ...)
  ├── exec-plans/
  │   ├── active/
  │   ├── completed/
  │   └── tech-debt-tracker.md
  ├── generated/          (db-schema.md)
  ├── product-specs/      (index.md, new-user-onboarding.md, ...)
  ├── references/         (LLM-readable reference files, e.g. uv-llms.txt)
  ├── DESIGN.md  FRONTEND.md  PLANS.md  PRODUCT_SENSE.md
  ├── QUALITY_SCORE.md  RELIABILITY.md  SECURITY.md
  ```
  — [npaka translation](https://note.com/npaka/n/nb4c5488e82fd?hl=en); original at [openai.com](https://openai.com/index/harness-engineering/)
- Rationale given: from the agent's perspective anything it cannot reach in context does not exist; Google Docs, chat threads and knowledge in people's heads are inaccessible, so decisions made in Slack had to be moved into the repo as version-controlled artifacts (opened via translation) — [npaka translation](https://note.com/npaka/n/nb4c5488e82fd?hl=en)
- Scale claims for that project: first commit late August 2025, about five months of work, about one million lines of code, about 1,500 merged PRs, team grew from three to seven engineers, roughly 3.5 PRs per engineer per day (opened via translation) — [npaka translation](https://note.com/npaka/n/nb4c5488e82fd?hl=en)

#### 1c. Decision records (ADRs) in agent-driven repos
- Recurring practitioner pattern: keep ADRs as the detailed record and put only a short pointer in AGENTS.md telling the agent where decisions live and to check them before changing the affected area; copying decisions into the instruction file is discouraged because it creates two versions to maintain (snippet) — [Flavio Copes: AI coding agent context](https://flaviocopes.com/project-decisions/)
- A Codex-oriented guide recommends an AGENTS.md policy section: check `docs/adrs/` before any architectural choice, draft a proposed ADR before implementing, mark superseded ADRs (snippet) — [Daniel Vaughan: ADRs with Codex CLI](https://codex.danielvaughan.com/2026/04/28/codex-cli-architecture-decision-records-adr-automated-governance/)
- Retrieval caveat raised in the same body of posts: writing a record does not ensure an agent reads it; an index mapping topics (storage, authentication) to decision files is suggested for larger projects (snippet) — [dev.to: ADRs for AI coding agents](https://dev.to/naman_here/adrs-for-ai-coding-agents-how-to-make-every-agent-read-architecture-decisions-3he4)
- Dissenting framing: one article argues AGENTS.md is displacing ADRs because it is "active" (consulted every session); another frames AGENTS.md/CLAUDE.md as "hot memory" and architecture.md, ADRs and specs as "cold memory" (snippets; individual blogs) — [AI Advances article](https://aiadvances.org/agents-md-is-the-ew-architecture-decision-record-adr-3cfb6bdd6f2c); [ceaksan.com](https://ceaksan.com/en/ai-agent-living-architecture-documentation)
- Academic framing: an arXiv paper describes "vibe architecting" (architecture shaped by prompts rather than deliberate design) and proposes review practices, decision records and tooling to bring hidden decisions under governance (snippet) — [arXiv:2604.04990](https://arxiv.org/pdf/2604.04990)
- In the OpenAI layout, decisions live in two places: `docs/design-docs/` for design rationale, and a mandatory Decision Log inside each execution plan (opened) — [npaka translation](https://note.com/npaka/n/nb4c5488e82fd?hl=en); [OpenAI Cookbook: ExecPlans](https://developers.openai.com/cookbook/articles/codex_exec_plans)
- Backlog.md has a decisions facility (`backlog decision list`; `backlog search` spans tasks, docs and decisions) alongside tasks (opened) — [MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md)
- The "exit strategy" essay keeps ADRs as one of the few prose artifacts that should survive a change, but only for rationale a future team would otherwise have to re-investigate: "Keep that prose short, owned, and close to the thing it explains" (opened) — [The Main Thread: SDD needs an exit strategy](https://www.the-main-thread.com/p/spec-driven-development-exit-strategy)

#### 1d. Per-change specs and plans (spec-driven development toolkits)
- Böckeler's three levels (15 Oct 2025): spec-first (spec written before the task), spec-anchored (spec kept afterwards and used to evolve the feature), spec-as-source (humans edit only the spec, never the code). She distinguishes specs (apply to a task changing a particular feature) from "memory bank" files (apply across all sessions) (opened) — [martinfowler.com: Understanding SDD: Kiro, spec-kit, Tessl](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- github/spec-kit: about 150k stars, 13.5k forks. Core commands `/speckit-constitution`, `/speckit-specify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement`, `/speckit-converge`; bundled extensions for bug fixing (`.specify/bugs/<slug>/`) and idea assessment (`.specify/assessments/<slug>/`); presets for organisational standards; README links to a how-to on evolving existing specs (opened) — [github/spec-kit](https://github.com/github/spec-kit)
- spec-kit layout as observed by Böckeler: a `.specify/` folder with `memory/` (holding `constitution.md`), `scripts/`, `templates/`; slash-command files in `.github/prompts`; one folder per spec such as `specs/001-when-a-user/` containing spec, plan, tasks, research, data-model, api and component files; a git branch per spec (opened; reflects the October 2025 version) — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- AWS Kiro: each spec yields `requirements.md` (or `bugfix.md`), `design.md` and `tasks.md`; spec types are Feature (requirements-first or design-first) and Bugfix, plus a Quick Spec mode that generates all three without approval gates; task status is updated in real time. A "steering" memory bank defaults to `product.md`, `tech.md`, `structure.md` (opened) — [Kiro docs: specs](https://kiro.dev/docs/specs/); [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- OpenSpec (Fission-AI): 74.9k stars. Current-state specs in `openspec/specs/`; each change in `openspec/changes/<change-name>/` with `proposal.md`, `specs/` (deltas using headers such as `## ADDED Requirements`), `design.md`, `tasks.md`; archived to `openspec/changes/archive/<date>-<change-name>/`. Works with "30+ AI assistants via skills". Its README positions spec-kit as "Thorough but heavyweight" and Kiro as tied to its own IDE (opened) — [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)
- Tessl Framework (private beta when reviewed): CLI that also runs as an MCP server; creates `.tessl/framework/`, `KNOWLEDGE.md` and `AGENTS.md`; specs like `dynamic-data-renderer.spec.md` map one-to-one to generated code files marked "GENERATED FROM SPEC - DO NOT EDIT"; `tessl document --code` reverse-engineers a spec, `tessl build` generates code (opened) — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- OpenAI ExecPlans: `PLANS.md` is a repo file defining how to write an ExecPlan ("a design document that a coding agent can follow to deliver a working feature or system change"); the example AGENTS.md points to `.agent/PLANS.md` and says "When writing complex features or significant refactors, use an ExecPlan." Mandatory living sections: Progress, Surprises & Discoveries, Decision Log, Outcomes & Retrospective; "it should always be possible to restart from only the ExecPlan". The cookbook page is now marked archived (opened) — [OpenAI Cookbook: Using PLANS.md for multi-hour problem solving](https://developers.openai.com/cookbook/articles/codex_exec_plans)
- BMAD-METHOD: newer releases install a framework folder `_bmad/` and write outputs to `_bmad-output/` (planning artifacts such as PRD and architecture under `_bmad-output/planning-artifacts/`); older versions used a hidden `.bmad-core/`. One course page writes the folder as `bmad-output/` (snippets; sources disagree on the prefix) — [dev.to: BMAD standard workflow](https://dev.to/jacktt/bmad-standard-workflow-2kma); [TalTech course page](https://courses.taltech.akaver.com/agentic-software-development/lectures/bmad)
- Agent OS (buildermethods): 1.x used `.agent-os/` with `product/` and `specs/` subfolders, spec folders prefixed `YYYY-MM-DD-`; 2.0 uses an `agent-os/` folder into which those can be moved (snippet of a GitHub discussion) — [buildermethods/agent-os discussion #173](https://github.com/buildermethods/agent-os/discussions/173)
- Empirical study of SDD in practice (Agarwal, Singhal, Macvean, Vasilescu, Breaux; submitted 25 Aug 2026, v4 15 Oct 2026): Reddit thematic analysis, 21 practitioner interviews (8 tool makers), and 266 active popular repositories drawn from SpecMine, a corpus of 470,795 spec files from 73,030 public GitHub repositories. Findings in the abstract: SDD is used selectively, mainly for new features; specs often include implementation detail, which may help agents but makes specs prone to decay; participants report more reliable agent behaviour with greater planning and review costs; spec-code checks happen mainly at change completion, not continuously (opened, abstract page only) — [arXiv:2608.25202](https://arxiv.org/abs/2608.25202)

#### 1e. Task trackers: in-repo versus external
- beads (steveyegge/beads): 28.8k stars; "a distributed graph issue tracker for AI coding agents, powered by Dolt", tagline "A memory upgrade for your coding agent". Storage is an embedded Dolt database in `.beads/embeddeddolt/` (or `.beads/dolt/` in server mode); sync via `bd dolt push/pull` using `refs/dolt/data` on the git remote; `.beads/issues.jsonl` is "an export for viewers and interchange, not the source of truth or a backup". Hash-based IDs (`bd-a1b2`) avoid merge collisions across agents and branches. Commands include `bd ready`, `bd update <id> --claim`, `bd dep add`, `bd prime`, `bd remember`. The project's agent guidance says not to use markdown TODO lists for task tracking (opened) — [steveyegge/beads](https://github.com/steveyegge/beads)
- beads can be kept out of the main repo: `bd init --stealth` uses it locally without committing files, and `BEADS_DIR` points at a `.beads/` directory outside git discovery (opened) — [steveyegge/beads](https://github.com/steveyegge/beads)
- Backlog.md (MrLesk): 7.4k stars, MIT. Each task is a Markdown file under `backlog/` (or `.backlog/`, or a custom `backlog_directory`), e.g. `backlog/tasks/` and `backlog/docs/`; IDs like TASK-1; CLI, MCP server (`backlog mcp start`) and a local Kanban web UI; `backlog init` writes a short agent-instruction stub into AGENTS.md / CLAUDE.md telling agents to run `backlog instructions overview`; git is optional (`--no-git`) (opened) — [MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md)
- A secondary guide lists Backlog.md subfolders for tasks, drafts, archive, docs and decisions (snippet; not confirmed on the README I opened) — [The Atlas: Backlog.md](https://yigitkonur.com/atlas/spec-driven-development/frameworks/backlog-md)
- Task Master (eyaltoledano/claude-task-master): 28.4k stars; state under `.taskmaster/` with the PRD at `.taskmaster/docs/prd.txt`; workflow is parse-PRD, expand, `task-master next`; tags used as workstreams/status; runs as an MCP server with selectable tool sets (7 to 36 tools) (opened) — [eyaltoledano/claude-task-master](https://github.com/eyaltoledano/claude-task-master)
- External trackers with agents as assignees: Linear lets you choose an agent in the assignee field or mention it in a comment; assigning to Cursor starts a background agent, assigning to Codex starts a cloud agent that posts updates back to the issue, and assigning to GitHub Copilot produces a draft pull request from an ephemeral GitHub Actions environment (snippets of Linear's own pages) — [Linear docs: assigning issues](https://linear.app/docs/assigning-issues); [Linear changelog: Codex agent](https://linear.app/changelog/2025-12-04-openai-codex-agent); [Linear: GitHub Copilot integration](https://linear.app/integrations/github-copilot)
- Stripe's Minions are started from Slack and end in a pull request for human review; over 1,300 fully minion-produced PRs merge per week (opened) — [Stripe: Minions part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)
- Other in-house background agents: Spotify's Honk reported more than 1,500 merged agent PRs in November 2025; Ramp's Inspect share of merged PRs is reported inconsistently (about 30% in one source, over half in another) (snippets; primary posts not opened) — [Spotify Engineering: Honk part 1](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1); [Pragmatic Engineer: Why Ramp built Inspect](https://newsletter.pragmaticengineer.com/p/why-ramp-built-inspect)

#### 1f. Session state and agent-written memory
- Claude Code auto memory is written by Claude (not the user), scoped per repository and shared across worktrees, and loaded every session up to the first 200 lines or 25KB; it is distinct from the user-written, source-controlled CLAUDE.md (opened) — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Anthropic's long-running harness (26 Nov 2025) bridges context windows with files in the working directory: `feature_list.json` (every feature with test steps and a `passes` flag, all initially failing), `claude-progress.txt` (session log), `init.sh`, and git history. An initializer session creates them; each later session reads them, does one feature, commits, and updates the progress file. Coding agents may change only the `passes` field; JSON was chosen because the model is less likely to rewrite it inappropriately than Markdown (opened) — [Anthropic: Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Anthropic's context-engineering post names structured note-taking as a core technique: the agent "regularly writes notes persisted to memory outside of the context window", e.g. Claude Code to-do lists or a `NOTES.md` file (opened) — [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- beads combines task tracking with memory (`bd remember "insight"`, `bd prime` prints workflow context and persistent memories) (opened) — [steveyegge/beads](https://github.com/steveyegge/beads)

### Inferences
- A workable taxonomy, with the storage location that the sources converge on:
  1. Invariants and rules (AGENTS.md / CLAUDE.md, path-scoped rules, constitution, steering): in-repo, short, always or conditionally loaded. The strongest evidence-based advice is to restrict these to non-obvious, non-standard requirements and to omit repository overviews.
  2. Durable knowledge and decisions (architecture docs, ADRs, current-state specs, product specs): in-repo, loaded on demand through an index or pointer, not pre-loaded.
  3. Per-change plans, specs and task lists: in-repo while active in most toolkits; post-merge fate varies (see key question 2).
  4. Session logs, progress notes, agent-written memory, evaluation output: machine-local or external by default (Claude Code auto memory, beads stealth mode); placed in the working tree only where the harness relies on it for continuity.
  5. Tool configuration (slash commands, skills, hooks, MCP config, `.specify/`, `.kiro/`, `.taskmaster/`, `_bmad/`): in-repo, per tool, which is the main source of root-directory clutter when several tools are used.
- The choice between in-repo task files and an external tracker tracks who needs to see the queue: Markdown or database-in-repo trackers (beads, Backlog.md, Task Master) optimise for the agent reading and claiming work offline, while Linear and GitHub Issues optimise for humans assigning work and reviewing a PR. The two are combinable, since the external issue becomes the prompt and the repo holds the rules.
- beads' move from JSONL-in-git to a Dolt database synced through a separate git ref suggests that plain task files in the main branch produce merge and noise problems at multi-agent scale.
- ADR practice is not displaced by agents; the consistent recommendation is ADRs for rationale plus a one-line pointer in the rules file. The claim that AGENTS.md replaces ADRs comes from a single blog.

## Key question 2: What do leading practitioners say about the lifecycle of plan/task docs after the work merges?

### Takeaway
There are three distinct positions: keep completed plans in the repo as history (OpenAI harness team, spec-kit's numbered spec folders), fold the durable part into a living spec and archive the rest (OpenSpec, Backlog.md), or let the plan disappear and move each durable fact into code, tests, schemas or a short ADR (the "exit strategy" critique, Böckeler's scepticism). No source I found recommends keeping per-change plans as an authoritative, maintained description of the system.

### Cited Findings
- Keep, separated by status: the OpenAI harness repo has `docs/exec-plans/active/` and `docs/exec-plans/completed/` plus `tech-debt-tracker.md`; active plans, completed plans and tech debt are all version-controlled and co-located. Small changes use lightweight temporary plans; only complex work gets a checked-in execution plan with progress and decision logs (opened via translation) — [npaka translation of "Harness engineering"](https://note.com/npaka/n/nb4c5488e82fd?hl=en); original at [openai.com](https://openai.com/index/harness-engineering/)
- The ExecPlans cookbook requires an "Outcomes & Retrospective" entry at completion but does not say whether finished plans are archived, kept or deleted (opened) — [OpenAI Cookbook: ExecPlans](https://developers.openai.com/cookbook/articles/codex_exec_plans)
- Merge-then-archive: in OpenSpec, `/openspec-archive-change` moves the change folder to `openspec/changes/archive/<date>-<change-name>/` and updates `openspec/specs/`, so the current-state spec persists while the proposal, design and tasks become dated history (opened) — [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)
- A reviewer of OpenSpec notes that deltas and archiving help, but someone still has to read the specs and keep them lean (snippet) — [dev.to: OpenSpec part 1](https://dev.to/rosidotidev/openspec-part-1-spec-driven-development-one-change-at-a-time-17pa)
- Archive with restore and delete: Backlog.md marks tasks Done, then `backlog task archive` removes them from the board; archived tasks keep ID, record and dependency links and are read-only; `backlog task restore` and `backlog task delete` exist (opened) — [MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md)
- Summarise old work: beads has compaction described as "Semantic 'memory decay'", summarising old closed tasks to save context window space (opened) — [steveyegge/beads](https://github.com/steveyegge/beads)
- Accumulate: spec-kit creates a numbered folder and a git branch per spec (`specs/001-...`) with around eight files each; its README now links guidance on evolving existing specs and maintaining capability-level specifications (opened) — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); [github/spec-kit](https://github.com/github/spec-kit)
- Böckeler's observation that every SDD tool she found is spec-first, while spec-anchored and spec-as-source use over time remained unclear or unproven in the tools reviewed (opened) — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Discard: Markus Eisele (15 Jul 2026) argues specs should be temporary "change briefs": "After the change ships, most of it should disappear." What survives is code, schemas and interface definitions (OpenAPI, AsyncAPI, types), tests and checks, policy and configuration, telemetry and alerts, and short ADRs; "Ask which fact must survive and what its authoritative form should be." A sprawling spec tree is "a second codebase with weaker tooling" (opened) — [The Main Thread: SDD needs an exit strategy](https://www.the-main-thread.com/p/spec-driven-development-exit-strategy)
- Observed practice: spec-code consistency checks happen mainly when a change is completed, not continuously; implementation detail in specs makes them decay-prone; SDD is applied selectively, mostly to new features (opened, abstract) — [arXiv:2608.25202](https://arxiv.org/abs/2608.25202)
- Long-running harness state is treated as working state, not documentation: `claude-progress.txt` and `feature_list.json` exist to hand over between context windows, with git commits as the durable record (opened) — [Anthropic: Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Other published critiques relevant to lifecycle: an InfoQ article warns of a "markdown monster" producing layers of documentation outdated on arrival; a TrueFoundry post describes dozens of spec files, competing AGENTS.md variants and no record of which spec produced which behaviour; a Manning book chapter says specs go stale when changes bypass them and are made directly in code (snippets) — [InfoQ: enterprise SDD](https://www.infoq.com/articles/enterprise-spec-driven-development); [TrueFoundry](https://www.truefoundry.com/blog/spec-driven-development-ai-agents); [Manning: Keeping Specs Alive](https://www.manning.com/preview/spec-driven-development/chapter-3)
- Böckeler's critique list: one workflow for all problem sizes (Kiro turned a small bug fix into 4 user stories with 16 acceptance criteria); spec-kit output was verbose and repetitive and she "would rather review code"; agents still ignored or over-applied instructions, giving a false sense of control; spec-as-source resembles model-driven development, risking its inflexibility combined with LLM non-determinism; she closes by asking whether this is "Verschlimmbesserung" (opened) — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

### Inferences
- The positions are less contradictory than they look: all of them separate "what is true now" (kept and maintained) from "how we got here" (frozen or dropped). OpenAI freezes plans in `completed/`, OpenSpec freezes them in `archive/`, the exit-strategy view deletes them. None treats a finished plan as something to keep editing.
- The practical rule that follows is that a completed plan must be visibly marked as historical (separate folder, date prefix, or status field), because an agent that greps the repo cannot otherwise tell a superseded plan from a current instruction. The OpenAI rationale for mechanical freshness checks and the staleness critiques both point at this failure.
- A repo that keeps backlog task definitions and ADRs in-tree already has the two durable halves (intent and rationale); the open design choice is only where in-flight plans live and whether they are retained after merge.
- Plan size should scale with the change: OpenAI (temporary plans for small changes), Kiro (Quick Spec), and Böckeler's "one workflow for all sizes" critique all converge on this.

### Gaps
- No quantitative data found on how often archived or completed plans are read again by agents or humans, or on whether retaining them helps or harms agent performance.
- Counts from the SpecMine corpus on spec retention, update frequency or deletion after merge are in the full paper, which I did not open.
- I found no explicit statement from Anthropic, Cursor or GitHub on what to do with plan-mode output after merge.
- The exit-strategy essay's year is inferred from the site footer (2026); the post shows only "Jul 15".

## Key question 3: What mechanical enforcement (lints, hooks, CI checks) is used to keep in-repo knowledge fresh?

### Takeaway
The most complete published example is OpenAI's harness-engineering setup: linters and CI jobs validate the docs tree (currency, cross-links, structure), a recurring doc-gardening agent opens fix-up PRs, and background agents scan for violations of encoded "golden principles". Elsewhere the mechanisms are narrower: hooks for hard blocks, path-scoped rule loading, spec-code verification at archive time, and constraints on which fields an agent may edit.

### Cited Findings
- Dedicated linters and CI jobs check that the knowledge base is up to date, cross-linked and correctly structured; a periodic doc-gardening agent finds documentation that no longer matches the code and opens pull requests to fix it (opened via translation; also in the official page's search snippet) — [npaka translation of "Harness engineering"](https://note.com/npaka/n/nb4c5488e82fd?hl=en); [openai.com](https://openai.com/index/harness-engineering/)
- "Golden principles" are encoded in the repo (e.g. prefer shared utility packages over hand-rolled helpers; validate data shapes instead of guessing). Background Codex tasks periodically scan for deviations, update quality grades (`docs/QUALITY_SCORE.md`) and open targeted refactoring PRs, most auto-merged within a minute. Before this automation the team spent every Friday, about 20% of the week, on manual cleanup (opened via translation) — [npaka translation](https://note.com/npaka/n/nb4c5488e82fd?hl=en)
- The stated reason a monolithic AGENTS.md fails is partly mechanical: a single blob cannot be checked for coverage, freshness, ownership or cross-links, so drift is inevitable; splitting into an indexed docs tree makes those checks possible (opened via translation) — [npaka translation](https://note.com/npaka/n/nb4c5488e82fd?hl=en)
- Generated documentation is kept in its own folder (`docs/generated/db-schema.md`), separating machine-derived facts from hand-written prose (opened via translation) — [npaka translation](https://note.com/npaka/n/nb4c5488e82fd?hl=en)
- Claude Code: instruction files are "context, not enforced configuration"; to block an action regardless of the model's decision, use a PreToolUse hook. The docs recommend periodically reviewing CLAUDE.md, nested CLAUDE.md and `.claude/rules/` for outdated or conflicting instructions and provide a prompt audit (`/doctor prompt-audit`) covering CLAUDE.md, CLAUDE.local.md, AGENTS.md, rules, skills, commands, subagents and output styles (opened) — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Path-scoped loading as a freshness and relevance control: `.claude/rules/` files with a `paths` field load only when matching files are read or edited (opened) — [Claude Code docs: memory](https://code.claude.com/docs/en/memory); Stripe attaches directory- and pattern-scoped rules automatically and keeps a single rule source synced across Cursor, Claude Code and Minions to avoid duplicated copies drifting (opened) — [Stripe: Minions part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)
- Stripe "blueprints" interleave deterministic nodes (run linters, push changes; no LLM) with agent nodes; lint runs locally via pre-push hooks and a background daemon; at most one full CI iteration with autofixes plus one further fix attempt before handing to a human (opened) — [Stripe: Minions part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)
- Edit constraints on state files: Anthropic's harness allows coding agents to change only the `passes` field of `feature_list.json`, forbids removing or editing tests ("It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality"), and uses JSON instead of Markdown to reduce inappropriate rewrites (opened) — [Anthropic: Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Spec toolkits check at change boundaries: OpenSpec's expanded profile has `openspec-verify-change` and archiving updates the main specs; spec-kit adds `/speckit-converge`, repeated with implement until it reports `Converged` (opened) — [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec); [github/spec-kit](https://github.com/github/spec-kit)
- Field evidence that this is the norm: spec-code checks were mainly done when changes were complete, not continuously over time (opened, abstract) — [arXiv:2608.25202](https://arxiv.org/abs/2608.25202)
- Task-state integrity in trackers: beads uses atomic claims (`bd update <id> --claim`), hash IDs and a dependency graph so `bd ready` lists only unblocked work; Backlog.md has `checkActiveBranches` and `activeBranchDays` settings for cross-branch task state (opened) — [steveyegge/beads](https://github.com/steveyegge/beads); [MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md)
- The exit-strategy argument is itself an enforcement argument: move each durable fact into the artifact that is mechanically checked (schemas, tests, architecture rules, policy config) instead of prose that nothing verifies (opened) — [The Main Thread: SDD needs an exit strategy](https://www.the-main-thread.com/p/spec-driven-development-exit-strategy)
- The AGENTS.md evaluation paper's closing advice is that any context-file change intended to improve performance "should be rigorously evaluated before deployment" (opened, abstract) — [arXiv:2602.11988](https://arxiv.org/abs/2602.11988)

### Inferences
- Enforcement falls into four layers, in decreasing order of reliability: (a) deterministic checks on code that make a rule unnecessary to state in prose (architecture lints, structural tests, hooks); (b) deterministic checks on the docs themselves (link checks, index completeness, required front-matter, status fields); (c) scheduled agent passes that compare docs to code and open small PRs; (d) human review prompted by an audit command. Published examples of (b) and (c) come almost entirely from the OpenAI post.
- Rules that are enforced by a hook or lint can be removed from the always-loaded context file, which is consistent with both the "under 200 lines" guidance and the finding that extra context raises cost without raising success.
- Continuous spec-code consistency checking is largely absent in practice; checks cluster at archive or merge time. A repo that wants fresher docs than that needs a scheduled job, since none of the toolkits provides one by default.

### Gaps
- The specific lint rules OpenAI uses for docs (what "freshness" means mechanically, cadence of the doc-gardening agent) are not given in the material I could open; the translation says no fixed cadence is stated.
- I found no open-source, widely adopted linter specifically for AGENTS.md or agent docs trees with sourced adoption figures; none was searched in depth.
- No measured data on false-positive rates or review load from doc-gardening or auto-merged cleanup PRs.
- Kiro hooks (agent hooks that update docs or tests on file events) are only linked from the page I opened; behaviour not verified.
- Enforcement practices at Spotify, Ramp, Vercel, Cloudflare and Shopify were not opened as primary sources.
