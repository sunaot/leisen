# Agent-heavy OSS product repositories: what harness, context and planning material they commit (state at 2026-11-15)

Method note (applies to every "tree" finding below): I shallow-cloned each repository's default branch on 2026-11-15 (treeless, `git ls-tree -r HEAD`) and fetched individual files from `raw.githubusercontent.com/<repo>/HEAD/...`. File counts are counts of tracked paths at HEAD; "120000" means the path is a git symlink. Line/byte sizes are of the file at HEAD on that date. Links use `blob/HEAD/` so they resolve to the current default branch (content may have changed since). Anything not observed directly is marked "unverified".

## 1. Which projects commit rich agent context (AGENTS.md / CLAUDE.md / .claude / skills / hooks), and what does it contain?

### Takeaway
By November 2026 almost every surveyed product repo commits a root `AGENTS.md` as the single source of truth, with `CLAUDE.md` reduced to a symlink or a one-line `@AGENTS.md` import; the growth area is committed skills (dozens to hundreds of files under `.agents/skills/` or `skills/`, symlinked into `.claude/skills`), nested per-directory `AGENTS.md`, and a small number of hooks. Size varies by two orders of magnitude: from 5-line files (datasette) to 30–50 KB rulebooks (next.js, vinext, modelcontextprotocol/servers).

### Inferences
- The de facto 2026 layout is: root `AGENTS.md` (rules, always loaded) + nested `AGENTS.md` per package + a tool-neutral skills directory symlinked into `.claude/skills` / `.cursor/skills`. Tool-specific directories hold only what cannot be shared (settings, hooks, MCP config).
- Committed hooks are narrow guards (block an interactive command, format after edit, session-start setup). None of the surveyed product repos commits a large hook-based policy engine.
- Large company-backed monorepos (PostHog, Sentry, Next.js, Mastra, Supabase) treat skills as the main carrier of procedural knowledge (tens to hundreds of files); single-maintainer libraries (simonw, mitsuhiko, antirez) commit almost nothing and rely on the agent reading code and tests.
- `.claude/agents/` subagent definitions are rare in product repos (PostHog was the only one found with a sizeable set); skills and commands are far more common.

### Gaps
- I did not read every nested AGENTS.md or skill; characterizations of contents beyond the quoted lines are from file names only.
- Byte counts exclude skill bodies; I did not total skill sizes per repo.
- steveyegge/beads was fetched via the `steveyegge/beads` URL, but its AGENTS.md refers to `gastownhall/beads`; whether the canonical repo has moved organizations (redirect) was not confirmed directly.
- rails/rails has an AGENTS.md (201 lines) but no other agent material; Shopify repos were not examined.

## 2. Which keep planning / task state in-repo versus GitHub Issues / Linear?

### Takeaway
Committing live task state is the exception: almost all surveyed projects keep work items in GitHub Issues/Projects or Linear and tell the agent how to use that tracker; what gets committed is durable design material (specs, RFCs, ADRs), occasionally a point-in-time plan file. Even beads — the project that popularized in-repo issue files — now gitignores its own `.beads/` data and names GitHub Issues as its public tracker.

## 3. ADRs / RFCs / design docs in-repo, and who they are written for

### Takeaway
Several agent-heavy projects added or formalized in-repo decision records in 2026 and explicitly tell the agent to read them before architectural changes and to stop when a change would contradict one; these documents are written for humans and agents alike, with the agent-facing part being the pointer and the stop rule in AGENTS.md.

### Cited Findings

- cloudflare/agents has `design/` with 58 files: living design docs named by topic (`think.md`, `mcp.md`, `sessions.md`) and 27 `rfc-*.md`. `design/AGENTS.md` (119 lines / 13.5 KB) defines the system: design docs are "Living documents that describe how a concept or subsystem works **right now**"; RFCs are "Point-in-time decision records ... - The pattern that recurs is "index + trigger": a short index file (ADR README, design README, routing table) and an AGENTS.md line saying when to read which document. Documents themselves are ordinary prose usable by humans.

- ADR creation is itself being turned into a skill (vercel/ai `adr-skill`, MCP `draft-sep`), so that the agent produces decision records in the house format.

### Gaps
- I did not verify how many of cloudflare/agents' RFCs are accepted vs rejected, or how consistently the status line is maintained.
- Whether these design docs were themselves mostly agent-written is not stated in the repos.

## 4. Deliberate separation of private "thoughts"/context from the public code repo

### Takeaway
HumanLayer is the clearest case: research, plans and task notes live outside the public repo (a separate "thoughts" repository exposed through a gitignored, symlinked directory), while the prompts/skills that produce them are public. More broadly, every surveyed repo splits "shared, committed" from "local, ignored" along the same line: `*.local.*` files, worktrees, runtime state and ephemeral plan output are ignored.

### Cited Findings
- HumanLayer CLI README (npm `humanlayer@0.17.2`): `thoughts` exists to "Manage developer thoughts and notes separately from code repositories."; "Each profile can have its own thoughts repository location"; `humanlayer thoughts sync -m "..."` "Manually sync thoughts and update searchable index"; "The thoughts system keeps your notes separate from code while making them easily accessible to AI assistants." — [humanlayer npm README](https://unpkg.com/humanlayer@0.17.2-npm/README.md)
- Third-party reimplementations describe the mechanism: `thts` (Go) says it reimplements HumanLayer's `humanlayer thoughts` subcommand with the same symlink layout, where editing `thoughts/{user}/notes.md` in the project edits the file in the central thoughts repo (secondary source; search-result summary, page not read in full) — [scottames/thts](https://pkg.go.dev/github.com/scottames/thts@v0.7.1)
- In the public humanlayer repo at HEAD: `.gitignore` line 2 is `/thoughts/`; also ignored are `.humanlayer/tasks/`, `.humanlayer/workspace.local.json`, `CLAUDE.local.md`, `.claude/settings.local.json`, `.agents/skills/`, `.agents/artifacts/`, `CLAUDE_OUTPUT.md`. CLAUDE.md "## THOUGHTS": "there is a directory called .humanlayer/ in the repo root. The `Grep` and `Glob` and `Search` tools WILL NOT WORK. - The committed `.humanlayer/workspace.json` shows the worktree mechanism: `"pathTemplate": "~/.humanlayer/workspaces/{{ TASKSLUG }}/{{ REPOBASENAME }}"`, `"branchTemplate": "{{ TASKSLUG }}"`, and `copyGlobs` that copy `.env`, `CLAUDE.local.md`, `.claude/settings.local.json`, `.humanlayer/workspace.local.json` into each new worktree — [.humanlayer/workspace.json](https://github.com/humanlayer/humanlayer/blob/HEAD/.humanlayer/workspace.json)

- sentry-mcp's AGENTS.md references a private sibling checkout as ground truth: "ALWAYS validate the endpoint behavior against the Sentry source code in `~/src/sentry`" — [sentry-mcp AGENTS.md](https://github.com/getsentry/sentry-mcp/blob/HEAD/AGENTS.md)

### Inferences
- The stable split observed is: public = rules, skills, commands, hooks, decision records; private/ignored = per-task research and plans, session handoffs, local overrides, worktree state, credentials. - A practical cost of symlinked context is tool behaviour: HumanLayer has to warn the agent that Grep/Glob do not traverse the symlink.
- Pulling skills from a separate public repo with a manifest (Sentry) is a middle path that reduces repo noise without hiding anything.

### Gaps
- I did not read HumanLayer's thoughts-tool source; the exact hook/sync behaviour (auto-commit, searchable hard-link directory) is unverified beyond the README and the third-party description.
- The older humanlayer layout cited in the ACE write-up (`.claude/commands/create_plan.md`, `implement_plan.md`) no longer matches HEAD, where these are plugin skills; when that change happened was not determined.
- No surveyed project was found using a git submodule or a `-internal` repository for agent context; absence in the tree does not prove such repos do not exist.

## 5. Public write-ups and policies (2025–2026): harness management, regrets, reviewer/contributor reactions, repo noise

### Takeaway
The public friction is less about agent files as noise and more about AI-generated contributions: several projects answered with an `AI_POLICY.md` plus agent-directed rules inside AGENTS.md. ### Inferences
- In none of the solo/tiny-team cases examined does the default branch carry a running backlog or dated per-task plans as a standing practice; the durable public artifacts are instructions, skills/commands, tests/evals definitions, design/decision docs, and commit/PR history.
- Experienced solo maintainers (Ronacher, Willison, antirez) keep personal harness material outside product repos (a separate dotfiles-like repo, or nothing), which keeps product repos nearly free of agent files.
- Eval definitions are committed; eval run outputs are generally not (humanlayer ignores them; none of the others showed dated eval logs in the tree). Dated eval reports in-repo were not observed in this set.

### Gaps
- "Mostly built through agents" is self-reported (Cloudflare posts, policy files); the share of agent-authored commits was not measured for any repo.
- I did not check non-default branches, where plan files may live during development (pydantic-ai's PLAN.md suggests this happens).
- langchain-ai/langgraph, getzep/graphiti, E2B and rails were only inspected at the tree/root-file level; they show light agent material and no evidence either way about how agent-heavy their development is.
