## What distinct patterns exist, who uses each, and what are the trade-offs for a small team?

### Takeaway
Six patterns are in real use: (1) private source of truth with a one-way sync to a public mirror, (2) a private companion repo for plans/notes linked into the working tree, (3) per-user or per-machine files kept out of git (local settings, global excludes), (4) harness distributed as a plugin/marketplace from its own repo, (5) a separate public design-record repo, and (6) everything in the one public repo. For a small agent-driven team the cheap, well-supported options are (3) and (4) plus (6) for anything contributors' agents need; (1) is the most expensive because inbound contributions are the fragile part.

### Cited Findings

Pattern 1: private monorepo to public mirror
- Copybara is Google's Apache-2.0 tool for moving code between a confidential and a public repo, for ongoing sync as well as one-time migration (search summary only). — [Copybara mirror page](https://sourceforge.net/mirror/copybara/)
- Dagster describes a "hub and spoke" layout: the internal monorepo is the hub, public repos are spokes, a subdirectory is exported to the root of the public repo, and commits that originated in the public repo are skipped to avoid echo loops (search summary only). — [Dagster blog](https://dagster.io/blog/monorepos-the-hub-and-spoke-model-and-copybara)
- Users report that the reverse direction (public PRs imported back into the private monorepo) is the fragile part: Copybara "picking the wrong base", and PR mirroring with "mixed success" (search summary only). — [copybara-discuss thread](https://groups.google.com/g/copybara-discuss/c/_FKHC4VF3QM)
- A newer tool in the same family, Copybarista, sends public changes back through separate source PRs for maintainer review and can refresh lockfiles for the public side to handle private dependency entries (search summary only). — [Copybarista listing](https://awesome.ecosyste.ms/projects/github.com%2Frekursiv-ai%2Fcopybarista)

Pattern 2: private companion repo for plans and notes
- HumanLayer's CLI ships a `thoughts` subsystem (`init`, `sync`, `status`, `config`, `uninit`, `profile`) described as "Manage developer thoughts and notes separately from code repositories"; the stated rationale is that it "keeps your notes separate from code while making them easily accessible to AI assistants". Profiles map different code repos (and worktrees) to different thoughts repositories (`--repo`, `--repos-dir`, `--global-dir`). (Fetched.) — [humanlayer README, v0.17.2](https://app.unpkg.com/humanlayer@0.17.2-npm/files/README.md)
- The workflow built on it (Research, Plan, Implement, Validate) saves outputs into a symlinked `thoughts/` directory created by `npx humanlayer thoughts init`, with research under `thoughts/shared/research/` (search summary only; third-party write-up). — [Substack write-up](https://humaineinterface.substack.com/p/i-mastered-the-claude-code-workflow)
- `thts`, a Go reimplementation, states it shares HumanLayer's layout (`~/thoughts/repos/<project>/`, symlinks into projects, git hooks) and syncs notes to a central git repo (search summary only). — [scottames/thts](https://gh.r-mj.com/scottames/thts)

Pattern 3: per-user and per-machine files kept out of git
- Claude Code defines four settings scopes: user (`~/.claude/settings.json`), shared project (`.claude/settings.json`, meant to be committed), project local (`.claude/settings.local.json`, personal), and managed (`managed-settings.json`, MDM, or server-managed settings from the claude.ai console). Precedence, highest first: managed, command line, project local, shared project, user. (Fetched.) — [Claude Code settings docs](https://code.claude.com/docs/en/settings)
- The local file is kept out of git by a machine-level mechanism, not a repo-level one: the first time Claude Code writes it, it adds `**/.claude/settings.local.json` to the user's global git excludes (`core.excludesFile`, else `~/.config/git/ignore`). A hand-created file must be added to `.gitignore` manually. (Fetched.) — [Claude Code settings docs](https://code.claude.com/docs/en/settings)
- Some keys never apply from a committed repo file (for example `permissions.defaultMode` values `auto` and `bypassPermissions`, telemetry export variables), and `permissions.allow`, `additionalDirectories`, `extraKnownMarketplaces` and most `env` values wait until each user trusts the folder; `deny` and `ask` rules apply immediately. (Fetched.) — [Claude Code settings docs](https://code.claude.com/docs/en/settings)
- In cloud sessions, user and project-local settings are not read at all; only the committed `.claude/settings.json` (single-repo session) and server-managed settings reach the session. (Fetched.) — [Claude Code settings docs](https://code.claude.com/docs/en/settings)

Pattern 4: harness distributed as a plugin/marketplace
- A Claude Code marketplace is a directory or repo with `.claude-plugin/marketplace.json` listing plugins; "the repository can be private", and an administrator can require it on every machine. Plugin sources can be a relative path, a GitHub repo, a subdirectory of another repo (`git-subdir`, including a monorepo), a git URL, an HTTPS zip, an npm package, or a command; git sources can be pinned to a `ref` or `sha`. (Fetched.) — [Claude Code: Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)
- A product repo can point at a marketplace instead of carrying the harness: `enabledPlugins` and `extraKnownMarketplaces` are keys in the committed `.claude/settings.json`, and the marketplace declaration waits for folder trust. (Fetched.) — [Claude Code settings docs](https://code.claude.com/docs/en/settings)
- Limitation: marketplaces and plugins declared through those two keys "don't load in a cloud session" (the docs link this statement to the cloud-environments page, which I did not open). (Fetched, one hop unverified.) — [Claude Code settings docs](https://code.claude.com/docs/en/settings)

Pattern 5: separate public design-record repos
- Rust keeps RFCs in a dedicated repo, Kubernetes keeps KEPs in `kubernetes/enhancements`, and GitLab publishes its handbook as its own site/repo (background, not fetched). — [rust-lang/rfcs](https://github.com/rust-lang/rfcs); [kubernetes/enhancements](https://github.com/kubernetes/enhancements); [GitLab handbook](https://handbook.gitlab.com/)

Pattern 6: everything in the public repo, including agent files
- AutoGPT (over 180,000 stars, about 150 open PRs, many agent-written, at a May 2026 interview) places directory-scoped `AGENTS.md` files beside the code they govern because "Agents read what's in front of them, at the level of the directory they're working in", moved from `CLAUDE.md` to `AGENTS.md` because Copilot and Codex ignore Claude files, and ships skills with trigger descriptions. (Fetched; GitHub Blog, 12 Aug 2026.) — [GitHub Blog](https://github.blog/open-source/maintainers/your-contributors-are-ai-first-now-is-your-project/)
- Prefect writes `AGENTS.md` files throughout its repo and runs a workflow that opens PRs when code changes make them drift (search summary only). — [Prefect dev log](https://dev-log.prefect.io/your-repo-has-new-contributors-whether-you-like-it-or-not)
- `AGENTS.md` is described as vendor-neutral, supported by 20+ tools and adopted by more than 60,000 repositories (search summary only; secondary sources). — [InfoQ, Aug 2025](https://infoq.com/news/2025/08/agents-md/)
- Committed plan files are rare in practice: an ESEM 2026 study screened 36,710 engineered GitHub repositories and found 85 Markdown plan files in only 10 repositories, stored in tool-specific directories such as `.claude/plans/` and `.cursor/plans/`. (Fetched abstract page.) — [Abubakar et al., ESEM 2026](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.54)

### Inferences
- Patterns 3 and 4 are complementary: 3 keeps personal and machine state out of the repo, 4 moves the reusable harness (skills, agents, hooks) into a repo with its own access control and release cadence. Neither needs sync tooling.
- Pattern 1 gives the strongest guarantee that internal material never appears publicly, but it makes the public repo a derived artifact; external contributors' PRs must be imported, which the Copybara user reports identify as the weak point. For a team of a few people this is a standing tax.
- Pattern 2 separates by access control while keeping material visible to the agent, but it depends on symlinks and hooks on each machine; the Claude Code docs say cloud sessions run on a fresh clone and read no user-level files, so a symlinked private notes repo would not be present there unless attached as a second repository.
- Pattern 6 serves contributors' agents best (instructions sit where the agent works), and the ESEM numbers suggest most projects that commit agent instructions still do not commit plans.
- A split by audience is consistent with all the evidence: what a contributor's agent needs to do correct work goes in the repo; what only the core team needs (plans in flight, review notes, eval logs, customer context) goes to a private companion or stays local.

### Gaps
- Meta ShipIt/fbshipit: no source retrieved in this session; I could not confirm its current maintenance status.
- "Open core" companies with private plus public repos: no concrete, sourced example gathered.
- No "newer AI-era" example of an internal-to-public sync pipeline that specifically strips agent artifacts was found, apart from the Copybarista listing.
- HumanLayer's README does not state whether the thoughts store is a git repo or how it is linked (symlink, hooks); those details come only from third-party write-ups and the `thts` reimplementation. The HumanLayer homepage reportedly describes syncing through its own API instead (search summary only).
- `CLAUDE.local.md`, `.git/info/exclude`, submodule and worktree mounting of private notes: not verified against a source in this session.
- Whether separate RFC/KEP repos work for small projects (as opposed to very large ones) was not researched; I found no small-project example.
- No first-hand "build in public" retrospective from a project that publishes its full agent process (plans, backlogs, eval logs) was found.

## What concrete incidents demonstrate risk from committed agent configuration or over-sharing?

### Takeaway
Two distinct risk families are documented with primary evidence: repository-controlled agent config executing code or redirecting credentials on a cloner's machine (Check Point's Claude Code findings; Cursor's MCP CVEs; Pillar's rules-file backdoor), and agent-written local files leaking secrets when committed (`.claude/settings.local.json`). A third family, prompt injection into agents running in CI on a public repo, applies to any project that lets agents read issues and PRs.

### Cited Findings

Repository-controlled config as an execution path
- Check Point Research (public disclosure 25 Feb 2026) reported three Claude Code issues, all patched before publication. (Fetched.) — [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
  - Hooks in `.claude/settings.json` (a SessionStart hook) ran a command without the confirmation that Bash commands require; GHSA-ph6w-f82w-28w6, reported 21 Jul 2025, fixed 26 Aug 2025.
  - `enableAllProjectMcpServers` / `enabledMcpjsonServers` in `.claude/settings.json` auto-approved servers from `.mcp.json`, so a command ran "immediately upon running claude" before the trust dialog could be read; CVE-2025-59536, reported 3 Sep 2025, fixed 22 Sep 2025.
  - `ANTHROPIC_BASE_URL` set in `.claude/settings.json` redirected API traffic, sending the API key before the trust dialog was accepted; CVE-2026-21852, reported 28 Oct 2025, fixed 28 Dec 2025, published 21 Jan 2026.
  - Authors' conclusion: configuration files "were once passive data" and now "control active execution paths"; teams should "treat project setup files with the same careful attention we apply to executable code", and review config changes in code review. They name malicious PRs, honeypot repos and insiders as delivery channels.
- Conflict on CVE mapping and versions: The Hacker News coverage (search summary only) attaches CVE-2025-59536 (CVSS 8.7) to the hooks issue with a fix in 1.0.87, and CVE-2026-21852 (CVSS 5.3) with a fix in 2.0.65; the Check Point article attaches CVE-2025-59536 to the MCP consent bypass and gives no version numbers. — [The Hacker News](https://thehackernews.com/2026/02/claude-code-flaws-allow-remote-code.html?hl=en); contradicted in part by [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
- Adversa's "TrustFall" report claims a repo that ships an MCP server and auto-approves it can still reach code execution with one Enter keypress across Claude Code, Cursor, Gemini CLI and Copilot. Unverified: search summary only, vendor source, patch status unknown. — [Adversa](https://adversa.ai/?p=345894)
- Pillar Security's "Rules File Backdoor" (Mar 2025): instructions hidden in a rules file, invisible to a human reviewer, made Cursor and GitHub Copilot insert an external script into generated files. No CVE; Cursor and GitHub both said reviewing suggestions is the user's responsibility (search summary only). — [Pillar Security](https://pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)
- Cursor: CVE-2025-54135 ("CurXecute", content causing the agent to rewrite MCP config and run commands) and CVE-2025-54136 ("MCPoison", CVSS 7.2, an approved MCP config in a shared repo later altered to run commands on teammates' machines). Search summary only, via a secondary blog; verify against Check Point and Cursor advisories. — [aiproductivity.ai](https://aiproductivity.ai/news/ai-code-editors-security-risks-cves-backdoors/)

Secrets leaking through agent-written files
- Apiiro found secrets in public copies of `.claude/settings.local.json`: choosing "Yes, and don't ask again" stores the approved command, including any secret in it, as an allow rule. Reported figure: 2,539 secrets across 1,994 public repositories; leaked items included medical-records database passwords and university SSH logins. (Fetched; Privacy Guides, 9-10 Nov 2026, linking the Apiiro post.) — [Privacy Guides](https://www.privacyguides.org/news/2026/11/10/claude-code-leaks-secrets-and-passwords-in-public-github-repositories/); primary: [Apiiro](https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again)
- Why the built-in protection failed, per the same article: the ignore rule goes into the developer's global excludes, so it does not cover a folder that becomes a repo later, a clone on another machine, or an already-committed file; it is never written to the repo's own `.gitignore`; and Claude's commit instructions exclude `.env` and `credentials.json` but not its own settings file. Anthropic's head of Claude Code said prevention options are being looked at. (Fetched.) — [Privacy Guides](https://www.privacyguides.org/news/2026/11/10/claude-code-leaks-secrets-and-passwords-in-public-github-repositories/)
- Conflicting counts: another outlet reports Apiiro's result as 1,122 of 104,185 public copies of the file holding real secrets; GitGuardian separately reports 31,088 distinct secrets in 23,276 public repos, 5,343 still valid at detection, with monthly leaks peaking at 12,535 in April 2026 and falling to 959 by October. All search summary only. — [buildmvpfast](https://www.buildmvpfast.com/blog/claude-code-dont-ask-again-secrets-settings-local-json-2026); [Dark Reading](https://darkreading.com/cyber-risk/ai-coding-agents-leak-secrets-github); [CSO Online](https://www.csoonline.com/article/4247336/claude-codes-dont-ask-again-button-has-a-secrets-spilling-problem.html)
- The same file leaks through package publishing: Check Point reportedly found 428 of about 46,500 monitored npm packages containing `.claude/settings.local.json`, 33 files in 30 packages with credentials (search summary only). — [SecurityBrief](https://securitybrief.news/story/claude-code-can-leak-secrets-in-public-npm-packages)
- GitGuardian's 2026 State of Secrets Sprawl reportedly counted 29 million hardcoded secrets on public GitHub in 2025 and 24,008 secrets in MCP config files (search summary only, secondary outlet). — [turbogeek summary](https://www.turbogeek.co.uk/?p=9468)
- Remediation advice in coverage: rotate first, then `git rm --cached .claude/settings.local.json` and add the path to the repo's own `.gitignore`; deleting the file does not remove it from history, forks or clones (search summary only). — [buildmvpfast](https://www.buildmvpfast.com/blog/claude-code-dont-ask-again-secrets-settings-local-json-2026)
- Over-sharing of non-secret business material: CybelAngel published an analyst commentary titled "How an AI Tool Pushed Client Strategy Notes to GitHub" (title only; not opened). — [CybelAngel](https://cybelangel.com/blog/ai-tool-client-data-github-exposure/)

Agents in CI reading untrusted public input
- Aikido's "PromptPwnd" (Dec 2025): hidden instructions in a GitHub issue can make AI agents in GitHub Actions (Gemini CLI, Claude Code, OpenAI Codex named) run commands and leak secrets; it needs two conditions together, a high-privilege token and prompts that embed unsanitized user strings (search summary only). — [Aikido](https://aikido.dev/blog/promptpwnd-github-actions-ai-agents); [CSO Online](https://www.csoonline.com/article/4101751/ai-in-ci-cd-pipelines-can-be-tricked-into-behaving-badly-2.html)
- A Cloud Security Alliance research note (May 2026) covers the same class for Copilot Coding Agent, Gemini CLI and Claude Code in Actions workflows (search summary only). — [CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-github-actions-security-20260503-csa-st/)
- The Nx build-system compromise ("s1ngularity") targeted AI tool credentials including Claude Code, Gemini CLI and Amazon Q; sources disagree on the date (August 2025 vs May 2025). Search summary only. — [eSecurity Planet](https://www.esecurityplanet.com/threats/ai-agents-create-critical-supply-chain-risk-in-github-actions/)

### Inferences
- For a public repo, committed agent config is part of the attack surface in both directions: a malicious PR that edits `.claude/settings.json`, `.mcp.json`, hooks or rules files targets maintainers; the project's own committed config is something every cloner must trust. Treating these paths like CI workflow files (CODEOWNERS, mandatory human review, no auto-merge) follows directly from Check Point's recommendation.
- The secrets incident is a separation failure, not a design-disclosure failure: the file was meant to be local, and the only guard was machine-level. A repo-level `.gitignore` entry for local agent files plus secret scanning in CI closes the gap the reports describe.
- Hooks and guard scripts committed to a public repo are not secret by nature; the documented harm comes from executable config and from leaked credentials, not from revealing that guardrails exist. I found no incident where publishing harness or guardrail definitions by itself was exploited.

### Gaps
- No documented incident was found where a public ADR, backlog or review note disclosed a security-sensitive design detail or an unresolved vulnerability that was then exploited. The risk is plausible but unsupported by a case here.
- No count of secrets found specifically in public `CLAUDE.md` / `AGENTS.md` files; it appears only in generic lists of places secrets can hide.
- No source found for secrets or private data leaking via committed agent transcripts or session logs.
- Exact fixed versions and the CVE-to-issue mapping for the Claude Code findings should be confirmed against Anthropic's GitHub security advisories; I did not open them.
- TrustFall's current status, and the Cursor CVE details, are unverified.

## What do respected OSS maintainers recommend about keeping process artifacts (plans, backlogs, review notes, eval logs) in the repo, and how is governance adapting?

### Takeaway
There is no consensus on committing agent process artifacts: some practitioners argue plans should be merged like RFCs, large projects (Linux, Drupal) pushed back on even an `AGENTS.md`, and empirically few repos keep plans. Governance has converged much more clearly on a different point: the human submitter is accountable and must understand the change, with disclosure rules now diverging (Fedora and ASF recommend a trailer; the Linux kernel reached consensus in October 2026 to drop its mandatory tag).

### Cited Findings

Process artifacts in the repo
- Charles-Axel Dein argues the agent's plan should be checked in and treated as an RFC: one PR for the plan (architecture and trade-offs), a second for the implementation. Claimed benefits: it works like an ADR, gives future agents context, and lets reviewers check the implementation against the plan. He notes plans need cleanup because AI-generated text is repetitive, and that length should match complexity. (Fetched.) — [dein.fr, 8 Jan 2026](https://www.dein.fr/posts/2026-01-08-write-and-checkout-the-plan)
- One team keeps docs, backlog, specs and runbooks in a root `docs/` folder (search summary only). — [umans.ai](https://blog.umans.ai/blog/stop-being-your-ai-agents-assistant)
- Counter-evidence on prevalence: 85 plan files in 10 of 36,710 repositories. (Fetched abstract.) — [ESEM 2026](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.54)
- AutoGPT's maintainer warns "A bad AGENTS.md file is worse than no AGENTS.md"; poorly placed files polluted context. The project also turned off an agent that narrated every CI failure because it became noise. (Fetched.) — [GitHub Blog](https://github.blog/open-source/maintainers/your-contributors-are-ai-first-now-is-your-project/)
- Pushback in large projects: Sasha Levin's proposal to add `AGENTS.md` to the Linux kernel drew objections that a shared file is not useful for experienced contributors, with no resolution in the thread; a Drupal core `AGENTS.md` proposal was opened and closed within days; an Open edX participant asked to consider not having such files at all (search summary only). — [mindstudio summary](https://www.mindstudio.ai/blog/linux-kernel-agents-md-debate); [The Drop Times](https://www.thedroptimes.com/node/66452); [Open edX forum](https://discuss.openedx.org/t/what-should-go-into-agents-md-files/19076)
- A study linked to ETH Zurich reportedly found context files gave only marginal benefit on well-documented open-source repos; the conclusion is contested in commentary (search summary only). — [InfoQ, Mar 2026](https://infoq.com/news/2026/03/agents-context-file-value-review/)

Making a repo usable by contributors' agents while keeping control (AutoGPT, fetched)
- PRs that do not follow the template are closed; agents follow the template, so the rule works before automation runs. Required CI checks (Codecov thresholds, 80% on the backend) block merges. An unsigned CLA after one week leads to closure, and the OAuth flow is hard for agents, so it acts as a human check. A `pr-address` skill requires fix, commit, push, reply (citing the full SHA), then resolve. Maintainers may decline to merge LLM output and rewrite the fix, crediting the contributor as co-author. GitHub settings now allow disabling PRs or restricting issue creation to collaborators. — [GitHub Blog](https://github.blog/open-source/maintainers/your-contributors-are-ai-first-now-is-your-project/)

- Date conflict: The Register says the tag entered kernel documentation in January 2026; another summary says the policy file was added in April 2026. — [The Register](https://www.theregister.com/ai-and-ml/2026/10/14/linux-kernel-devs-drop_obligatory_confession_of_ai_tool_usage/5303140); contradicted by [Phoronix](https://phoronix.com/news/Linux-Dropping-Assisted-By-Req) (search summary only)
- One secondary source says Linux, Fedora, LLVM, OpenTelemetry, OpenInfra and Rocky Linux had converged on `Assisted-by` (search summary only; now outdated for Linux). — [daily.dev summary](https://app.daily.dev/posts/assisted-by-how-open-source-projects-are-drawing-the-line-on-ai-contributions-6hd4efvtt)
- ASF generative tooling guidance (fetched; page refers to August 2026 as current): AI-generated code may be contributed if the tool's terms do not conflict with the Open Source Definition and either the output is not copyrightable, contains no third-party material, or third-party material is used with permission; relying on non-copyrightability alone is called risky. Recommended trailer: `Generated-by: <Name of Tool> <Version>` or `Co-authored-by: <Name of Tool> <Version>`. It notes the U.S. Copyright Office position that purely AI-generated output is not copyrightable while human-authored portions may be, and that prompts alone generally do not create protectable material. — [ASF generative tooling](https://www.apache.org/legal/generative-tooling.html)

### Inferences
- The disclosure question is unsettled in late 2026: the kernel moved away from mandatory tags the same year ASF and Fedora kept recommending them. A project that uses a `Co-Authored-By` trailer for agent commits is within ASF's recommended practice; a project that drops it is within the kernel's. What every policy keeps is human accountability and comprehension.
- Ghostty is the closest published model for an agent-heavy core team: the policy says openly that maintainers use AI, exempts them, and puts the burden on outside contributors. This addresses the asymmetry a small agent-driven team faces (its own agent output is supervised; strangers' is not).
- The ASF copyright note matters for a mostly agent-written codebase: if large parts have little human authorship, copyright in those parts may be thin, which weakens copyleft enforcement more than permissive licensing. This is an inference from the ASF text, not legal advice.
- On process artifacts, the published arguments for committing them are about durable decisions (ADR-like plans); the published complaints are about noise and context pollution. A reasonable reading is that decision records belong in the repo and transient working state (backlog churn, review findings, eval run logs) does not, but no maintainer source I read states that rule explicitly.
- Private vulnerability reporting is now the default intake channel even for projects that removed bounties (curl), so a `SECURITY.md` pointing to GitHub Private Vulnerability Reporting is the low-cost baseline.

### Gaps
- OpenSSF guidance, OpenInfra policy text, Servo policy, and the Gentoo council motion text were not opened; Gentoo/NetBSD/QEMU/LLVM/Fedora details rest on a secondary compilation with primary links.
- No maintainer statement was found that specifically addresses backlogs, review notes or eval logs in a public repo.
- Whether the kernel's Assisted-by removal patch is merged in mainline is unconfirmed; the linux-next doc lacking the section is suggestive only.
- No source gathered on how DCO sign-off is handled when an agent commits autonomously under a bot identity, beyond the kernel's rule that agents must not sign off.
- No source found for `SECURITY.md` conventions specific to agent-era projects beyond curl's and Django's handling of AI-generated reports.

## How did early-stage projects move from "prototype with everything in the repo" to public OSS (history, scrubbing, docs restructuring)?

### Takeaway
The sourced guidance is about secrets and history mechanics, not about agent process artifacts: rotate credentials first, scan the whole history, and choose between a rewritten history and a fresh squashed repo knowing that each has leak paths. I found no documented case study of a project restructuring agent-era process docs at the point of going public, and nothing that addresses a repo that is already public.

### Cited Findings
(All items in this section are search summary only; the underlying pages were not opened.)
- `git-filter-repo` is the recommended rewrite tool; BFG and `git filter-branch` are described as outdated (filter-branch has shown a deprecation warning since Git 2.36). Useful modes: `--analyze`, `--path ... --invert-paths` to drop files, `--replace-text` to replace strings across history, `--mailmap` for contributor identities; work on a fresh `git clone --mirror`. — [NHSBSA digital playbook](https://nhsbsa.github.io/nhsbsa-digital-playbook/development/coding-git-rewrite-history)
- Rotate credentials before scrubbing, because removing a secret in a new commit leaves it in history; data that cannot be revoked must be removed from history before opening; scan deleted files and earlier revisions, not only the current tree. — [Truffle Security: securely open sourcing on GitHub](https://trufflesecurity.com/blog/securely-open-sourcing-on-github)
- A fresh squashed repo loses all commit history and disrupts collaborators, and can still leak: if the public repo later pulls from the private one, old history comes with it; data in private forks committed before open-sourcing, and dangling commits, can remain reachable. — [Truffle Security](https://trufflesecurity.com/blog/securely-open-sourcing-on-github)
- Rewriting has limits: anyone who cloned before the rewrite keeps the old data, and a force push is required. — [hoop.dev](https://hoop.dev/blog/removing-sensitive-data-from-git-history/)
- A first-person account exists of what one team scrubbed from history before open-sourcing an app (title only). — [dev.to](https://dev.to/agent_paaru/we-open-sourced-our-app-heres-everything-we-had-to-scrub-from-git-history-first-2cb5)
- Tooling exists for the fresh-repo route (`git-opensource`). — [ph101pp/git-opensource](https://github.com/ph101pp/git-opensource)

### Inferences
- Once a repo is public, history rewriting no longer removes anything from existing clones and forks; for an already-public project the practical move is forward-only: stop adding the material, relocate it, and rotate anything sensitive. This follows from the cited limits of rewriting.
- The scrub list implied by this research for an agent-developed repo: credentials (including those embedded in agent permission files), contributor emails, customer or deployment-specific names, unresolved security review findings, and local agent state files.
- A three-way docs split (user docs, contributor docs including agent instructions, decision records) matches what the cited projects publish; in-flight plans and review notes are the category with no public precedent among the sources I read.

### Gaps
- No case study found of an agent-developed project's transition to public OSS, including what it did with plans, backlogs and eval logs.
- No source on documentation restructuring (user vs contributor vs internal decision logs) at open-sourcing time.
- The cited pages in this section were not opened; commands should be checked against the `git-filter-repo` manual before use.
