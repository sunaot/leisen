# LLM によるクエリ生成と反復・エージェント型検索(語彙検索バックエンド)の学術・実証文献調査(2026-11 時点)

凡例と注意
- 【語彙】= BM25 / grep / boolean など語彙検索での結果。【密】= 密ベクトル検索での結果。【両方】= 両方を比較。区別のない転用は避けること。
- 数値は原論文の本文・表を読んだもの(「本文確認」)と、arXiv の要旨ページを小型モデルで要約させたもの(「要旨のみ」)がある。後者は効果量が載っていない場合が多く、その旨を各項目に書いた。
- 2026 年の arXiv プレプリントは査読前のものが多い。査読の有無が分かるものは書いた。
- BrowseComp-Plus(BCP)は英語の Web 文書 約 10 万件・830 問で、「複数の手掛かりから対象を特定する」型の質問。社内文書の日本語検索とは質問の形が違うので、絶対値ではなく傾向として読むこと。

## 1. LLM によるクエリ書き換え・拡張(疎検索向け): 何が効き、いつ害になるか

### Takeaway
BM25 に対しては LLM 拡張(疑似文書の付加、キーワード生成)が nDCG@10・Recall をはっきり上げるが、効果は検索器が弱いほど大きく、強い検索器(SPLADE、密)では消えるか逆転する。害が出るのは「LLM が知らない題材」「曖昧なクエリ」「根拠のない語の大量注入」であり、社内固有語が多いコーパスはまさにこの条件に当たるため、**コーパスから得た語に基づく拡張(検索結果を見てから語を足す)と、元のクエリ語を必ず残す設計**が文献上の安全策である。

### Cited Findings
- 【語彙】同一条件での再現研究(SIGIR 2026、10 手法 × BM25 / SPLADE++ / BGE × 9 データセット、GPT-4.1)。BM25 では全手法が改善: TREC DL 2019 の nDCG@10 は 元クエリ 0.506 → Query2Doc(zero-shot)0.687、MUGI 0.695、CSQE 0.690、キーワード型の Q2K 0.594、GenQR 0.548、古典的 RM3 0.522。Recall@1000 は 0.750 → 0.87〜0.90。BEIR 6 件平均 nDCG@10 は 0.421 → 0.47〜0.53(本文確認)— [A Reproducibility Study of LLM-Based Query Reformulation](https://arxiv.org/abs/2604.27421)
- 【両方】同研究: SPLADE++ では元クエリが最良のことが多い(DL19 nDCG@10 0.731 に対し拡張後 0.68〜0.73、BEIR 平均 0.539 に対し 0.495〜0.521)。BGE では改善は小さく、手法によっては悪化。著者の結論は「改善幅は、検索器が厳密な語一致から暗黙の拡張を持つニューラル符号化へ移るにつれて系統的に縮む」— [同上](https://arxiv.org/abs/2604.27421)
- 【語彙】同研究: 文書生成型(Q2D、MUGI)は上位の順位品質に強く、キーワード型(GenQREnsemble)は Recall に強い(BEIR 6 件中 4 件で Recall@100 最良)。ただし難しいクエリ集合 DL-HARD ではキーワードの無差別な追加が nDCG@10 を元クエリ以下に下げた(0.285 → 0.270)。コーパスに基づく手法(CSQE、LameR)は DL-HARD で最も安定(CSQE 0.366)— [同上](https://arxiv.org/abs/2604.27421)
- 【語彙】同研究: Query2Doc の chain-of-thought 版は zero-shot / few-shot 版より一貫して低い(DL19 で 0.653 対 0.687 / 0.690)。著者は中間推論の冗長さが関連性の信号を薄めると解釈— [同上](https://arxiv.org/abs/2604.27421)
- 【両方】同研究: LLM の規模と効果は単調でない。GPT-4.1 と GPT-4.1-nano はほぼ同じ改善、Qwen2.5-7B は COVID で元クエリ以下。全モデルで最も効くのは難クエリ(DL-HARD)、最も効かないのは FiQA。「BM25 + LLM 拡張は、拡張なしの密検索に近いか並ぶことが多い」とも報告— [同上](https://arxiv.org/abs/2604.27421)
- 【語彙】Jagerman ら(Google、2023): BM25(Terrier)に対し、元クエリを 5 回繰り返してから LLM 出力を連結する。MS MARCO dev の Recall@1K は BM25 87.82、Bo1 88.68、CoT プロンプト 90.61(最良)。zero-shot の Q2D は 86.60 で BM25 を下回る。BEIR 平均 Recall@1K は BM25 72.43 → Q2D/PRF 75.23。小さいモデルでは検索結果(PRF 文書)をプロンプトに入れる方が効き、大きいモデルでは PRF が CoT を悪化させた。Q2D が Bo1 に並ぶには 11B 規模が必要、CoT は 3B で並ぶ(Flan-T5 系での結果)— [Query Expansion by Prompting Large Language Models](https://arxiv.org/abs/2305.03653)
- 【語彙】Query2doc(2023)は LLM 生成の疑似文書をクエリに連結し、BM25 を MS MARCO / TREC DL で 3〜15% 改善と報告(2026 年の論文による要約)— [Query2doc](https://arxiv.org/abs/2303.07678); [SAFE-QE の関連研究節](https://arxiv.org/abs/2610.13810)
- 【両方】Weller ら(EACL Findings 2024): 11 拡張手法 × 12 データセット × 24 検索モデル。「検索器の性能と拡張の利得には強い負の相関」。拡張は弱いモデルや、対象データの形式が学習コーパスと大きく違う場合に使い、それ以外は関連性の信号を保つため避けよ、と勧告。原因の仮説は、拡張が再現率を上げる一方で上位の関連文書を見分けにくくする雑音を足すこと(要旨のみ、効果量は未確認)— [When do Generative Query and Document Expansions Fail?](https://arxiv.org/abs/2309.08541)
- 【両方】Abe ら(SIGIR 2025 short): LLM 拡張の失敗は 2 類型。(1) LLM がクエリの題材を知らず、誤った拡張をする。(2) クエリが曖昧で、拡張が有力な一つの解釈に寄り検索範囲を狭める。疎・密の両方で有意に悪化(要旨のみ)— [LLM-based Query Expansion Fails for Unfamiliar and Ambiguous Queries](https://arxiv.org/abs/2505.12694)
- 【両方】SAFE-QE(2026 プレプリント): 拡張語のうち関連文書に裏付けのない語の数を測る指標 HETR を提案。1 クエリあたりの「裏付けのない注入語」は Query2doc 27.83 語、HyDE 57.47 語、CSQE 7.90 語、提案手法 4.79 語。nDCG@10 は生成型と統計的に同等。強い学習型疎検索(SPLADE)では全拡張手法が悪化。なお同論文の表 2 では BM25 の平均利得は Query2doc +0.0231 が最大で、HyDE は −0.0045(Gemma-2-9B 生成)(本文確認)— [Tracing and Taming Hallucinated Terms ... for LLM Query Expansion](https://arxiv.org/abs/2610.13810)
- 【両方】同論文の関連研究の整理: Yoon ら(ACL Findings 2025)は、LLM 拡張の利得の多くは生成文に正解を含意する内容が入っている場合(知識の漏れ)に生じると主張— [同上](https://arxiv.org/abs/2610.13810)
- 【密(注意)】ServiceNow(EMNLP 2026 採択): 強い密パイプライン(BGE + cross-encoder 再順位付け + MMR)の上では、単独の書き換えは「良くて同等」。しかし手法ごとに失敗するクエリが違うため、結果の合併が効く。企業風コーパス EnterpriseRAG-Bench(約 51 万文書、470 問)で HIT@10 は 基準 39.22 → 同義語言い換え単独 42.91 → 4 手法合併 51.70(+12.5)。取得件数を増やすだけ(Top-100 再順位付け)では 44.3 止まりで、利得の約 6 割は相補性。逆に各手法の結果が重なるコーパス(AmbigNQ)では合併で −2.4pt(p<0.001)。基準検索の top-1 スコアが低いときだけ書き換える確信度ゲートは、39% のクエリにだけ書き換えを使い +4.3 を得た(シミュレーション)(本文確認)— [Better Together: Complementary Query Rewriting Under a Strong RAG Baseline](https://arxiv.org/abs/2609.05637)
- 【密】Adobe(2026): 検索結果を見ないプロンプトだけの 1 回の書き換えは、密検索で助ける場合と害する場合がある(要旨の冒頭のみ確認、数値未確認)— [Not All Queries Need Rewriting](https://arxiv.org/abs/2603.13301)
- 【語彙】日本発の IterKey(NAIST、NLP2025 / arXiv 版あり): LLM にキーワードを生成させ BM25 で検索 → 回答生成 → 回答の自己検証 → 不合格ならキーワードを作り直す、を反復。BM25 の RAG や検索なしより精度が 5〜20% 向上と報告(検索結果の要約による。PDF の本文抽出は文字化けで詳細未確認)— [ITERKEY(NLP2025 P8-6)](https://www.anlp.jp/proceedings/annual_meeting/2025/pdf_dir/P8-6.pdf)

### Inferences
- 対象システムのバックエンドは各 SaaS のネイティブなキーワード検索であり、文献の区分では「弱い〜中程度の語彙検索器」。拡張が効きやすい側にある。一方、社内固有語(製品名、チーム名、略語)は LLM が知らない題材なので、Abe らと SAFE-QE が示す失敗条件(知らない題材での誤拡張、裏付けのない語の注入)に当たる。したがって検索前に LLM の知識だけで語を足す方式(HyDE / Query2doc 型)は不利で、**1 回目の検索結果に出た語を使って 2 回目以降のクエリを作る方式(CSQE / LameR / PRF 型)**が筋が良い。
- BM25 系の研究はクエリ語が OR 的に加点される前提で、長い拡張クエリでも元の語を繰り返して重みを保てる。多くの SaaS 検索は AND 既定(語を足すほど 0 件に近づく)なので、疑似文書をそのままクエリに連結する手法は移せない。移せるのは「語彙の違う短いクエリを複数投げて結果を合併する」形である(ServiceNow の相補性の結果、再現研究の GenQREnsemble の Recall 優位が根拠)。
- 「強いモデルほど拡張がうまい」とは言えない(再現研究)。モデルを上げるより、拡張の根拠をコーパスに置くこと、元の語を残すことの方が効果が安定している。
- 適合率が低いという現状の症状は、Weller らの仮説(拡張が上位に偽陽性を入れる)と整合する。拡張の量を増やす前に、拡張語の出所を絞る・結果を LLM で選別する(§5)方が先である。

### Gaps
- AND 既定・フィールド指定付きの SaaS 検索 API に対する LLM 拡張の統制実験は見つからなかった。上の推論は BM25(OR 的スコアリング)の結果からの外挿である。
- HyDE 原論文(arXiv 2212.10496)と Rewrite-Retrieve-Read(arXiv 2305.14283)は今回本文を取得しておらず、効果量を引用できない。HyDE は密検索向けの手法で、BM25 に対する単独の効果は SAFE-QE 表 2 の値(平均で微減)しか確認していない。
- Weller ら・Abe らの効果量(何ポイント悪化するか)は要旨から取れなかった。

## 2. 反復・マルチホップ検索: 回数、打ち切り、振り返り

### Takeaway
2023〜2024 年の手法群(IRCoT、Adaptive-RAG など)は「単発検索より複数回の方が複雑な質問で数〜十数ポイント良いが、単純な質問では無駄」という結論で、質問の複雑さで回数を変えるのが定石だった。2025〜2026 年の強いモデルによる深い検索では、良い系は 1 問あたり 10〜30 回検索しており、3 回前後は「検索不足」の領域にある。ただし回数そのものより、累積の証拠再現率・新しい文書が出続けているか・質問の各条件が埋まったかが精度を決め、これらを信号にした打ち切り・方向転換の制御が有効と報告されている。

### Cited Findings
- 【語彙】IRCoT(ACL 2023): 推論の 1 文ごとに検索をはさむ。GPT-3 で検索が最大 21pt、下流 QA が最大 15pt 改善(4 データセット、要旨)— [Interleaving Retrieval with Chain-of-Thought Reasoning](https://arxiv.org/abs/2212.10509)
- 【語彙】Adaptive-RAG(NAACL 2024): 全手法で検索器は BM25。GPT-3.5 での平均 F1 / 検索ステップ数: 検索なし 48.56 / 0、単発 46.99 / 1.00、多段(IRCoT)50.87 / 2.81、Adaptive-RAG 50.91 / 1.03、複雑さの正解ラベルを与えた上限 62.80 / 0.50。FLAN-T5-XL では 検索なし 21.12、単発 44.31 / 1.00、多段 48.85 / 4.69、Adaptive-RAG 46.94 / 2.17。複雑さ分類器(T5-Large)の正解率は 54.52% にとどまる(本文確認)— [Adaptive-RAG](https://arxiv.org/abs/2403.14403)
- 【注】同表で GPT-3.5 は検索なし(F1 48.56)が単発検索(46.99)を上回る。強いモデルでは、公開知識の質問に対する質の低い単発検索は害になりうる— [Adaptive-RAG](https://arxiv.org/abs/2403.14403)
- DeepRAG(2025): 検索付き推論をマルコフ決定過程として定式化し、各ステップで「検索するか、モデル内の知識で進むか」を決める。回答精度 26.4% 改善と報告(要旨)— [DeepRAG](https://arxiv.org/abs/2502.01142)
- Search-o1(EMNLP 2025): 推論モデルが「不確かな知識点」に来たときに検索し、取得文書は別モジュール(Reason-in-Documents)で要点だけにしてから推論に戻す(要旨のみ、数値なし)— [Search-o1](https://arxiv.org/abs/2501.05366)
- Corrective RAG(2024): 軽量の評価器が取得文書の質を採点し、確信度に応じて次の取得行動を切り替える。質が低ければ Web 検索で補い、取得文書は分解して要点だけ残す(要旨のみ、数値なし)— [CRAG](https://arxiv.org/abs/2401.15884)
- 【両方】BrowseComp-Plus(2025): 検索回数と精度の関係。gpt-5 は 1 問あたり 23.23 回(BM25)で 55.9%、o3 は 25.93 回で 49.28%、gpt-4.1 は 10.35 回で 14.58%、Sonnet 4 は 9.95 回で 14.34%、Qwen3-32B は 0.92 回で 3.49%。gpt-oss-120B の推論量を low → high にすると検索回数 2.06 → 19.45、精度 9.52% → 28.67%(BM25)。著者は「より徹底した検索が良い結果と相関する test-time scaling 効果」と述べる(本文確認)— [BrowseComp-Plus](https://arxiv.org/abs/2508.06600)
- 【語彙】Pi-Serini(2026): 打ち切りを反復回数の上限でなく実時間(300 秒)にした。100 問の部分集合で、100 反復上限 76.0% に対し 300 秒 82.0%、3600 秒 83.0% で、時間を 12 倍にしても +1pt。平均ツール呼び出しは 23〜27 回(本文確認)— [Rethinking Agentic Search with Pi-Serini](https://arxiv.org/abs/2605.10848)
- 【密】停滞の分析(Radboud / Thomson Reuters、2026): 7 種のエージェントで、最初の数ステップの後は累積再現率・中間正解率が飽和し、以後の反復はほとんど寄与しない。反復が進むほど新規文書は減り、既に見た文書の再取得が増える。原因は (1) 何を集め終えたかの自覚の不足、(2) 観点を変える探索の不足— [When Deep Research Agents Stagnate](https://arxiv.org/abs/2608.15191)
- 【密】同論文の制御器 RAAC: 教師なしの 4 信号(文書の新規性、質問の条件の充足度、連続するクエリの多様性、元の質問との類似度)を見て「続行 / 介入(停滞の理由を批判的に見直し、語彙の大きく違うクエリを 1 つ出す)/ 停止」を選ぶ。BCP で検索回数を平均 14 回減らし、精度は平均 +3pt、最大 +10pt(Tongyi-DR: 検索 77.8 → 33.6 回、精度 37.9 → 47.9%。ReAct + Claude Sonnet 4.5: 35.3 → 25.4 回、35.7 → 39.1%)。信号のうち文書の新規性が新規関連文書の取得と最も相関し、条件の充足度が次ぐ(本文確認)— [同上](https://arxiv.org/abs/2608.15191)
- 【注】同論文: 逆に早く止まりすぎるエージェント(CPM-Report)では、制御器が検索回数を増やし(14.4 → 18.2)、再現率を 18.6 → 30.5 に上げた。制御は「減らす」だけでなく「足りなければ増やす」方向にも働く— [同上](https://arxiv.org/abs/2608.15191)
- 6 種の検索エージェントの診断(2026): 失敗は「検索の穴(必要な証拠が一度も取れない)」と「利用の穴(取れたのに正しく使われない)」に分かれる。検索の労力と回答の質の対応は弱く、精度は検索回数や消費した文脈量よりも累積の検索再現率に追随する。有用な証拠は軌跡の早い段階で出ることが多いのに、エージェントは検索を続け、収穫の少ない長い尾を作る。最良のエージェントは冗長なクエリがはるかに少ない(要旨のみ、数値なし)— [Diagnosing Search Behavior and Failure Modes in Long-Horizon Search Agents](https://arxiv.org/abs/2608.01913)
- 【語彙】最初の一手(2026): 質問を手掛かり(平均 9.6 個)に分解し、手掛かりごとにコーパスに基づく拡張をかけて BM25 で深さ 1000 まで取得、合併して質問全体に対して再順位付けし、上位 5 件を最初の観測として渡す。以後のループは変更なし。BCP の精度は gpt-5.5 83.1 → 90.5%、gpt-5.4-mini 68.1 → 79.0%、deepseek-v4-pro 71.4 → 76.9%。エージェントが自分で出す検索回数はほぼ同じ(13.5 → 14.5 など)。追加コストは 1 問あたり中央値 28.5 秒・約 0.05 ドル。通常のマルチホップ(MultiHop-RAG)では +0.5〜1.0pt と小さい(本文確認)— [Question's Gambit](https://arxiv.org/abs/2609.14412)

### Inferences
- 現状の「約 3 回」は、Adaptive-RAG 時代の多段検索(2.8〜4.7 ステップ)の水準であり、強いモデルによる深い検索(10〜30 回)の水準ではない。ただし文献は「回数を増やせば良い」とは言っておらず、飽和後の反復は無駄という結果が複数ある。回数の固定上限を上げるより、**(a) 質問を条件・手掛かりに分けて充足を追う、(b) 新規文書が出なくなったら方向転換か停止、(c) 単純な質問は 1〜2 回で止める**という制御を入れるのが文献に沿う。
- 「最初の一手」の結果は、最初の検索を 1 本の長いクエリにせず、手掛かりごとの短い検索に分けて並列に投げ、合併・選別してから渡す設計が、ループ内の反復を増やすより費用対効果が良いことを示す。API 呼び出し回数が効くバックエンド(SaaS のレート制限)でも、並列化でき回数が予測できる点で扱いやすい。
- Adaptive-RAG の分類器の正解率 54.5% は、複雑さの事前分類が難しいことを示す。事前に経路を決め打ちするより、1 回目の結果を見てから続行を判断する方が安全である。

### Gaps
- FLARE(arXiv 2305.06983)、Self-RAG(arXiv 2310.11511)、Self-Ask(arXiv 2210.03350)、Iter-RetGen(arXiv 2305.15294)は今回本文を取得しておらず、個別の効果量を引用できない。Self-RAG については Adaptive-RAG の表での再評価値(F1 約 21〜23、著者は直接比較不可と注記)しか確認していない。
- 社内文書のような「答えが 1〜2 文書にある事実照会」に対する最適な検索回数を測った研究は見つからなかった。BCP は意図的に難しい多手掛かり質問で、回数は上振れしている。
- 2023 年の手法(IRCoT など)の結論が強いモデルでどう変わったかを同一条件で比べた研究は見つからなかった。

## 3. エージェント型検索・深い検索の評価(2025〜2026): 検索器の質とエージェントの質

### Takeaway
2025 年の時点では「BM25 は密検索に 14pt 前後負ける」が定説だったが、2026 年には、設定を整えた BM25(パラメータ調整、深い取得、検索・結果閲覧・本文読みを分けたツール)と強いモデルの組で密検索の系を上回る結果が複数出た。残る失敗の大半は「取れているのに見ない・使わない」側にあり、検索器の差と同じ大きさでハーネス(プロンプト、ツールの形、結果の渡し方)が精度を動かす。一方、企業内の異種ソース検索のベンチマークでは最良手法でも得点が低く、検索が主なボトルネックと報告されている。

### Cited Findings
- 【両方】BrowseComp-Plus(2025): 同じエージェントで BM25 → Qwen3-Embedding-8B に替えると、gpt-5 55.9 → 70.12%、o3 49.28 → 63.49%、gpt-4.1 14.58 → 35.42%、Sonnet 4 14.34 → 36.75%、Opus 4 15.54 → 36.14%。検索回数は密の方が 1〜3 回少ない。正解文書をすべて与えると gpt-4.1 で 93.49%。質問文をそのままクエリにした単発検索の Recall@1000 は BM25 13.7%、Qwen3-8B 76.7%(質問全文は語彙検索に極端に不向き)。検索ツールは上位 5 件・各 512 トークンの抜粋を返す設定(本文確認)— [BrowseComp-Plus](https://arxiv.org/abs/2508.06600)
- 【両方】同論文: 全文を読むツールを足すと gpt-4.1 は 35.42 → 43.61%(全文読み 1.85 回 / 問)。弱いモデル(Qwen3-32B)は 10.36 → 11.69% とほとんど使えない— [同上](https://arxiv.org/abs/2508.06600)
- 【語彙】Pi-Serini(Waterloo、2026): BM25 のみで gpt-5.5 83.1%(表出再現率 94.7%)、gpt-5 74.6%(公開済みの gpt-5 + BM25 基準 58.3%、gpt-5 + Qwen3-8B 73.0% を上回る)、gpt-5.2 70.5%(別研究の gpt-5.2 + Qwen3-8B は 45.1%・73.8 回検索)、claude-opus-4.7 69.8%、claude-haiku-4.5 54.8%、deepseek-v4-flash 68.1%(総額 28.9 ドル)。ツールは 3 つ: search(1000 件を取得してキャッシュし 1〜5 位だけ表示)、read_search_results(同じランキングの続きを閲覧)、read_document(行単位で本文を読む)(本文確認)— [Pi-Serini](https://arxiv.org/abs/2605.10848)
- 【語彙】同論文の切り分け(100 問、gpt-5.4): BM25 既定値(k1=0.9, b=0.4)64.0% → 長文向け調整(k1=25, b=1)82.0%、表出再現率 84.6 → 95.7%。表示件数 k を 5 → 100 → 1000 にすると表出再現率 70.5 → 86.2 → 95.8% だが、エージェントが実際に目を通した文書の再現率は k=50 の 74.7% で頭打ち。著者の結論は「過去の BM25 基準の低さは設定と浅い取得が主因」「課題は、検索器が証拠を見つけられるかから、エージェントが既に与えられた証拠を認識して文脈を割けるかへ移った」— [同上](https://arxiv.org/abs/2605.10848)
- 【語彙】同論文の失敗分析: gpt-5.5 と claude-opus-4.7 の差(83.1 対 69.8%)の一因は「早すぎる枝への固執」。両者とも内部知識や弱く関連する語で候補を立てるが、gpt-5.5 は確認できなければ元の手掛かりに戻り、opus-4.7 は同じ弱い仮説の中で検索を続ける傾向。opus-4.7 は検索 6.8 回 / 問と少ない— [同上](https://arxiv.org/abs/2605.10848)
- 【語彙】Question's Gambit の残差分析(gpt-5.5、誤答 79 件): 正解文書が一度も表出しなかったのは 3.8%。表出したが抜粋を見ていない 55.7%、抜粋は見たが開かず引用もしない 11.4%、開いた・引用したのに誤答 29.1%— [Question's Gambit](https://arxiv.org/abs/2609.14412)
- 【両方】Meng ら(SIGIR 2026): エージェントが出すクエリは Web 検索風(キーワード、句、引用符による完全一致。例 `"90+7" attendance 61700`)。パッセージ単位のコーパスでは BM25 が最良(gpt-oss-20b: 再現率 0.616 / 精度 0.572 / 検索 30.97 回)で、ColBERTv2 0.552 / 0.521、SPLADE-v3 0.545 / 0.516、Qwen3-Embed-8B 0.470 / 0.417 を上回る。長い文書単位では BM25 既定値は最下位(0.366 / 0.259)だが、先頭 512 トークンだけ索引すると 0.642 / 0.513。エージェントのクエリを自然文の質問に書き直す(Q2Q)と SPLADE は +7〜8% だが BM25 は悪化(0.572 → 0.557)。BM25 + monoT5-3B 再順位付け(深さ 50)で 再現率 0.716 / 精度 0.689、検索回数 11% 減。推論型の再順位付けモデルに明確な優位はなし(本文確認)— [Revisiting Text Ranking in Deep Research](https://arxiv.org/abs/2602.21456)
- 【両方】PwC(2026): LongMemEval の 116 問で、結果をインラインで返す場合、grep はすべてのハーネス × モデルの組でベクトル検索を上回る(例: Chronos + Claude Opus 4.6 で 93.1 対 83.6%、Gemini 3.1 Flash-Lite で 86.2 対 62.9%)。同じ Opus 4.6 でもハーネスを替えると 93.1%(独自ハーネス)対 76.7%(Claude Code)で、検索器を替えるのと同程度の差。検索結果をファイルに書いてエージェントに読ませる方式では優劣が入れ替わり、最悪 93.1 → 55.2% に落ちた。著者は限界として、答えが文字どおりの文字列として存在する課題だから語彙検索が勝ったのであり一般化はしない、と明記(本文確認)— [Is Grep All You Need?](https://arxiv.org/abs/2605.15184)
- 【両方】直接コーパス操作(DCI、2026): 検索 API を使わず、エージェントが grep・ファイル読み・シェルで生のコーパスを直接探す方式が、BRIGHT / BEIR の複数データセットで疎・密・再順位付けの基準を上回り、BCP でも強いと報告(要旨のみ)。Pi-Serini の著者は、この方式は探索空間を事前に手元へ置けることを前提にしており、大きく動的なコーパスでは満たしにくいと指摘— [Beyond Semantic Similarity: ... Direct Corpus Interaction](https://arxiv.org/abs/2605.05242); [Pi-Serini](https://arxiv.org/abs/2605.10848)
- 【両方】SearchWeaver(2026): 検索インターフェース(コーパスから作る補助索引、ツール、使い方の指示)を実行軌跡から自動で改訂。GPT-5.4-nano で BCP 71.6 → 78.4%。**指示文だけの最適化でも 75.6%**。同じ軽量モデルで、5 件の抜粋を返す反復検索ツールは BM25 47.5%、密 62.6%。発見されたインターフェースの例: 題名の索引、文書内の該当箇所を返す locate、候補が各手掛かりを満たすかの行を返す verify、「質問全体で検索 → 題名を見る → 原文を読む → 手掛かりごとに判定してから回答」という指示(本文確認)— [Let Agents Design How They Search](https://arxiv.org/abs/2610.29250)
- 【両方】BRIGHT(2024): 推論が必要な検索では BM25 の平均 nDCG@10 は 14.5、最良の密モデルで 22.5(表の値)。GPT-4 などの推論の文章をクエリに使うと最大 12.2pt 改善し、BM25 が最も恩恵を受ける。BM25 上位の再順位付けは、cross-encoder(MiniLM)だと悪化(14.3 → 13.1、上位 100 件では 8.3)、GPT-4 だと 17.4(本文の前半を確認)— [BRIGHT](https://arxiv.org/abs/2407.12883)
- 企業内の深い検索(Salesforce の HERB、2025): 文書、会議の書き起こし、Slack、GitHub、URL にまたがる 39,190 件から複数ホップで探す。最良のエージェント型 RAG でも平均スコア 32.96。主なボトルネックは検索で、必要な証拠を取り逃がすと部分的な文脈で推論して大きく落ちる(要旨)— [Benchmarking Deep Search over Heterogeneous Enterprise Data](https://arxiv.org/abs/2506.23139)
- EnterpriseRAG-Bench(Onyx、2026): Slack、Gmail、Linear、Google Drive、HubSpot、Fireflies、GitHub、Jira、Confluence の 9 ソース、約 50 万文書、500 問(要旨)。別研究によると、強い密 + 再順位付けの基準でも約 6 割の質問で上位 10 件に関連文書が入らない— [EnterpriseRAG-Bench](https://arxiv.org/abs/2605.05253); [Better Together](https://arxiv.org/abs/2609.05637)
- 実運用のログ(1444 万件の検索要求、397 万セッション、2025-06〜12): 47.77% が単発。複数回のセッションの 90% は 10 ステップ以下。クエリの遷移は 探索 約 37%、反復(ほぼ同じクエリ)約 32%、特殊化 約 22%、一般化 約 9%。反復の遷移では結果の約 78% が前回と重なり、探索では約 7%。事実照会では反復の割合がステップ 9 までに 42.68% に上がる。新しいクエリの語のうち、それまでの検索結果に出ていた語の割合は平均 54.35%(直前ステップだけだと 48.54%)。著者は、重なりの大きい再試行を停滞の信号として方針転換を起こす設計を提案(未検証の提案)(本文の前半を確認)— [Agentic Search in the Wild](https://arxiv.org/abs/2601.17617)

### Inferences
- 対象システムで適合率が低い原因として文献が示す候補は、検索器の弱さよりも次の順である。(1) 表示件数が浅く、順位付けが弱いので、良い文書が取れていても見えていない。(2) クエリの形がバックエンドに合っていない(質問文のまま、または語を詰め込みすぎ)。(3) 取れた結果を読まずに次のクエリへ進む。Pi-Serini の「検索」と「同じ結果の続きを見る」を分けたツール設計は、SaaS API のページングにそのまま対応させられる。
- BM25 の調整(k1, b)は SaaS のネイティブ検索では触れない。代わりに効くのは、深く取ってエージェントかハーネスの側で選別すること(§5)と、抜粋ではなく本文の該当箇所を読めるようにすることである。
- エージェントのクエリを自然文に直すと BM25 は悪化する(Meng ら)。語彙検索に対しては、キーワード・句・完全一致の引用符という Web 検索風の形を保たせるのが正しい。
- ハーネスの違いが検索器の違いと同程度に効く(PwC、SearchWeaver の指示文だけで +4pt)ことは、今回の「ハーネス・プロンプト設計の見直し」という方針を支持する。

### Gaps
- BCP・LongMemEval・BRIGHT はいずれも英語で、社内 wiki・課題管理・コードの検索ではない。HERB と EnterpriseRAG-Bench は企業風だが合成データで、検索器別の内訳を今回は確認できていない(要旨のみ)。
- エージェントが 0 件の結果を受けた後に適応できるか(語を減らす、表記を変えるなど)を直接測った研究は見つからなかった。近いのは反復率・重なりの分析(Agentic Search in the Wild、停滞の分析)で、0 件時の規則(同義語を試す、質問を分解する)は設計パターンとして提案されているだけである。
- エージェントのクエリ長の統計は、Meng らの論文には載っていなかった(例示のみ)。

## 4. ツール・検索器を意識させる工夫

### Takeaway
検索器の性質をモデルに伝える・検索器に合わせてクエリの型を変えることの効果は、直接の統制実験は少ないが、間接的な証拠は揃っている。語彙検索には Web 検索風のキーワードが合い自然文は合わない、ツールの使い方の文書は少数例より有効、インターフェースと指示文の最適化だけで数ポイント動く、という結果である。

### Cited Findings
- 【両方】クエリの型と検索器の相性: エージェントのキーワード型クエリを自然文の質問に書き直すと、SPLADE-v3 は再現率 +7.34%・精度 +7.95%、BM25 は精度が 0.572 → 0.557 に悪化。検索器ごとに最適なクエリの型が逆になる— [Revisiting Text Ranking in Deep Research](https://arxiv.org/abs/2602.21456)
- ツール文書と例示(2023): ツールの使い方の説明だけの zero-shot は、既存ベンチマークで few-shot と同等。数百の API を持つ新データセットでは文書の方が例示より有意に有用。例示は入手が難しく、選び方を誤ると偏った使い方を招く(要旨)— [Tool Documentation Enables Zero-Shot Tool-Usage with Large Language Models](https://arxiv.org/abs/2308.00675)
- 【語彙】Pi-Serini の search ツール定義は、引数に「理由(100 語以内、先に書く)」と「生のクエリ文字列。構造化オブジェクトでも Lucene 構文でもない」を持ち、出力に search_id・表示した docid・切り詰めの有無を含める。検索器の入力の型をツール定義に明記している— [Pi-Serini 付録 A.2](https://arxiv.org/abs/2605.10848)
- 【語彙】Question's Gambit のエージェント用プロンプトは、質問の型で最初の一手を選ばせる: 複数の手掛かりで対象を述べる質問は分解ツールを先に呼ぶ、質問に引用できる文字どおりの句がある場合は例外としてその句で検索する— [Question's Gambit 付録 C](https://arxiv.org/abs/2609.14412)
- 【語彙】IterKey のキーワード生成プロンプトは「BM25 検索で文書に現れそうな、関連する重要キーワードを列挙せよ」と検索器を名指しし、再生成時は前回のキーワードを見せて改良させる— [ITERKEY(NLP2025 P8-6)](https://www.anlp.jp/proceedings/annual_meeting/2025/pdf_dir/P8-6.pdf)
- 【両方】インターフェースと指示の自動最適化: 指示文だけの最適化で BCP 71.6 → 75.6%、ツールと補助索引も含めると 78.4%。GPT-5.4-nano で最適化したインターフェースは、作り直さずに Gemini 3.5 Flash-Lite に移しても BCP 60.9 → 73.9%— [Let Agents Design How They Search](https://arxiv.org/abs/2610.29250)
- 【密】停滞時の介入プロンプト(RAAC)は、新しいクエリに「未探索の側面を狙い、大きく異なる用語を使い、簡潔でキーワード中心で具体的」であることを要求する— [When Deep Research Agents Stagnate 付録](https://arxiv.org/abs/2608.15191)
- 検索器の側をエージェントに合わせる方向の研究もある: エージェントの推論や過去のクエリを符号化する検索器 AgentIR、ITER(BCP で従来の軌跡学習型検索器に対し平均 15.4% 相対改善)。これは検索器を学習できる場合の話で、SaaS のネイティブ検索には適用できない— [ITER](https://arxiv.org/abs/2608.27912); [AgentIR](https://arxiv.org/abs/2603.04384)

### Inferences
- 各コネクタのツール説明に、その検索の性質を具体的に書くことは文献に沿う: 既定が AND か OR か、句検索や引用符の可否、フィールド指定、対象(題名か本文か)、日本語の分かち書きの挙動、0 件になりやすい条件。例示を数個並べるより、規則の説明と「良いクエリの形」の説明の方が偏りを生みにくい(ツール文書の研究)。
- 検索結果の応答に、次の判断に使える情報(総ヒット数、表示範囲、切り詰めの有無、ページングのための識別子)を含めるのは Pi-Serini の設計と一致する。ただし leisen の不変条件 3(未認可候補の件数を外に出さない)があるため、総ヒット数は認可後の値か、出さないかのどちらかにする必要がある。
- クエリごとの成績の手掛かり(前回のクエリが何件新しい文書を返したか)をエージェントに返すことは、RAAC の新規性信号と同じ発想で、ハーネス側で安く計算できる。

### Gaps
- 「検索器の性質(AND 既定、句検索、形態素解析)をプロンプトで説明した場合としない場合」を直接比べた統制実験は見つからなかった。
- 検索器ごとの良いクエリ例を few-shot で与える効果を、語彙検索に対して測った研究は見つからなかった。
- クエリ性能予測(QPP)をエージェントへのフィードバックに使う研究は今回確認できていない。

## 5. 複数ソースの検索: ソース選択、バックエンドごとのクエリ変換、結果の合併と再順位付け

### Takeaway
LLM によるソース選択は zero-shot でも競争力があるという報告があり、boolean クエリの生成は適合率は高いが再現率を落としやすい。キーワード検索で広く取った後に LLM か再順位付けモデルで選別する構成は、検索回数を減らしつつ精度を上げる最も確かな手段の一つだが、推論が必要な質問では小さい cross-encoder がかえって悪化させる。複数クエリの結果の合併は、結果が互いに異なるときだけ効く。

### Cited Findings
- ソース選択: ReSLLM は連合検索のソース選択を LLM に zero-shot で行わせ、ソースごとの学習ラベルなしで競争力のある有効性を報告。過去のクエリとソースの抜粋に LLM が付けた関連性ラベルで微調整するとさらに改善(要旨のみ、数値なし)— [ReSLLM: Large Language Models are Strong Resource Selectors for Federated Search](https://arxiv.org/abs/2401.17645)
- boolean クエリ生成: ChatGPT は系統的レビュー用の boolean クエリを作れ、検索の適合率は高いが再現率と引き換えになる。時間の限られる迅速レビュー向き(要旨)— [Can ChatGPT Write a Good Boolean Query for Systematic Review Literature Search?](https://arxiv.org/abs/2302.03495)
- 【語彙】再順位付け: BM25 + monoT5-3B(深さ 50)で BCP の再現率 +16.23%、精度 +20.45%、検索回数 −10.98%。深さ 10 → 20 → 50 で精度 0.631 → 0.674 → 0.689 と、深いほど良い— [Revisiting Text Ranking in Deep Research](https://arxiv.org/abs/2602.21456)
- 【語彙】推論が要る質問での再順位付け(BRIGHT): BM25 上位に対し cross-encoder(MiniLM)は悪化(14.3 → 13.1、深さ 100 で 8.3)、GPT-4 のリスト型は 17.4、Gemini は 15.7。「最終結果は下の検索系に強く依存する」— [BRIGHT](https://arxiv.org/abs/2407.12883)
- RankGPT(EMNLP 2023): 適切に指示した ChatGPT / GPT-4 の順位付けは教師ありの手法と同等以上。蒸留した 440M モデルが BEIR で 3B の教師ありモデルを上回る(要旨のみ)— [Is ChatGPT Good at Search?](https://arxiv.org/abs/2304.09542)
- 【語彙】手掛かりごとに取得して合併し、質問全体に対して点ごとに再順位付けする(Cohere Rerank、約 2,500 候補)構成で、BCP の精度 +5.5〜10.9pt。採点前に、検索の抜粋を文書本文に置き換えている(抜粋は一致語の周辺の短い窓で、文書をうまく表さないため)— [Question's Gambit](https://arxiv.org/abs/2609.14412)
- 【密】合併が効く条件: 手法間の上位 10 件の重なり(Jaccard)が 0.14〜0.45 の企業風コーパスでは合併で +8〜13pt、0.55〜0.99 の AmbigNQ では −2.4pt。合併方式を順位融合(RRF)に替えても AmbigNQ では失敗— [Better Together](https://arxiv.org/abs/2609.05637)
- 【両方】忠実なクエリを 2 倍の重みにした重み付き RRF(忠実な解決 + 学習済み書き換え + 生の発話、BM25 と SPLADE の両方)は、iKAT 2026 の対話検索で nDCG@5 0.534 と自チームの他構成より 5.3% 相対改善— [Faithful Query Resolution for Conversational Search](https://arxiv.org/abs/2610.15034)
- 複数ソースを LLM に束ねさせる連合検索は、BCP の著者が今後の課題として挙げている段階で、確立した評価はない— [BrowseComp-Plus(今後の課題)](https://arxiv.org/abs/2508.06600)

### Inferences
- 各 SaaS の検索は順位付けが弱い(更新日順や単純な一致)ことが多い。「広く取る(1 ソースあたり数十件)→ 題名と抜粋を LLM に一括で見せて選ばせる → 選んだものの本文を読む」という 2 段構成は、文献上は検索回数を増やすより効く。BRIGHT の結果から、選別役は小さい cross-encoder より LLM の方が、推論が要る質問で安全である。
- スコアの尺度が違う複数ソースの合併には、スコアを使わない順位融合か LLM による選別が合う。ソースごとに元のクエリ語を使った検索結果を優先(重み 2 倍)する Faithful Query Resolution の方式は、書き換えによるずれへの保険として移しやすい。
- boolean や検索演算子の生成は適合率を上げるが 0 件・取り逃しを増やす(系統的レビューの結果)。演算子は最初から使わず、結果が多すぎるときの絞り込み手段として段階的に使わせるのが妥当。
- 合併のたびに、重なりが大きいクエリは追加の価値がないことを思い出すこと。クエリの多様化は、言い換えの数ではなく、結果集合の違いで測るべきである。

### Gaps
- wiki・課題管理・コードホスティングのような異種の SaaS 検索 API を対象にした LLM のソース選択の評価は見つからなかった。ReSLLM は Web の連合検索データでの結果である。
- バックエンドごとの検索構文(GitHub の修飾子、Redmine のフィルタ、esa の検索オプション)へ LLM がクエリを変換する精度を測った研究は見つからなかった。
- ReSLLM、RankGPT、boolean 生成の効果量は要旨から取れず、未確認である。

## 6. 多段エージェント・受け渡しでの情報の損失

### Takeaway
上流の LLM が利用者の質問を言い換えて下流の検索役に渡すと、利用者が言っていない意図が足される(過剰な具体化)か、元の語が失われる。対話検索の研究は、参照の解決だけを行い利用者の語をそのまま残す「最小限で忠実な書き換え」を軸にし、広げるための別表現は別のクエリとして並行に投げて合併する設計を支持している。

### Cited Findings
- 【両方】iKAT 2026 参加システムの報告(2026): 文脈を足しすぎた書き換えは、利用者が表明していない情報要求を持ち込む。例: 「I mean black garlic.」を「how to use black garlic in gourmet cooking」に書き換えると、利用者が指定していない用途が入る。最小限で忠実な解決器は、代名詞と省略だけを先行詞に置き換え、それ以外の語は残し、既に解釈できる発話は変えない— [Faithful Query Resolution for Conversational Search](https://arxiv.org/abs/2610.15034)
- 【両方】同報告のオフライン結果(iKAT 2023、BM25 + SPLADE の融合): nDCG@10 は 忠実なクエリ単独 0.231、文脈を足す統合型の解決器 0.221、絞り込み型 0.171、学習済み書き換え器単独 0.153、人手の書き換え 0.345。再現率(Recall@1000)は 忠実単独 0.448、統合型 0.581、忠実 + 書き換え + 生の発話(忠実を 2 倍の重み)0.519。順位品質と再現率は両立せず、一律の勝者はない— [同上](https://arxiv.org/abs/2610.15034)
- 同報告の注意: 過剰な具体化の頻度は測っていない(例の観察にとどまる)。検索の指標が最良の構成が、対話の満足度で最良とは限らなかった(満足度 3.614 対 最良 3.773)。また、制御役が提案した改良クエリが、クエリ生成器の出力に上書きされて検索に反映されない、という受け渡しの欠陥を自ら報告している— [同上](https://arxiv.org/abs/2610.15034)
- LLM による有益な書き換え(EMNLP Findings 2023): 人手の書き換え(CANARD 型のラベル)は良い検索に必要な情報が足りないことがあるとし、正しさ(元の意味を保つ)、明確さ(照応と省略の解決)、有益さ、冗長でないことの 4 性質を指示して QReCC で書き換えさせる(検索結果の要約による)— [Enhancing Conversational Search: Large Language Model-Aided Informative Query Rewriting](https://arxiv.org/abs/2310.09716)
- 【語彙】エージェントの推論や長い質問をそのまま語彙検索に渡すと失敗する: 質問全文を BM25 のクエリにすると Recall@1000 は 13.7%— [BrowseComp-Plus](https://arxiv.org/abs/2508.06600)
- 【語彙】逆に、1 本のクエリに条件を詰め込みすぎることも既知の非効率として挙げられている(既出の軌跡分析の整理: 答えに関係する文書を外す検索、散らかった文脈、過去のクエリの繰り返し、1 本の広い検索への条件の詰め込み)— [Question's Gambit(序論)](https://arxiv.org/abs/2609.14412)
- 曖昧なクエリでは LLM の拡張が最も有力な解釈に寄り、検索範囲を狭める— [LLM-based Query Expansion Fails for Unfamiliar and Ambiguous Queries](https://arxiv.org/abs/2505.12694)

### Inferences
- 上流(対話・計画役)から下流(検索役)へ渡すものは、要約した依頼文だけにせず、**利用者の原文をそのまま添える**べきである。固有名詞、型番、エラー文、引用符で囲まれた句は、語彙検索では 1 文字違いで 0 件になるため、言い換えで失うと取り返せない。
- 下流の検索役には、(1) 原文の語をそのまま使ったクエリを必ず 1 本含める、(2) 言い換えや上位概念は別のクエリとして出す、(3) 原文由来のクエリの結果を優先する、という規則を置くと、忠実さと広さを分けて制御できる(Faithful Query Resolution の設計)。
- 上流が「たぶんこういう意図だろう」と用途・範囲・期間を足すのは、過剰な具体化の典型で、語彙検索では AND 条件が増えて取り逃しになる。足した条件は「利用者が言ったこと」と区別できる形(別フィールド)で渡すのがよい。
- 受け渡しの欠陥(改良案が上書きされて使われない)は実システムで実際に起きている。検索役が実際に投げたクエリを上流に返し、記録に残すことが検証の前提になる。

### Gaps
- 多段エージェント構成(上流の LLM → 下流の検索エージェント)での情報損失を定量化した研究は見つからなかった。上の知見は対話検索のクエリ書き換え研究からの類推である。
- CANARD / QReCC での、書き換えによる固有表現の脱落率や過剰な具体化の発生率といった数値は見つからなかった。
- 書き換えの忠実さが語彙検索と密検索でどう違って効くかを分けて報告した研究は確認できていない(iKAT の結果は BM25 と SPLADE の融合)。

## 7. 日本語(CJK)でのキーワード検索の事情と LLM のクエリ生成

### Takeaway
日本語の全文検索は、形態素解析(辞書にない語と複合語の分割で取り逃す)と n-gram(取り逃しは少ないが雑音が多い)の間の妥協で作られており、表記ゆれ(全角・半角、長音、送り仮名、同義語)が取り逃しの主因とされる。SaaS のネイティブ検索は解析器や同義語辞書を導入側で変えられないので、表記の違いを吸収する役はクエリを作る LLM の側に回る。ただし「LLM エージェントが日本語コーパスをキーワード検索する」場面を測った学術研究はほとんど見つからず、この節は実務の解説と少数の国内発表に基づく。

### Cited Findings
- 形態素解析と n-gram の得失(Elastic 公式ブログ): n-gram は検索漏れが少ないが索引が大きくなり、意味のない分割による雑音が増える。形態素解析は辞書にない新語に弱く、検索漏れが出やすい。両方の解析を併用して補い合うのが推奨。例の設定は、本文フィールドに kuromoji(search モード)、サブフィールドに bigram、文字フィルタに icu_normalizer(NFKC)で全角・半角などを正規化、同義語は索引用と検索用で別のフィルタ— [Elasticsearch で日本語の全文検索を実装する方法](https://www.elastic.co/jp/blog/how-to-implement-japanese-full-text-search-in-elasticsearch)
- 複合語の分割(kuromoji 公式文書): search モードは検索向けの分割で、長い名詞の複合語を分解し、複合語全体も同義語として出力する。例: 「関西国際空港」→「関西」「関西国際空港」「国際」「空港」— [kuromoji tokenizer](https://www.elastic.co/guide/en/elasticsearch/plugins/current/analysis-kuromoji-tokenizer.html)
- 適合率と再現率の両立のための併用(リクルートの事例、2015): 形態素解析と n-gram を併用して検索の適合率と再現率を上げる構成— [Elasticsearch と Kuromoji を使った形態素解析と N-Gram による検索の適合率と再現率の向上(@IT)](https://atmarkit.itmedia.co.jp/ait/articles/1507/29/news010_2.html)
- 表記ゆれ(実装記事): 従来の全文検索(BM25)は表記ゆれ(例「サーバー」と「サーバ」)や同義語に対応できない。Sudachi の正規化を使って日本語のハイブリッド検索を組む例— [Sudachi × Zilliz(Milvus)の日本語ハイブリッド検索](https://zilliz.com/jp/blog/how-to-improve-retrieval-quality-for-japanese-text-with-sudachi-milvus-and-aws-bedrock)
- 言葉のゆれ(@IT の解説、2025): 「ログイン」と「サインイン」のような語のゆれで取りこぼしが起きるため、同義語や関連語を補って検索する。キーワード検索は型番や固有名詞の完全一致に強く、言い回しの違いはベクトル検索で補う、という使い分け— [RAG の精度が出ないのはなぜ?(@IT)](https://atmarkit.itmedia.co.jp/ait/articles/2509/10/news008_2.html)
- 【密】同義語の影響(Acroquest、NLP2025): 日本語の検索では多様な表記ゆれが精度に影響するとして、クエリ中の語を Sudachi の同義語辞書で置き換えた場合と、同義語で語を増やした「同義語拡張クエリ」を、埋め込みモデル(multilingual-e5、ruri)で JAQKET・JaGovFaqs-22k に対し比較。同義語に置き換えると上位 5 件が変わり(入れ替わり件数 / 両方で当たった件数の比が 0.06〜0.14)、同義語拡張クエリでは当たりが増える(例: 440 → 467、1817 → 1899)(PDF の抽出が部分的で、表の数値のみ読み取り。条件の詳細は未確認)— [NLP2025 P8-5](https://www.anlp.jp/proceedings/annual_meeting/2025/pdf_dir/P8-5.pdf)
- 【語彙】LLM のキーワード生成と BM25 の反復(NAIST の IterKey、NLP2025): 図の例では質問「江戸時代に日本で唯一、西洋との交易が許されていた場所は?」に対し、LLM が「江戸時代, 交易, 日本, 長崎, 港, 西洋」のような短い名詞のキーワード列を作り、回答の検証に失敗すると「江戸時代, 貿易拠点, 長崎, オランダ, 西洋」に作り直す。ただし評価は英語の QA データ(Natural Questions、EntityQA、WebQA、HotpotQA)で、日本語コーパスでの結果ではない— [ITERKEY(NLP2025 P8-6)](https://www.anlp.jp/proceedings/annual_meeting/2025/pdf_dir/P8-6.pdf)
- LLM による構造化(AMBL / 明星大、NLP2026、査読なし): 社内ヘルプデスクの合成データで、LLM が自然文の問い合わせから属性タグ(Category、Device_model など)を作って検索すると、Hit@1 が 0.6444 → 0.8889、MRR が 0.7691 → 0.9119(小規模・合成データ。PDF の抽出が部分的)— [NLP2026 P2-4](https://www.anlp.jp/proceedings/annual_meeting/2026/pdf_dir/P2-4.pdf)
- 言語をまたぐ深い検索(XBCP、2026、早稲田・理研・東大ほか): 質問は英語のまま証拠文書を他言語(12 言語)にすると精度が大きく落ちる。密検索でも証拠の再現率が落ち、正解文書をすべて与えても精度は低いまま(エージェント側が言語の違う証拠を統合しにくい)。対象言語に日本語が含まれるかは要旨からは確認できなかった— [Beyond Monolingual Deep Research: Cross-Lingual BrowseComp-Plus](https://arxiv.org/abs/2606.15345)

### Inferences
- SaaS のネイティブ検索では解析器が見えない。形態素解析型なら複合語の一部や辞書にない社内用語で取り逃し、n-gram 型や部分一致型なら短い語で雑音が増える。どちらであっても、**文ではなく短い名詞(1〜3 語)のクエリ**が安全である。助詞や活用語尾を含む文は、AND 既定の検索では余計な条件になり、形態素解析型では不要語として落ちるだけで得がない(IterKey の例、Meng らの「語彙検索にはキーワード型」の結果と整合)。
- 表記ゆれは同義語辞書を足せないので、LLM に別表記のクエリを別々に出させる: カタカナ長音の有無(サーバー / サーバ)、英語と日本語(deploy / デプロイ / 配備)、略語と正式名、全角と半角の英数字、漢字とかな、複合語の分割(「関西国際空港」と「関西 空港」)。LLM が知らない社内語については推測で言い換えず、1 回目の検索結果に現れた表記を拾って次のクエリに使う(§1 のコーパスに基づく拡張と同じ理由)。
- 複合語は、まとめた形と分けた形の両方を試す価値がある。解析器が複合語を分解しない設定(または辞書に 1 語として載っている)なら部分語では当たらず、逆に分解する設定なら部分語の AND で当たる。どちらの挙動かは、コネクタごとに一度試して調べ、ツール説明に書いておくのがよい(§4)。
- 英語の質問で日本語の文書を探す(またはその逆)場合、語彙検索は当たらない。利用者の言語と文書の言語が違いうるソース(コード、英語の課題)では、両言語のクエリを出させる必要がある。XBCP は、取れた後の統合でも言語の違いが効くことを示している。

### Gaps
- LLM エージェントが日本語コーパスをキーワード検索する場面(クエリの型、表記ゆれの扱い、0 件時の言い換え)を扱った実務記事(Zenn、企業の技術ブログ)を検索したが、該当するものは見つからなかった。見つかったのは RAG 一般の精度改善と、検索基盤側(解析器、ハイブリッド検索)の解説である。
- 日本語での LLM クエリ拡張(BM25 向け)の統制実験は見つからなかった。IterKey は日本の研究だが評価は英語データ。日本語の検索ベンチマーク(JMTEB、JQaRA など)は埋め込みモデルの評価が中心である。
- カタカナ長音・送り仮名・漢字かな混じりのゆれが語彙検索の再現率をどれだけ落とすかの定量値は見つからなかった。
- esa・Redmine・GitHub の検索が日本語をどう分かち書きするかは、この調査の範囲では確認していない(各コネクタの調査で実測が必要)。
- 国内発表 3 件(NLP2025 P8-5、P8-6、NLP2026 P2-4)は PDF の本文抽出が文字化けし、表の数値と英字部分しか読めていない。引用する場合は原文で確認が必要。
